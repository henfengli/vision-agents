# 外部接口文档（/v1）

平台对外的全部 HTTP 接口。调用方有业务项目、脚本、Dagster / GitLab 回调和控制台。
控制台只是这套接口的一个客户端，没有私有接口。`sdk/agent_client` 是它的 Python 薄封装，
见 `docs/SDK开发指南.md`。

契约有三处出处，改一处必须同时改另两处：

| 内容 | 后端 | 前端 |
|---|---|---|
| 请求体 | `src/agent_platform/api/schemas.py` | `web/src/api/types.ts` |
| 响应形状 | `src/agent_platform/api/views.py` + 各领域模型 | 同上 |
| 端点清单 | 每个 `api/routes/*.py` 开头的文档串 | `web/src/api/hooks.ts` 的 `api` 对象 |

运行中的服务自带 OpenAPI：交互页面在 `/v1/docs`，规范在 `/v1/openapi.json`。

## 1. 通用约定

### 1.1 地址与格式

- 服务只监听 `127.0.0.1:8100`，对外经反向代理（见部署指南 §4）。
- 请求和响应都是 JSON（SSE 端点除外），字段名一律 `snake_case`。
- 时间是带时区的 ISO 8601 字符串。

### 1.2 身份与权限

平台没有用户体系，**身份就是 API 密钥**。每个调用方一把密钥：一个项目、一个回调来源或一个人。
密钥名就是运行记录里的「发起方」（`caller`）。

| 方式 | 用法 |
|---|---|
| `Authorization: Bearer <密钥>` | 项目、脚本、SDK |
| `X-Gitlab-Token: <密钥>` | GitLab Webhook，GitLab 只能这样带密钥 |
| Cookie `ap_session` | 控制台：`POST /auth/session` 用密钥换取，httponly |

密钥有两种范围：

| scope | 能做什么 |
|---|---|
| `run` | 发起运行、对话、推事件，取消 / 重跑 / 续跑 / 纠正 / 评价 / 回归重放，以及全部只读查询 |
| `admin` | 在 `run` 之上还能：改定义（服务、角色、任务）、改设置、管密钥、审批、改记忆、启停进程 |

密钥还可以限定**只能调用哪些服务、哪些环境**（`services` / `envs`，空表示不限）。越界返回
`403 forbidden`。

部署配置里的 `root_token` 是引导密钥：权限最高、不可吊销，只用于首次登录和创建第一批密钥。

### 1.3 错误

所有错误都是同一个形状：

```json
{"error": {"code": "service_env_disabled", "message": "服务 board 在 prod 环境已停用", "detail": null}}
```

**程序只认 `code`**。`message` 是给人看的；`detail` 是附加结构，例如字段错误表。

| HTTP | 含义 | 常见 code |
|---|---|---|
| 400 | 请求能理解，但按规则不能办 | 闸门链原因码（§1.4）、`invalid_input`、`service_required`、`service_not_allowed`、`invalid_subtask`、`unknown_env`、`unknown_channel`、`config_missing`、`process_control_off`、`nothing_to_replay` |
| 401 | 没带身份，或密钥无效 / 已吊销 / 已过期 | `unauthorized` |
| 403 | 身份有效，但没有权限 | `forbidden` |
| 404 | 对象不存在 | `not_found`、`unknown_task`、`unknown_service`、`unknown_source` |
| 409 | 状态冲突 | `conflict`、`in_use`、`already_finished`、`already_decided`、`not_running` |
| 422 | 参数或定义校验不过 | `invalid_request`（`detail` 为「字段 → 错误」）、`invalid_definition` |
| 500 / 502 / 503 | 平台内部错误，或依赖不可用 | `internal`、`start_failed`、`stop_failed`、`channel_failed` |

不在闸门链里的几个：

| code | 含义 |
|---|---|
| `service_not_allowed` | 专属任务的请求里写了别的服务 |
| `unknown_channel` | 投递或测试用的通知渠道不存在 |
| `config_missing` | 启动进程时该环境的配置文件不存在，或固定路径建不出来 |
| `process_control_off` | 部署配置关闭了进程启停（`process_control.backend: off`） |
| `nothing_to_replay` | 发起回归重放时没有符合条件的被 👎 的运行 |
| `channel_failed` | 通知渠道测试发送失败 |
| `invalid_input` | 运行的输入不合法（`detail.fields` 逐字段说明）；新建记忆、升格缺必填字段（§8） |

### 1.4 闸门链原因码

一次提交能不能办，只在闸门链里判断（`orchestration/gates.py`）。闸门按下表顺序检查，先粗后细，
遇到第一个不通过的就停：

| 顺序 | code | 含义 | 怎么解 |
|---|---|---|---|
| 1 | `service_disabled` | 服务整体停用 | 服务详情 → 启用 |
| 2 | `service_env_disabled` | 服务在这个环境停用 | 服务详情 → 环境 → 打开该环境 |
| 3 | `task_disabled` | 任务停用，或子任务的父任务停用 | 任务详情 → 启用 |
| 4 | `env_not_allowed` | 任务的 `envs` 不含这个环境 | 换环境，或改任务的环境限定 |
| 5 | `trigger_not_allowed` | 任务没声明这种触发，例如没有 `api` 触发却被 API 调用 | 任务定义 → 触发 → 添加 |

新提交（含定时、事件）要过全部 5 道闸门。续跑、重跑、纠正、回归重放只检查前 4 道。控制台手动运行不检查第 5 道。
运行被 worker 认领后会再检查一次前 4 道（排队期间开关可能变了），没过就以对应的原因码失败。

### 1.5 列表与分页

列表的过滤条件都是平铺的查询参数，空值表示不过滤。只有运行列表分页：

```json
{"items": [...], "total": 1234, "next_cursor": "next:2026-10-20T09:41:02+08:00|4b1e…", "prev_cursor": null}
```

游标不透明，把 `next_cursor` / `prev_cursor` 原样作为 `cursor` 传回即可。翻页基于
`(created_at, run_id)`，翻页过程中有新运行进来也不会重复或漏掉。

### 1.6 运行状态机

```
queued ──→ running ──→ success | failed | cancelled
              ⇅
       awaiting_approval（运行中途的审批；设置里打开了审批才会有）
```

终态是 `success`、`failed`、`cancelled`。运行中途的审批（危险命令、进程启停）被拒或超时时，
运行不结束：工具拿到「未执行」的结果，agent 自己决定怎么继续。

失败与取消的 `error_code`：

| error_code | 含义 |
|---|---|
| `timeout` | 超过任务的 `timeout_s`（打开了审批时另加一次审批的等待时间） |
| `error` | 执行出错（模型、工具、处理器抛错） |
| `cancelled` | 被人取消 |
| `interrupted` | worker 退出（重启、停机）时运行还在执行，可以续跑 |
| `orphaned` | 执行进程没了（崩溃或被杀，心跳超过 120 秒没动静），可以续跑 |
| `code_sync_failed` | 内建任务 code-sync 失败（有未提交改动、找不到分支、git 出错） |
| 闸门链原因码 | 运行开始前重过开关（§1.4 的 1–4）没通过 |
| `unknown_task` | 排队期间任务被删除 |

`resolution` 记录运行是怎么结束的：

| resolution | 含义 |
|---|---|
| `agent` | 主角色执行（可能委派了子代理） |
| `builtin` | 内建处理器 |
| `rule` | 事件规则先行命中，没有调模型 |

## 2. 运行

### `POST /v1/runs` 发起一次运行

请求头 `Idempotency-Key` 可选：同一个键只受理一次，重复提交返回已有运行，回执里 `dedup: true`。
键不限时间；只有失败的运行会释放这个键，之后可以用同一个键重提。

```json
{
  "task": "failure-analysis",
  "subtask": "dwd_trade_order",
  "service": null,
  "env": "prod",
  "input": {"run_id": "8f2c…", "asset_key": "dwd_trade_order", "error": "…"},
  "session_id": null,
  "memory": {"recall": null, "save": false},
  "wait": 0
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `task` | 否 | 任务名，也可以直接写子任务全名 `父任务:对象`。**不写 = 通用入口 `ask`**：任何服务任何环境直接提问或交代一件事，输入 `{question}`，要指定 `service` |
| `subtask` | 否 | 子任务的对象名。**不存在时按父任务自动创建**：继承全部定义，档案待补；闸门受理之后才建，被拒的请求不留子任务。回执的 `subtask_created` 会说明 |
| `service` | 通用任务必填 | 通用任务（`service: "*"`）要指定服务。专属任务省略即可；填了就必须与任务的服务一致 |
| `env` | 否 | 业务环境。缺省为平台默认环境（设置 → 环境），出厂默认是 `test`，所以生产必须显式写 |
| `input` | 否 | 任务输入，按任务的输入定义校验并补默认值。不合法返回 `invalid_input`，`detail.fields` 逐字段说明 |
| `session_id` | 否 | 续进已有会话，共享多轮上下文 |
| `memory` | 否 | 这一次的记忆开关 `{recall, save}`。`null` 表示依次跟随任务的设置、平台默认 |
| `wait` | 否 | 同步等待的秒数（0–300），运行在这段时间内结束就直接带结果返回 |

角色由任务决定，调用方不传。

返回 `202`：

```json
{
  "run_id": "4b1e0c2a-…", "session_id": "4b1e0c2a-…",
  "status": "queued", "output": null,
  "dedup": false, "subtask_created": null
}
```

| 字段 | 说明 |
|---|---|
| `status` | 受理时是 `queued`；`wait>0` 时是等待结束那一刻的状态，已经结束就是终态 |
| `output` | 结束时的结果，形如 `{answer}` 或 `{error}`；还没结束时为 `null` |
| `dedup` | `true` 表示命中幂等键或任务去重窗口，返回的是已有运行 |
| `subtask_created` | 这次顺带新建的子任务全名 |

### `GET /v1/runs` 运行列表

| 参数 | 说明 |
|---|---|
| `status` | `queued` / `awaiting_approval` / `running` / `success` / `failed` / `cancelled` |
| `service` `env` | 服务、环境 |
| `task` | 任务名；写父任务名时**包含其子任务** |
| `trigger` | `api` / `chat` / `schedule` / `event` / `web` / `rerun` / `resume` / `correction` / `replay` |
| `caller` | 发起方：密钥名、控制台用户或 `schedule` |
| `session_id` | 某个会话的全部运行 |
| `q` | run id 前缀，或摘要里的关键词 |
| `hours` | 最近 N 小时 |
| `cursor` `limit` | 分页；`limit` 默认 30，最大 200 |

列表项：

```json
{
  "run_id": "…", "session_id": "…", "task": "failure-analysis:dwd_trade_order", "task_title": "Dagster 失败分析",
  "service": "dagster", "env": "prod", "role": "ops_analyst",
  "status": "success", "resolution": "agent",
  "trigger": {"type": "event", "id": "on-failure", "source": "dagster", "caller": "dagster-sensor"},
  "summary": "dwd_trade_order · connection refused", "tokens": 18230, "duration_ms": 41200,
  "created_at": "…", "finished_at": "…"
}
```

`trigger.type` 为 `replay` 时，`trigger.id` 是被重放的原运行。

### `GET /v1/runs/{id}` 运行详情

除列表字段外还有：

| 字段 | 说明 |
|---|---|
| `task_version` `role_version` | 这次运行钉死的定义版本 |
| `replay_of` | 回归重放出来的运行指向原运行；其他运行为 `null` |
| `input` | 输入 |
| `output` | 结果，`{answer}` 或 `{error}` |
| `error_code` | 失败原因码 |
| `memory` | 这次实际生效的记忆开关 |
| `pending_approval` | 正在等的审批单，没有时为 `null` |
| `feedback` | 所有人对整次运行和各步的评价，见「反馈」一节 |
| `context.profile` | 注入的档案原文（服务档案 + 任务档案） |
| `context.recalled_knowledge` / `recalled_assets` | 召回了哪些记忆和方法；记忆每项 `{id, key, kind, rank}` |
| `context.saved_knowledge` / `saved_assets` | 沉淀了哪些记忆和方法；记忆每项 `{id, key, kind}`，不含交接摘要 |
| `context.session_runs` | 同一会话里的其他运行 |

### `GET /v1/runs/{id}/events?after=` 过程事件

事件按 `seq` 递增；带 `after` 时只取它之后的事件。一条事件：

```json
{"seq": 7, "kind": "tool_call", "at": "…", "payload": {"tool": "sql_query", "args": {"sql": "select …"}}, "feedback": null}
```

| kind | 含义 |
|---|---|
| `stage` | 阶段：profile / recall / assets / rule / resume / deliver 等 |
| `thought` | 思考 |
| `tool_call` / `tool_result` | 工具调用及其返回 |
| `approval` | 审批 |
| `final` | 结论 |
| `error` | 出错 |

### `GET /v1/runs/{id}/stream?after=` 过程推流（SSE）

接口先补发已有事件，再实时推送新事件。每条 `data:` 是一个事件，形状同上。

运行结束时推最后一条 `{"done": true, "status": "success"}`，然后关闭连接。没有新事件时，每 15 秒发一条注释行保活。

### 运行操作

| 端点 | 请求体 | 说明 |
|---|---|---|
| `POST /v1/runs/{id}/cancel` | — | 取消运行，挂起中的审批一并拒绝。已结束返回 `409 already_finished` |
| `POST /v1/runs/{id}/rerun` | — | 用同样的输入**新开**一次运行（新会话），跳过去重，沿用任务、服务和环境 |
| `POST /v1/runs/{id}/resume` | — | 失败的 agent 运行**断点续跑**（含 `orphaned`、`interrupted`），沿用同一个 run id。非失败态或内建任务返回 `409 conflict`，内建任务请用重跑 |
| `POST /v1/runs/{id}/correct` | `{text}` | 纠正：在同一会话里新开一轮，agent 带着原结论和纠正重新回答。成功后取代上一轮沉淀的记忆 |

`rerun`、`resume`、`correct` 返回的回执与 `POST /v1/runs` 相同。`cancel` 返回运行详情。

### 反馈（评价）

对整次运行或其中某一步打分，并说明哪里有问题。**一个人对同一次运行的同一步只有一条反馈**：
再提交就是覆盖，`DELETE` 是撤回。所以重复点 👎 不会把权重扣两次。

| 端点 | 说明 |
|---|---|
| `PUT /v1/runs/{id}/feedback` | 评价整次运行 |
| `DELETE /v1/runs/{id}/feedback` | 撤回 |
| `PUT /v1/runs/{id}/events/{seq}/feedback` | 评价时间线上的某一步 |
| `DELETE /v1/runs/{id}/events/{seq}/feedback` | 撤回 |
| `GET /v1/feedback?score=-1&service=&env=&task=&reason=&hours=&limit=` | 反馈收件箱：新的在前，带运行的任务、服务、环境、摘要 |

请求体：

```json
{"score": -1, "reasons": ["wrong_definition"], "comment": "GMV 不扣退款，退款单独看 refund_amount"}
```

| 字段 | 说明 |
|---|---|
| `score` | `1` 有用 / `-1` 有问题 |
| `reasons` | 问题类型，可多选；取值与中文名见 `GET /v1/meta` 的 `feedback_reasons` |
| `comment` | 说明，最长 2000 字 |

问题类型：

| 值 | 含义 |
|---|---|
| `wrong_conclusion` | 结论不对 |
| `wrong_definition` | 口径 / 业务理解不对 |
| `wrong_data` | 取数或查询有误 |
| `incomplete` | 没答全 |
| `off_topic` | 答非所问 |
| `wrong_tool` | 工具或命令用错 |
| `detour` | 绕远路 / 太慢 |
| `unsafe` | 操作有风险 |
| `other` | 其他 |

返回保存后的反馈：`{id, run_id, step_seq, score, reasons, comment, created_by, created_at, updated_at}`。
`step_seq` 为 `0` 表示整次运行。

反馈产生的效果：

- **整次运行的 👎 只罚不奖**：这次运行沉淀的记忆和召回的记忆各扣 1 分（排序时最多算到 -5），沉淀的方法也扣 1 分；
  👍 只留档、不改权重（没人点 👍，正分没有信号）。改主意、撤回按差值回补。
- **单步评价**只留档，供排查问题和改进角色提示词时回看。
- **新的 👎**（不是修改已有的 👎）会按通知规则推送，对应事件 `feedback_negative`（设置 → 通知）。
- **想让 agent 按意见重答**，用 `correct`。控制台的 👎 面板里可以勾选「按这条意见让 agent 重答」，提交时一并发起纠正。
- **改完提示词或定义后验证**，用回归重放（下一节）：👎 的问题类型、说明和被点的那一步就是判定标准。

运行详情的 `feedback` 字段是所有人对整次和各步的全部评价；对话详情每一轮的 `feedback` 是当前用户自己的评价。

### 回归重放

改完角色提示词、任务定义或档案后，拿被 👎 的 agent 运行用当前定义重跑，由模型判定问题改好没有。
原理见设计文档 §5.1。`run` 范围的密钥即可调用。

| 端点 | 说明 |
|---|---|
| `GET /v1/replays?limit=50` | 重放列表，新的在前 |
| `POST /v1/replays` | 发起一次重放，返回 `201` 和详情 |
| `GET /v1/replays/{id}` | 详情：逐条对照与判定 |
| `POST /v1/replays/{id}/judge` | 把还没判定或判定为 `unclear` 的条目重判一遍，返回详情 |

请求体（字段都可选）：

```json
{"task": "data-qa", "service": "board", "env": "test", "hours": 168, "limit": 20,
 "title": "", "note": "data_searcher 提示词加了口径确认"}
```

| 字段 | 说明 |
|---|---|
| `run_ids` | 直接点名要重放的运行；给了就不按条件选 |
| `task` `service` `env` | 选样条件；`task` 写父任务名时包含其子任务 |
| `hours` | 只看最近多少小时内被 👎 的（≥ 1） |
| `limit` | 最多几条，默认 20，最大 100 |
| `title` | 标题；不填按条件生成 |
| `note` | 这次改了什么，方便回看 |

不给 `run_ids` 时按条件选被 👎（整次或某一步）的 agent 运行，最近被评的在前，重放出来的运行不算；
一条都没有返回 `400 nothing_to_replay`。

每条原运行用同样的输入开一个重放运行：`trigger.type` 为 `replay`、`trigger.id` 是原运行；新会话、不沉淀记忆、不投递，
只过闸门前 4 道，也受密钥的服务 / 环境限定。重放运行结束后，模型对照「原答案 + 人指出的问题 + 新答案」给出判定。

列表项：

```json
{"id": 3, "title": "data-qa · board · test · 5 条 👎", "filter": {"task": "data-qa", "service": "board", "env": "test", "hours": 168, "limit": 20},
 "note": "…", "created_by": "…", "created_at": "…",
 "counts": {"total": 5, "fixed": 3, "same": 1, "worse": 0, "unclear": 0, "pending": 1}}
```

`counts.unclear` 含 `error`；`pending` 是还没判的。

详情在列表项之外多一个 `items`，每条：

```json
{"id": 11, "source_run": "…", "new_run": "…", "verdict": "fixed", "reason": "…", "judged_at": "…",
 "task": "data-qa", "service": "board", "env": "test", "summary": "…",
 "before": {"task_version": 3, "role_version": 5, "answer": "…", "status": "success"},
 "after":  {"task_version": 4, "role_version": 6, "answer": "…", "status": "success"}}
```

| verdict | 含义 |
|---|---|
| `fixed` | 被指出的问题解决了，且没引入明显的新错 |
| `same` | 问题还在 |
| `worse` | 更糟，或引入了明显的新错 |
| `unclear` | 判断不了，或判定调用失败；可以重判 |
| `error` | 重放运行没建成（被闸门拒、没权限）：`new_run` 为空，`reason` 是原因 |
| `null` | 还没判（重放运行还没结束） |

重放运行没有成功结束时不调模型：原运行成功的记 `worse`，否则记 `same`。

### `POST /v1/chat`

```json
{
  "message": "华东区 10 月订单量按天给我一下",
  "session_id": null,
  "service": "board", "env": "test",
  "task": null, "subtask": null,
  "input": {},
  "memory": {"recall": true, "save": null},

```

| 字段 | 说明 |
|---|---|
| `message` | 这一轮的问题，作为任务输入里的 `question` |
| `session_id` | 续会话；续会话且不写 `task` 时，沿用上一轮的任务 |
| `service` `env` | 问哪个服务、哪个环境 |
| `task` | 对话任务（声明了 `chat` 触发）；缺省时服务专属的对话任务优先，没有就用通用入口 `ask` |
| `subtask` | 针对某个对象问：会带上这个对象的档案，沉淀的记忆也归到它名下 |
| `input` | 对话任务的其他输入字段 |
| `memory` | 这一轮的记忆开关 |
| `stream` | `true`（默认）走 SSE；`false` 等运行结束后返回 `{run_id, session_id, status, answer, error}` |

SSE 的每条 `data:` 是一个 JSON，用 `type` 区分：

| type | 字段 | 说明 |
|---|---|---|
| `run` | `run_id` `session_id` `subtask_created` | 已受理 |
| `stage` `thought` `tool_call` `tool_result` `approval` | `seq` 加平铺的事件 payload | 执行过程 |
| `final` | `status` `output` | 运行结束 |
| `error` | `code` `message` | 受理失败（例如被闸门链拒绝），随后流结束 |

## 4. 事件

### `POST /v1/events/{source}`

外部系统回调的统一入口。请求体就是来源系统的回调原文。

平台的处理步骤：

1. 把回调翻译成「事件名 + 扁平字段」。
2. 找出声明了对应 `source + event` 触发器的任务。
3. 每个匹配的任务发起一次运行。

| source | 事件 | 字段 | 接法 |
|---|---|---|---|
| `dagster` | `run_failure` | `run_id` `asset_key` `error` `env` `subtask` `job` | `run_failure_sensor` 回调本地址 |
| `gitlab` | `deployment`（只认部署成功） | `project` `ref` `env` `sha` `url` `user` | 项目 Webhook 勾选 Deployment events，密钥填在 Secret token |
| `webhook` | 任意，事件名取请求头 `X-Event` 或请求体 `event` | 请求体原样 | 通用 |

事件数据里有三个字段有特殊含义：

- `env`：业务环境。
- `subtask`：指定子任务对象。
- `service`：给通用任务指定服务。任务的触发器上写了 `service` 时，以触发器为准。

每个匹配的触发器依次经过下面几步：

1. `filter`（字段 → 正则）全部满足才触发。
2. `map` 把事件字段映射成任务输入；没写 `map` 就整份透传。
3. `rules` 规则先行：报错命中规则时直接给结论、不调模型，但同样留一条 `resolution=rule` 的运行记录。
4. `session` 模板决定续进哪个会话。

返回每个匹配的处理结果。某个匹配被闸门拒绝，不影响其他匹配：

```json
{
  "source": "dagster", "events": ["run_failure"],
  "matched": [
    {"task": "failure-analysis:dwd_trade_order", "trigger": "on-failure", "rule": "infra",
     "run_id": "…", "status": "queued", "dedup": false, "error": null},
    {"task": "lineage-check", "trigger": "dagster", "rule": null,
     "run_id": null, "status": "rejected", "error": {"code": "service_env_disabled", "message": "…"}}
  ]
}
```

## 5. 定义：服务 / 角色 / 任务

三种定义共用一套读写接口，`{kind}` 取 `services`、`roles`、`tasks` 之一。
定义写库即生效，每次修改留一个版本。

| 端点 | 说明 |
|---|---|
| `GET /v1/{kind}` | 列表。服务与任务附带统计（见下）。`GET /v1/tasks?service=` 只看某个服务的任务，含通用任务 |
| `POST /v1/{kind}` | 新建，请求体含 `name`，返回 `201` |
| `GET /v1/{kind}/{name}` | 单个 |
| `PATCH /v1/{kind}/{name}` | 局部更新：**请求里出现的顶层字段整体替换**，没出现的不动 |
| `DELETE /v1/{kind}/{name}` | 删除。仍被引用时返回 `409 in_use`（例如角色正被任务使用、被别的角色继承或列为子代理）。删父任务会连带删除子任务，返回 `{deleted: [...]}` |
| `GET /v1/{kind}/{name}/versions` | 版本历史，新的在前：`{version, updated_by, created_at, deleted, definition}` |
| `POST /v1/{kind}/{name}/versions/{v}/restore` | 恢复到某个版本。恢复本身产生一个新版本，已删除的定义也能恢复 |
| `GET /v1/roles/{name}/resolved` | 角色沿 `extends` 合并后的生效结果 `{name, title, description, prompt, tools, subagents, service_tools, lineage}`，`lineage` 是继承链 |

所有定义都带台账字段 `version`、`updated_by`、`updated_at`。

### 5.1 服务

```yaml
name: dagster
title: Dagster 数据编排
description: 数仓 ETL 编排
root: /srv/svc/dagster/code/{env}      # 部署目录（agent 只读）；路径都可以写 {env}：每个环境一份代码
code_paths: []                         # 读代码、校验记忆新鲜度；缺省 = [root]
repo: git@gitlab.internal:data/dagster.git   # 代码同步（内建任务 code-sync）从这里拉
ref: main                              # 默认跟踪的分支
python: /srv/svc/dagster/venv/{env}/bin/python   # 项目解释器：每个环境一个 venv；空 = python3
env_vars: {DAGSTER_HOME: "/srv/svc/dagster/code/{env}"}   # 服务级环境变量，可写 {env}；项目内核与进程都带上
urls:                                  # 有名字的地址，可写 {env}、{port:进程名}
  local: "http://127.0.0.1:{port:webserver}"
hosts: [10.0.0.11]
readonly_dsn: null
configs:                               # 进程和项目内核读固定路径，每个环境一份真实文件
  - {canonical: "/srv/svc/dagster/code/{env}/dagster.yaml", template: "/srv/svc/dagster/conf/{env}/dagster.yaml"}
processes:
  webserver:
    cmd: ["/srv/svc/dagster/venv/{env}/bin/dagster-webserver", -p, "{port}"]   # 可写 {env} {port} {python}
    ports: {prod: 3000, test: 3001}
    lease_hours: null                  # 空 = 平台默认租约
    env_vars: {}                       # 叠加在服务级 env_vars 之上
mcp:                                   # 服务自己的 MCP server：{名字: langchain-mcp-adapters 连接配置}
  dagster:
    transport: stdio
    command: "{platform_python}"
    args: ["{platform}/mcp_servers/dagster_mcp.py"]
    env: {DAGSTER_URL: "{url:deployed}"}
    envs: {prod: {}, test: {}}         # 按环境深合并的覆盖；写了就只在列出的环境可用
envs:                                  # 按环境覆盖，只写差异
  prod: {ref: release, readonly_dsn: "postgresql://ro:${DAGSTER_RO_PASSWORD}@prod-db/dagster",
         urls: {deployed: "http://10.0.0.11:3000"}}   # urls 按键覆盖服务的 urls
  test: {ref: test, urls: {deployed: "http://10.0.1.11:3001"}}   # 还可以写 python：这个环境单独的解释器（同样可写 {env}）
  dev:  {enabled: false}               # 这个服务在 dev 不接收运行、不起进程和项目内核
profile:                               # 服务档案：逐字置顶注入该服务的所有运行
  conventions: 资产按 dt 分区，T+1 物化
enabled: true
```

- `python`（或 `envs[env].python`）渲染 `{env}` 后就是该环境的解释器：项目内核（`py` 工具）用它，进程 `cmd` 里的 `{python}` 也换成它。
- 服务和进程的 `env_vars` 都不支持 `${VAR}`：启动规格是落盘的明文 JSON，口令放进该环境的配置文件。
- `urls`：`{port:进程名}` 换成该进程在这个环境的端口；`envs[env].urls` 按键覆盖。渲染后出现在 agent 的运行环境提示里，
  浏览器之类的工具按它打开页面，`mcp` 里用 `{url:名字}` 引用。

`mcp` 的规则：

| 项 | 规则 |
|---|---|
| 连接配置 | 原样交给 langchain-mcp-adapters（`transport`、`command`、`args`、`env`、`url` 等）；平台要装 `agent-platform[mcp]`，仓库自带的 dagster MCP 另需 `[dagster-mcp]` |
| `envs` | `{环境: 覆盖}`，深合并到基础配置上。**写了 `envs` 就只在列出的环境可用**，没配的环境不会悄悄连到别处；不写就每个启用的环境都用基础配置 |
| 占位 | `{env}`；`{url:名字}`（该环境的 urls）；`${VAR}`（连接时才从 secrets.env 取值）；`{platform}`（平台安装目录）；`{platform_python}`（平台解释器） |
| 生效 | 运行在这个服务上时工具自动出现，调用按运行的环境路由；角色 `service_tools: false` 时不带；和角色 `tools` 里的工具重名时以角色的为准 |
| 连接 | 懒加载：第一次有运行用到，或调 `GET /v1/services/{s}/tools` 时才连；按定义内容缓存，改了定义下次自动重连；有连接失败时 5 分钟后重试，一个连接失败不影响别的 |
| 出错 | 工具调用出错如实返回给模型（`[调用失败] …`），不炸运行；没配本环境连接的返回 `[不可用] …` |

列表和单个接口额外返回：

- `task_count`：该服务的任务数。
- `health[env]`：每个环境的健康汇总，`{enabled, python, runs_24h, failed_24h, last_run, running_processes, total_processes}`。

**只读库口令**：

- 建议写成 `${VAR}`，真实值放 secrets.env，连库时才取值。库里、接口里、版本历史里都只有占位。
- 直接写了明文口令的，读回时（列表、单个、版本历史）口令显示为 `***`。
- 保存时把 `***` 原样传回表示不改；连接串的其余部分改了而口令还是 `***`，返回 `422 invalid_definition`。

### 5.2 角色

```yaml
name: qa_engineer
title: 冒烟测试
description: 部署后按沉淀的方法跑冒烟脚本和页面检查   # 也是委派时给主角色看的「擅长什么」
prompt: …                              # 系统提示（有 extends 时可空）
tools: [py, bash, service_info, service_ctl, save_asset, "mcp:browser"]
subagents: [ops_analyst]               # 运行中可委派的角色；null = 跟随父角色
service_tools: true                    # 自动带上运行所在服务的 MCP 工具；null = 跟随父角色（没有父角色就是 true）
extends: null                          # 继承父角色
prompt_append: ""                      # 有 extends 时追加在父角色提示词之后
```

| 字段 | 规则 |
|---|---|
| `tools` | 内置工具名或平台 MCP 工具名。`"*"` = 全部内置工具 + 全部平台 MCP 工具；`"mcp:<server>"` = 某个平台 MCP server 的全部工具（如 `mcp:browser`）。没登记的名字忽略并记 warning |
| `subagents` | 主角色运行中按需把子问题委派给这些角色：子代理用自己的提示词和工具、独立上下文，结论交回主角色。只委派一层，子代理自己的 `subagents` 不生效。列出的角色必须存在，不能列自己，否则 `422 invalid_definition` |
| `service_tools` | 运行所在服务声明的 MCP 工具（§5.1 的 `mcp`）是否自动带上；`null` = 跟随父角色，没有父角色时等于 `true` |
| `extends` | 子角色写了 `tools`（非空）/ `subagents`（非 `null`）/ `service_tools`（非 `null`）就**整体替换**父角色的，没写就跟随；`subagents: []` 表示明确不要子代理。提示词在父角色之后追加 `prompt_append` |

一个任务只有一个主角色；需要多种能力时用子代理，而不是多角色流水线。

内置工具：`py`（项目内核）`bash` `run_code` `service_info` `service_ctl` `sql_query` `host_metrics` `save_asset` `notify`，
加上部署配置里的平台 MCP 工具；文件工具（`read_file` 等）总是可用，不用写。`service_ctl` 在进程控制关闭时不出现，
`host_metrics` 没配 Grafana 时不出现。实际可用的目录见 `GET /v1/meta` 返回的 `tools`（MCP 工具带 `server`）。
服务 MCP 的工具不在这个目录里，见 `GET /v1/services/{s}/tools`。

### 5.3 任务

```yaml
name: failure-analysis
title: Dagster 失败分析
service: dagster            # 专属服务 / "*" 通用（调用时指定）/ null 平台任务
role: ops_analyst
form: agent                 # agent | builtin
input:
  run_id:    {type: str, required: true}
  asset_key: {type: str, required: true, description: 失败的资产}
  error:     {type: text, required: true}
envs: [prod, test]          # 能跑的环境；空 = 全部
triggers:
  - {id: api, type: api}
  - {id: chat, type: chat}
  - {id: daily, type: schedule, cron: "0 9 * * *", envs: [prod, test], input: {}, timezone: Asia/Shanghai, service: null}
  - id: on-failure
    type: event
    source: dagster
    event: run_failure
    filter: {asset_key: "^dwd_"}
    map: {run_id: run_id, asset_key: asset_key, error: error}
    rules: [{pattern: "connection.*refused", category: infra, conclusion: 目标库连不上，检查实例存活}]
    session: "dagster:{asset_key}:{error_class}:{date}"
    service: null
deliver: {channel: default}  # 或 {url: "https://…"}；null = 调用方自取
dedup: {key: run_id, window_s: 600}
memory: {recall: null, save: null}   # null = 跟随平台默认
timeout_s: 300
profile:                     # 任务档案
  pitfalls: 上游 ods 延迟会级联失败
enabled: true
```

| 字段 | 规则 |
|---|---|
| `input.*.type` | `str` `text` `int` `bool` `json` `enum`；`enum` 需配 `options` |
| `schedule` 触发 | 每个环境各触发一次；通用任务必须写 `service`。同一触发器同一环境上一次没跑完就跳过，停机期间错过的不补 |
| `event` 触发 | 通用任务没写 `service` 时，取事件数据里的 `service` 字段 |
| `session` 模板 | 可以引用事件的任意字段，另有 `{error_class}`（命中规则的类别，否则为 unknown）和 `{date}` |
| `deliver` | `channel`（设置 → 通知里的渠道名）与 `url` 二选一。投递失败重试 3 次，仍失败只记事件，不改运行状态 |
| `dedup.key` | 输入字段名，用 `a+b` 拼接多个字段；时间窗内同键、排队 / 等审批 / 运行中 / 成功的运行直接返回它（`dedup: true`），失败和取消的不算 |
| `timeout_s` | 1–7200 秒 |
| `handler` | `form: builtin` 的处理器名：`memory-gardener` / `code-sync` |

列表和单个接口额外返回：

| 字段 | 说明 |
|---|---|
| `overrides` | 子任务自己写了哪些字段 |
| `stats_24h` | 近 24 小时 `{runs, success, failed, p50_ms}` |
| `last_run` | 最近一次运行 |
| `next_fire` | 下一次定时 `{env, at}` |
| `subtask_count` | 子任务数 |

**子任务**的名字是 `父任务:对象名`，只嵌套一层。**接口返回的是合并后的生效定义**：
档案与父任务按键合并；其他字段子任务写了就用自己的，没写就跟随父任务。

| 端点 | 说明 |
|---|---|
| `GET /v1/tasks/{name}/subtasks` | 子任务列表（带统计） |
| `POST /v1/tasks/{name}/subtasks` | `{object, title?, description?, profile?, input?, envs?, enabled?}`，只写与父任务不同的部分 |
| `GET /v1/tasks/{name}/schedule` | 接下来的定时触发：`[{task, trigger_id, service, env, at}]` |

对象名不能含冒号、空白或斜杠，最长 120 个字符。修改子任务就用 `PATCH /v1/tasks/父任务:对象`。

## 6. 服务 × 环境

| 端点 | 说明 |
|---|---|
| `GET /v1/services/{s}/envs/{env}` | 该环境的解析结果（字段见下） |
| `GET /v1/services/{s}/envs/{env}/config?path=` | 读本环境声明过的配置文件，密钥类的值会打码。读未声明的路径返回 `404` |
| `GET /v1/services/{s}/tools?reload=` | 服务自己声明的 MCP 工具：`{servers, loaded, tools: [{name, description, server, envs}], failed}`。还没有运行用到时现连一次；`reload=true` 强制重连（改了 MCP 服务端之后）。`failed` 是连不上的连接，形如 `<服务>.<server>@<环境>` |
| `GET /v1/services/{s}/processes` | 全部「环境 × 进程」的实例：`{service, env, process, state, port, pid, started_at, lease_until, started_by, last_exit, enabled}`；`enabled` 是服务在该环境是否启用 |
| `POST /v1/services/{s}/envs/{env}/processes/{p}/start` | 启动。`{hours}` 是租约时长；缺省用进程设置或平台默认，不超过平台上限 |
| `POST …/stop` | 停止 |
| `POST …/renew` | 续租 `{hours}`。进程没在运行时返回 `409 not_running` |
| `GET …/logs?lines=200` | 最近的日志 `{lines: [...]}` |

环境解析结果包含：`enabled`、`python`（该环境的解释器，已渲染 `{env}`）、`root`、`code_paths`、`repo`、`ref`（该环境跟踪的分支）、
`urls`（本环境的地址，已渲染）、`mcp_servers`（服务声明的 MCP server 名）、`hosts`、
`readonly_dsn`（口令打码）、`config_files[{canonical, path, exists, size}]`、`profile`、`git{branch, commit, dirty, committed_at}`。
路径里的 `{env}` 已经替换成该环境。

启停需要 admin，返回 `{instance, approval}`。

- 服务在该环境启用就能起进程；停用时启动被拒（`service_env_disabled`），在发审批之前就拒，不会产生注定被拒的审批单。
- 设置 → 审批 打开时（默认关闭）启停要先审批：`required_in: protected` 只在受保护环境，`all` 所有环境。
  此时 `approval` 不为空，`instance` 是当前状态，放行后才执行（执行时再检查一次能不能起）。续租不审批。
- 该环境的配置文件不存在时，启动被拒（`config_missing`）。固定路径不存在时平台先建一个空文件占位。
- 平台关闭了进程控制时，返回 `process_control_off`。

**代码同步**不是单独的端点，是内建任务 `code-sync`（通用任务）：
`POST /v1/runs {"task": "code-sync", "service": "board", "env": "test", "input": {"ref": "可选"}}`。
不填 `ref` 就切到该环境跟踪的分支；目录不存在就 clone，有未提交改动就拒绝（`code_sync_failed`）。
种子里它还声明了 GitLab 部署事件的触发：部署成功后把对应环境切到刚部署的提交。

实例的 `state` 取值：`stopped` `starting` `running` `stopping` `failed`。租约到期后进程自动停止。
`started_by` 记录是谁启动的：人、`run:<id>` 或 `lease`。

## 7. 审批

审批默认关闭（设置 → 审批 的 `required_in` 为 `off`）。打开后，两类人工门共用一种审批单：

| kind | 何时产生 | 放行后 |
|---|---|---|
| `command` | 运行中执行危险命令：`py` / `bash` / `run_code` 的代码命中危险模式，且所在环境需要审批 | 运行继续 |
| `process` | 进程启停（运行里的 `service_ctl`，或控制台 / 接口发起），且所在环境需要审批 | 执行启停 |

| 端点 | 说明 |
|---|---|
| `GET /v1/approvals?status=pending&kind=&service=&env=` | `status` 取 `pending` 或 `decided`（已处理，含超时） |
| `GET /v1/approvals/{id}` | 单个 |
| `POST /v1/approvals/{id}/approve` | `{comment}`，需要 admin |
| `POST /v1/approvals/{id}/reject` | `{comment}`，需要 admin |

审批单的字段：`{id, kind, run_id, title, detail, service, env, task, payload, requested_by, status,
decided_by, comment, created_at, decided_at, expires_at}`。

- `status` 取值：`pending` `approved` `rejected` `expired`。
- 超时未处理视同拒绝，时限在 设置 → 审批。
- 对已处理的审批单再操作，返回 `409 already_decided`。

## 8. 记忆

记忆层分三样（原理见设计文档 §5）：

- **档案**：人写的，在服务 / 任务定义的 `profile` 里，用定义接口改（§5），逐字置顶注入、不检索、不过期；
- **记忆**：agent 记下的事，本节的 `/v1/knowledge`；
- **方法**：可执行的做法与脚本，本节的 `/v1/assets`。

`task` 过滤写父任务名时包含其子任务。增删改、升格需要 admin。

### 记忆

一张表三种 `kind`：`fact` 事实（口径、表与字段、拓扑）/ `lesson` 报错教训（带报错指纹与类别）/ `handoff` 会话交接摘要。
记忆按服务分区，`env` 为空的条目对该服务所有环境成立。

| 端点 | 说明 |
|---|---|
| `GET /v1/knowledge?service=&env=&task=&kind=&status=&q=` | `kind`：`fact` / `lesson` / `handoff`，不给 = 事实与教训。`env=X` 返回该环境的 + 通用的，`env=*` 只看通用的。`status`：`active`（默认）/ `expired` / `superseded` / `all` |
| `POST /v1/knowledge` | 人工录入（见下），返回 `201` 和条目 |
| `GET /v1/knowledge/{id}` | 单条 |
| `PATCH /v1/knowledge/{id}` | `{content?, status?: active \| expired}`。改内容视为人工纠正，旧内容进入历史 |
| `DELETE /v1/knowledge/{id}` | 作废，等同于 `status: expired`，可以恢复 |
| `GET /v1/knowledge/{id}/history` | 内容历史 |
| `POST /v1/knowledge/{id}/promote` | 升格进档案（见下） |
| `GET /v1/knowledge/promotable?service=&env=` | 值得升格的：近 30 天被 ≥ 5 次运行召回、没挨过 👎 的生效事实，召回多的在前，最多 30 条 |
| `GET /v1/knowledge/health?service=&env=` | `{active, zero_recall, negative, drifted, conflicts, lessons, promotable}`：`lessons` 是生效的教训数，`promotable` 是近 30 天被 ≥ 5 次运行召回的生效条目数 |
| `POST /v1/knowledge/search` | 试检索 `{query, service, env, task}` → `{hits, block}`。`block` 是 agent 实际会看到的提示词块；试检索不计入命中统计 |

**人工录入**：

```json
{"service": "board", "env": "", "kind": "fact", "key": "metric:gmv", "content": "GMV 不含退款，退款单独看 refund_amount"}
{"service": "dagster", "env": "", "kind": "lesson", "content": "上游 ods_order 分区延迟导致级联失败，先看上游", "error": "…报错原文…", "category": "upstream"}
```

| 字段 | 说明 |
|---|---|
| `service` | 必填 |
| `env` | 空（默认）= 对该服务所有环境成立；写环境名 = 只在该环境成立 |
| `kind` | `fact`（默认）/ `lesson` |
| `key` | `fact` 必填，如 `metric:gmv`，最长 200；同一服务、同一 `env` 下已存在时返回 `409 conflict`，请直接编辑。`lesson` 不填，按报错指纹生成 `lesson:<指纹>` |
| `content` | 必填：事实的内容，或教训的结论 |
| `task` | 归到哪个任务名下（召回时同谱系优先），可空 |
| `error` | `lesson` 必填：报错原文，按它算指纹，同类报错才能精确命中；内容会附上报错的最后一行。同一指纹已有教训时覆盖，旧内容进历史 |
| `category` | `lesson` 的类别：`code` / `data` / `infra` / `upstream`，空 = `code` |

缺 `key`（事实）或 `error`（教训）返回 `400 invalid_input`。人工录入的条目在召回排序上加 3 分。

**升格**：把一条记忆写进档案，适合被反复用到、确认无误的口径与约定。

```json
{"target": "service", "key": "conventions", "task": "", "content": null}
```

| 字段 | 说明 |
|---|---|
| `target` | `service`：写进服务档案，条目只在某环境成立（`env` 非空）时写进 `envs[env].profile`；`task`：写进任务档案 |
| `key` | 档案的键，如 `conventions` / `pitfalls` / 自定义，最长 60 |
| `task` | `target=task` 时写进哪个任务；不填用条目的来源任务，条目没有来源任务时返回 `400 invalid_input` |
| `content` | 写进档案的文字；不填用条目原文 |

- 同一个键已有内容就接在后面（已经包含就不重复）；写入产生服务 / 任务定义的一个新版本。
- 原条目标为被取代：`status` 变成 `superseded`，`superseded_by` 为 `profile:<目标>:<键>`，目标形如 `service:board`、
  `service:board@test`、`task:data-qa`，召回不再重复注入。
- 只有生效中的条目能升格，否则 `409 conflict`。
- 返回 `{entry, profile: {target, key}}`，`entry` 是升格后的原条目。

**条目字段**：`{id, service, env, task, kind, key, content, fingerprint, category, source_run, code_ref{path, commit}, status,
superseded_by, feedback_score, hits_30d, last_hit_at, updated_at}`。

- `env` 为空表示对所有环境成立；`source_run` 为空表示人工录入。
- `fingerprint`、`category` 只有教训有。
- `feedback_score` 是 👎 扣分的累计（只罚不奖，见「反馈」）。
- `code_ref` 引用的代码在沉淀之后改过时，条目自动过期，召回时跳过。

原来的案例已并进记忆（`kind=lesson`），`/v1/cases` 两个端点已删除（升级见部署指南 §6）。

### 方法（可执行的做法与脚本）

| 端点 | 说明 |
|---|---|
| `GET /v1/assets?service=&env=&task=&kind=&status=` | `kind`：`procedure` `script` `query` `baseline` |
| `POST /v1/assets` | `{service, env, task, kind, name, summary, content}` |
| `PATCH /v1/assets/{id}` | `{summary?, content?, status?: active \| superseded}` |
| `DELETE /v1/assets/{id}` | 作废 |

方法按 服务 × 环境 分区。文件类方法（agent 用 `save_asset` 收编的脚本）的目录在项目内核启动时加到 `sys.path`，`py` 里可以直接 import。

## 9. 设置

### 9.1 平台配置

平台配置对所有人生效，存在库里，带版本历史。个人偏好（主题、密度、默认环境视角等）存在浏览器里，
不经过后端。

| 端点 | 说明 |
|---|---|
| `GET /v1/settings` | 全部配置节，每节带 `section` `version` `updated_by` `updated_at` |
| `GET /v1/settings/{section}` | 单节 |
| `PUT /v1/settings/{section}` | 整节替换，需要 admin |
| `GET /v1/settings/{section}/versions` | 版本历史 |
| `POST /v1/settings/{section}/versions/{v}/restore` | 恢复到某个版本 |
| `POST /v1/settings/notifications/test` | `{channel}`，向该渠道发一条测试消息；发送失败返回 `channel_failed` |

| section | 内容 |
|---|---|
| `envs` | `{items: [{name, title, description, protected, color}], default}`：有哪些业务环境、默认哪个、哪些受保护 |
| `approvals` | `{danger_patterns, required_in: off \| protected \| all, timeout_minutes}`：哪些命令算危险、要不要审批（默认 `off`；`protected` 只在受保护环境，`all` 所有环境）、多久超时 |
| `notifications` | `{channels: {名字: {type: dingtalk \| webhook, url, token}}, rules: [{name, enabled, events, services, envs, tasks, triggers, channel}]}` |
| `memory` | `{recall, save, handoff_summary, knowledge_limit, asset_limit}`：记忆的平台默认 |
| `processes` | `{default_lease_hours, max_lease_hours}` |

通知规则：

- `events` 取值：`run_failed` `run_succeeded` `approval_requested` `process_stopped` `feedback_negative`。
- `services` `envs` `tasks` `triggers` 为空表示不限；多个非空项之间是「且」的关系。
- 渠道的 `token` 读回时是 `"***"`（版本历史里也是），原样传回表示不改。`url` 与 `token` 里可以写 `${VAR}`，发送时才取值。

「某服务在某环境是否启用」不在平台配置里，它是服务自己的 `envs[env].enabled`。

### 9.2 API 密钥

全部需要 admin。

| 端点 | 说明 |
|---|---|
| `GET /v1/api-keys` | `{id, name, prefix, scope, services, envs, note, created_by, created_at, expires_at, last_used_at, revoked_at}` |
| `POST /v1/api-keys` | `{name, scope: run \| admin, services, envs, note, expires_at}`。返回里的 `token` **只出现这一次** |
| `PATCH /v1/api-keys/{id}` | 修改 `services` `envs` `note` `expires_at`；名字和范围不能改 |
| `DELETE /v1/api-keys/{id}` | 吊销，立即生效，不可恢复 |

`name` 为 2–40 个字母、数字或 `.` `_` `-`，建议用项目名，例如 `board-backend`、`dagster-sensor`。

## 11. 调用示例

```bash
AGENT=https://agent.internal KEY=ak_xxx

# 问一个口径问题，最多等 120 秒拿结果
curl -sX POST $AGENT/v1/runs -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"task":"data-qa","service":"board","env":"test","input":{"question":"7 天留存怎么算"},"wait":120}'

# 不写 task = 通用入口 ask：直接交代一件事，不用先建任务
curl -sX POST $AGENT/v1/runs -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"service":"dagster","env":"prod","input":{"question":"dwd_trade_order 今天为什么没物化"},"wait":300}'

# 把一条记忆升格进服务档案（需要 admin 范围的密钥）
curl -sX POST $AGENT/v1/knowledge/42/promote -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"target":"service","key":"conventions"}'

# 某个对象的失败分析（对象不存在时会自动建子任务）
curl -sX POST $AGENT/v1/runs -H "Authorization: Bearer $KEY" -H 'Idempotency-Key: dagster-8f2c' \
  -H 'Content-Type: application/json' \
  -d '{"task":"failure-analysis","subtask":"dwd_trade_order","env":"prod","input":{"run_id":"8f2c","asset_key":"dwd_trade_order","error":"…"}}'

# 对话（SSE）
curl -N -X POST $AGENT/v1/chat -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"message":"华东区 10 月订单量按天","service":"board","env":"test"}'

# 推一个通用 webhook 事件
curl -sX POST $AGENT/v1/events/webhook -H "Authorization: Bearer $KEY" -H 'X-Event: release' \
  -H 'Content-Type: application/json' -d '{"service":"board","env":"test","version":"1.2.0"}'

# 改完提示词后，拿最近一周 data-qa 在 board/test 上被 👎 的运行回归重放
curl -sX POST $AGENT/v1/replays -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"task":"data-qa","service":"board","env":"test","hours":168,"note":"data_searcher 提示词加了口径确认"}'
```
