# 外部接口文档（/v1）

平台对外的全部 HTTP 接口。调用方有业务项目、脚本、Dagster / GitLab 回调和控制台。
控制台只是这套接口的一个客户端，没有私有接口。`sdk/agent_client` 是它的 Python 薄封装，
见 `docs/SDK开发指南.md`。

契约有三处出处，改一处必须同时改另两处：

| 内容 | 后端 | 前端 |
|---|---|---|
| 请求体 | `src/agent_platform/api/schemas.py` | `web/src/api/types.ts` |
| 响应形状 | `src/agent_platform/api/views.py` + 各领域模型 | 同上 |
| 端点清单 | 每个 `api/routes/*.py` 开头的文档串 | `web/src/api/hooks.ts` 的 `api` 对象 |

运行中的服务自带 OpenAPI：交互页面在 `/v1/docs`，规范在 `/v1/openapi.json`。

## 1. 通用约定

### 1.1 地址与格式

- 平台在每台部署主机上一个 agent 服务，各台共用一个库；对外的只有控制台主机（地址即部署配置 `public_url`），它自己做 HTTPS 或经反向代理，
  其他主机只听 `127.0.0.1:8100`（见部署指南 §2.1、§4）。所有接口都打到控制台主机；运行由负责该环境（和服务）的那台主机认领执行，调用方不用管。
  那台没在跑时运行停在 `queued`，起来后接着执行。
- 请求和响应都是 JSON（SSE 端点除外），字段名一律 `snake_case`。
- 时间是带时区的 ISO 8601 字符串。

### 1.2 身份

平台没有用户体系，**身份就是 API 密钥**。每个调用方一把密钥：一个项目、一个回调来源或一个人。
密钥名就是运行记录里的「发起方」（`caller`）。

| 方式 | 用法 |
|---|---|
| `Authorization: Bearer <密钥>` | 项目、脚本、SDK |
| `X-Gitlab-Token: <密钥>` | GitLab Webhook，GitLab 只能这样带密钥 |
| Cookie `ap_session` | 控制台：`POST /auth/session` 用密钥换取，httponly |

密钥只标识身份，**不分权限**：任何有效密钥（和用它登录的控制台）都能调全部接口，包括改定义、改设置、管密钥、改给 agent 的配置。

部署配置里的 `root_token` 是引导密钥：不可吊销，只用于首次登录和创建第一批密钥。

### 1.3 错误

所有错误都是同一个形状：

```json
{"error": {"code": "service_env_disabled", "message": "服务 vision-board 在 prod 环境已停用", "detail": null}}
```

**程序只认 `code`**。`message` 是给人看的；`detail` 是附加结构，例如字段错误表。

| HTTP | 含义 | 常见 code |
|---|---|---|
| 400 | 请求能理解，但按规则不能办 | 闸门链原因码（§1.4）、`invalid_input`、`service_required`、`service_not_allowed`、`invalid_subtask`、`unknown_env`、`unknown_channel`、`nothing_to_replay` |
| 401 | 没带身份，或密钥无效 / 已吊销 / 已过期 | `unauthorized` |
| 404 | 对象不存在 | `not_found`、`unknown_task`、`unknown_service`、`unknown_source`、`unknown_run` |
| 409 | 状态冲突 | `conflict`、`in_use`、`already_finished`、`config_not_used`、`upstream_failed`、`triggers_paused` |
| 422 | 参数或定义校验不过 | `invalid_request`（参数校验不过时 `detail` 为「字段 → 错误」；游标不对、事件请求体不是 JSON、配置超过 1MB 也是它）、`invalid_definition` |
| 500 / 502 | 平台内部错误，或依赖不可用 | `internal`、`channel_failed`（502） |

不在闸门链里的几个：

| code | 含义 |
|---|---|
| `service_not_allowed` | 专属任务的请求里写了别的服务 |
| `unknown_channel` | 投递或测试用的通知渠道不存在 |
| `nothing_to_replay` | 发起回归重放时没有符合条件的运行（被 👎 的；`negative_only=false` 时是结束了的 agent 运行） |
| `channel_failed` | 通知渠道测试发送失败 |
| `invalid_input` | 运行的输入不合法（`detail.fields` 逐字段说明）；新建记忆、升格缺必填字段（§7） |
| `config_not_used` | 读写不受保护的环境（测试）给 agent 的配置：那个环境 agent 直接用项目的真实配置，不用填只读版（§6） |
| `unknown_run` | `POST /v1/runs` 的 `after` 点名的运行不存在 |
| `upstream_failed` | `after` 点名的运行已经失败或取消（409）；也是运行的失败原因码：它等的上游最终失败 / 取消了，这次没有执行（§1.6） |

`config_missing`（受保护的环境里给 agent 的配置没填，或配置路径在部署主机上不存在）和 `wrong_env`（这台主机不负责这个服务×环境；认领时已按环境过滤，一般不会出现）不是 HTTP 错误：
它们出现在运行时间线里 `py` 工具的返回中，说明写在返回文字里，解法见部署指南 §9。

### 1.4 闸门链原因码

一次提交能不能办，只在闸门链里判断（`orchestration/gates.py`）。闸门按下表顺序检查，先粗后细，
遇到第一个不通过的就停：

| 顺序 | code | 含义 | 怎么解 |
|---|---|---|---|
| 1 | `service_disabled` | 服务整体停用 | 服务详情 → 启用 |
| 2 | `service_env_disabled` | 服务在这个环境停用 | 服务详情 → 环境 → 打开该环境 |
| 3 | `task_disabled` | 任务停用，或子任务的父任务停用 | 任务详情 → 启用 |
| 4 | `env_not_allowed` | 任务的 `envs` 不含这个环境 | 换环境，或改任务的环境限定 |
| 5 | `trigger_not_allowed` | 任务没声明这种触发，例如没有 `api` 触发却被 API 调用 | 任务定义 → 触发 → 添加 |
| 6 | `triggers_paused`（409） | 自动触发（定时、事件、上游联动）时：服务在这个环境暂停了自动触发 | 服务详情 → 环境 → 关掉「暂停自动触发」 |

新提交（含定时、事件、联动）要过全部 6 道闸门（第 6 道只管自动触发）。续跑、重跑、纠正、回归重放只检查前 4 道。控制台手动运行不检查第 5 道。
运行被 worker 认领后会再检查一次前 4 道（排队期间开关可能变了），没过就以对应的原因码失败。

### 1.5 列表与分页

列表的过滤条件都是平铺的查询参数，空值表示不过滤。只有运行列表分页：

```json
{"items": [...], "total": 1234, "next_cursor": "next:2026-10-20T09:41:02+08:00|4b1e…", "prev_cursor": null}
```

游标不透明，把 `next_cursor` / `prev_cursor` 原样作为 `cursor` 传回即可。翻页基于
`(created_at, run_id)`，翻页过程中有新运行进来也不会重复或漏掉。

### 1.6 运行状态机

```
queued ──→ running ──→ success | failed | cancelled
```

终态是 `success`、`failed`、`cancelled`。只有 queued / running 的运行会被改成终态：已取消或已判成孤儿（`orphaned`）的运行，
执行端迟到的成功或失败不会覆盖它。

任务配了自动重试（§5.3 的 `retry`）时，临时性的失败（`error` / `orphaned` / `interrupted`）落 `failed` 的同时带 `retry_at`：
到点后同一个运行续跑（`attempt` +1，又回到 queued → running）。等着重试的期间不算最终失败：不发失败通知、不投递、
不触发「失败后」的联动、点名等它的运行接着等。对它调 `cancel` 取消的是这次重试（返回运行详情，不是 409），运行就此算失败。

排队中的运行按优先级被认领：对话 / 网页 / 纠正先于 API / 重跑 / 续跑，再先于定时 / 事件 / 联动 / 回归重放，同一档先到先得。
点名的上游还没成功、任务的同时执行上限满了的，留在 queued 不占名额（详情的 `queue` 说明在等什么）。

失败与取消的 `error_code`：

| error_code | 含义 |
|---|---|
| `timeout` | 超过任务的 `timeout_s`（模型排队的时间也算在里面） |
| `error` | 执行出错（模型、工具、处理器抛错） |
| `cancelled` | 被人取消 |
| `interrupted` | worker 退出（重启、停机）时运行还在执行，可以续跑 |
| `orphaned` | 执行进程没了（崩溃或被杀，心跳超过 120 秒没动静），可以续跑 |
| `invalid_output` | 任务声明了 `output_schema`，agent 到最后（提醒过一次）也没交回通过校验的结构化结果 |
| `step_limit` | 很少见：LangGraph 的步数兜底（主 agent 280 步）用完了还没结束；可以续跑。模型调用次数到上限（主 agent 80 次）时通常不会走到这里：工具停用、agent 收尾，运行照常成功，`output.step_limit` 为 `true`。子代理到上限同样收尾、把说明交回主 agent，不算失败 |
| `upstream_failed` | 它点名等的上游运行（`after`）最终失败或被取消，这次没有执行；不能续跑，上游成功后重跑 |
| 闸门链原因码 | 运行开始前重过开关（§1.4 的 1–4）没通过 |
| `unknown_task` | 排队期间任务被删除 |

`resolution` 记录运行是怎么结束的：

| resolution | 含义 |
|---|---|
| `agent` | 主角色执行（可能委派了子代理） |
| `builtin` | 内建处理器 |
| `rule` | 事件规则先行命中，没有调模型 |

## 2. 运行

### `POST /v1/runs` 发起一次运行

请求头 `Idempotency-Key` 可选：同一个键只受理一次，重复提交返回已有运行，回执里 `dedup: true`。
键最长 200 个字符（超了 `422 invalid_request`），不限时间；只有失败的运行会释放这个键（定时触发的除外），之后可以用同一个键重提。

```json
{
  "task": "failure-analysis",
  "subtask": "<资产>",
  "service": null,
  "env": "prod",
  "input": {"run_id": "8f2c…", "asset_key": "<资产>", "error": "…"},
  "session_id": null,
  "memory": {"recall": null, "save": false},
  "wait": 0,
  "after": []
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `task` | 否 | 任务名，也可以直接写子任务全名 `父任务:对象`。**不写 = 通用入口 `ask`**：任何服务任何环境直接提问或交代一件事，输入 `{question}`，要指定 `service` |
| `subtask` | 否 | 子任务的对象名。**不存在时按父任务自动创建**：继承全部定义，档案待补；闸门受理之后才建，被拒的请求不留子任务。回执的 `subtask_created` 会说明。任务声明了 `object_input`（如失败分析的 `asset_key`）时可以不写：按那个输入的值落到对应子任务（值含 `/`、`:`、空白时留在父任务）；写了 `subtask` 而没给那个输入，就把对象名填进去。内建任务没有子任务（`400 invalid_subtask`） |
| `service` | 通用任务必填 | 通用任务（`service: "*"`）要指定服务。专属任务省略即可；填了就必须与任务的服务一致 |
| `env` | 否 | 业务环境。缺省为平台默认环境（设置 → 环境），出厂默认是 `test`，所以生产必须显式写 |
| `input` | 否 | 任务输入，按任务的输入定义校验并补默认值。不合法返回 `invalid_input`，`detail.fields` 逐字段说明 |
| `session_id` | 否 | 续进已有会话，共享多轮上下文 |
| `memory` | 否 | 这一次的记忆开关 `{recall, save}`。`null` 表示依次跟随任务的设置、平台默认 |
| `wait` | 否 | 同步等待的秒数（0–300），运行在这段时间内结束就直接带结果返回 |
| `after` | 否 | 点名等的上游运行 id（最多 20 个）：先排着队，**都成功了才开始**；有一个最终失败或被取消，这次就落 `failed` / `upstream_failed`（没执行过，不能续跑，用重跑），点名等它的也跟着落。上游不存在 `404 unknown_run`；已经失败或取消（且没在等自动重试）`409 upstream_failed` |

角色由任务决定，调用方不传。

按依赖排一串（A、B 都成功后跑 C）：

```bash
H=(-H "Authorization: Bearer $KEY" -H 'Content-Type: application/json')
A=$(curl -sX POST $AGENT/v1/runs "${H[@]}" -d '{"task":"daily-inspection","env":"test"}' | jq -r .run_id)
B=$(curl -sX POST $AGENT/v1/runs "${H[@]}" -d '{"task":"frontend-smoke","env":"test"}' | jq -r .run_id)
curl -sX POST $AGENT/v1/runs "${H[@]}" -d "{\"task\":\"release-report\",\"env\":\"test\",\"after\":[\"$A\",\"$B\"],\"input\":{\"version\":\"e5f6a7b\"}}"
```

（`release-report` 是示例任务名。）每次都这么接的，在下游任务上声明上游联动（§5.3 的 `after` 触发），不用调用方自己串。

返回 `202`：

```json
{
  "run_id": "4b1e0c2a9f3d7e21", "session_id": "4b1e0c2a9f3d7e21",
  "status": "queued", "output": null,
  "dedup": false, "subtask_created": null
}
```

| 字段 | 说明 |
|---|---|
| `status` | 受理时是 `queued`；`wait>0` 时是等待结束那一刻的状态，已经结束就是终态 |
| `output` | 结束时的结果，形如 `{answer}`（任务声明了 `output_schema` 时另有 `data`，§5.3）或 `{error}`；还没结束时为 `null` |
| `dedup` | `true` 表示命中幂等键或任务去重窗口，返回的是已有运行 |
| `subtask_created` | 这次顺带新建的子任务全名 |

### `GET /v1/runs` 运行列表

| 参数 | 说明 |
|---|---|
| `status` | `queued` / `running` / `success` / `failed` / `cancelled` |
| `service` `env` | 服务、环境 |
| `task` | 任务名；写父任务名时**包含其子任务** |
| `trigger` | `api` / `chat` / `schedule` / `event` / `after` / `web` / `rerun` / `resume` / `correction` / `replay` |
| `caller` | 发起方：密钥名、控制台用户或 `schedule` |
| `session_id` | 某个会话的全部运行 |
| `q` | run id 前缀，或摘要里的关键词 |
| `hours` | 最近 N 小时 |
| `cursor` `limit` | 分页；`limit` 默认 30，最大 200 |

列表项：

```json
{
  "run_id": "…", "session_id": "…", "task": "failure-analysis:<资产>", "task_title": "Dagster 失败分析",
  "service": "vision-dagster", "env": "prod", "role": "ops_analyst",
  "status": "success", "resolution": "agent",
  "trigger": {"type": "event", "id": "on-failure", "source": "dagster", "caller": "dagster-sensor"},
  "summary": "<资产> · connection refused", "tokens": 18230, "duration_ms": 161200,
  "created_at": "…", "finished_at": "…",
  "error_code": null, "attempt": 1, "retry_at": null, "depends_on": []
}
```

`trigger.type` 为 `replay` 时，`trigger.id` 是被重放的原运行；为 `after`（上游联动）时，`trigger.id` 是联动触发器，`trigger.source` 是触发它的上游运行。
`attempt` 是第几次执行（续跑、自动重试 +1）；`retry_at` 不为空 = 失败了、等着在这个时刻自动重试；`depends_on` 是它点名等的上游运行。

### `GET /v1/runs/{id}` 运行详情

除列表字段外还有：

| 字段 | 说明 |
|---|---|
| `worker` | 认领它的 worker（主机:pid）；还没认领时为 `null` |
| `task_version` `role_version` | 任务、主角色的版本（`role_version` 是角色继承链最末一层的） |
| `recipe` | 配方：这次运行用到的每样定义各是第几版（见下）；还没开始执行（排队中，或认领后没过闸门）的运行为 `null` |
| `replay_of` | 回归重放出来的运行指向原运行；其他运行为 `null` |
| `input` | 输入 |
| `output` | 结果，`{answer}`、`{answer, data}`（结构化输出，§5.3）或 `{error}`；模型调用次数到上限、停用工具收尾的另带 `step_limit: true`（结论可能没查完） |
| `error_code` | 失败原因码 |
| `memory` | 这次实际生效的记忆开关 |
| `feedback` | 所有人对整次运行和各步的评价，见「反馈」一节 |
| `context.profile` | 注入的档案原文（服务档案 + 任务档案） |
| `context.recalled_knowledge` / `recalled_assets` | 召回了哪些记忆和方法；记忆每项 `{id, key, kind, rank}` |
| `context.saved_knowledge` / `saved_assets` | 沉淀了哪些记忆和方法；记忆每项 `{id, key, kind}`，不含交接摘要 |
| `context.session_runs` | 同一会话里的其他运行 |
| `context.todo` | agent 的待办清单：主 agent 最后一次 `todo` 工具调用的 `[{content, status}]`，`status` 是 `pending` / `in_progress` / `completed` / `cancelled`；没用过为 `null` |
| `progress` | 执行中才有：正在跑的 bash / py 的输出尾部，`{键: {tool, title, output, ms, at}}`（`output` 最多 2000 字，`ms` 已跑多久，`at` 写入时间），每 3 秒刷新；工具结束就删掉，运行结束为 `null`。要实时看就轮询本接口 |
| `lineage` | 前后关系：`triggered_by`（上游联动：触发它的上游运行 `{run_id, status, task, task_title, env, summary, retry_at}`，否则 `null`）、`depends_on`（它点名等的运行，同样形状）、`downstream`（它引出的运行：联动触发的 + 点名等它的，列表项形状） |
| `queue` | 排队中才有：在等什么。`waiting_for`（还没成功的点名上游 `[{run_id, status, task}]`）、`concurrency`（任务的同时执行上限 `{limit, running}`，没配为 `null`）、`hosts`（在线、负责它的主机 `[{host, running, max_concurrent}]`，空 = 没有主机负责，会一直排着）、`priority`（0 对话 / 1 接口 / 2 定时、事件、联动） |

`recipe`：

```json
{"task": {"name": "failure-analysis:<资产>", "version": 3, "parent": {"name": "failure-analysis", "version": 7}},
 "role": {"name": "ops_analyst", "lineage": [{"name": "ops_analyst", "version": 5}]},
 "subagents": [{"name": "data_searcher", "lineage": [{"name": "data_searcher", "version": 4}]}],
 "service": {"name": "vision-dagster", "version": 12}, "prompts": 2, "model": "kimi-k2.7-code", "platform": "9.0.0"}
```

| 字段 | 说明 |
|---|---|
| `task.parent` | 子任务才有：父任务及其版本 |
| `role.lineage` / `subagents[].lineage` | 继承链（根 → 自己）每一层的版本；`subagents` 只在 agent 形态、角色有子代理时有 |
| `service` | 服务及其版本；平台任务没有 |
| `prompts` | 平台提示词（设置 → 提示词）的版本；只在 agent 形态有 |
| `model` `platform` | 模型名、平台版本 |

### `GET /v1/runs/{id}/events?after=` 过程事件

事件按 `seq` 递增；带 `after` 时只取它之后的事件。一条事件：

```json
{"seq": 7, "kind": "tool_call", "at": "…", "payload": {"tool": "db_query", "args": {"query": "select …", "db": "ck"}}, "feedback": null}
```

| kind | 含义 |
|---|---|
| `stage` | 阶段：profile / recall / assets / rule / system（系统提示原文）/ output（提醒交回结构化结果）/ step_limit（模型调用次数到上限，停用工具收尾）/ resume / deliver |
| `model_call` | 一次模型调用（见下） |
| `tool_call` / `tool_result` | 工具调用及其返回：`{tool, args, call}` / `{tool, output, call}`；`call` 配对同一次调用（几个工具并行时按它对上，旧事件没有）；子代理里的带 `agent` |
| `final` | 结论 `{content}`，有结构化结果时另带 `data` |
| `error` | 出错 |

`model_call` 的 payload：

```json
{"agent": "data_searcher", "model": "kimi-k2.7-code", "ms": 58310, "queued_ms": 55120, "input_tokens": 5120,
 "output_tokens": 180, "tokens": 5300, "tool_calls": ["db_query"], "content": "先确认这张报表读的是哪张表…"}
```

- `agent` 只在子代理的调用里有。
- `ms` 是这次调用的总耗时，`queued_ms` 是其中在平台侧排队等账号并发名额（`model.max_concurrency`，prod、test 合计）的部分，不到 0.5 秒不带。
  同一运行里几个子代理同时调模型时 `queued_ms` 是近似值。
- `content` 是思考：Kimi 返回的 `reasoning_content`；没有时是调工具前说的话（不调工具的那次是最终回答，见 `final`）。
- 平台自己的辅助调用（记忆沉淀、交接摘要、回归判定）也各记一条，带 `purpose`（如 `"记忆沉淀"`），没有 `agent` / `tool_calls`；
  它们的 token 计入运行的 `tokens`。

过程事件按保留期清理（已结束的运行默认留 90 天，被 👎 过的不清，见部署指南 §3.2）；运行本身（输入、输出、配方）一直保留。

### `GET /v1/runs/{id}/stream?after=` 过程推流（SSE）

接口先补发已有事件，再实时推送新事件。每条 `data:` 是一个事件，形状同上。

运行一进入终态就推最后一条 `{"done": true, "status": "success"}`，然后关闭连接。没有新事件时，每 15 秒发一条注释行保活。

### 运行操作

| 端点 | 请求体 | 说明 |
|---|---|---|
| `POST /v1/runs/{id}/cancel` | — | 取消运行（排队中的也能取消），点名等它的排队运行跟着落 `upstream_failed`。失败后正等着自动重试的：取消这次重试，运行就此算失败（发失败通知、触发「失败后」的联动）。已结束返回 `409 already_finished` |
| `POST /v1/runs/{id}/rerun` | — | 用同样的输入**新开**一次运行（新会话），跳过去重，沿用任务、服务和环境 |
| `POST /v1/runs/{id}/resume` | — | 失败的 agent 运行**断点续跑**（含 `orphaned`、`interrupted`），沿用同一个 run id，`attempt` +1，上一次的 `error_code`、`finished_at`、`duration_ms` 清空，等着的自动重试改成现在就跑。上次没走到 agent（准备阶段就失败）的从头执行。非失败态、内建任务、规则命中、`upstream_failed`（从没执行过）的运行返回 `409 conflict`，请用重跑；会话里另有一轮在排队 / 执行时也是 `409 conflict` |
| `POST /v1/runs/{id}/correct` | `{text}` | 纠正：在同一会话里新开一轮（`trigger.type=correction`，`trigger.id` = 被纠正的运行），agent 带着原结论和纠正重新回答。成功后取代被纠正那一轮沉淀的记忆。运行还没结束、或会话里还有一轮在排队 / 执行时返回 `409 conflict` |

`rerun`、`resume`、`correct` 返回的回执与 `POST /v1/runs` 相同。`cancel` 返回运行详情。

### 反馈（评价）

对整次运行或其中某一步打分，并说明哪里有问题。**一个人对同一次运行的同一步只有一条反馈**：
再提交就是覆盖，`DELETE` 是撤回。所以重复点 👎 不会把权重扣两次。

| 端点 | 说明 |
|---|---|
| `PUT /v1/runs/{id}/feedback` | 评价整次运行 |
| `DELETE /v1/runs/{id}/feedback` | 撤回 |
| `PUT /v1/runs/{id}/events/{seq}/feedback` | 评价时间线上的某一步 |
| `DELETE /v1/runs/{id}/events/{seq}/feedback` | 撤回 |
| `GET /v1/feedback?score=-1&service=&env=&task=&reason=&hours=&limit=` | 反馈收件箱：新的在前，带运行的任务、服务、环境、摘要 |

请求体：

```json
{"score": -1, "reasons": ["wrong_data"], "comment": "问的是国内生产，查的却是测试库的 ck"}
```

| 字段 | 说明 |
|---|---|
| `score` | `1` 有用 / `-1` 有问题 |
| `reasons` | 问题类型，可多选；取值与中文名见 `GET /v1/meta` 的 `feedback_reasons` |
| `comment` | 说明，最长 2000 字 |

问题类型：

| 值 | 含义 |
|---|---|
| `wrong_conclusion` | 结论不对 |
| `wrong_definition` | 口径 / 业务理解不对 |
| `wrong_data` | 取数或查询有误 |
| `incomplete` | 没答全 |
| `off_topic` | 答非所问 |
| `wrong_tool` | 工具或命令用错 |
| `detour` | 绕远路 / 太慢 |
| `unsafe` | 操作有风险 |
| `other` | 其他 |

返回保存后的反馈：`{id, run_id, step_seq, score, reasons, comment, created_by, created_at, updated_at}`。
`step_seq` 为 `0` 表示整次运行。

反馈产生的效果：

- **整次运行的 👎 只罚不奖**：这次运行沉淀的记忆和召回的记忆各扣 1 分（排序时最多算到 -5），沉淀的方法也扣 1 分；
  👍 只留档、不改权重（没人点 👍，正分没有信号）。改主意、撤回按差值回补。
- **单步评价**只留档，供排查问题和改进角色提示词时回看。
- **新的 👎**（不是修改已有的 👎）会按通知规则推送，对应事件 `feedback_negative`（设置 → 通知）。
- **想让 agent 按意见重答**，用 `correct`。控制台的 👎 面板里可以勾选「按这条意见让 agent 重答」，提交时一并发起纠正。
- **改完提示词或定义后验证**，用回归重放（下一节）：👎 的问题类型、说明和被点的那一步就是判定标准。

运行详情的 `feedback` 字段是所有人对整次和各步的全部评价；对话详情每一轮的 `feedback` 是当前用户自己的评价。

### 回归重放

改完角色提示词、任务定义、档案、平台提示词或记忆后，拿过去的 agent 运行用现在的一切重跑，由模型判定：
被 👎 的看问题改好没有，没被 👎 的把原答案当参照，看有没有退步。原理见设计文档 §5.1。

| 端点 | 说明 |
|---|---|
| `GET /v1/replays?limit=50` | 重放列表，新的在前 |
| `POST /v1/replays` | 发起一次重放，返回 `201` 和详情 |
| `GET /v1/replays/{id}` | 详情：逐条对照与判定 |
| `POST /v1/replays/{id}/judge` | 把还没判定或判定为 `unclear` 的条目重判一遍，返回详情 |

请求体（字段都可选）：

```json
{"task": "data-qa", "service": "vision-board", "env": "test", "hours": 168, "limit": 20,
 "title": "", "note": "data_searcher 提示词加了口径确认"}
```

| 字段 | 说明 |
|---|---|
| `run_ids` | 直接点名要重放的运行，可以是任何结束了的 agent 运行；给了就不按条件选 |
| `task` `service` `env` | 选样条件；`task` 写父任务名时包含其子任务 |
| `negative_only` | 默认 `true`：选被 👎 的；`false`：选最近结束（`success` / `failed`）的 agent 运行，看改动有没有带来退步 |
| `hours` | 只看最近多少小时内的（≥ 1）：被 👎 的按评价时间，`negative_only=false` 时按运行创建时间 |
| `limit` | 最多几条，默认 20，最大 100 |
| `title` | 标题；不填按条件生成 |
| `note` | 这次改了什么，方便回看 |

不给 `run_ids` 时按条件选：默认是被 👎（整次或某一步）的 agent 运行，最近被评的在前；`negative_only=false` 时是最近结束的 agent 运行，
新的在前。重放出来的运行都不算；一条都没有返回 `400 nothing_to_replay`。点名的运行里有重放出来的、还在跑的、规则命中的或内建任务的，
那一条记 `verdict: error`，`reason` 是原因，其余照常重放。

每条原运行用同样的输入开一个重放运行：`trigger.type` 为 `replay`、`trigger.id` 是原运行；新会话、不投递，只过闸门前 4 道。

- 召回用现在的记忆，但不含原运行自己沉淀的（事实、教训、`source_run` 是原运行的方法、原会话自己的交接摘要）；
  前序交接摘要按原运行的会话找，和原运行当时看到的一致。
- 只读：不沉淀记忆、不记召回命中、不加方法的使用次数、不标过期；`save_asset`、`notify` 返回「[回归重放] …」，不执行。
- 服务 MCP 的工具不拦：比如 dagster 的 `launch_job` / `reexecute_run` 在重放里照样会在线上执行。

重放运行结束后，模型对照「原答案 + 人指出的问题（没被 👎 的为「无」）+ 新答案」给出判定。

列表项：

```json
{"id": 3, "title": "data-qa · vision-board · test · 5 条 👎", "filter": {"task": "data-qa", "service": "vision-board", "env": "test", "hours": 168, "limit": 20},
 "note": "…", "created_by": "…", "created_at": "…", "regression": false,
 "counts": {"total": 5, "fixed": 3, "same": 1, "worse": 0, "unclear": 0, "pending": 1}}
```

`counts.unclear` 含 `error`；`pending` 是还没判的。`regression` 为 `true` 表示这批里有原运行没被 👎 的条目（判定按「有没有退步」读，见下）。

详情在列表项之外多一个 `items`，每条：

```json
{"id": 11, "source_run": "…", "new_run": "…", "verdict": "fixed", "reason": "…", "judged_at": "…", "negative": true,
 "task": "data-qa", "service": "vision-board", "env": "test", "summary": "…",
 "before": {"task_version": 3, "role_version": 5, "answer": "…", "status": "success", "recipe": {…}},
 "after":  {"task_version": 4, "role_version": 6, "answer": "…", "status": "success", "recipe": {…}}}
```

`recipe` 是两边运行的配方（形状同运行详情），用来对照这次改了哪一版。`negative` 是原运行有没有被 👎 过，决定判定怎么读：

| verdict | `negative: true` | `negative: false`（原答案当参照） |
|---|---|---|
| `fixed` | 已改好：被指出的问题解决了，且没引入明显的新错 | 更好 |
| `same` | 没改好：问题还在 | 持平 |
| `worse` | 更差：更糟，或引入了明显的新错 | 退步 |
| `unclear` | 判断不了，或判定调用失败；可以重判 | 同左 |
| `error` | 重放运行没建成（被闸门拒，或这条不能重放）：`new_run` 为空，`reason` 是原因 | 同左 |
| `null` | 还没判（重放运行还没结束） | 同左 |

重放运行没有成功结束时不调模型：原运行成功的记 `worse`，否则记 `same`。

## 3. 对话

### `POST /v1/chat`

```json
{
  "message": "报表页面的数据来自 ck 库的哪几张表",
  "session_id": null,
  "service": "vision-board", "env": "test",
  "task": null, "subtask": null,
  "input": {},
  "memory": {"recall": true, "save": null},
  "stream": true
}
```

| 字段 | 说明 |
|---|---|
| `message` | 这一轮的问题，作为任务输入里的 `question` |
| `session_id` | 续会话；续会话时没写的 `task`、`subtask`、`service`、`env` 沿用上一轮，`input` 里除 `question` 以外的字段也沿用（这一轮写了的以这一轮为准）。会话里还有一轮在排队 / 执行时返回 `409 conflict`（流式时是一条 `error`） |
| `service` `env` | 问哪个服务、哪个环境 |
| `task` | 对话任务（声明了 `chat` 触发）；缺省时服务专属的对话任务优先，没有就用通用入口 `ask` |
| `subtask` | 针对某个对象问：会带上这个对象的档案，沉淀的记忆也归到它名下 |
| `input` | 对话任务的其他输入字段 |
| `memory` | 这一轮的记忆开关 |
| `stream` | `true`（默认）走 SSE；`false` 等运行结束后返回 `{run_id, session_id, status, answer, error}` |

SSE 的每条 `data:` 是一个 JSON，用 `type` 区分：

| type | 字段 | 说明 |
|---|---|---|
| `run` | `run_id` `session_id` `subtask_created` | 已受理 |
| `stage` `model_call` `tool_call` `tool_result` | `seq` 加平铺的事件 payload | 执行过程 |
| `final` | `status` `output` | 运行结束 |
| `error` | `code` `message` | 受理失败（例如被闸门链拒绝；意外出错时 `code` 是 `internal`），随后流结束。也可能出现在 `run` 之后：`code` 为 `stream_broken`，推流断了，运行照常在跑，到运行详情看结果 |

### 会话

| 端点 | 说明 |
|---|---|
| `GET /v1/sessions?service=&env=&task=&q=` | 会话列表，每项 `{session_id, title, service, env, task, runs, last_at}`。只列至少有一轮是对话发起的会话（只纠正过的 API / 定时运行不算），`runs` 数的是对话和纠正的轮数 |
| `GET /v1/sessions/{id}` | 会话详情，多一个 `turns`：每轮 `{run_id, question, answer, status, events, feedback, created_at}` |

## 4. 事件

### `POST /v1/events/{source}`

外部系统回调的统一入口。请求体就是来源系统的回调原文。

平台的处理步骤：

1. 把回调翻译成「事件名 + 扁平字段」。
2. 找出声明了对应 `source + event` 触发器的任务。
3. 每个匹配的任务发起一次运行。

| source | 事件 | 字段 | 接法 |
|---|---|---|---|
| `dagster` | `run_failure`（请求体没写 `event` 时的默认） | `run_id` `asset_key` `error` `env` `subtask` `job` | `run_failure_sensor` 回调本地址 |
| `dagster` | `run_success` | `run_id` `asset_key` `asset_keys`（列表拼成逗号分隔的一串）`env` `subtask` `job` `partition` | `run_status_sensor`（SUCCESS）回调，请求体带 `"event": "run_success"` |
| `dagster` | `asset_check_failed` | `asset_key` `check` `severity` `description` `run_id` `env` `subtask` | asset check 失败（如新鲜度检查）的传感器回调，带 `"event": "asset_check_failed"` |
| `gitlab` | `deployment`（只认部署成功） | `project` `ref` `env` `sha` `url` `user` | 项目 Webhook 勾选 Deployment events，密钥填在 Secret token |
| `webhook` | 任意，事件名取请求头 `X-Event` 或请求体 `event` | 请求体原样 | 通用 |

事件数据里有三个字段有特殊含义：

- `env`：业务环境。
- `subtask`：指定子任务对象。
- `service`：给通用任务指定服务。任务的触发器上写了 `service` 时，以触发器为准。

每个匹配的触发器依次经过下面几步：

1. `filter`（字段 → 正则）全部满足才触发。
2. `map` 把事件字段映射成任务输入；没写 `map` 就整份透传。
3. `rules` 规则先行：报错命中规则时直接给结论、不调模型，但同样留一条 `resolution=rule` 的运行记录。
4. `session` 模板决定续进哪个会话。

Dagster 的事件名也可以放请求头 `X-Event`。每次判定（触发了、命中去重、过滤不满足、被拒、没有任务接）都记一条触发记录（§9 `GET /v1/ticks`）。

返回每个匹配的处理结果。某个匹配被拒绝（闸门链），不影响其他匹配：

```json
{
  "source": "dagster", "events": ["run_failure"],
  "matched": [
    {"task": "failure-analysis:<资产>", "trigger": "on-failure", "rule": "infra",
     "run_id": "…", "status": "queued", "dedup": false, "error": null},
    {"task": "lineage-check", "trigger": "dagster", "rule": null,
     "run_id": null, "status": "rejected", "error": {"code": "service_env_disabled", "message": "…"}}
  ]
}
```

## 5. 定义：服务 / 角色 / 任务

三种定义共用一套读写接口，`{kind}` 取 `services`、`roles`、`tasks` 之一。
定义写库即生效，每次修改留一个版本。

| 端点 | 说明 |
|---|---|
| `GET /v1/{kind}` | 列表。服务与任务附带统计（见下）。`GET /v1/tasks?service=` 只看某个服务的任务，含通用任务 |
| `POST /v1/{kind}` | 新建，请求体含 `name`，返回 `201` |
| `GET /v1/{kind}/{name}` | 单个 |
| `PATCH /v1/{kind}/{name}` | 局部更新：**请求里出现的顶层字段整体替换**，没出现的不动；合并在库里的最新版本上 |
| `DELETE /v1/{kind}/{name}` | 删除。仍被引用时返回 `409 in_use`（例如角色正被任务使用、被别的角色继承或列为子代理）。删父任务会连带删除子任务，返回 `{deleted: [...]}` |
| `GET /v1/{kind}/{name}/versions` | 版本历史，新的在前：`{version, updated_by, created_at, deleted, definition}` |
| `POST /v1/{kind}/{name}/versions/{v}/restore` | 恢复到某个版本。恢复本身产生一个新版本，已删除的定义也能恢复 |
| `GET /v1/roles/{name}/resolved` | 角色沿 `extends` 合并后的生效结果 `{name, title, description, prompt, tools, subagents, service_tools, lineage}`，`lineage` 是继承链 |
| `GET /v1/{roles,tasks}/{name}/version-stats` | 每个版本跑出来的效果（见下）；角色按任务主角色的版本算 |

所有定义都带台账字段 `version`、`updated_by`、`updated_at`。

`version-stats`（平台提示词的同款见 §8.1）返回数组，新版本在前，回归重放的运行不算：

```json
[{"version": 6, "runs": 42, "success": 39, "failed": 3, "negative": 2, "avg_tokens": 18230, "avg_ms": 41200,
  "first_at": "…", "last_at": "…"}]
```

`negative` 是被 👎 过（整次或某一步）的运行数。

### 5.1 服务

示例取自种子 `conf/seeds/services/vision-dagster.yaml`，其中的路径、容器名都是【占位】，以实际部署为准（部署指南 §3.7）。

```yaml

title: Vision Dagster
description: Vision 的数据编排（Dagster）：资产、调度、传感器；docker 部署，国内生产 / 测试各一套

code_paths: []                         # 读代码、核对记忆新鲜度；缺省 = [root]
python: ~/miniconda3/envs/vision-dagster/bin/python   # 项目解释器（项目内核用）；空 = python3
env_vars: {}                           # 项目内核带上的环境变量，可写 {env}、{python}；不支持 ${VAR}

databases:                             # 只读库 {库名: 连接串}，scheme 决定类型（见下）；口令写 ${VAR}
  ck: "clickhouse://${CK_RO_USER}:${CK_TEST_RO_PASSWORD}@172.24.17.66:8123/default"
configs:                               # 项目读的配置路径。生产：真实内容 agent 看不到，项目内核里盖上给 agent 的只读版（§6）；测试：用真实的
  - ~/deploy/vision-dagster/.env
  - ~/deploy/vision-dagster/dagster.yaml
hidden:                                # 其他含口令的文件或目录：生产只遮蔽、不替换；测试不遮
  - ~/deploy/vision-dagster/docker-compose.yaml
logs:                                  # {名字: 文件路径（可带通配）| docker:<容器名> | journal:<systemd 单元>}，logs 工具只能读这些
  webserver: "docker:vision-dagster-webserver"
  daemon: "docker:vision-dagster-daemon"
  code: "docker:vision-dagster-code"
mcp:                                   # 服务自己的 MCP server：{名字: langchain-mcp-adapters 连接配置}
  dagster:
    transport: stdio
    command: "{platform_python}"
    args: ["{platform}/mcp_servers/dagster_mcp.py"]
    env: {DAGSTER_URL: "{url:deployed}", DAGSTER_LAUNCH_JOBS: ".*"}   # 证书校验不过时加 DAGSTER_VERIFY：CA 文件路径，或 false
    envs: {prod: {}, test: {}}         # 按环境深合并的覆盖；写了就只在列出的环境可用
envs:                                  # 按环境覆盖，只写差异
  prod:
    urls: {deployed: "https://vision-dagster-prod.ipa.zs:9902"}   # urls 按键覆盖服务的 urls
    databases:                         # 按库名覆盖；值写空串 = 这个环境没有该库
      ck: "clickhouse://${CK_RO_USER}:${CK_PROD_RO_PASSWORD}@172.168.0.125:8123/default"
  test:
    urls: {deployed: "https://vision-dagster-test.ipa.zs:9901"}   # 还可以写 root / python / code_paths / logs / profile / enabled
profile:                               # 服务档案：逐字置顶注入该服务的所有运行
  no_go: 不在宿主上起 dagster-daemon / webserver；要在线上重跑作业用 dagster 的 MCP 工具
enabled: true
```

- `envs.<环境>` 能写的键：`enabled`、`root`、`databases`、`code_paths`、`python`、`urls`、`logs`、`profile`。
  `configs`、`hidden`、`env_vars`、`mcp` 不按环境覆盖（`configs`、`hidden` 里写 `{env}`，`mcp` 用自己的 `envs`）。
- 定义里不写部署在哪台主机：哪台执行由各台部署配置的 `env`、`services` 决定（部署指南 §2.1）。
  旧定义里的 `node` 字段（顶层和各环境里的）读取时忽略，保存时去掉。
- `python`（或 `envs[env].python`）渲染 `{env}` 后就是该环境的解释器，项目内核（`py` 工具）用它，工作目录是 `root`。
- `configs`：项目读配置的路径列表（绝对路径，可以 `~` 开头、写 `{env}`）。受保护的环境（生产）里每个路径给 agent 的只读版用 §6 的接口读写；
  不受保护的环境（测试）直接用项目的真实配置，不用填。旧写法 `[{canonical, template, …}]` 仍能读，取 `canonical`。
- `hidden`：其他含口令的路径，只遮蔽、不替换。遮蔽按环境：生产的运行里所有服务所有环境的 `configs` 和 `hidden` 在沙箱里都被遮蔽；
  测试的运行里只遮受保护环境的，和本环境路径相同的不遮（没写 `{env}` 的路径在测试机上就是测试那份）。
- `logs`：名字是小写字母开头的 `[a-z0-9_-]`，最长 31 个字符；值是绝对路径（可以 `~` 开头，可带 `*` `?` `[` 通配，读匹配到的最新那个文件，
  适合按日期滚动的日志，如 `~/deploy/x/logs/app-*.log`）、`docker:<容器名>` 或 `journal:<systemd 单元>`，否则 `422 invalid_definition`。
  `envs[env].logs` 按名字覆盖，值写空串表示这个环境没有该日志。
- `databases`：`{库名: 连接串}`，库名是小写字母开头的 `[a-z0-9_-]`，最长 31 个字符。scheme 决定类型：
  `postgresql://` / `postgres://`（PostgreSQL）、`mysql://` / `mariadb://`（MySQL / MariaDB）、`doris://`（Doris，MySQL 协议，默认端口 9030）、
  `clickhouse://` / `clickhouses://`（ClickHouse HTTP 接口，默认 8123 / HTTPS 8443）、`mongodb://` / `mongodb+srv://`（MongoDB）；
  不认识的 scheme 返回 `422 invalid_definition`。`envs[env].databases` 按库名覆盖，值写空串表示这个环境没有该库。
  agent 用 `db_query` 查（§5.2）；账户要用只读的，平台侧的只读检查只是第一道。
- `env_vars` 不支持 `${VAR}`：它会出现在项目内核进程的环境里，口令写进给 agent 的配置。
- `urls`：`envs[env].urls` 按键覆盖。渲染后出现在 agent 的运行环境提示里，浏览器之类的工具按它打开页面，`mcp` 里用 `{url:名字}` 引用。
- 种子 dagster MCP 的 8 个工具与重跑约束（`DAGSTER_LAUNCH_JOBS` 作业白名单、同一作业同一分区在跑时拒绝、`launch_job` 打标签
  `agent/launched_by=agent-platform`）见部署指南 §3.10。

`mcp` 的规则：

| 项 | 规则 |
|---|---|
| 连接配置 | 原样交给 langchain-mcp-adapters（`transport`、`command`、`args`、`env`、`url` 等） |
| `envs` | `{环境: 覆盖}`，深合并到基础配置上。**写了 `envs` 就只在列出的环境可用**，没配的环境不会悄悄连到别处；不写就每个启用的环境都用基础配置 |
| 占位 | `{env}`；`{url:名字}`（该环境的 urls）；`${VAR}`（连接时才从 secrets.env 取值）；`{platform}`（平台安装目录）；`{platform_python}`（平台解释器） |
| 生效 | 运行在这个服务上时工具自动出现，调用按运行的环境路由；角色 `service_tools: false` 时不带；和角色 `tools` 里的工具重名时以角色的为准 |
| 连接 | 懒加载：第一次有运行用到，或调 `GET /v1/services/{s}/tools` 时才连；按定义内容缓存，改了定义下次自动重连；有连接失败时 5 分钟后重试，一个连接失败不影响别的 |
| 调用 | 走常驻会话：同一个会话对同一条连接的调用共用一条 MCP 会话（有状态的 server 状态不丢），空闲 30 分钟回收，断了下次调用自动重连；平台 MCP 同样如此 |
| 出错 | 工具调用出错如实返回给模型（`[调用失败] …`），不炸运行；没配本环境连接的返回 `[不可用] …` |

列表和单个接口额外返回：

- `task_count`：该服务专属的任务数（不含子任务）；`generic_task_count`：通用任务（`service: "*"`）数，每个服务都能用。
- `health[env]`：每个环境的健康汇总，`{enabled, env_enabled, python, runs_24h, failed_24h, last_run}`。
  `enabled` 是实际接不接收运行（服务整体启用且该环境启用），`env_enabled` 只看该环境自己的开关。

**只读库口令**（`databases` 的每一项，含各环境覆盖）：

- 建议写成 `${VAR}`，真实值放 secrets.env，连库时才取值。库里、接口里、版本历史里都只有占位。
- 直接写了明文口令的，读回时（列表、单个、版本历史）这一项的口令显示为 `***`。
- 保存时把 `***` 原样传回表示不改（按库名对上原值）；连接串的其余部分改了而口令还是 `***`，返回 `422 invalid_definition`。

### 5.2 角色

```yaml
name: qa_engineer
title: 冒烟测试
description: 部署后按沉淀的方法跑冒烟脚本和页面检查   # 也是委派时给主角色看的「擅长什么」
prompt: …                              # 系统提示（有 extends 时可空）
tools: [py, bash, service_info, logs, host_status, save_asset, "mcp:browser"]
subagents: [ops_analyst]               # 运行中可委派的角色；null = 跟随父角色
service_tools: true                    # 自动带上运行所在服务的 MCP 工具；null = 跟随父角色（没有父角色就是 true）
extends: null                          # 继承父角色
prompt_append: ""                      # 有 extends 时追加在父角色提示词之后
```

| 字段 | 规则 |
|---|---|
| `tools` | 内置工具名或平台 MCP 工具名。`"*"` = 全部内置工具 + 全部平台 MCP 工具；`"mcp:<server>"` = 某个平台 MCP server 的全部工具（如 `mcp:browser`）。写成 `sql_query` 的按 `db_query` 处理；没登记的名字忽略并记 warning |
| `subagents` | 主角色运行中按需把子问题委派给这些角色（`task` 工具）：子代理用自己的提示词和工具、独立上下文，最后一条回复交回主角色。只委派一层，子代理自己的 `subagents` 不生效。列出的角色必须存在，不能列自己，否则 `422 invalid_definition` |
| `service_tools` | 运行所在服务声明的 MCP 工具（§5.1 的 `mcp`）是否自动带上；`null` = 跟随父角色，没有父角色时等于 `true` |
| `extends` | 子角色写了 `tools`（非空）/ `subagents`（非 `null`）/ `service_tools`（非 `null`）就**整体替换**父角色的，没写就跟随；`subagents: []` 表示明确不要子代理。提示词在父角色之后追加 `prompt_append` |

一个任务只有一个主角色；需要多种能力时用子代理，而不是多角色流水线。

内置工具：`py`（项目内核）`bash` `read` `grep` `todo` `service_info` `logs` `host_status` `db_query` `save_asset` `notify`，
加上部署配置里的平台 MCP 工具。读代码用 `read` / `grep`，写文件、跑命令用 `bash`；`py` 里角色的其他工具（和服务 MCP 工具）是同名函数，批量 / 循环调工具写一段 `py` 即可。
`read`、`grep` 跟着 `bash` 自动带上，`todo` 所有角色都有，角色里不用写（写了也行）；`read_file` 按 `read` 处理。
`py` 和 `bash` 在 `GET /v1/meta` 的 `tools` 里标为 `dangerous: true`（模型写的代码，跑在沙箱里）。

- `bash(command, timeout=60)`：沙箱里跑一条命令；给模型的输出最多 12000 字（开头 + 结尾），全文在工作目录 `outputs/` 下、返回里带路径。
  `py` 的输出超过 20000 字同样处理。
- `read(path, offset=1, limit=2000)`：带行号读文件（一次最多 2000 行、50KB）或列目录；相对路径相对本服务代码目录；
  能读什么和 bash 沙箱一样，看不到的返回 `[看不到]`。
- `grep(pattern, path="", glob="", ignore_case=false)`：在 bash 沙箱里按正则搜（有 `rg` 用 ripgrep，否则 `grep -rnIE`），
  返回 `文件:行号:内容`，最多 300 条。
- `todo(items)`：整份替换待办清单 `[{content, status}]`，运行详情的 `context.todo` 就是主 agent 最后一次的。
- `service_info(what="overview", path="")`：`overview` 是服务×环境总览，含代码目录当前的 git 提交、每个配置的状态
  （生产：给 agent 的只读版填没填、第几版；测试：项目的真实配置在本机在不在）；`config` 读本环境的一份配置（`path` 填配置路径，密钥打码；
  生产读给 agent 的只读版，测试读本机上的真实文件）；`git` 是代码目录最近 10 次提交。
- `logs(name="", lines=200, grep="", since="")`：读本服务本环境声明过的日志（服务定义 `logs`）。`name` 不填列出有哪些；
  文件（带通配的读最新那个）取最后 `lines` 行，`docker:<容器>` 用 `docker logs --tail <lines> --timestamps`，`journal:<单元>` 用 journalctl
  （先查系统日志，平台用户要在 systemd-journal 组里；没有再查用户日志）；`lines` 最多 2000，给模型的最多 12000 字，超了全文在 `outputs/` 下。
  `grep` 是不分大小写的正则：文件在整个文件里流式搜（超过 512MB 只搜末尾 512MB），docker / journal 在最后 5 万行里搜，返回最后 `lines` 条匹配和匹配总数。
  `since`（如 `30m`、`2h`、`"2026-10-21 08:00:00"`）对 docker、journal 有效，文件忽略。读不了时返回 `[没有权限]` / `[不存在]` / `[读取失败]`。
- `host_status()`：部署主机（执行运行的那台）的负载、内存与 swap、`/` 和代码目录所在磁盘、占内存最多的 10 个进程；本服务的进程
  （命令行里带代码目录的）、监听端口（`ss -ltnp`）、本用户的 crontab（去掉注释行）、本服务容器（`logs` 里 `docker:` 的）的 CPU / 内存
  （`docker stats --no-stream`）；`docker ps -a`、`systemctl is-active nginx`（没在跑也显示状态）。

`db_query(query, db="")` 查本服务本环境 `databases` 里的库（`db` 是库名，只登记了一个时可省略）：

- `query` 是一条 SQL（用该库自己的方言），或 MongoDB 的 JSON：`{"collection", "filter", "projection", "sort", "limit", "skip"}`、
  `{"collection", "pipeline"}`（不能有 `$out` / `$merge`）、`{"collection", "count"}`、`{"collection", "distinct", "filter"}`、
  `{"collections": true}`，都可另带 `"database"`。
- 只读：单条语句、开头关键字白名单，除 PostgreSQL 外再查写操作关键字；PostgreSQL 用只读事务，MySQL / MariaDB 用只读会话，
  ClickHouse 带 `readonly=2`（账号本身是 `readonly=1`、报「Cannot modify … readonly」时不带设置重试；查询里写了 `SETTINGS` 的不重试），
  MongoDB 只允许上面几种读法。真正兜底的是只读账号。
- 每条限时 30 秒（各库的执行超时 + 客户端读超时）。
- 结果 20 行以内直接返回；更多时整份写进本会话工作目录下 `queries/<run_id>/` 的文件（SQL 是 CSV，MongoDB 是 JSONL），
  只返回行数、列、前 20 行和路径，agent 再用 read / grep 或 py（pandas）按需读。最多 10 万行、50MB。

平台另会按需添两个工具，不用写：
`task`（角色有子代理时，参数 `subagent`、`description`）和 `submit_result`（任务声明了 `output_schema` 时，§5.3）。实际可用的目录见 `GET /v1/meta` 返回的 `tools`（MCP 工具带 `server`）。
服务 MCP 的工具不在这个目录里，见 `GET /v1/services/{s}/tools`。

### 5.3 任务

```yaml
name: failure-analysis
title: Dagster 失败分析
service: vision-dagster     # 专属服务 / "*" 通用（调用时指定）/ null 平台任务
role: ops_analyst
form: agent                 # agent | builtin
input:                      # 都不必填：Dagster 回调总会带齐，手动跑时给一个就行
  run_id:    {type: str}
  asset_key: {type: str, description: 失败的资产}
  error:     {type: text}
object_input: asset_key     # 对象字段：它的值就是子任务的对象名（见下表）
envs: [prod, test]          # 能跑的环境；空 = 全部
triggers:
  - {id: api, type: api}
  - {id: chat, type: chat}
  - {id: daily, type: schedule, cron: "0 9 * * *", envs: [prod, test], input: {}, timezone: Asia/Shanghai, service: null}
  - id: on-failure
    type: event
    source: dagster
    event: run_failure
    filter: {env: "^(prod|test)$"}   # 字段 → 正则，可选
    map: {run_id: run_id, asset_key: asset_key, error: error}
    rules: [{pattern: "connection.*(refused|timeout|reset)", category: infra, conclusion: 数据库/服务连接失败，检查目标服务存活与网络}]
    session: "dagster:{asset_key}:{error_class}:{date}"
    service: null
  - id: after-smoke          # 上游联动：上游任务结束后在同一个环境跑（见下表）
    type: after
    tasks: [frontend-smoke]
    mode: any                # any 任一上游结束 / all 全部上游都结束
    on: [success]            # success / failed，可都写
    filter: {}               # 上游字段 → 正则
    map: {}                  # 本任务输入 ← 上游字段；不写 = 上游输入里同名的字段带过来
    window_s: 86400          # all 模式的等待窗口
    service: null
deliver: {channel: default}  # 或 {url: "https://…"}；null = 调用方自取
dedup: {key: run_id, window_s: 600}
memory: {recall: null, save: null}   # null = 跟随平台默认
timeout_s: 900
retry: {max: 2, delay_s: 120}  # 可选：临时性失败自动续跑；null = 不重试
concurrency: 4               # 可选：每个环境最多同时执行几个；null = 不单独限制
output_schema: null          # 可选：结构化输出的 JSON Schema，顶层须是 object（见下表）
profile:                     # 任务档案
  pitfalls: 资产失败先看上游资产是否完成，多数失败是上游延迟级联
enabled: true
```

| 字段 | 规则 |
|---|---|
| `input.*.type` | `str` `text` `int` `bool` `json` `enum`；`enum` 需配 `options`。字段名：字母、数字、下划线，不以数字开头 |
| `object_input` | 可选，agent 形态。须是 `input` 里的字段。提交时只给了这个字段就落到同名子任务（没有就建），只点了 `subtask` 就把对象名填进这个字段（§3 `POST /v1/runs`） |
| `schedule` 触发 | 每个环境各触发一次；通用任务必须写 `service`。同一触发器同一环境上一次没跑完就跳过，停机期间错过的不补 |
| `event` 触发 | 通用任务没写 `service` 时，取事件数据里的 `service` 字段 |
| `session` 模板 | 可以引用事件的任意字段，另有 `{error_class}`（命中规则的类别，否则为 unknown）和 `{date}` |
| `after` 触发 | 上游（`tasks`，父任务 = 它和它的子任务，也可以写子任务全名）的一次运行**最终**落到 `on` 里的状态时，在同一个环境跑这个任务（失败后还要自动重试的，等重试完再算；回归重放、被取消的不触发）。`mode: all` 要每个上游都在 `window_s`（60 秒 ~ 7 天）内、且在这个联动上一次触发之后结束过，由最后结束的那个触发。`filter` / `map` 引用上游字段：`run_id` `task` `env` `service` `status` `caller` `error` `error_code` `output.answer` `input.<字段>` `output.data.<路径>`；all 模式可写 `<上游任务名>.<字段>` 取某一个上游的，any 模式不能带前缀。下游运行 `trigger = {type: after, id, source: 上游运行, caller: 上游的调用身份}`，幂等键 `after:<上游运行>:<状态>:<下游>:<触发器>`。上游要存在、不能是自己、整张联动图不能成环；联动超过 5 层不再往下。被联动引用的任务不能删（`409 in_use`） |
| `retry` | 只对 agent 任务（内建任务写了返回 `422`）。`max` 1–5、`delay_s` 10–3600。只重试 `error` / `orphaned` / `interrupted`，走续跑（同一个运行，`attempt` +1）；回归重放的运行不重试 |
| `concurrency` | 1–50。同一个环境里这个任务（连同子任务）同时执行的上限，多出来的排队（详情的 `queue.concurrency`） |
| `deliver` | `channel`（设置 → 通知里的渠道名）与 `url` 二选一。投递失败重试 3 次，仍失败只记事件，不改运行状态 |
| `dedup.key` | 输入字段名，用 `a+b` 拼接多个字段；时间窗内同键、排队 / 运行中 / 成功的运行直接返回它（`dedup: true`），失败和取消的不算 |
| `timeout_s` | 1–7200 秒 |
| `handler` | `form: builtin` 的处理器名，可选值见 `GET /v1/meta` 的 `builtin_handlers`（现在只有 `memory-gardener`） |
| `output_schema` | 结构化输出（agent 形态）。JSON Schema（Draft 2020-12），顶层须是 `{"type": "object", "properties": …}`，不合法返回 `422 invalid_definition`。声明了 agent 就多一个 `submit_result` 工具（参数即此 schema），调用时当场校验、不合格把错误还给它改；最后一次通过校验的提交放进 `output.data`，`output.answer` 仍是文字结论；`deliver.url` 回调的请求体 `{run_id, task, service, env, status, output}` 里照常带上（通知渠道只发文字结论）。到最后（提醒过一次）还没交，运行失败，`error_code: invalid_output` |

列表和单个接口额外返回：

| 字段 | 说明 |
|---|---|
| `overrides` | 子任务自己写了哪些字段 |
| `stats_24h` | 近 24 小时 `{runs, success, failed, p50_ms}` |
| `last_run` | 最近一次运行 |
| `next_fire` | 下一次定时 `{env, at}` |
| `subtask_count` | 子任务数 |

**写入检查**：新建、`PATCH`、恢复版本时对生效定义（子任务是合并之后的；子任务没写自己的 `triggers` 时不查触发器，只有 `extends` 的不查）检查一遍，不过返回 `422 invalid_definition`，`message` 说明哪里不对：
角色 / 处理器存在；`object_input`、`dedup.key` 里的字段在 `input` 里；`enum` 有选项；触发器 id 不重复；
事件的 `filter` 和规则的正则能编译，规则的 `pattern`、`conclusion` 不为空；`session` 模板的占位是字段名（字面花括号写成 `{{ }}`）；
定时的 `envs` 在任务的 `envs` 里、固定 `input` 能通过输入校验；`deliver.channel` 是已有的渠道。
改父任务时，它的每个子任务合并后也要还成立，否则拒绝并指出是哪个子任务。

**子任务**的名字是 `父任务:对象名`，只嵌套一层。**接口返回的是合并后的生效定义**：
档案、输入与父任务按键合并；其他字段子任务写了就用自己的，没写就跟随父任务。内建任务不能建子任务。
`PATCH` 子任务时，字段写 `null` 表示去掉这项覆盖、重新跟随父任务；人改过一次，`auto_created` 就变成 `false`。

| 端点 | 说明 |
|---|---|
| `GET /v1/tasks/{name}/subtasks` | 子任务列表（带统计） |
| `POST /v1/tasks/{name}/subtasks` | `{object, title?, description?, profile?, input?, envs?, enabled?}`，只写与父任务不同的部分 |
| `GET /v1/tasks/{name}/schedule` | 接下来的定时触发：`[{task, trigger_id, service, env, at}]` |

对象名不能含冒号、空白或斜杠，最长 120 个字符。修改子任务就用 `PATCH /v1/tasks/父任务:对象`。

**任务图** `GET /v1/tasks/_graph`（`_graph` 不是合法任务名，不会和任务撞）：

```json
{"nodes": [{"name": "frontend-smoke", "title": "Board 冒烟测试", "service": "vision-board", "form": "agent", "enabled": true,
            "subtask_count": 0, "stats_24h": {"runs": 13, "success": 7, "failed": 6, "p50_ms": 160000},
            "last_run": {"run_id": "…", "status": "success", "created_at": "…"}, "next_fire": null,
            "entry": [{"type": "event", "id": "on-deploy", "source": "gitlab", "event": "deployment"}, {"type": "api", "id": "api"}]}],
 "edges": [{"from": "frontend-smoke", "to": "daily-inspection", "trigger_id": "after-smoke", "mode": "any", "on": ["success"],
            "enabled": true, "from_object": null, "to_object": null, "upstreams": 1}]}
```

节点是父任务（子任务归到父任务上），`entry` 是它自己的入口触发（不含联动、不含停用的）；边是联动，`from_object` / `to_object`
是上游写了子任务全名、联动写在子任务上时的对象名，`upstreams` 是这个联动一共几个上游，`enabled` = 触发器和下游任务都启用。

## 6. 服务 × 环境

| 端点 | 说明 |
|---|---|
| `GET /v1/services/{s}/envs/{env}` | 该环境的解析结果（字段见下） |
| `GET /v1/services/{s}/envs/{env}/config?path=` | 读本环境给 agent 的一份配置 `{path, key, content}`，密钥类的值和连接串里的口令打码（agent 和展示用）。`path` 可以写定义里的写法（`key`）或渲染后的路径；不是本环境声明过的配置，或还没填只读版，返回 `404`；环境不受保护返回 `409 config_not_used` |
| `GET …/config?path=&raw=true` | 编辑用：原文 `{path, key, exists, content, version, updated_by, updated_at}`。`exists` 是填没填过；还没有版本时 `content` 为空串，`version` 为 `null`。环境不受保护返回 `409 config_not_used` |
| `PUT /v1/services/{s}/envs/{env}/config` | 保存 `{path, content}`，存成一个新版本（见下）。返回 `{path, key, version, changed}`。环境不受保护返回 `409 config_not_used` |
| `GET …/config/history?path=` | 版本列表，新的在前：`[{version, updated_by, updated_at, size}]` |
| `GET …/config/history/{version}?path=` | 某一版的内容 `{version, content, updated_by, updated_at}`；没有这一版返回 `404` |
| `GET /v1/services/{s}/tools?reload=` | 服务自己声明的 MCP 工具：`{servers, loaded, tools: [{name, description, server, envs}], failed}`。还没有运行用到时现连一次；`reload=true` 强制重连（改了 MCP 服务端之后）。`failed` 是连不上的连接，形如 `<服务>.<server>@<环境>`。连接由回答请求的那台主机建 |

环境解析结果（示例里的路径是按种子渲染的，【占位】）：

```json
{"service": "vision-board", "env": "prod", "enabled": true, "protected": true, "triggers_paused": false,
 "python": "/home/vision-service/miniconda3/envs/vision-board/bin/python",
 "root": "/home/vision-service/deploy/vision-board", "code_paths": ["/home/vision-service/deploy/vision-board"],
 "urls": {"site": "https://vision-board.moon-prod.ipa.zs/"}, "mcp_servers": [],
 "databases": {"ck": "clickhouse://${CK_RO_USER}:${CK_PROD_RO_PASSWORD}@172.168.0.125:8123/default"},
 "logs": {"app": "/home/vision-service/deploy/vision-board/vision-board.log", "nginx_error": "/var/log/nginx/error.log"},
 "profile": {"conventions": "…"},
 "config_files": [{"key": "~/deploy/vision-board/vision_board/settings-{env}.py",
                   "path": "/home/vision-service/deploy/vision-board/vision_board/settings-prod.py",
                   "version": 3, "updated_by": "…", "updated_at": "…"}]}
```

| 字段 | 说明 |
|---|---|
| `protected` | 环境是否受保护（平台配置 `envs.items[].protected`，§8.1）。`true`：agent 用控制台填的只读版，要填；`false`：agent 直接用项目的真实配置，不用填，配置读写接口返回 `409 config_not_used` |
| `triggers_paused` | 暂停了自动触发：服务定义 `envs.<env>.triggers_paused: true`（`PATCH /v1/services/{s}` 写 `envs`）。定时、事件、上游联动在这个服务×环境都不建运行（闸门第 6 环，触发记录里记 `rejected`）；手动运行、API、对话照常。服务列表的 `health[env]` 里也有这一项 |
| `python` `root` `code_paths` `urls` `logs` | 已渲染：`{env}` 换成该环境，`~` 展开成部署用户的 home |
| `databases` | 本环境的只读库，基座与覆盖已合并；`${VAR}` 占位原样显示，明文口令打码成 `***` |
| `mcp_servers` | 服务声明的 MCP server 名 |
| `config_files` | 每个配置路径一项：`key` 是定义里的写法（给 agent 的配置按它存），`path` 是渲染后的路径；`version` `updated_by` `updated_at` 是给 agent 的只读版的当前版本，还没填时都为 `null`；不受保护的环境存不进只读版，这几项都为 `null` |

这些接口由哪台主机回答都一样：返回的只有定义解析的结果和库里的配置版本。代码目录在不在、git 提交、配置路径在不在只有部署主机上看得到，
而控制台可能由另一台回答，所以接口不返回这些；agent 运行时用 `service_info` 看（§5.2）。

**给 agent 的配置**（只在受保护的环境）：生产的真实配置 agent 看不到。每个服务×环境、每个声明过的配置路径存一份只读账号的版本
（PG 表 `service_configs`），项目内核启动时由执行运行的那台主机写到本机、只读 bind 到项目读配置的那个路径上。
不受保护的环境（测试）agent 直接用项目的真实配置：不用填，读、存只读版返回 `409 config_not_used`（「{env} 不是受保护的环境：
agent 直接用项目的真实配置，不用填只读版」），`service_info(what=config)` 读本机上的真实文件（打码）。

- 每次 `PUT` 存一个新版本，记保存人和时间；内容和当前版本相同时不加版本，返回 `changed: false`。超过 1MB 返回 `422 invalid_request`。
- 不做并发编辑检查：组里几个人分工明确，不会有两个人同时改同一份。后保存的就是当前版本，之前的都在版本历史里。
- 保存后不用重启：该服务×环境的项目内核下一次被调用时发现版本变了，自动重启（之前的变量清空）。
- 某个路径还没有版本时，这个服务×环境的 `py` 起不来（`config_missing`，§1.3）；其他工具照常。
- 受保护的环境里，读接口和 agent 的 `service_info(what=config)` 读的都是这份；线上真实文件平台不读、不显示。

旧版的这些接口已删除：`/v1/services/{s}/sync`、`…/envs/{env}/sync`、`…/processes` 与 `…/envs/{env}/processes/{p}/start|stop|renew|logs`、
`…/config/ack`、`GET /v1/nodes` 与 `DELETE /v1/nodes/{name}`，以及设置里的进程一节。

## 7. 记忆

记忆层分三样（原理见设计文档 §5）：

- **档案**：人写的，在服务 / 任务定义的 `profile` 里，用定义接口改（§5），逐字置顶注入、不检索、不过期；
- **记忆**：agent 记下的事，本节的 `/v1/knowledge`；
- **方法**：可执行的做法与脚本，本节的 `/v1/assets`。

`task` 过滤写父任务名时包含其子任务。

### 记忆

一张表三种 `kind`：`fact` 事实（口径、表与字段、拓扑）/ `lesson` 报错教训（带报错指纹与类别）/ `handoff` 会话交接摘要。
记忆按服务分区，`env` 为空的条目对该服务所有环境成立。

| 端点 | 说明 |
|---|---|
| `GET /v1/knowledge?service=&env=&task=&kind=&status=&q=` | `kind`：`fact` / `lesson` / `handoff`，不给 = 事实与教训。`env=X` 返回该环境的 + 通用的，`env=*` 只看通用的。`status`：`active`（默认）/ `negative`（生效中、`feedback_score < 0`，即挨过 👎 的）/ `expired` / `superseded` / `all` |
| `POST /v1/knowledge` | 人工录入（见下），返回 `201` 和条目 |
| `GET /v1/knowledge/{id}` | 单条 |
| `PATCH /v1/knowledge/{id}` | `{content?, status?: active \| expired}`。改内容视为人工纠正，旧内容进入历史 |
| `DELETE /v1/knowledge/{id}` | 作废，等同于 `status: expired`，可以恢复 |
| `GET /v1/knowledge/{id}/history` | 内容历史 |
| `POST /v1/knowledge/{id}/promote` | 升格进档案（见下） |
| `GET /v1/knowledge/promotable?service=&env=` | 值得升格的：近 30 天被 ≥ 5 次运行召回、没挨过 👎 的生效事实，召回多的在前，最多 30 条 |

**人工录入**：

```json
{"service": "vision-board", "env": "", "kind": "fact", "key": "conf:settings", "content": "manage.py 命令都按 DJANGO_SETTINGS_MODULE=vision_board.settings-<环境> 的配置走"}
{"service": "vision-dagster", "env": "", "kind": "lesson", "content": "上游资产分区延迟导致级联失败，先看上游", "error": "…报错原文…", "category": "upstream"}
```

| 字段 | 说明 |
|---|---|
| `service` | 必填 |
| `env` | 空（默认）= 对该服务所有环境成立；写环境名 = 只在该环境成立 |
| `kind` | `fact`（默认）/ `lesson` |
| `key` | `fact` 必填，如 `conf:settings`，最长 200；同一服务、同一 `env` 下已存在时返回 `409 conflict`，请直接编辑。`lesson` 不填，按报错指纹生成 `lesson:<指纹>` |
| `content` | 必填：事实的内容，或教训的结论 |
| `task` | 归到哪个任务名下（召回时同谱系优先），可空 |
| `error` | `lesson` 必填：报错原文，按它算指纹，同类报错才能精确命中；内容会附上报错的最后一行。同一指纹已有教训时覆盖，旧内容进历史 |
| `category` | `lesson` 的类别：`code` / `data` / `infra` / `upstream`，空 = `code` |

缺 `key`（事实）或 `error`（教训）返回 `400 invalid_input`。人工录入的条目在召回排序上加 3 分。

**升格**：把一条记忆写进档案，适合被反复用到、确认无误的口径与约定。

```json
{"target": "service", "key": "conventions", "task": "", "content": null}
```

| 字段 | 说明 |
|---|---|
| `target` | `service`：写进服务档案，条目只在某环境成立（`env` 非空）时写进 `envs[env].profile`；`task`：写进任务档案 |
| `key` | 档案的键，如 `conventions` / `pitfalls` / 自定义，最长 60 |
| `task` | `target=task` 时写进哪个任务；不填用条目的来源任务，条目没有来源任务时返回 `400 invalid_input` |
| `content` | 写进档案的文字；不填用条目原文 |

- 同一个键已有内容就接在后面（已经包含就不重复）；写入产生服务 / 任务定义的一个新版本。
- 原条目标为被取代：`status` 变成 `superseded`，`superseded_by` 为 `profile:<目标>:<键>`，目标形如 `service:vision-board`、
  `service:vision-board@test`、`task:data-qa`，召回不再重复注入。
- 只有生效中的条目能升格，否则 `409 conflict`。
- 返回 `{entry, profile: {target, key}}`，`entry` 是升格后的原条目。

**条目字段**：`{id, service, env, task, kind, key, content, fingerprint, category, source_run, code_ref{path, commit}, status,
superseded_by, feedback_score, hits_30d, last_hit_at, updated_at}`。

- `env` 为空表示对所有环境成立；`source_run` 为空表示人工录入。
- `fingerprint`、`category` 只有教训有。
- `feedback_score` 是 👎 扣分的累计（只罚不奖，见「反馈」）。
- `code_ref` 引用的代码在沉淀之后改过时，条目自动过期，召回时跳过。

### 方法（可执行的做法与脚本）

| 端点 | 说明 |
|---|---|
| `GET /v1/assets?service=&env=&task=&kind=&status=&q=` | `kind`：`procedure` `script` `query` `baseline`；`q` 在名字、摘要、内容里找（不分大小写） |
| `POST /v1/assets` | `{service, env, task, kind, name, summary, content}` |
| `PATCH /v1/assets/{id}` | `{summary?, content?, status?: active \| superseded}` |
| `DELETE /v1/assets/{id}` | 作废 |

方法按 服务 × 环境 分区。文件类方法（agent 用 `save_asset` 收编的脚本）的目录在项目内核启动时加到 `sys.path`，`py` 里可以直接 import。

## 8. 设置

### 8.1 平台配置

平台配置对所有人生效，存在库里，带版本历史。控制台的界面状态（主题、环境视角、对话页上次用的服务 / 环境 / 任务 / 记忆开关）
存在浏览器里，不经过后端。

| 端点 | 说明 |
|---|---|
| `GET /v1/settings` | 全部配置节，每节带 `section` `version` `updated_by` `updated_at` |
| `GET /v1/settings/{section}` | 单节 |
| `PUT /v1/settings/{section}` | 整节替换。去掉（或改名）还被用着的环境 / 渠道返回 `409 in_use`，`detail.used_by` 列出谁在用：环境看服务的环境覆盖、任务与定时的环境、通知规则、给 agent 的配置；渠道看任务的结果投递 |
| `GET /v1/settings/prompts/defaults` | 平台提示词的内置默认文本（形状同 `prompts` 节），控制台「恢复默认」用 |
| `GET /v1/settings/{section}/versions` | 版本历史 |
| `POST /v1/settings/{section}/versions/{v}/restore` | 恢复到某个版本 |
| `GET /v1/settings/prompts/version-stats` | 平台提示词每个版本的运行效果（按运行配方里记的版本聚合），形状同 §5 的 `version-stats` |
| `POST /v1/settings/notifications/test` | `{channel}`，向该渠道发一条测试消息；发送失败返回 `channel_failed` |

| section | 内容 |
|---|---|
| `envs` | `{items: [{name, title, description, protected, color}], default}`：有哪些业务环境、默认哪个、哪些受保护。`protected` 决定配置怎么给：`true`（生产）agent 看不到真实配置，项目内核里用控制台填的只读版（§6），bash 里遮蔽所有环境的配置；`false`（测试）直接用项目的真实配置，库只读靠提示词，只遮受保护环境的配置。改了它，该环境的项目内核下次调用时重启。不拦任何操作，受保护的环境在控制台上醒目显示。种子：`prod` 国内生产（受保护）、`test` 国内测试（默认） |
| `notifications` | `{channels: {名字: {type: dingtalk \| webhook, url, token}}, rules: [{name, enabled, events, services, envs, tasks, triggers, channel}]}` |
| `memory` | `{recall, save, handoff_summary, knowledge_limit, asset_limit}`：记忆的平台默认 |
| `prompts` | `{base, subagent, compaction, distill, handoff_summary, replay_judge}`：平台提示词（见下） |

平台提示词：

| 键 | 用途 | 占位 |
|---|---|---|
| `base` | 每个主 agent 的系统提示开头，后接角色提示词 | — |
| `subagent` | 每个子代理的系统提示开头，后接子代理角色的提示词 | — |
| `compaction` | 对话太长时压缩历史（必须含 `{messages}`） | `{messages}` |
| `distill` | 运行后沉淀事实 / 教训 | `{service}` `{env}` `{task}` `{input}` `{output}` |
| `handoff_summary` | 会话交接摘要 | `{task}` `{input}` `{output}` |
| `replay_judge` | 回归重放的判定 | `{task}` `{where}` `{input}` `{old}` `{issues}` `{new}` |

- 带占位的是 `str.format` 模板，字面花括号写成 `{{ }}`；`base` / `subagent` 不能为空。校验不过返回 `422 invalid_definition`。
- 整节替换时没写的键用内置默认文本。改了下一次运行就用新的；运行详情的 `recipe.prompts` 记着用的是第几版。
- `replay_judge` 的默认文本分两种读法：原运行被 👎 的看问题改好没有，没被 👎 的把原答案当参照看有没有退步（占位不变）。
  存过自定义版本的保持原来的写法，要两种读法就按默认文本改一下。
- 实际生效的系统提示（`base` + 角色提示词 + 子代理清单等）每次运行落一条 `stage=system` 事件。

通知规则：

- `events` 取值：`run_failed` `run_succeeded` `feedback_negative` `run_queued_long`（排了 `worker.queued_alert_s`，默认 10 分钟，还没开始；
  等上游、任务并发满的不算；每条只发一次）。规则里写了别的事件名，整节校验不过（`422 invalid_definition`）。
  等着自动重试的失败不发 `run_failed`，重试也失败了才发。
- `triggers` 取运行的触发类型（§2，含 `after`）。种子规则「自动运行失败」覆盖 `schedule` `event`。
- 通知由执行运行的那台主机发出，链接按部署配置 `public_url` 拼。
- `services` `envs` `tasks` `triggers` 为空表示不限；多个非空项之间是「且」的关系。
- 渠道的 `token` 读回时是 `"***"`（版本历史里也是），原样传回表示不改。`url` 与 `token` 里可以写 `${VAR}`，发送时才取值。

「某服务在某环境是否启用」不在平台配置里，它是服务自己的 `envs[env].enabled`。

### 8.2 API 密钥

密钥只标识身份，没有范围、不限服务和环境（§1.2）。

| 端点 | 说明 |
|---|---|
| `GET /v1/api-keys` | `{id, name, prefix, note, created_by, created_at, expires_at, last_used_at, revoked_at}` |
| `POST /v1/api-keys` | `{name, note, expires_at}`。返回里的 `token`（`ap_` 开头）**只出现这一次**；同名的已存在返回 `409 conflict` |
| `PATCH /v1/api-keys/{id}` | 修改 `note` `expires_at`；名字不能改 |
| `DELETE /v1/api-keys/{id}` | 吊销，立即生效，不可恢复 |

`name` 为 2–40 个字母、数字或 `.` `_` `-`，建议用项目名，例如 `vision-board`、`dagster-sensor`。

## 9. 元信息、统计、搜索、登录

| 端点 | 说明 |
|---|---|
| `GET /healthz` | 存活检查，免鉴权：`{ok, version, profile}` |
| `GET /v1/meta` | `{version, envs, default_env, tools, event_sources, channels, feedback_reasons, builtin_handlers, features{vector_search}, me}`；`builtin_handlers` 是内建任务可选的处理器名；`me` 是当前身份 `{name, kind}`，`kind` 取 `key` / `user` / `root` |
| `GET /v1/stats?hours=24&service=&env=` | `{totals, by_env, series, top_failures, upcoming, upcoming_total, tokens}`；`hours` 取 1–2160。`totals.running` 是现在执行中的（也按服务、环境过滤）。`upcoming` 是接下来最多 8 次定时 `{task, task_title, trigger_id, service, env, at}`，不含内建任务（记忆园丁这类夜间维护），`upcoming_total` 是去掉内建任务后的总次数 |
| `GET /v1/search?q=` | 全局搜索：`[{type: service \| task \| role \| run \| knowledge \| asset, id, title, subtitle, href}]` |
| `POST /auth/session` | 控制台登录 `{token, name}`。设置 httponly cookie，返回身份 |
| `GET /auth/session` | 当前身份 |
| `DELETE /auth/session` | 退出 |

登录时的 `name` 是操作人姓名，会写进版本台账和运行的发起方；不填则显示密钥名。

**调度的可见面**：

| 端点 | 说明 |
|---|---|
| `GET /v1/ticks?task=&kind=&outcome=&env=&hours=&before=&limit=` | 触发记录，新的在前：`{items: [{id, at, kind, task, trigger_id, env, source, outcome, run_id, reason, detail}], next_before}`。`kind`：`schedule` / `event` / `after` / `retry`；`outcome`：`fired` 建了运行、`deduped` 命中去重或幂等、`skipped` 上一次还没跑完、`filtered` 过滤条件不满足、`waiting` 联动在等其它上游、`rejected` 被闸门或校验拒了（`detail.code` 是原因码）、`unmatched` 事件没有任务接。`task` 写父任务时连同子任务；`source` 是事件来源 / 联动的上游运行 / 重试的原运行；`skipped` 的 `run_id` 是还没跑完的那条。翻页：`before` 传上一页的 `next_before`（`limit` 默认 100，最大 500）。保留 30 天（部署配置 `retention.trigger_ticks_days`）。手动运行和 API 调用不记 |
| `GET /v1/workers` | 执行主机与排队：`{workers: [{worker_id, host, env, services, version, max_concurrent, running, started_at, seen_at, stopped_at, online}], queue: {groups: [{env, service, queued, oldest_at, waiting_upstream, stuck, served}], total}, queued_alert_s}`。主机每 20 秒报到一次，90 秒没报到或正常退出算离线，列出 7 天内报过到的；`env` 空 = 开发机（什么都认领），`services` 空 = 全部服务。`served: false` = 没有在线的主机负责这组，它们会一直排着；`stuck` 是排太久告警过的 |

## 10. 调用示例

```bash
AGENT=https://agent.internal KEY=ap_xxx

# 问一个数据问题，最多等 120 秒拿结果
curl -sX POST $AGENT/v1/runs -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"task":"data-qa","service":"vision-board","env":"test","input":{"question":"报表页面的数据来自 ck 库的哪几张表"},"wait":120}'

# 不写 task = 通用入口 ask：直接交代一件事，不用先建任务
curl -sX POST $AGENT/v1/runs -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"service":"vision-dagster","env":"prod","input":{"question":"昨天哪些资产物化失败了，原因是什么"},"wait":300}'

# 把一条记忆升格进服务档案
curl -sX POST $AGENT/v1/knowledge/42/promote -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"target":"service","key":"conventions"}'

# 某个资产的失败分析（子任务不存在时会自动建）
curl -sX POST $AGENT/v1/runs -H "Authorization: Bearer $KEY" -H 'Idempotency-Key: dagster-8f2c' \
  -H 'Content-Type: application/json' \
  -d '{"task":"failure-analysis","subtask":"<资产>","env":"prod","input":{"run_id":"8f2c","asset_key":"<资产>","error":"…"}}'

# 给 agent 的配置（只在受保护的环境，比如 prod）：读原文，改好后保存（每次保存一个新版本）
P='~/deploy/vision-board/vision_board/settings-{env}.py'
curl -sG $AGENT/v1/services/vision-board/envs/prod/config -H "Authorization: Bearer $KEY" \
  --data-urlencode "path=$P" --data-urlencode raw=true
curl -sX PUT $AGENT/v1/services/vision-board/envs/prod/config -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d "$(jq -n --arg p "$P" --rawfile c settings-prod.readonly.py '{path: $p, content: $c}')"

# 对话（SSE）
curl -N -X POST $AGENT/v1/chat -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"message":"离线 HTML 导出是怎么实现的","service":"vision-board","env":"test"}'

# 推一个通用 webhook 事件
curl -sX POST $AGENT/v1/events/webhook -H "Authorization: Bearer $KEY" -H 'X-Event: release' \
  -H 'Content-Type: application/json' -d '{"service":"vision-board","env":"test","version":"1.2.0"}'

# 改完提示词后，拿最近一周 data-qa 在 vision-board/test 上被 👎 的运行回归重放
curl -sX POST $AGENT/v1/replays -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"task":"data-qa","service":"vision-board","env":"test","hours":168,"note":"data_searcher 提示词加了口径确认"}'

# 同样的改动，再拿最近 20 条 data-qa 运行（不管有没有被 👎）看有没有退步
curl -sX POST $AGENT/v1/replays -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"task":"data-qa","service":"vision-board","env":"test","negative_only":false,"limit":20}'
```
