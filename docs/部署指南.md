# 部署指南

内网主机的完整部署手册。部署形态是**主机 + systemd，不用容器**：平台和它起的业务进程都以一个普通用户运行
（`deploy/install-user.sh`，systemd --user），只在开头请管理员做几件事（§3.0）。

平台主进程 `agent-platform serve` 里包含：

- FastAPI 接入层：`/v1` 接口和控制台页面；
- worker：执行队列（PG 里的 runs 表）、定时、代码跟踪、维护循环；
- agent 运行时，以及项目内核（`py` 工具用的常驻 Python 进程，是平台进程的子进程）。

外部依赖只有 PostgreSQL。模型是 Kimi 开放平台（OpenAI 兼容）。业务项目的进程由平台通过 systemd 用户模板单元
`agent-svc@.service` 按环境启停。

业务项目（vision-dagster、vision-board、vision-web）在这台机器上是**本机副本**：每个服务、每个环境各一份代码
（都跟踪 master，平台自动同步），每个项目一个 conda 环境，加上各环境的配置文件，供 agent 读代码、读配置、查只读库、
在项目 Python 里跑项目代码，需要长驻时起进程。线上服务跑在别处，不受平台管理。

拉代码、装依赖、collectstatic、改配置都由**平台进程以平台用户**来做，不由 agent 做：agent 的 bash 沙箱和 `py` 内核只读
（scratch 除外），装不了依赖、改不了代码，这是有意的。所以 conda 环境和 `/srv/svc`（代码与配置目录）必须对平台用户可写。

---

## 1. 前置条件

| 项 | 要求 | 说明 |
|---|---|---|
| OS | Linux x86_64，systemd | 要管理员开一次 linger（§3.0） |
| Python | ≥ 3.11 | 平台自身用 |
| conda | 每个业务项目一个环境，平台用户可写 | 项目的解释器；同步步骤往里装依赖（§3.7） |
| PostgreSQL | ≥ 14 | 需要 **pg_trgm**；pgvector 可选（§3.1） |
| bubblewrap | `bwrap` 可用 | **必装**：agent 沙箱、项目内核、同步步骤、按环境隔离配置文件都依赖它 |
| 网络 | Kimi 开放平台（`api.moonshot.cn`）、钉钉中继、PG、git 远端、pip 源、各服务登记的只读库（种子：ClickHouse 国内生产 172.168.0.125、国内测试 172.24.17.66 的 8123）、线上 Dagster（MCP 用）可达 | agent 沙箱默认断网，出网都收口在少数工具里；同步步骤照常联网 |
| git | 平台用户能 clone / `ls-remote` 各业务仓库 | 代码跟踪与同步用，见 §3.8 |
| 可选 | Node.js | 仓库里没有构建好的控制台、需要现场构建时用；平台 MCP 用 npx 起浏览器（§3.10）时也要 |
| 可选 | OTLP 后端（Jaeger、Tempo、各家 APM）、Grafana | 链路追踪、主机监控；不配则对应能力自动关闭 |

## 2. 安装后的布局

**业务服务目录**（种子按这个写）：

```
/srv/svc/<服务>/
├── code/<环境>/                每个环境一份 git 工作目录，跟踪 master（code-sync 维护，不要在这里改代码）
└── conf/<环境>/                该环境的配置文件（不进仓库；运维放置，或在控制台改）
/opt/conda/envs/<项目>/         项目同名的 conda 环境，各环境共用（同步步骤往里装依赖）
```

以 vision-board 为例，服务定义里写成 `root: /srv/svc/vision-board/code/{env}`、`python: /opt/conda/envs/vision-board/bin/python`、
`configs: [{template: /srv/svc/vision-board/conf/{env}/settings.py, canonical: /srv/svc/vision-board/code/{env}/vision_board/settings-{env}.py, upstream: vision_board/settings.py}]`。
进程、项目内核和同步步骤启动时，选中环境的配置文件只读 bind 到代码目录里的固定路径，别的环境的配置遮蔽掉。

**平台**：

```
~/agent-platform/                      代码（src、conf、mcp_servers、pyproject.toml）+ venv
~/.config/agent-platform/secrets.env   密钥（600，目录 700）
~/.local/share/agent-platform/         数据目录
├── scratch/                           agent 工作区（沙箱内唯一可写目录，bash 与项目内核共用；db_query 的大结果在 queries/ 下）
├── assets/                            沉淀的方法的文件本体
├── instances/                         业务进程的启动规格与本地日志
├── config-history/                    控制台改配置前的旧内容（700，含口令）
└── sync-backups/                      代码同步丢弃本地改动前留的补丁（700，可能含口令）
~/.config/systemd/user/                agent-platform / agent-svc@ 两个用户单元
```

平台、项目内核、同步步骤、业务进程都是这个用户。密钥目录、`~/.ssh` 等凭据和两个备份目录在 agent 沙箱、项目内核与业务进程里都被遮蔽。

| systemd 用户单元 | 内容 |
|---|---|
| `agent-platform.service` | 平台主服务，127.0.0.1:8100，`AGENT_ENV=prod` |
| `agent-svc@<服务:环境:进程>.service` | 业务进程模板单元，由平台启停 |

## 3. 首次部署

### 3.0 管理员先做的事

平台跑在部署 agent 的那个普通用户下，不需要长期 root。管理员先做一次：

```bash
apt-get install -y bubblewrap                      # 沙箱、项目内核、同步步骤与按环境起服务都依赖它
loginctl enable-linger <用户>                       # 退出登录后 systemd --user 不停
install -d -o <用户> -m 750 /srv/svc                # 业务服务目录（代码 + 配置），平台用户要能写；也可以全放在该用户 home 下，改服务定义里的路径即可
# conda：每个项目一个环境，建好后交给该用户（同步步骤要往里装依赖）；也可以让该用户把 conda 装在自己 home 下
# vision-board、vision-web 按各自 README 用 python 3.12；vision-dagster 按它 README 里的版本
for p in vision-board vision-web; do /opt/conda/bin/conda create -y -n $p python=3.12 && chown -R <用户> /opt/conda/envs/$p; done
/opt/conda/bin/conda create -y -n vision-dagster python=<项目的版本> && chown -R <用户> /opt/conda/envs/vision-dagster
# Ubuntu 24.04+ 默认限制非特权用户命名空间，bwrap 会失败；二选一：
sysctl -w kernel.apparmor_restrict_unprivileged_userns=0   # 并写进 /etc/sysctl.d/
# 或给 /usr/bin/bwrap 配一个允许 userns 的 AppArmor profile
```

然后用该用户经 ssh 或 `machinectl shell <用户>@` 登录（`sudo -u` 拿不到用户的 systemd 会话），在仓库根目录执行
`bash deploy/install-user.sh`。脚本会检查 bwrap、linger、secrets 与 `/srv/svc`，缺什么就提示什么。

### 3.1 准备数据库

```sql
-- 以 PG 超级用户执行
CREATE USER agent PASSWORD '<强密码>';
CREATE DATABASE agent_platform OWNER agent;
\c agent_platform
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE EXTENSION IF NOT EXISTS vector;    -- 可选：pgvector，只能超级用户建
```

表结构在服务启动时幂等创建（`store/db.py` 是全库唯一的建表点），不需要手工迁移。

召回用 pg_trgm 做关键词检索。pgvector 只在配了嵌入模型（`model.embedding_name`）时才用得上；Kimi 没有嵌入接口，
默认不配。建不了 `vector` 扩展时服务只记一条 warning，不影响启动。

### 3.2 部署配置

部署配置只有「平台怎么跑起来」的参数，放在 `conf/` 里：

| 文件 | 内容 |
|---|---|
| `conf/base/common.yaml` | 所有机器共享的默认值：模型（Kimi）、执行队列（`worker`）、项目内核（`kernel`）、进程控制、代码跟踪（`code_sync`）、链路追踪（`otel`）、数据保留（`retention`）、Grafana、平台 MCP（`mcp_servers`） |
| `conf/env/prod.yaml` | 生产机的差异，深合并到上面：`db_dsn`、`root_token`、`public_url`、`model.tokens`、`process_control.backend: systemd`。安装脚本装的单元用它（`AGENT_ENV=prod`） |
| `conf/env/dev.yaml` | 开发机的差异 |

配置里的 `${VAR}` 从环境变量（`secrets.env`）取值，**没设置时启动直接报错**。
配置问题在启动时就暴露，不会带病运行。

**模型**（`model` 节，Kimi 开放平台，OpenAI 兼容）：

| 键 | 默认 | 说明 |
|---|---|---|
| `model.url` | `https://api.moonshot.cn/v1` | OpenAI 兼容的接口地址 |
| `model.name` | `kimi-k2.7-code` | 能用哪些模型看 key，`GET {url}/models` 可查。现在这把 key 只列出 `kimi-k2.7-code`、`kimi-k2.6`，`kimi-k2.8` 返回 404 |
| `model.tokens` | `["${MODEL_TOKEN_A}"]`（prod.yaml） | 有多把 key 就都列上，按请求轮换 |
| `model.max_concurrency` | 1 | 同时在途的模型请求上限（流式响应读完才算结束）：agent 的调用和平台的辅助调用合计，平台侧排队；0 = 不限。Kimi 按组织限并发，这个账号是 1 |
| `model.rpm` | 3 | 每分钟最多发几次请求：平台侧 60 秒滑动窗口排队，同样所有调用合计；0 = 不限。Kimi 按组织限 RPM，这个账号是 3 |
| `model.max_retries` | 6 | 撞了 429 或网关错误时的重试次数（指数退避） |
| `model.stream_usage` | true | 流式响应里要 token 用量；网关不支持就关掉 |
| `model.context_tokens` | 400000 | 模型的上下文长度：对话历史到它的 75% 时自动压缩成摘要。换了模型按实际窗口改 |
| `model.embedding_name` | 不配 | 配了才开向量检索；Kimi 没有嵌入接口 |

并发 1、3 RPM 决定了吞吐：一次调 8 次左右模型的 agent 运行要 3 分钟上下；同时有几个运行时，它们在模型这一层排队，
调大 `worker.max_concurrent_runs` 不会更快。任务的 `timeout_s` 把排队时间也算在内（种子的 agent 任务是 600–900 秒）。
账号充值升档后按开放平台控制台显示的额度改 `model.max_concurrency` 和 `model.rpm`，重启生效。
429 的报错原文会写明撞的是哪一项（`max organization concurrency` / RPM / TPM）。

其他常调的键：

| 键 | 默认 | 说明 |
|---|---|---|
| `worker.max_concurrent_runs` | 10 | 一个 worker 同时执行几个运行；满了就不再认领，排队的按创建时间先到先得 |
| `kernel.idle_minutes` | 30 | 项目内核空闲多久回收 |
| `kernel.max_kernels` | 8 | 同时最多几个项目内核（每个 会话×服务×环境 一个），超了先回收最久没用的 |
| `code_sync.interval_minutes` | 60 | 代码跟踪多久看一次各服务的远端，落后才同步；0 = 不自动跟踪，只在控制台 / 接口手动同步 |
| `hidden_paths` | `~/.config/agent-platform`、`~/.ssh`、`~/.git-credentials`、`~/.netrc`、`~/.pgpass` | agent 沙箱、项目内核与业务进程里遮蔽的路径（存在的才遮）；服务声明的配置文件总是遮蔽，不用写 |
| `retention.run_events_days` | 90 | 已结束运行的过程事件保留几天；被 👎 过的运行不清（回归重放要用） |
| `retention.checkpoints_days` | 30 | 会话 checkpoint：最后一轮结束这么久后清掉，之后该会话不能续跑，新一轮从头开始 |
| `retention.recall_hits_days` | 90 | 召回埋点 |

数据保留由维护循环每 6 小时清一次；运行台账本身（输入、输出、配方）一直保留。

链路追踪（可选）：`otel` 打开后经 OTLP/HTTP 导出到任意兼容后端，需要装 `[obs]`（§3.3）。页面不依赖它，运行详情的时间线
（含每次模型调用的耗时、token 与思考）来自平台自己的过程事件。

```yaml
otel:
  enabled: true
  endpoint: http://otel-collector.internal:4318/v1/traces   # 默认 http://127.0.0.1:4318/v1/traces
  headers: {Authorization: "Bearer ${OTEL_TOKEN}"}           # 口令写 secrets.env
```

`serve` 默认同进程跑 worker。要分开时用 `serve --no-worker` 加单独的 `agent-platform worker`；多开 worker 也安全：
认领用 `FOR UPDATE SKIP LOCKED`，定时带幂等键，不会重复执行或重复触发。模型的 RPM 排队是进程内的，多开 worker 时
每个进程各算各的，`model.rpm` 要按进程数分摊。

服务、角色、任务，以及平台配置（环境、通知、记忆、进程、提示词）**都不在这里**。
它们存在库里，在控制台编辑。`conf/seeds/` 只在库里还没有对应对象时播种一次，之后改种子文件不会覆盖库里的内容。
种子与库里的定义不一致时，启动日志会提示。

### 3.3 执行安装

```bash
bash deploy/install-user.sh          # 以该用户登录后在仓库根目录执行（§3.0）
```

脚本依次完成以下动作：

1. 拷贝代码（`src`、`conf`、`mcp_servers`、`pyproject.toml`）到 `~/agent-platform`，建数据目录；
2. 构建控制台（仓库里没有 dist 且装了 node 时才做）；
3. 建 venv 并安装；`db_query` 的驱动（pymysql、clickhouse-connect、pymongo）是核心依赖，一起装上；
4. 检查 bwrap、linger、secrets.env 与 `/srv/svc`，缺什么提示什么；
5. 安装用户单元（`AGENT_ENV=prod`），然后启动。

这时 secrets.env 还没放，服务起不来，**这是预期的**；下一步放好后重启即可。

内网不通外网时，先配 pip 镜像：执行安装脚本前设置环境变量 `PIP_INDEX_URL`。同步步骤给业务项目装依赖用的镜像写进 secrets.env（§3.4）。

可选依赖不随安装脚本装。服务 MCP（服务定义里的 `mcp`）要 `mcp` 这一组，仓库自带的 dagster MCP（`mcp_servers/dagster_mcp.py`，
种子 vision-dagster 在用）另需 `dagster-mcp`。装进平台 venv：

```bash
~/agent-platform/venv/bin/pip install "$HOME/agent-platform[mcp,dagster-mcp]"
```

开链路追踪（§3.2 的 `otel`）另装 `obs`：`[mcp,dagster-mcp,obs]`。

升级重跑安装脚本不会卸掉已装的可选依赖。

### 3.4 放置密钥并重启

```bash
install -m 600 /dev/null ~/.config/agent-platform/secrets.env
cat > ~/.config/agent-platform/secrets.env <<'EOF'
# 注释只能单独成行：systemd 的 EnvironmentFile 不认行尾注释，会把它当成值的一部分
# 引导密钥：首次登录、创建 API 密钥；不可吊销，务必够长
AGENT_ROOT_TOKEN=...
# 3.1 的 PG 密码
AGENT_DB_PASSWORD=...
# Kimi 开放平台的 API key（prod.yaml 的 model.tokens 引用它）
MODEL_TOKEN_A=sk-...
# 种子通知渠道 default 用（设置 → 通知 里也能改）
DINGTALK_ACCESS_TOKEN=...
# 种子里只读库 ck（ClickHouse）的只读账户：服务定义里写 ${VAR}，连库时才取值
CK_RO_USER=...
CK_PROD_RO_PASSWORD=...
CK_TEST_RO_PASSWORD=...
# 可选：同步步骤（pip install）用的镜像 / 代理；平台进程有就透传给步骤
# 透传的是 PIP_INDEX_URL、PIP_EXTRA_INDEX_URL、PIP_TRUSTED_HOST、PIP_DEFAULT_TIMEOUT 与 HTTP(S)_PROXY、NO_PROXY
# PIP_INDEX_URL=https://pypi.internal/simple
# HTTPS_PROXY=http://proxy.internal:3128
# 可选：部署配置里引用了才需要，比如 otel.headers 里的 ${OTEL_TOKEN}（§3.2）
# OTEL_TOKEN=...
EOF
systemctl --user restart agent-platform
```

环境变量只在平台启动时读：以后服务定义里新登记的库、通知渠道用到新的 `${VAR}`，加进这个文件后要重启平台。

### 3.5 验证

```bash
systemctl --user status agent-platform --no-pager
curl -s http://127.0.0.1:8100/healthz        # {"ok": true, "version": "9.0.0", "profile": "prod"}
(set -a; . ~/.config/agent-platform/secrets.env; \
  AGENT_ENV=prod AGENT_CONF=$HOME/agent-platform/conf $HOME/agent-platform/venv/bin/agent-platform check)
# 配置 prod 正常；环境 prod、test、dev（默认 test）；服务 3 个，任务 7 个
journalctl --user -u agent-platform -n 100 --no-pager  # 不应有 ERROR；应有「执行队列已启动」
```

首次启动会自动做两件事：

1. 建表；
2. 播种：平台配置、服务、角色、任务，只写库里还没有的。

定时由 worker 每轮读最新定义按 cron 触发，不需要额外同步。启动 2 分钟后代码跟踪看第一次远端，代码目录不存在的会被 clone（§3.7）；
在那之前把 `/srv/svc` 和 conda 环境准备好，否则首轮同步会失败（下一轮自动重试）。

### 3.6 首次登录与发密钥

1. 打开控制台的 `/login`，用 `AGENT_ROOT_TOKEN` 登录，「你的名字」填自己。这个名字会写进版本台账与运行的发起方。
2. 进入 设置 → API 密钥，给每个调用方各建一把。密钥只标识身份、不分权限，有效密钥能做全部操作，所以只发给需要的人和项目：
   - 自己：建一把，以后用它登录，不再用 root_token；
   - 业务项目：用项目名，如 `vision-board`；
   - Dagster 回调（`dagster-sensor`）、GitLab Webhook（`gitlab`）：各建一把。
3. 进入 设置 → 环境 / 通知，确认平台配置。然后在各服务的「环境」标签里，确认这个服务在哪些环境启用。

冒烟测试：

```bash
pip install ./sdk
export AGENT_URL=http://127.0.0.1:8100 AGENT_KEY=<刚建的密钥>
agent-chat vision-board --env test   # 问一句，看到工具调用与回答即可；3 RPM 下一轮要等一会儿
```

### 3.7 放置业务代码、conda 环境与配置

**代码**不用手工 clone。服务定义里配好 `repo` 和 `ref: master`（种子已配，`git@gitlab.ipa.zs:vision/<项目>.git`），
代码跟踪发现代码目录不存在或落后于远端，就提交一次 code-sync 去克隆 / 对齐；也可以在控制台 服务 → 代码同步 点「立即同步」，
或 `POST /v1/services/vision-board/sync`。三个环境的副本都跟踪 master。每次同步：

- 已跟踪文件的本地改动先存成补丁（数据目录 `sync-backups/<服务>/<环境>/`）再丢弃，所以不要在代码目录里改代码；
- 未跟踪的文件（`.env`、收集出来的静态资源）不动；
- 已声明的配置文件如果直接改在了代码目录里（比如手工改过的 settings 文件），而 `conf/<环境>/` 下还没有它，
  先自动收编过去再丢弃改动，不会丢；
- 然后按服务定义的 `sync.steps` 跑该跑的步骤：种子 vision-dagster 是 `pip install -e .`；vision-board、vision-web 是
  `pip install -r requirements.txt` 加 `collectstatic --noinput`。代码或依赖变了就重启该环境的项目内核和在跑的进程。

代码目录已存在却不是 git 仓库时，同步拒绝覆盖（`code_sync_failed`），先挪走它。

**conda 环境**：每个项目一个，名字和项目相同，三个环境共用；服务定义里写 `python: /opt/conda/envs/<项目>/bin/python`。
建出空环境即可，依赖由同步步骤装：第一次同步装一遍，之后依赖文件变了才再装，共用一个环境的几个副本只装一次。
平台用户必须能写这个环境（§3.0）。项目内核、同步步骤和业务进程都用这个解释器，内核的驱动只用标准库，环境里不用额外装东西。

```bash
conda create -y -n vision-board python=3.12   # 以平台用户执行；/opt/conda 不归它时请管理员建好后 chown（§3.0）
```

重建了 conda 环境之后，库里还记着「依赖已装过」：同步时带 `force`，所有步骤重跑一遍：

```bash
curl -sX POST 127.0.0.1:8100/v1/services/vision-board/sync -H "Authorization: Bearer $AGENT_KEY" \
  -H 'Content-Type: application/json' -d '{"force": true}'
```

**配置文件**：每个环境一份，放在代码目录外，只有平台用户能读。库、接口账户用只读的。种子里的约定：

| 服务 | 放在 `conf/<环境>/` | 进程读到的路径（代码目录里） | 从哪改出来 |
|---|---|---|---|
| vision-dagster | `.env`、`dagster.yaml` | `.env`、`dagster.yaml`（`DAGSTER_HOME` 指向代码目录） | 仓库的 `.env.template`、`dagster.template.yaml`（`*.india` 是印度部署的，不用） |
| vision-board | `settings.py` | `vision_board/settings-<环境>.py`，`DJANGO_SETTINGS_MODULE=vision_board.settings-<环境>` | 复制 `vision_board/settings.py`，改 STATIC_ROOT、CRONTAB_COMMAND_PREFIX、库口令、认证授权 |
| vision-web | `settings.py` | `vision_web/settings-<环境>.py`，`DJANGO_SETTINGS_MODULE=vision_web.settings-<环境>` | 复制 `vision_web/settings.py`；登录走 FreeIPA，本地应用授权码要手动生成后写进去 |

```bash
install -d -m 750 /srv/svc/vision-board/conf/{prod,test,dev}
install -m 600 settings.test.py /srv/svc/vision-board/conf/test/settings.py
```

也可以在控制台 服务 → 配置文件 直接新建或修改（新建的文件是 640；保存前的内容自动备份到数据目录 `config-history/`）。
仓库里对应的上游（服务定义里配置的 `upstream`）变了，服务页会提示「配置待更新」并给出 diff，同时按服务发一次通知。

本机副本不要执行 vision-board 的 `manage.py crontab add`：它会按该环境的配置真的跑定时任务。同步步骤里没有这一步。

### 3.8 代码同步的 git 访问

代码同步和代码跟踪在宿主上直接跑 git（不在沙箱里），用平台用户自己的 ssh 密钥，不弹交互提示。

平台用户的 `~/.ssh` 里放一把只读部署密钥，加到各项目（GitLab → 项目 → Deploy keys），之后普通 git 就能拉。
先手工连一次，把主机指纹记进 `known_hosts`（同步时不会问）：

```bash
ssh -T git@gitlab.ipa.zs                                          # 接受主机指纹
git ls-remote git@gitlab.ipa.zs:vision/vision-board.git master    # 能列出提交即可
```

`~/.ssh` 在 agent 沙箱、项目内核、业务进程和同步步骤里都被遮蔽（`hidden_paths` 的默认值），所以依赖里有 `git+ssh://` 的包
在同步步骤里装不上，改用内部 pip 源。

### 3.9 接外部事件

| 来源 | 配法 |
|---|---|
| Dagster | `run_failure_sensor` 里 `POST {public_url}/v1/events/dagster`，请求头 `Authorization: Bearer <dagster-sensor 的密钥>`，请求体 `{run_id, asset_key, error, env}` |
| GitLab | 项目 → Webhooks，地址 `{public_url}/v1/events/gitlab`，Secret token 填 gitlab 那把密钥，勾选 Deployment events |
| 其他系统 | `POST /v1/events/webhook`，事件名放请求头 `X-Event` |

接通之后，哪个事件触发哪个任务，在任务的「触发」里声明。种子任务 `frontend-smoke`（Board 冒烟测试）声明了 GitLab 部署事件，
只认 `filter.project: ^vision-board$`（回调里的项目名），GitLab 项目名不同的话改它。GitLab 部署的 `environment` 要和平台的环境名一致（prod / test / dev）。
代码同步不靠部署事件，由代码跟踪按 master 自动做（§3.7）。

### 3.10 MCP（可选）

MCP 工具分两种，都要先装 `[mcp]`（§3.3）：

| | 平台 MCP | 服务 MCP |
|---|---|---|
| 放什么 | 通用能力，比如浏览器 | 某个服务特有的能力，比如 vision-dagster 的运行记录 |
| 写在哪 | 部署配置 `mcp_servers`（`conf/`），改了要重启 | 服务定义的 `mcp`（控制台），写库即生效，下次运行自动重连 |
| 怎么用上 | 角色的 `tools` 里写 `"mcp:<名字>"`、工具名或 `"*"` | 运行在该服务上自动出现 |

平台 MCP 以浏览器为例（种子角色 `qa_engineer` 用 `"mcp:browser"`），写进 `conf/env/prod.yaml`：

```yaml
mcp_servers:
  browser:
    transport: stdio
    command: npx
    args: ["-y", "@playwright/mcp@0.0.83", "--headless", "--isolated", "--output-dir", "/home/<用户>/.local/share/agent-platform/scratch"]
```

- 需要 Node.js；内网不通外网时先在平台用户下把 `@playwright/mcp` 和浏览器装好，或配 npm 镜像。
- MCP 会话按 会话 × 连接 常驻：同一个会话里先 navigate 再 snapshot 落在同一个浏览器进程上。空闲 30 分钟回收，
  所有 MCP 连接合计同时最多 16 条（超了回收最久没用的），浏览器进程数也就不会超过它。
- 页面地址来自服务定义的 `urls`（如 vision-board 的 `site`、`local`），agent 在运行环境提示里看得到。
- 没配 `browser` 时，角色里的 `"mcp:browser"` 被忽略，只记一条 warning。

服务 MCP 以种子 vision-dagster 为例：`mcp.dagster` 用平台解释器跑仓库自带的 `mcp_servers/dagster_mcp.py`，按运行的环境连该环境线上部署的
Dagster（`urls.deployed`：prod `https://vision-dagster-prod.ipa.zs:9902`、test `https://vision-dagster-test.ipa.zs:9901`；dev 没有）。
要求平台机器能访问这两个地址，平台 venv 装了 `[mcp,dagster-mcp]`。内网证书校验不过时，在服务定义 `mcp.dagster.env` 里加
`DAGSTER_VERIFY`：CA 文件路径（如 `/etc/ipa/ca.crt`），实在不行写 `false`。
连接配置里的口令写 `${VAR}`，放 secrets.env，连接时才取值。

验证：`GET /v1/services/vision-dagster/tools?reload=true`，`tools` 里应有 5 个工具，`failed` 为空。

### 3.11 只读库（db_query）

服务定义的 `databases` 登记 agent 能查的库：`{库名: 连接串}`，scheme 决定类型（PostgreSQL / MySQL / MariaDB / Doris /
ClickHouse / MongoDB，见设计文档 §2.3），`envs[env].databases` 按库名覆盖。种子里 vision-dagster、vision-board 登记了 `ck`：

| 环境 | ClickHouse | 连接串 |
|---|---|---|
| prod | 国内生产 172.168.0.125 | `clickhouse://${CK_RO_USER}:${CK_PROD_RO_PASSWORD}@172.168.0.125:8123/default` |
| test、dev | 国内测试 172.24.17.66 | `clickhouse://${CK_RO_USER}:${CK_TEST_RO_PASSWORD}@172.24.17.66:8123/default` |

- 账户必须是只读的。`db_query` 自己的检查（单条语句、关键字白名单、只读事务 / `readonly=2`、30 秒超时）只是第一道。
  ClickHouse 账户是 `readonly=1` 时不能带任何设置，平台去掉超时和行数上限的设置重试，按账户自己的限制执行。
- 口令写 `${VAR}`，放 secrets.env（§3.4），重启后生效。取不到时工具返回 `[未配置]`，不会把占位原样拿去连库。
- vision-web 还没登记库：按它 settings 里实际连的库加，例如 `main: "mysql://${VISION_WEB_RO_USER}:${VISION_WEB_RO_PASSWORD}@<地址>:3306/<库>"`；
  Doris 写 `doris://…:9030/<库>`，MongoDB 写 `mongodb://…/<库>`。
- 超过 20 行的结果整份写进 `scratch/queries/<run_id>/`（CSV / JSONL），最多 10 万行、50MB。
- 验证：对 vision-board 的 test 问一句「用 db_query 在 ck 库执行 SELECT version()」，时间线里看 `db_query` 的返回。

## 4. 反向代理

主服务只监听 `127.0.0.1:8100`，内网用户经反向代理访问：

```nginx
server {
    listen 443 ssl;
    server_name agent.internal;              # 与 public_url 一致
    location / {
        proxy_pass http://127.0.0.1:8100;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 3600s;            # SSE：对话与运行推流
        proxy_buffering off;                 # SSE 需要实时冲刷
    }
}
```

- `public_url` 必须与最终访问地址一致：通知里的跳转链接用它拼；它是 https 时，登录 cookie 带 Secure 标记。
- SSE 端点（`/v1/chat`、`/v1/runs/{id}/stream`）要求反代关闭缓冲、拉长超时。

## 5. 业务进程的启停

平台用 systemd 用户模板单元按「服务 × 环境」启停业务进程（`process_control.backend: systemd`）：

```
agent-svc@vision-board:test:server.service
  → 平台用户
  → python -m agent_platform.services.svcrun vision-board:test:server
  → 读 <数据目录>/instances/vision-board:test:server.json（平台启动前写好）
  → bwrap：把 test 环境的配置文件 bind 到服务读的固定路径，其他环境的同名文件遮蔽
  → exec 业务进程
```

- 平台用 `systemctl --user` 管自己的 `agent-svc@*.service`，不需要 root；日志 `journalctl --user -u 'agent-svc@vision-board:test:*'`。
- 种子里的进程：vision-dagster 只有 `webserver`（端口 3900–3902，不起 daemon：它会按该环境的配置真的跑调度和传感器）；
  vision-board、vision-web 是 `manage.py runserver`（8180–8182、8280–8282）。
- 服务在该环境启用（服务 → 环境）就能起进程；cmd 里可以写 `{python}`，换成服务的解释器。
- 每次启动带租约，到期自动停止。默认值与上限在 设置 → 进程；单个进程可以在服务定义里覆盖 `lease_hours`。
- 业务进程里遮蔽：其他环境的配置文件、`hidden_paths`（默认是平台密钥目录与运行用户的 `~/.ssh` 等凭据）、配置备份与同步补丁目录；
  有独立的 pid 命名空间，读不到平台进程的环境变量。
- 代码同步改了代码或依赖后，该环境在跑的进程自动重启（有同步步骤失败时不重启）；控制台保存配置文件后，返回里列出要手动重启的进程。
- 同步步骤（装依赖、collectstatic）不走 systemd：平台进程按同一份规格直接起 bwrap，配置就位、密钥遮蔽，和业务进程看到的一样，可写、可联网。
- 开发机用 `backend: local`，进程是平台的子进程，日志在 `instances/` 下。

**项目内核**（`py` 工具）不走 systemd：它是平台进程的子进程（以平台用户运行），每个 会话×服务×环境 一个。
用服务的解释器、在该环境的部署目录里跑，配置文件按和起进程同一份规格 bind 到固定路径；
文件系统只读、scratch 可写、网络照常，密钥与备份目录遮蔽，独立 pid 命名空间，环境变量只带白名单与服务的 `env_vars`。
代码同步或保存配置后自动重启（变量清空）。空闲回收与数量上限见 §3.2 的 `kernel` 节。没有 bwrap 时直接在宿主上跑，只适合开发机。

## 6. 升级与回滚

```bash
git pull
bash deploy/install-user.sh          # 幂等：重拷代码、重装依赖、重启
```

- 表结构在启动时幂等创建（`store/db.py`），不需要迁移脚本。
- 定义和平台配置在库里不在包里，升级不会动它们；改了种子文件也不会覆盖库里的内容。数据层面的「回滚」走控制台：
  - 定义、平台配置：版本恢复；
  - 记忆：内容历史恢复。
- 代码回滚：仓库切回旧提交，重跑安装脚本。
- 还没发正式版：表结构有不兼容的改动时，可能要重建开发库（删库后按 §3.1 重建，启动时重新建表、播种）。

## 7. 备份与恢复

| 数据 | 位置 | 方式 |
|---|---|---|
| PG 全库（台账与执行队列、定义与档案、平台配置、密钥摘要、记忆、方法元数据、回归重放、同步记账、全部历史） | `agent_platform` 库 | 定期 `pg_dump -Fc agent_platform` |
| 方法的文件本体 | 数据目录 `assets/` | 文件级备份 |
| 各环境配置文件及其历史 | `/srv/svc/*/conf/`、数据目录 `config-history/` | 文件级备份（含口令，按密钥文件对待） |

不需要备份的：

- `scratch/`：临时工作区（含 `db_query` 的结果文件）。
- `instances/`：启动时重写。
- 代码目录、conda 环境：重新同步即可重建。
- `sync-backups/`：同步丢弃的本地改动，确认没用后可以删。

恢复步骤：装 PG → 恢复 dump → 安装脚本 → 恢复 assets 与配置目录 → 建好 conda 环境 → 启动 → 各服务同步一次并带 `force`
（§3.7）：库里还记着「依赖已装过」，不带 `force` 新的 conda 环境里不会装依赖。

## 8. 日常运维

```bash
journalctl --user -u agent-platform -f                        # 平台日志
journalctl --user -u 'agent-svc@vision-board:test:*' -f       # 某服务某环境的业务进程日志
curl -s 127.0.0.1:8100/healthz
systemctl --user restart agent-platform                       # 只有改了 conf/ 或 secrets.env 才需要重启
```

- **定义和平台配置**在控制台改，写库即生效，不用重启。
- **部署配置**（`conf/`）和 secrets.env 只在启动时读，改了要重启。
- **代码**跟踪 master 自动同步。服务 → 代码同步 看各环境的当前提交、是否落后、步骤结果，「立即同步」随时可点；
  每次同步是一条 code-sync 运行，时间线里有变更文件、丢弃的改动、步骤的命令与输出。
- **配置文件**在 服务 → 配置文件 里改，保存前的内容自动备份（每个文件最近 30 份），改完按提示重启在跑的进程。
  不要改代码目录里的固定路径（那是 bind 上去的或仓库里的文件，同步会丢弃），改 `conf/<环境>/` 下的真实文件或用控制台。
- **重启平台**时执行中的运行记为 `interrupted`，可以在运行详情续跑。
- **密钥轮换**：
  - API 密钥：控制台新建一把 → 调用方换上 → 吊销旧的；
  - root_token、Kimi key、只读库口令：改 secrets.env 后重启。

## 9. 故障排查

| 现象 | 排查 |
|---|---|
| 启动即退出 | `journalctl --user -u agent-platform -n 200`：多半是 secrets.env 缺变量（`${VAR}` 插值报错）或 PG 连不上。`agent-platform check` 能单独验证配置与数据库 |
| 日志提示 vector 扩展 | 没装 pgvector：只是不能做向量检索。Kimi 没有嵌入接口，默认本来就不用，可以忽略 |
| 日志告警 bwrap | 安装 bubblewrap，不装则沙箱与配置隔离失效 |
| 运行一直 queued | 没有 worker 在跑：`serve` 加了 `--no-worker` 就要另起 `agent-platform worker`，日志里应有「执行队列已启动」。也可能并发满了（`worker.max_concurrent_runs`），看有没有长时间 running 的运行 |
| 运行很慢，时间线上两次模型调用之间隔很久 | 模型配额排队（`model.max_concurrency: 1`、`model.rpm: 3`，所有运行和辅助调用共用）：同时跑的运行越多越慢，见 §3.2。账号升档后再调大 |
| 运行失败，报 `timeout` | 排队也算在 `timeout_s` 里：同时运行多时调大任务的 `timeout_s`，或错开定时 |
| 模型调用报 404 / model not found | `model.name` 这把 key 用不了：`curl -H "Authorization: Bearer $MODEL_TOKEN_A" https://api.moonshot.cn/v1/models` 看可用的，改 `conf/` 后重启 |
| 模型调用一直 429 | 报错原文写了撞的是并发还是 RPM。多半是别的程序也在用这个账号，或多开了 worker（排队按进程算，§3.2）。`model.max_concurrency` / `model.rpm` 调小 |
| 运行失败，`error_code` 是 `orphaned` / `interrupted` | 执行它的进程崩溃或重启了，运行详情里续跑 |
| 定时没触发 | 控制台 → 任务 → 概览，看「下次定时」；任务或触发器是否停用；服务在该环境是否启用；同一触发器上一次还没跑完会跳过；停机期间错过的不补 |
| 调用返回 `service_env_disabled` 等 | 原因码与解法见接口文档 §1.4 |
| `py` 报找不到解释器 / 部署目录不存在 | 服务定义的 `python` 指向项目的 conda 环境并建好（§3.7）；部署目录不存在就先同步代码 |
| `db_query` 返回 `[未配置]` | 服务在该环境没登记库，或 `${VAR}` 在 secrets.env 里没有（加上后重启平台） |
| `db_query` 返回 `[拒绝]` | 只能执行一条查询类语句；MongoDB 要写成 JSON（工具说明里有写法），聚合不能有 `$out` / `$merge` |
| `db_query` 返回 `[查询出错]` | 库侧的原文：连不上就查平台机器到库的网络（种子 CK 是 8123 端口）和账户口令；超时就加条件或先在库里聚合 |
| `db_query` 返回 `[不可用] 平台没装 … 的驱动` | 平台 venv 少了核心依赖：重跑安装脚本 |
| 代码同步失败（`code_sync_failed`） | 运行详情里有 git 的原文：找不到分支看服务定义的 `ref`；拉不下来检查平台用户的 git 访问（§3.8，`git ls-remote` 试一下）；代码目录已存在却不是 git 仓库就先挪走 |
| 同步步骤失败（`sync_step_failed`） | 运行详情里有失败步骤的命令和输出。常见：pip 源不通（secrets.env 里设 `PIP_INDEX_URL` / 代理后重启平台）、conda 环境平台用户写不了（§3.0）、collectstatic 缺配置。代码已对齐，进程没重启；修好后点「立即同步」，失败的步骤会重跑 |
| 重建了 conda 环境，依赖却没重装 | 步骤按依赖文件的内容判断要不要跑，库里还记着装过：同步时带 `force`（§3.7） |
| 「配置待更新」一直不消失 | 仓库里的上游（`.env.template`、`settings.py`…）变了：服务 → 配置文件 对照 diff 改完保存，或确认不用改点「已核对」。直接在宿主上改文件不会清掉提示 |
| 远端有新提交却没自动同步 | 看 服务 → 代码同步 的远端检查时间：没有就是代码跟踪没跑或看不了远端。检查 `code_sync.interval_minutes`（0 = 关，改了要重启）、服务的 `sync.auto`、服务和该环境是否启用、是否配了 `repo`；平台用户 `git ls-remote <repo> master` 能否成功（日志搜「代码跟踪」）。上一次同步失败的，下一轮会重试 |
| bwrap 报 `setting up uid map: Permission denied` 一类错误 | 非特权用户命名空间被限制（Ubuntu 24.04+ 的 AppArmor），见 §3.0 |
| 启动进程报 `start_failed` | `journalctl --user -u agent-svc@<服务:环境:进程>`；确认 `~/.config/systemd/user/agent-svc@.service` 在、linger 开着 |
| 登录后又跳回登录页 | cookie 被拦：确认经反代访问、反代不改写 Set-Cookie；`public_url` 是 https 时必须走 https |
| 收不到钉钉 | 设置 → 通知 → 渠道「发送测试」；再看通知规则是否覆盖该事件 |
| SSE 首字节慢或断开 | 反代缓冲或超时：`proxy_buffering off`，并拉长 `proxy_read_timeout` |
| 服务的 MCP 工具没出现 | `GET /v1/services/<服务>/tools?reload=true` 看 `failed`；平台 venv 装了 `[mcp]`（dagster 的还要 `[dagster-mcp]`）；`mcp.envs` 里列了该环境、服务在该环境启用；`${VAR}` 在 secrets.env 里有值；日志搜「MCP 连接」 |
| dagster 的 MCP 工具报证书错误 | 线上 Dagster 是内网 HTTPS：在 `mcp.dagster.env` 里加 `DAGSTER_VERIFY`（CA 文件路径，或 `false`，§3.10） |
| 平台 MCP（浏览器）没出现 | 改了 `mcp_servers` 要重启；装了 `[mcp]`；`npx` 能拉到包；角色写了 `"mcp:browser"`。启动日志有「平台 MCP 加载 N 个工具」 |
| MCP 工具报 `[调用失败]`、连接相关 | 适配器版本要是 0.3.x（`pip show langchain-mcp-adapters`），不对就按 §3.3 重装 `[mcp]`；日志搜「MCP 常驻会话」看连接建没建起来 |
| 运行失败，`error_code` 是 `invalid_output` | 任务声明了 `output_schema`，agent 没交回合规的结构化结果：看时间线里 `submit_result` 的校验报错，放宽 schema 或在任务 / 角色提示词里写清字段 |
| 老会话续问时 agent 不记得前文 | 会话的 checkpoint 超过 `retention.checkpoints_days` 被清了，新一轮从头开始；交接摘要和记忆还在 |

## 10. 安全基线（部署后自查）

- [ ] `secrets.env` 没进任何仓库、压缩包或提交记录；文件 600，目录 700
- [ ] 8100 只绑 127.0.0.1，外部访问一律经反代，`public_url` 用 https
- [ ] root_token 只用于引导，日常用自己的密钥登录；密钥不分权限，每个调用方一把，只发给需要的人和项目，不用的及时吊销
- [ ] 设置 → 环境：生产标为受保护（只是醒目标记，不拦操作）；默认环境不是生产
- [ ] 各环境配置文件里的库、接口账户都是只读的：本机副本的进程、项目内核和同步步骤都按这份配置连库
- [ ] 服务定义 `databases` 里的账户（种子是 `CK_RO_USER`）是只读账户：`db_query` 的只读检查只是第一道
- [ ] bwrap 已安装，且平台用户能用它建命名空间（`bwrap --ro-bind / / --unshare-pid true`）
- [ ] 服务定义里的口令都写成 `${VAR}`；`GET /v1/services` 返回里看不到明文口令
- [ ] 部署密钥是只读的，在平台用户的 `~/.ssh`（600）
- [ ] `/srv/svc` 与 conda 环境只有平台用户可写；各环境配置文件只有平台用户能读
- [ ] 数据目录的 `config-history/`、`sync-backups/` 是 700（含口令）
