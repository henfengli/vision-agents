# 部署指南

内网主机的完整部署手册。部署形态是**主机 + systemd，不用容器**。

平台主进程 `agent-platform serve` 里包含：

- FastAPI 接入层：`/v1` 接口和控制台页面；
- worker：执行队列（PG 里的 runs 表）、定时、维护循环；
- agent 运行时，以及项目内核（`py` 工具用的常驻 Python 进程，是平台进程的子进程）。

外部依赖只有 PostgreSQL。业务项目的进程由平台通过 systemd 模板单元 `agent-svc@.service` 按环境启停。

业务项目在这台机器上是**本机副本**：每个服务、每个环境各一份代码和一个 venv，加上该环境的配置文件，
供 agent 读代码、读配置、查只读库、在该环境的项目 Python 里跑项目代码，需要长驻时起进程。线上服务跑在别处，不受平台管理。

---

## 1. 前置条件

| 项 | 要求 | 说明 |
|---|---|---|
| OS | Linux x86_64，systemd，polkit | 进程启停靠 polkit 授权 |
| Python | ≥ 3.11 | 平台自身用；业务项目各环境的 venv 按项目自己的要求 |
| PostgreSQL | ≥ 14 | 需要 **pg_trgm** 与 **pgvector**；pgvector 要超级用户预建，见 §3.1 |
| bubblewrap | `bwrap` 可用 | **必装**：agent 沙箱、项目内核、按环境隔离配置文件都依赖它 |
| 网络 | 内部模型 API、钉钉中继、PG 可达 | agent 沙箱默认断网，出网都收口在少数工具里 |
| 可选 | Node.js | 仓库里没有构建好的控制台、需要现场构建时用；平台 MCP 用 npx 起浏览器（§3.10）时也要 |
| git | 能访问各业务仓库 | 代码同步（内建任务 code-sync）用；部署密钥配法见 §3.8 |
| 可选 | Langfuse、Grafana | 链路追踪、主机监控；不配则对应能力自动关闭 |

## 2. 安装后的布局

下面是系统级安装（`install.sh`）的布局；用户级安装见 §3.0。

**业务服务目录**（两种安装方式相同，种子按这个写）：

```
/srv/svc/<服务>/
├── code/<环境>/                每个环境一份 git 工作目录，停在该环境部署的版本（code-sync 维护）
├── venv/<环境>/                每个环境一个 venv，按该环境代码的依赖装（运维维护，§3.7）
└── conf/<环境>/                该环境的配置文件（运维放置，不进仓库）
```

服务定义里写成 `root: /srv/svc/board/code/{env}`、`python: /srv/svc/board/venv/{env}/bin/python`、
`configs: [{template: /srv/svc/board/conf/{env}/.env, canonical: /srv/svc/board/code/{env}/.env}]`。
进程和项目内核启动时，选中环境的配置文件只读 bind 到代码目录里的固定路径，别的环境的配置遮蔽掉。

```
/opt/agent-platform/            代码（root 所有，平台只读）
├── venv/  src/  conf/  mcp_servers/  pyproject.toml
/etc/agent-platform/secrets.env 密钥（640 root:agent-svc）
/var/lib/agent-platform/        数据目录（平台唯一可写处）
├── scratch/                    agent 工作区（沙箱内唯一可写目录，bash 与项目内核共用）
├── assets/                     沉淀的方法的文件本体
└── instances/                  业务进程的启动规格与本地日志
```

| 用户 | 用途 |
|---|---|
| `agent-svc` | 平台自身（含项目内核） |
| `svc-runner` | 平台启动的业务进程 |

两个用户分开，业务进程拿不到平台的密钥。

| systemd 单元 | 内容 |
|---|---|
| `agent-platform.service` | 平台主服务，127.0.0.1:8100 |
| `agent-svc@<服务:环境:进程>.service` | 业务进程模板单元，由平台启停 |

## 3. 首次部署

### 3.0 选择安装方式

| | 系统级 `deploy/install.sh` | 用户级 `deploy/install-user.sh` |
|---|---|---|
| 需要 root | 每次安装 / 升级 | 只在开头请管理员做三件事（见下） |
| 运行用户 | `agent-svc`（平台）、`svc-runner`（业务进程），两个用户 | 部署用的那个普通用户，平台和业务进程同一个 |
| 进程启停 | 系统级模板单元 + polkit | `systemctl --user` 模板单元，不需要 polkit |
| 部署配置 | `AGENT_ENV=prod` | `AGENT_ENV=prod-user`（继承 prod，只把 `process_control.scope` 改成 `user`） |
| 业务代码位置 | `/srv/svc`（单元有 `ProtectHome=true`，放 home 读不到） | `/srv/svc` 或该用户的 home 下都行 |
| 隔离 | 业务进程拿不到平台的密钥文件（不同用户 + 遮蔽） | 靠遮蔽：密钥文件在 agent 沙箱、项目内核与业务进程里都看不到；业务进程有独立 pid 命名空间，读不到平台进程的环境变量 |

只有新建一个普通用户、没有长期 root 的场景，用用户级。管理员要先做一次：

```bash
apt-get install -y bubblewrap                      # 沙箱、项目内核与按环境起服务都依赖它
loginctl enable-linger <用户>                       # 退出登录后 systemd --user 不停
install -d -o <用户> -m 750 /srv/svc                # 业务服务目录（也可以全放在该用户 home 下，改服务定义里的路径即可）
# Ubuntu 24.04+ 默认限制非特权用户命名空间，bwrap 会失败；二选一：
sysctl -w kernel.apparmor_restrict_unprivileged_userns=0   # 并写进 /etc/sysctl.d/
# 或给 /usr/bin/bwrap 配一个允许 userns 的 AppArmor profile
```

然后用该用户经 ssh 或 `machinectl shell <用户>@` 登录（`sudo -u` 拿不到用户的 systemd 会话），在仓库根目录执行
`bash deploy/install-user.sh`。脚本会检查 bwrap、linger、secrets 与 `/srv/svc`，缺什么就提示什么。

用户级安装后的布局：

```
~/agent-platform/                代码 + venv + conf
~/.config/agent-platform/secrets.env   密钥（600）
~/.local/share/agent-platform/   数据目录（scratch / assets / instances）
~/.config/systemd/user/          agent-platform / agent-svc@ 两个用户单元
```

日常命令把 `systemctl` / `journalctl` 换成 `systemctl --user` / `journalctl --user`。下文其余步骤（数据库、密钥、
反代、登录）两种方式相同，密钥文件路径换成 `~/.config/agent-platform/secrets.env`。

### 3.1 准备数据库

```sql
-- 以 PG 超级用户执行
CREATE USER agent PASSWORD '<强密码>';
CREATE DATABASE agent_platform OWNER agent;
\c agent_platform
CREATE EXTENSION IF NOT EXISTS vector;    -- pgvector：必须超级用户预建
CREATE EXTENSION IF NOT EXISTS pg_trgm;
```

表结构在服务启动时幂等创建（`store/db.py` 是全库唯一的建表点），不需要手工迁移。

建不了 `vector` 扩展时，服务只记一条 warning，退化为关键词检索，不会启动失败。
**想用语义召回就必须预建这个扩展**，同时在部署配置里配 `model.embedding_name`。

### 3.2 部署配置

部署配置只有「平台怎么跑起来」的参数，放在 `conf/` 里：

| 文件 | 内容 |
|---|---|
| `conf/base/common.yaml` | 所有机器共享的默认值：模型、执行队列（`worker`）、项目内核（`kernel`）、进程控制、Langfuse、Grafana、平台 MCP（`mcp_servers`） |
| `conf/env/prod.yaml` | 生产机的差异，深合并到上面：`db_dsn`、`root_token`、`public_url`、`model.tokens`、`process_control.backend: systemd` |
| `conf/env/dev.yaml` | 开发机的差异 |

配置里的 `${VAR}` 从环境变量（`secrets.env`）取值，**没设置时启动直接报错**。
配置问题在启动时就暴露，不会带病运行。

执行队列与项目内核的两节：

| 键 | 默认 | 说明 |
|---|---|---|
| `worker.max_concurrent_runs` | 10 | 一个 worker 同时执行几个运行；满了就不再认领，排队的按创建时间先到先得 |
| `kernel.idle_minutes` | 30 | 项目内核空闲多久回收 |
| `kernel.max_kernels` | 8 | 同时最多几个项目内核（每个 会话×服务×环境 一个），超了先回收最久没用的 |

`serve` 默认同进程跑 worker。要分开时用 `serve --no-worker` 加单独的 `agent-platform worker`；多开 worker 也安全：
认领用 `FOR UPDATE SKIP LOCKED`，定时带幂等键，不会重复执行或重复触发。

服务、角色、任务，以及平台配置（环境、审批、通知、记忆、进程）**都不在这里**。
它们存在库里，在控制台编辑。`conf/seeds/` 只在库里还没有对应对象时播种一次，之后改种子文件不会覆盖库里的内容。
种子与库里的定义不一致时，启动日志会提示。

### 3.3 执行安装

```bash
sudo bash deploy/install.sh          # 生产机（AGENT_ENV=prod）
sudo bash deploy/install.sh dev      # 开发机
```

脚本依次完成以下动作：

1. 建 `agent-svc`、`svc-runner` 两个用户；
2. 拷贝代码到 `/opt/agent-platform`，建数据目录；
3. 构建控制台（仓库里没有 dist 且装了 node 时才做）；
4. 建 venv 并安装；
5. 检查 bwrap 和 secrets.env；
6. 安装 systemd 单元与 polkit 规则，然后启动。

这时 secrets.env 还没放，服务起不来，**这是预期的**；下一步放好后重启即可。

内网不通外网时，先配 pip 镜像：执行 `install.sh` 前设置环境变量 `PIP_INDEX_URL`。

可选依赖不随 `install.sh` 装。服务 MCP（服务定义里的 `mcp`）要 `mcp` 这一组，仓库自带的 dagster MCP（`mcp_servers/dagster_mcp.py`，
种子 dagster 服务在用）另需 `dagster-mcp`。装进平台 venv 即 `pip install 'agent-platform[mcp,dagster-mcp]'`：

```bash
sudo /opt/agent-platform/venv/bin/pip install '/opt/agent-platform[mcp,dagster-mcp]'
# 用户级：~/agent-platform/venv/bin/pip install "$HOME/agent-platform[mcp,dagster-mcp]"
```

升级重跑 `install.sh` 不会卸掉已装的可选依赖。

### 3.4 放置密钥并重启

```bash
sudo tee /etc/agent-platform/secrets.env > /dev/null <<'EOF'
# 注释只能单独成行：systemd 的 EnvironmentFile 不认行尾注释，会把它当成值的一部分
# 引导密钥：首次登录、创建 API 密钥；权限最高，务必够长
AGENT_ROOT_TOKEN=...
# 3.1 的 PG 密码
AGENT_DB_PASSWORD=...
# 内部模型 API token；第二个用于并发池轮换，只有一个就填同一个
MODEL_TOKEN_A=sk-...
MODEL_TOKEN_B=sk-...
# 种子通知渠道 default 用（设置 → 通知 里也能改）
DINGTALK_ACCESS_TOKEN=...
# 种子里各服务只读库的口令（服务定义里写 ${VAR}，连库时才取值）
BOARD_RO_PASSWORD=...
DAGSTER_RO_PASSWORD=...
# 代码同步用的只读部署密钥（§3.8）；值里有空格，必须加引号
GIT_SSH_COMMAND="ssh -i /etc/agent-platform/deploy_key -o UserKnownHostsFile=/var/lib/agent-platform/known_hosts -o StrictHostKeyChecking=accept-new"
# 可选
LANGFUSE_PUBLIC_KEY=pk-...
LANGFUSE_SECRET_KEY=sk-...
EOF
sudo chown root:agent-svc /etc/agent-platform/secrets.env
sudo chmod 640 /etc/agent-platform/secrets.env
sudo systemctl restart agent-platform
```

### 3.5 验证

```bash
systemctl status agent-platform --no-pager
curl -s http://127.0.0.1:8100/healthz        # {"ok": true, "version": "8.0.0", "profile": "prod"}
sudo -u agent-svc AGENT_ENV=prod AGENT_CONF=/opt/agent-platform/conf \
  bash -c 'set -a; . /etc/agent-platform/secrets.env; /opt/agent-platform/venv/bin/agent-platform check'
# 配置 prod 正常；环境 prod、test、dev（默认 test）；服务 N 个，任务 N 个
journalctl -u agent-platform -n 100 --no-pager  # 不应有 ERROR；应有「执行队列已启动」
```

首次启动会自动做两件事：

1. 建表；
2. 播种：平台配置、服务、角色、任务，只写库里还没有的。

定时由 worker 每轮读最新定义按 cron 触发，不需要额外同步。

### 3.6 首次登录与发密钥

1. 打开控制台的 `/login`，用 `AGENT_ROOT_TOKEN` 登录，「你的名字」填自己。这个名字会写进版本台账与审批记录。
2. 进入 设置 → API 密钥，给每个调用方各建一把：
   - 管理员：建 `admin` 范围的密钥，以后用它登录，不再用 root_token；
   - 业务项目（如 `board-backend`）：建 `run` 范围，最好限定服务与环境；
   - Dagster 回调（`dagster-sensor`）、GitLab Webhook（`gitlab`）：各建 `run` 范围的密钥。
3. 进入 设置 → 环境 / 审批 / 通知，确认平台配置。然后在各服务的「环境」标签里，确认这个服务在哪些环境启用。

审批默认关闭（`required_in: off`）：各环境配置里都是只读账户、文件系统只读，agent 做不了真正危险的事。
以后让 agent 执行变更类任务时，在 设置 → 审批 改成 `protected`（只在受保护环境审批）或 `all`。

冒烟测试：

```bash
pip install ./sdk
export AGENT_URL=http://127.0.0.1:8100 AGENT_KEY=<刚建的密钥>
agent-chat board --env test        # 问一句，看到工具调用与回答即可
```

### 3.7 放置业务代码、venv 与配置

每个服务、每个环境：

```bash
# 配置文件：运维放置，平台与业务进程能读，别人不能读。库、接口账户用只读的
install -d -o agent-svc -g svc-runner -m 750 /srv/svc/board/conf/{prod,test,dev}
install -o agent-svc -g svc-runner -m 640 board.test.env /srv/svc/board/conf/test/.env
```

代码不用手工拉：服务定义里配好 `repo` 和各环境的 `ref`，在控制台 服务 → 概览 → 同步代码，
或者 `POST /v1/runs {"task": "code-sync", "service": "board", "env": "test"}`。目录不存在会自动 clone。
GitLab 部署事件接通（§3.9）后，部署成功会自动把对应环境切到刚部署的提交。

venv 按环境建，代码同步之后按该环境代码的依赖装，然后在服务定义里填 `python`
（`/srv/svc/<服务>/venv/{env}/bin/python`；某个环境特殊就在 `envs.<环境>.python` 单独写）：

```bash
install -d -o agent-svc -g svc-runner -m 750 /srv/svc/board/venv
sudo -u agent-svc python3 -m venv /srv/svc/board/venv/test
sudo -u agent-svc /srv/svc/board/venv/test/bin/pip install -r /srv/svc/board/code/test/requirements.txt   # 按项目自己的方式装依赖
```

项目内核与业务进程都用这个解释器，内核的驱动只用标准库，venv 里不用额外装东西。
平台不维护 venv：代码同步切到的版本依赖有变时，要重装该环境的 venv。用户级安装去掉 `sudo -u agent-svc`。

### 3.8 代码同步的部署密钥

平台用户要能读各业务仓库。建一把只读部署密钥，加到各仓库（GitLab → 仓库 → Deploy keys）：

```bash
ssh-keygen -t ed25519 -N '' -f deploy_key
sudo install -o agent-svc -g agent-svc -m 600 deploy_key /etc/agent-platform/deploy_key   # ssh 要求私钥只有属主能读
```

secrets.env 里的 `GIT_SSH_COMMAND`（§3.4）让 git 用这把密钥。`/etc/agent-platform` 在 agent 沙箱、项目内核和业务进程里都被遮蔽。
用户级安装直接用该用户的 `~/.ssh`（同样被遮蔽），不用配 `GIT_SSH_COMMAND`。

### 3.9 接外部事件

| 来源 | 配法 |
|---|---|
| Dagster | `run_failure_sensor` 里 `POST {public_url}/v1/events/dagster`，请求头 `Authorization: Bearer <dagster-sensor 的密钥>`，请求体 `{run_id, asset_key, error, env}` |
| GitLab | 项目 → Webhooks，地址 `{public_url}/v1/events/gitlab`，Secret token 填 gitlab 那把密钥，勾选 Deployment events |
| 其他系统 | `POST /v1/events/webhook`，事件名放请求头 `X-Event` |

接通之后，哪个事件触发哪个任务，在任务的「触发」里声明。种子任务 `code-sync` 已经声明了三个服务的部署事件，
GitLab 项目名不同的话改它的 `filter.project`。GitLab 部署的 `environment` 要和平台的环境名一致（prod / test / dev）。

### 3.10 MCP（可选）

MCP 工具分两种，都要先装 `[mcp]`（§3.3）：

| | 平台 MCP | 服务 MCP |
|---|---|---|
| 放什么 | 通用能力，比如浏览器 | 某个服务特有的能力，比如 dagster 的运行记录 |
| 写在哪 | 部署配置 `mcp_servers`（`conf/`），改了要重启 | 服务定义的 `mcp`（控制台），写库即生效，下次运行自动重连 |
| 怎么用上 | 角色的 `tools` 里写 `"mcp:<名字>"`、工具名或 `"*"` | 运行在该服务上自动出现 |

平台 MCP 以浏览器为例（种子角色 `qa_engineer` 用 `"mcp:browser"`），写进 `conf/env/prod.yaml`：

```yaml
mcp_servers:
  browser:
    transport: stdio
    command: npx
    args: ["-y", "@playwright/mcp@0.0.83", "--headless", "--isolated", "--output-dir", "/var/lib/agent-platform/scratch"]
```

- 需要 Node.js；内网不通外网时先在平台用户下把 `@playwright/mcp` 和浏览器装好，或配 npm 镜像。
  系统级单元全盘只读、只有数据目录可写，npx 的缓存目录要可写；更稳妥的是预装好，把 `command` 换成装好的可执行文件。
- 用户级安装把 `--output-dir` 换成 `~/.local/share/agent-platform/scratch`。
- 页面地址来自服务定义的 `urls`（如 board 的 `site`、`local`），agent 在运行环境提示里看得到。
- 没配 `browser` 时，角色里的 `"mcp:browser"` 被忽略，只记一条 warning。

服务 MCP 以种子 dagster 为例：`mcp.dagster` 用平台解释器跑仓库自带的 `mcp_servers/dagster_mcp.py`，按运行的环境连该环境线上部署的
Dagster（`urls.deployed`，只配了 prod / test）。要求平台机器能访问这两个地址，平台 venv 装了 `[mcp,dagster-mcp]`。
连接配置里的口令写 `${VAR}`，放 secrets.env，连接时才取值。

验证：`GET /v1/services/dagster/tools?reload=true`，`tools` 里应有 5 个工具，`failed` 为空。

## 4. 反向代理

主服务只监听 `127.0.0.1:8100`，内网用户经反向代理访问：

```nginx
server {
    listen 443 ssl;
    server_name agent.internal;              # 与 public_url 一致
    location / {
        proxy_pass http://127.0.0.1:8100;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 3600s;            # SSE：对话与运行推流
        proxy_buffering off;                 # SSE 需要实时冲刷
    }
}
```

- `public_url` 必须与最终访问地址一致：通知里的跳转链接用它拼；它是 https 时，登录 cookie 带 Secure 标记。
- SSE 端点（`/v1/chat`、`/v1/runs/{id}/stream`）要求反代关闭缓冲、拉长超时。

## 5. 业务进程的启停

平台用 systemd 模板单元按「服务 × 环境」启停业务进程（`process_control.backend: systemd`）：

```
agent-svc@board:test:server.service
  → svc-runner 用户
  → python -m agent_platform.services.svcrun board:test:server
  → 读 /var/lib/agent-platform/instances/board:test:server.json（平台启动前写好）
  → bwrap：把 test 环境的配置文件 bind 到服务读的固定路径，其他环境的同名文件遮蔽
  → exec 业务进程
```

- 平台用户 `agent-svc` 通过 polkit 规则（`deploy/50-agent-svc.rules`）**只能**启停 `agent-svc@*.service`，管不了别的单元。
- `svc-runner` 需要能读业务项目目录（代码、venv、配置）；目录权限按实际部署调整。
- 服务在该环境启用（服务 → 环境）就能起进程；cmd 里可以写 `{python}`，换成该环境的解释器。
- 每次启动带租约，到期自动停止。默认值与上限在 设置 → 进程；单个进程可以在服务定义里覆盖 `lease_hours`。
- 设置 → 审批 打开后（默认关闭），受保护环境（`protected`）或所有环境（`all`）的启停要先审批。
- 业务进程里遮蔽：其他环境的配置文件、`hidden_paths`（默认是平台密钥目录与运行用户的 `~/.ssh` 等凭据），有独立的 pid 命名空间。
- 开发机用 `backend: local`，进程是平台的子进程，日志在 `instances/` 下。
- 用户级安装（`process_control.scope: user`）用 `systemctl --user` 管理 `agent-svc@*.service`，日志 `journalctl --user -u 'agent-svc@board:test:*'`。

**项目内核**（`py` 工具）不走 systemd：它是平台进程的子进程（系统级安装时以 `agent-svc` 运行），每个 会话×服务×环境 一个。
用该环境的解释器、在该环境的部署目录里跑，配置文件按和起进程同一份规格 bind 到固定路径；
文件系统只读、scratch 可写、网络照常，密钥目录遮蔽，独立 pid 命名空间，环境变量只带白名单与服务的 `env_vars`。
空闲回收与数量上限见 §3.2 的 `kernel` 节。没有 bwrap 时直接在宿主上跑，只适合开发机。

## 6. 升级与回滚

```bash
git pull
sudo bash deploy/install.sh          # 幂等：重拷代码、重装、重启
```

- 表结构变更随启动自动应用，只增不减，所以代码回滚是安全的。
- 定义和平台配置在库里不在包里，升级不会动它们。数据层面的「回滚」走控制台：
  - 定义、平台配置：版本恢复；
  - 记忆：内容历史恢复。
- 从 v5 升级：先 `pg_dump` 备份，再运行 `python scripts/migrate_v5.py`（幂等），然后安装新版本。
- 从 v6 升级到 v7：不需要迁移脚本。启动时自动给 runs 补 `resume`、`worker`、`heartbeat_at` 列，建 `replays`、`replay_items` 表；
  旧的 `artifacts` 表会留着，不再使用。另外：
  1. 升级前让在跑的运行跑完。v6 时在跑的运行没有心跳，v7 的维护循环不会替它们收尾，会一直停在 running / awaiting_approval，只能在控制台取消。
  2. 库里的 设置 → 审批 不会被种子改动：v6 播种的是 `protected`，要和新装一样默认关闭，改成 `off`。
  3. 库里 `form: graph` 的任务读不出来（启动日志 ERROR，列表里不出现）：删掉，或改成单角色任务。
  4. 各服务按 §3.7 建好每个环境的 venv，在服务定义里填 `python`；不填就用 `python3`。
- 库结构从 v7 升到 v8（`store/db.py` 的 `SCHEMA_VERSION = 8`）：不需要迁移脚本。
  1. 启动时自动把旧的 `cases` 表并进 `knowledge`（`kind=lesson`，key = `lesson:<指纹>`），幂等，重启多少次都不会重复插入。
     旧表留着不再使用，`/v1/cases` 端点已删除；回滚到 v7 代码时旧表还在，但 v8 期间记下的教训只在 `knowledge` 里。
  2. 库里的定义不会被种子改动。想要通用角色 `generalist`、通用入口任务 `ask`、服务的 `urls` / `mcp`、角色的 `subagents`，
     在控制台加，或参考 `conf/seeds/` 手工建。没有 `ask` 时，`POST /v1/runs` 不写 `task` 会返回 `unknown_task`。
  3. 角色继承规则变了：子角色写了 `tools`（非空）就整体替换父角色的（以前取交集）；`subagents` / `service_tools` 是 `null`
     （没写）就跟随父角色，`subagents: []` 表示明确不要子代理。库里写了 `extends` 的角色，用 `GET /v1/roles/{name}/resolved` 核对一下生效的工具。
  4. 之前因为 dagster 种子的 YAML 引号问题没播上的对象（dagster 服务，以及因此没建成的、引用它的任务），升级后启动时会补种：
     种子按名字判断，这些名字在库里从没出现过，所以会补上。
  5. 要用服务 MCP（种子 dagster 的 `mcp`），按 §3.3 装 `[mcp,dagster-mcp]`。
- 已有库升级到「每环境一份代码」的布局，库里的定义不会被种子改动，要手工确认两件事：
  1. 各服务的 `root` / `configs` 改成 `{env}` 布局并配 `repo`、`ref`（不改也能用，只是三个环境共用一份代码）。
  2. 早期播种时只读库口令已被展开成明文存进库：接口现在会打码，但建议改成 `${VAR}` 并把口令放 secrets.env。

## 8. 日常运维

```bash
journalctl -u agent-platform -f                 # 平台日志
journalctl -u 'agent-svc@board:test:*' -f       # 某服务某环境的业务进程日志
curl -s 127.0.0.1:8100/healthz
systemctl restart agent-platform                # 只有改了 conf/ 才需要重启
```

- **定义和平台配置**在控制台改，写库即生效，不用重启。
- **部署配置**（`conf/`）只在启动时读，改了要重启。
- **重启平台**时执行中的运行记为 `interrupted`，可以在运行详情续跑。
- **密钥轮换**：
  - API 密钥：控制台新建一把 → 调用方换上 → 吊销旧的；
  - root_token、模型 token：改 secrets.env 后重启。

## 9. 故障排查

| 现象 | 排查 |
|---|---|
| 启动即退出 | `journalctl -u agent-platform -n 200`：多半是 secrets.env 缺变量（`${VAR}` 插值报错）或 PG 连不上。`agent-platform check` 能单独验证配置与数据库 |
| 日志提示 vector 扩展 | pgvector 未预建：超级用户 `CREATE EXTENSION vector` 后重启 |
| 日志告警 bwrap | 安装 bubblewrap，不装则沙箱与配置隔离失效 |
| 运行一直 queued | 没有 worker 在跑：`serve` 加了 `--no-worker` 就要另起 `agent-platform worker`，日志里应有「执行队列已启动」。也可能并发满了（`worker.max_concurrent_runs`），看有没有长时间 running 的运行 |
| 运行失败，`error_code` 是 `orphaned` / `interrupted` | 执行它的进程崩溃或重启了，运行详情里续跑 |
| 定时没触发 | 控制台 → 任务 → 概览，看「下次定时」；任务或触发器是否停用；服务在该环境是否启用；同一触发器上一次还没跑完会跳过；停机期间错过的不补 |
| 调用返回 `service_env_disabled` 等 | 原因码与解法见接口文档 §1.4 |
| `py` 报找不到解释器 / 部署目录不存在 | 服务定义的 `python` 指向该环境的 venv 并建好（§3.7）；部署目录不存在就先同步代码 |
| 代码同步失败（`code_sync_failed`） | 运行详情里有 git 的原文：有未提交改动就先处理；找不到分支看服务 → 环境 → 跟踪；拉不下来检查部署密钥（§3.8） |
| bwrap 报 `setting up uid map: Permission denied` 一类错误 | 非特权用户命名空间被限制（Ubuntu 24.04+ 的 AppArmor），见 §3.0 |
| 启动进程报 `start_failed` | `journalctl -u agent-svc@<服务:环境:进程>`；检查 polkit 规则是否安装、`svc-runner` 能否读业务目录 |
| 登录后又跳回登录页 | cookie 被拦：确认经反代访问、反代不改写 Set-Cookie；`public_url` 是 https 时必须走 https |
| 收不到钉钉 | 设置 → 通知 → 渠道「发送测试」；再看通知规则是否覆盖该事件 |
| SSE 首字节慢或断开 | 反代缓冲或超时：`proxy_buffering off`，并拉长 `proxy_read_timeout` |
| 服务的 MCP 工具没出现 | `GET /v1/services/<服务>/tools?reload=true` 看 `failed`；平台 venv 装了 `[mcp]`（dagster 的还要 `[dagster-mcp]`）；`mcp.envs` 里列了该环境、服务在该环境启用；`${VAR}` 在 secrets.env 里有值；日志搜「MCP 连接」 |
| 平台 MCP（浏览器）没出现 | 改了 `mcp_servers` 要重启；装了 `[mcp]`；`npx` 能拉到包；角色写了 `"mcp:browser"`。启动日志有「平台 MCP 加载 N 个工具」 |

## 10. 安全基线（部署后自查）

- [ ] `secrets.env` 权限 640、属主 root:agent-svc，没进任何仓库、压缩包或提交记录
- [ ] 平台以 `agent-svc`、业务进程以 `svc-runner` 运行；`/opt/agent-platform` 属主 root、只读
- [ ] 单元加固（`ProtectSystem=strict`、`NoNewPrivileges`、`PrivateTmp`）生效，不要删
- [ ] polkit 规则只放行 `agent-svc@*.service`
- [ ] 8100 只绑 127.0.0.1，外部访问一律经反代，`public_url` 用 https
- [ ] root_token 只用于引导；日常用 admin 密钥登录；每个调用方一把 run 密钥，并限定服务与环境
- [ ] 设置 → 环境：生产标为受保护；默认环境不是生产
- [ ] 各环境配置文件里的库、接口账户都是只读的：本机副本的进程和项目内核都按这份配置连库
- [ ] 设置 → 审批：默认关闭；打开后危险命令正则按需扩充
- [ ] bwrap 已安装，且平台用户能用它建命名空间（`bwrap --ro-bind / / --unshare-pid true`）
- [ ] 服务定义里的口令都写成 `${VAR}`；`GET /v1/services` 返回里看不到明文口令
- [ ] 部署密钥是只读的，`/etc/agent-platform/deploy_key` 600 agent-svc
- [ ] `/srv/svc` 2750 agent-svc:svc-runner，各环境配置文件 640
