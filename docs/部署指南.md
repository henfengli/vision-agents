# 部署指南

内网主机的完整部署手册。部署形态是**同机部署**：平台装在业务项目实际部署的主机上，用部署这些项目的那个 Linux 用户运行
（`deploy/install-user.sh`，systemd --user）。不另起 agent 机器，也不新建用户。生产机上这个用户是 `vision-service`
（主机 `nmg-saturn-home1`，172.24.16.100）。示例按 Rocky Linux 9，别的发行版换包管理器即可。

同机部署带来的好处：

- agent 读的是线上正在跑的代码目录，用的是线上的 conda 环境；
- agent 能看真实的应用日志、nginx 日志、docker 容器日志和主机状况。

平台**不做**这些事：拉代码、同步代码、装依赖、执行 collectstatic、启停业务进程、跟踪配置模板的变化。
代码和环境照旧由项目原来的部署流程维护，平台只读。

每台主机装一个 agent 服务，本机的 `local.yaml` 写它负责的业务环境（`env`），同一环境的项目分在几台上时再写本机部署了哪些服务
（`services`）。各台共用一个 PostgreSQL 和一套控制台。平台主进程 `agent-platform serve` 里包含：

- FastAPI 接入层：`/v1` 接口和控制台页面；
- worker：执行队列（PG 里的 runs 表，只认领本机负责的环境和服务的运行）、定时、维护循环；
- agent 运行时，以及项目内核（`py` 工具用的常驻 Python 进程，跑在沙箱里）。

外部依赖只有 PostgreSQL。模型是 Kimi 开放平台（OpenAI 兼容）。

文中凡是标了 **【占位】** 的值都是推测，部署前按括号里的提示核对；全部占位汇总在文末「【占位】清单」。

## 1. 前置条件（每台主机）

| 项 | 要求 | 说明 |
|---|---|---|
| 用户 | 部署业务项目的那个普通用户 | 生产机是 `vision-service`；两台测试机【占位：确认 172.24.24.136、172.21.0.45 上部署项目的用户名】。要开 linger（§3.0） |
| OS | Linux x86_64，systemd（RHEL / Rocky 9、Ubuntu 22.04+ 都行） | |
| Python | ≥ 3.11，只给平台自己用 | Rocky 9 自带的 python3 是 3.9，见 §3.0 |
| 业务项目 | 已按原来的方式部署在这台主机上 | 代码目录、解释器、配置路径、日志位置写进服务定义（§3.7）；平台不改它们 |
| PostgreSQL | ≥ 14，各台都能连到同一个库 | 需要 **pg_trgm**；pgvector 可选（§3.1） |
| bubblewrap | `bwrap` 可用，普通用户能建命名空间 | **必装**：没有它平台拒绝执行模型写的代码（§5） |
| systemd 用户 scope | 有 `systemd-run`，memory / pids 控制器委派给了用户（cpu 也委派时 `CPUWeight` 才生效） | 项目内核与 bash 的内存上限靠它（§5） |
| git | 建议有 | 只在本机读代码目录的提交（`service_info`、记忆的代码引用核对）；平台不拉代码 |
| ripgrep | 可选 | agent 的 `grep` 工具在沙箱里看得到 `rg` 就用它（快，跳过 .gitignore 里的），没有就用系统的 `grep -rnIE`。装系统包 `ripgrep`（`/usr/bin/rg`）即可；放在 home 下的 `rg` 要在平台进程的 PATH 上，且所在目录写进 `home_allow`，否则沙箱里看不到、照样退回 grep |
| docker | 读容器日志的主机上，该用户能执行 `docker ps` | vision-dagster 的日志在容器里（§3.8） |
| 网络 | 平台进程能连：Kimi 开放平台（`api.moonshot.cn`）、钉钉中继、共用的 PG、本机负责的服务登记的只读库（种子：ClickHouse 国内生产 172.168.0.125、国内测试 172.24.17.66 的 8123）、线上 Dagster（MCP 用） | 沙箱不限网络（§5.7） |
| Node.js | 构建控制台用：构建产物不进仓库，安装脚本每次按当前代码构建（§3.3） | 没有 Node 的主机保留上一次装好的，或先把别处构建好的 `src/agent_platform/webui/dist` 拷进仓库再装；控制台主机上一定要有一份。平台 MCP 用 npx 起浏览器（§3.10）时也要 |
| 可选 | OTLP 后端（Jaeger、Tempo、各家 APM） | 链路追踪；不配则自动关闭 |

## 2. 架构与布局

### 2.1 主机与环境

| 主机 | `local.yaml` | 负责的服务×环境 |
|---|---|---|
| 生产机 `nmg-saturn-home1`，172.24.16.100 | `env: prod` | vision-dagster prod（docker）、vision-board prod（nginx + 源码）、vision-web prod【占位：确认 vision-web 生产部署在这台】 |
| 测试机 172.24.24.136 | `env: test`，`services: [vision-dagster]` | vision-dagster test |
| 测试机 172.21.0.45 | `env: test`，`services: [vision-board, vision-web]` | vision-board test、vision-web test【占位：确认 vision-web 测试部署在这台】 |

```
     浏览器 / 业务项目 / Dagster、GitLab 回调
                     │ https（public_url）
                     ▼
        控制台主机【占位：哪一台对外】
   ┌─────────────┬───────────────┬──────────────┐
   │ 生产机      │ 测试机 dagster│ 测试机 board │   每台一个 agent 服务，都跑 worker、定时、维护
   │ env: prod   │ env: test     │ env: test    │
   └──────┬──────┴───────┬───────┴──────┬───────┘
          └──────────────┼──────────────┘
                         ▼
          PostgreSQL（共用一个）【占位：地址】
```

规则：

- **负责哪个环境**写在每台主机自己的 `~/.config/agent-platform/local.yaml`（§3.2）：`env` 是这台负责的业务环境（`prod` / `test`，
  和用户单元里的 `AGENT_ENV` 无关）；同一个环境的项目分在几台上时（test：dagster 一台、board 一台），再写 `services`（本机部署了哪些服务）。
  服务定义里不写部署在哪台。
- **谁来执行**：worker 只认领 `env` 和自己相同、服务在自己 `services` 里（没写 `services` 就是该环境的全部服务）的运行。
  平台任务（不关联服务）由该环境的任意一台执行。
- **那台没在跑时**：提交照常受理，运行停在 `queued`，那台的 agent 服务起来后接着执行；不会被拒，也不会落到别的主机上。
- **定时**在每台都跑，幂等键保证每次触发只建一条运行；同一触发器上一次还没跑完（排队或运行中）就跳过这一次。
  **维护循环**（孤儿运行回收、数据保留）也在每台都跑，都是幂等的；工作目录（scratch）各台清自己的。
- **模型并发**（Kimi 账号：同时 3 个请求在途）经 PG 在各台之间共用（§3.2）。
- **共用一套控制台**：只有对外的那台打开 `listen`（§4）；`public_url` 指向它，各台发出的通知里的链接都用它。
- **单机 / 开发机**（`AGENT_ENV=dev`）：`env` 不写就认领一切；`conf/env/dev.yaml` 另设 `require_sandbox: false`（没有 bwrap 也让代码跑，不隔离）。

### 2.2 每台主机上的布局

```
~/agent-platform/                      平台代码（src、conf、mcp_servers、pyproject.toml）+ venv，安装脚本每次整份替换
~/.config/agent-platform/              700，沙箱里看不到
├── secrets.env                        密钥（600，§3.4）
├── local.yaml                         本机的部署配置（env、services 等，不进仓库，§3.2）
└── tls/                               控制台主机自己做 HTTPS 时的证书（§4）
~/.local/share/agent-platform/         数据目录（AGENT_DATA_DIR）
├── scratch/                           工作区：沙箱里唯一可写的目录。work/<会话键>/ 是每个 会话×服务×环境 的工作目录（bash 的当前目录、
│                                      两边的 $SCRATCH）；db_query 的大结果在它下面的 queries/<run_id>/；
│                                      超过 retention.scratch_days（默认 7 天）没动过的由维护循环清掉
├── assets/                            沉淀的方法的文件本体（在本机上沉淀的）
└── agent-conf/                        700：给 agent 用的只读版配置在本机的落地文件（只有受保护的环境，即生产；<服务>/<环境>/ 下，
                                       文件 600），起项目内核时 bind 到项目读配置的路径（§3.7）
~/.config/systemd/user/                agent-platform.service、agent.slice 两个用户单元
```

业务项目的目录（比如 `~/deploy/vision-board`、`~/miniconda3/envs/vision-board`【占位：按实际】）是项目自己的，平台只读。

| systemd 用户单元 | 内容 |
|---|---|
| `agent-platform.service` | 平台主服务，`AGENT_ENV=prod`，默认听 127.0.0.1:8100（部署配置 `listen`，§4）。平台进程不在 agent.slice 里，不设上限，slice 满了也不会杀到它；PATH 里 `~/.local/bin` 排在最前 |
| `agent.slice` | 模型写的代码（项目内核、bash）合计的内存总上限：`MemoryMax=64G`、`MemorySwapMax=0`；`CPUWeight=20`（CPU 不设上限，只在线上服务也要 CPU 时让着它们，cpu 控制器委派给用户才生效）；`TasksMax=16384`。生产机和测试机内存一样，所有主机同一个值（§5.5） |
| 临时 scope | 每个项目内核、每条 bash 命令运行时各起一个 `systemd-run --user --scope`，都在 agent.slice 下（§5） |

## 3. 首次部署

顺序：准备前提（每台）→ 建库（一次）→ 部署配置 → 每台安装 → 放密钥 → 验证 → 登录发密钥 → 核对服务定义、填生产给 agent 的配置 →
日志权限 → 接外部事件 → MCP → 只读库。

### 3.0 准备前提

下面都以部署用户的身份在每台主机上做。先看系统里已经有什么：

```bash
rpm -q bubblewrap git                       # 装没装（Debian / Ubuntu：dpkg -l bubblewrap git）
cat /proc/sys/user/max_user_namespaces      # 大于 0 才能用 bwrap；RHEL / Rocky 9 默认就是
loginctl show-user $USER -p Linger          # linger
cat /sys/fs/cgroup/user.slice/user-$(id -u).slice/user@$(id -u).service/cgroup.controllers   # 要有 memory、pids；cpu 只影响 CPUWeight
command -v systemd-run
docker ps >/dev/null && echo docker 可用     # 读容器日志的主机才需要
ls -ld /var/log/nginx; ls -l /var/log/nginx/ # 读 nginx 日志的主机才需要（§3.8）
systemctl is-active firewalld               # active 的话，对外端口要管理员放行
```

**平台自己的 Python**（≥ 3.11，和业务项目的环境无关）。安装脚本按这个顺序找：`python3.13`、`python3.12`、`python3.11`、
`~/miniforge3/bin/python3`、`~/miniconda3/bin/python3`、`~/anaconda3/bin/python3`，也可以 `PYTHON=/path/to/python3` 指定。
该用户已有的 conda 的 base 是 3.11 以上就直接能用（平台建自己的 venv，不往 base 里装东西）。不够时任选一种：

```bash
~/miniconda3/bin/conda create -y -n agent-platform python=3.12       # 在已有的 conda 里新建一个环境，不碰业务环境
PYTHON=~/miniconda3/envs/agent-platform/bin/python3 bash deploy/install-user.sh
# 或者把 Miniforge 装到 ~/miniforge3（只给平台用，不需要 root）：
# bash Miniforge3-Linux-x86_64.sh -b -p ~/miniforge3
```

**linger**（退出登录后 systemd --user 照常运行）：安装脚本会自己试 `loginctl enable-linger`。

**bubblewrap**：系统里有就跳过。没有时请管理员 `dnf install -y bubblewrap`；不想找管理员，也可以自己从系统包里取出 bwrap
（RHEL 系的 bwrap 不是 setuid，靠用户命名空间，普通用户能直接用）：

```bash
mkdir -p ~/.local/bin /tmp/bw && cd /tmp/bw
dnf download bubblewrap                                  # 只下载不安装，普通用户可以执行
rpm2cpio bubblewrap-*.rpm | cpio -idm ./usr/bin/bwrap
install -m 755 usr/bin/bwrap ~/.local/bin/bwrap
```

平台的用户单元和安装脚本都把 `~/.local/bin` 放在 PATH 最前面。

**一定要管理员的**，都是一次性的，没有就跳过：

| 事 | 什么时候需要 | 怎么做 |
|---|---|---|
| 防火墙放行控制台端口 | 控制台主机上 `firewalld` 是 active | `firewall-cmd --permanent --add-port=8100/tcp && firewall-cmd --reload` |
| 防火墙放行 PG 端口 | PG 所在主机，别的主机要连它 | 按来源放行，每台一条：`firewall-cmd --permanent --add-rich-rule='rule family=ipv4 source address=172.24.24.136/32 port port=5432 protocol=tcp accept'`，然后 `firewall-cmd --reload` |
| 装 bubblewrap、git | 系统里没有（bwrap 也可以自己取，见上） | `dnf install -y bubblewrap git` |
| 开 linger | `loginctl enable-linger` 报 Access denied（本机 polkit 收紧了） | `loginctl enable-linger <用户>` |
| 调大用户命名空间 | `/proc/sys/user/max_user_namespaces` 是 0 | `sysctl -w user.max_user_namespaces=15000`，并写进 `/etc/sysctl.d/`。Ubuntu 24.04+ 是 `kernel.apparmor_restrict_unprivileged_userns=0` |
| 委派 memory / pids / cpu | `cgroup.controllers` 里没有 `memory`（安装脚本会提示） | 建 `/etc/systemd/system/user@.service.d/delegate.conf`，内容见下，然后 `systemctl daemon-reload`。memory、pids 是内存与进程数上限要的；cpu 只影响 agent.slice 的 `CPUWeight` |
| nginx 日志的读权限 | 服务定义里登记了 nginx 日志，部署用户读不了 | §3.8 |
| 系统日志的读权限 | 服务定义里登记了系统单元的 `journal:` 日志 | `usermod -aG systemd-journal <用户>`，§3.8 |
| PG 建用户、库、扩展 | 用现成的 PG | §3.1 |
| HTTPS 证书 | 控制台主机直接做 HTTPS | 内部 CA（FreeIPA）按主机名签，§4 |
| 装 nginx、用 443 | 只在要走 443 或统一网关时 | §4 |

`delegate.conf`：

```ini
[Service]
Delegate=memory pids cpu
```

改完重跑一次安装脚本，看「没有把 memory 控制器委派给用户」的提示还在不在。还在的话，要等该用户的 `user@<uid>.service` 重启后才生效：
它会连带重启这个用户的全部 systemd --user 服务，挑维护窗口做，或者等下次重启主机【占位：按实际验证是否需要重启；先确认线上进程有没有跑在该用户的 systemd --user 里】。

另外要找其他人的：只读库账号（DBA，§3.11）、钉钉机器人 token、Kimi 开放平台的 key。平台不再需要 GitLab 的拉取权限：
git 只用来在本机读代码目录的提交。

### 3.1 数据库（各台共用一个）

各台连同一个库。`conf/env/prod.yaml` 里是：

```yaml
db_dsn: "postgresql://agent:${AGENT_DB_PASSWORD}@${AGENT_DB_HOST}:5432/agent_platform"
```

地址由每台 secrets.env 里的 `AGENT_DB_HOST` 给（PG 所在的那台主机上可以写 127.0.0.1）。PG 放在哪台、地址是什么【占位：确认】；
三台主机所在网段（172.24.16.x、172.24.24.x、172.21.0.x）之间 5432 端口要通【占位：确认网络可达】。PG 停了，各台都没法工作，按这个级别选机器。

**用现成的 PG**（请它的管理员执行）：

```sql
-- 以 PG 超级用户执行
CREATE USER agent PASSWORD '<强密码>';
CREATE DATABASE agent_platform OWNER agent;
\c agent_platform
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE EXTENSION IF NOT EXISTS vector;    -- 可选：pgvector，只能超级用户建
```

`pg_hba.conf` 给每台加一行（地址按实际改），然后重载 PG：

```
host  agent_platform  agent  172.24.16.100/32  scram-sha-256
host  agent_platform  agent  172.24.24.136/32  scram-sha-256
host  agent_platform  agent  172.21.0.45/32    scram-sha-256
```

**没有现成的 PG**：在某台上由部署用户自己用 conda 起一个，也是 systemd 用户单元（conda-forge 的 postgresql 带 pg_trgm）。
它要听一个别的主机能连到的地址，并给每台配 pg_hba：

```bash
CONDA=~/miniconda3/bin/conda          # 该用户已有的 conda【占位：按实际路径】
$CONDA create -y -n agent-pg -c conda-forge postgresql=16
PG=~/miniconda3/envs/agent-pg/bin
$PG/initdb -D ~/pgdata -U agent -W -E UTF8 --no-locale --auth=scram-sha-256   # -W 交互输入口令，就是 secrets.env 的 AGENT_DB_PASSWORD
cat >> ~/pgdata/pg_hba.conf <<'EOF'
host  agent_platform  agent  172.24.24.136/32  scram-sha-256
host  agent_platform  agent  172.21.0.45/32    scram-sha-256
EOF
cat > ~/.config/systemd/user/agent-pg.service <<'EOF'
[Unit]
Description=PostgreSQL for agent-platform

[Service]
# listen_addresses：本机 + 别的主机连过来的那个地址【占位：本机 IP】
ExecStart=%h/miniconda3/envs/agent-pg/bin/postgres -D %h/pgdata -c listen_addresses=127.0.0.1,172.24.16.100 -p 5432
Restart=on-failure

[Install]
WantedBy=default.target
EOF
systemctl --user daemon-reload && systemctl --user enable --now agent-pg
$PG/psql -h 127.0.0.1 -U agent -d postgres -c 'CREATE DATABASE agent_platform'
$PG/psql -h 127.0.0.1 -U agent -d agent_platform -c 'CREATE EXTENSION IF NOT EXISTS pg_trgm'
```

上例把 PG 放在生产机上，pg_hba 放行两台测试机【占位：PG 放哪台按实际改地址】。防火墙要管理员按来源放行 5432（§3.0）。
本机 5432 已被占用时换个端口，`db_dsn` 跟着改。平台比 PG 先起、连不上库时，会自己隔 5 秒重启。备份见 §7（`$PG/pg_dump`）。

连接数：每台的连接池最多 10 条，另加执行队列的 LISTEN 1 条、每个打开着的推流页面 1 条、每个在等或在用模型名额的请求 1 条（§3.2）。
三台在 PG 默认的 `max_connections=100` 以内【占位：主机变多或 max_connections 调小过时核对】。

表结构在服务启动时幂等创建（`store/db.py` 是全库唯一的建表点，当前 `SCHEMA_VERSION` 是 10），不需要手工迁移；
旧版留下的 `service_instances`、`code_sync_state` 两张表启动时自动删掉。

召回用 pg_trgm 做关键词检索。pgvector 只在配了嵌入模型（`model.embedding_name`）时才用得上；Kimi 没有嵌入接口，
默认不配。建不了 `vector` 扩展时服务只记一条 warning，不影响启动。

### 3.2 部署配置

部署配置只有「平台怎么跑起来」的参数，分四层，后面的深合并到前面的上面：

| 层 | 文件 | 内容 |
|---|---|---|
| 1 | `conf/base/common.yaml` | 所有主机共享的默认值：模型（Kimi）、执行队列（`worker`）、项目内核（`kernel`）、资源上限（`limits`）、沙箱（`require_sandbox`、`home_allow`、`hidden_paths`）、链路追踪（`otel`）、数据保留（`retention`）、平台 MCP（`mcp_servers`） |
| 2 | `conf/env/<AGENT_ENV>.yaml` | `prod.yaml`：生产机和测试机都用它（用户单元里 `AGENT_ENV=prod`）；`dev.yaml`：开发机 |
| 3 | `~/.config/agent-platform/local.yaml` | 本机的值：`env`（这台负责的业务环境，线上主机必填）、`services`（同一环境的项目分在几台上时写），以及只有这台主机才有的覆盖，比如 `listen`（只在控制台主机）。不进仓库；路径可用环境变量 `AGENT_CONF_LOCAL` 改 |
| 4 | `~/.config/agent-platform/secrets.env` | 前三层里 `${VAR}` 的值（§3.4） |

配置里的 `${VAR}` 从环境变量取值，**没设置时启动直接报错**。配置问题在启动时就暴露，不会带病运行。
旧配置里的 `process_control`、`code_sync` 两节已经删掉，留着也不生效。

`conf/env/prod.yaml`：

```yaml
db_dsn: "postgresql://agent:${AGENT_DB_PASSWORD}@${AGENT_DB_HOST}:5432/agent_platform"
root_token: "${AGENT_ROOT_TOKEN}"
public_url: "https://agent.internal"   # 【占位：控制台主机的实际地址，如 https://<hostname -f>:8100】
model:
  tokens: ["${MODEL_TOKEN_A}"]        # 多把 key 就都列上，按请求轮换
limits:
  enabled: true                       # 和线上服务同机：模型写的代码限内存（§5）
```

`public_url` 各台必须一致（通知由执行运行的那台发，链接都指向控制台）：写在 `prod.yaml` 里，或者每台的 `local.yaml` 写同一个值。

**local.yaml**（每台主机一份）：

```bash
install -d -m 700 ~/.config/agent-platform                  # 安装脚本也会建；先建好可以先写 local.yaml
install -m 600 /dev/null ~/.config/agent-platform/local.yaml
```

```yaml
# 生产机。若它也是控制台主机【占位：控制台放哪台】，在这里打开对外监听（§4）
env: prod
listen:
  host: 0.0.0.0
  port: 8100
  tls_cert: ~/.config/agent-platform/tls/cert.pem
  tls_key: ~/.config/agent-platform/tls/key.pem
```

```yaml
# 测试机 172.24.24.136
env: test

```

```yaml
# 测试机 172.21.0.45【占位：vision-web 测试不在这台就从 services 里去掉】
env: test
services: [vision-board, vision-web]
```

- `env` 和 `AGENT_ENV` 无关：用户单元里的 `AGENT_ENV=prod` 只决定读 `conf/env/prod.yaml`，测试机也是它。
- 线上主机一定要写 `env`：`AGENT_ENV` 不是 dev 而 `local.yaml` 没写 `env` 时，平台拒绝启动 worker（日志里是「部署配置没有写 env…」），
  安装脚本也会提示。只有开发机可以不写（认领一切）。
- `services` 里的名字要和服务定义的名字一致。写错了，那个服务在这个环境的运行没有哪台认领，一直 `queued`（§9）。

**模型**（`model` 节，Kimi 开放平台，OpenAI 兼容）：

| 键 | 默认 | 说明 |
|---|---|---|
| `model.url` | `https://api.moonshot.cn/v1` | OpenAI 兼容的接口地址 |
| `model.name` | `kimi-k2.7-code` | 能用哪些模型看 key，`GET {url}/models` 可查。现在这把 key 只列出 `kimi-k2.7-code`、`kimi-k2.6`，`kimi-k2.8` 返回 404 |
| `model.tokens` | `["${MODEL_TOKEN_A}"]`（prod.yaml） | 有多把 key 就都列上，按请求轮换 |
| `model.max_concurrency` | 3 | **整个账号**同时在途的模型请求上限（流式响应读完才算结束）：prod、test 各台，agent 的调用和平台的辅助调用合计；有空位就立刻发，不按分钟限速；0 = 不限 |
| `model.max_retries` | 6 | 撞了 429 或网关错误时的重试次数（指数退避） |
| `model.stream_usage` | true | 流式响应里要 token 用量；网关不支持就关掉 |
| `model.context_tokens` | 400000 | 模型的上下文长度：对话历史到它的 75% 时自动压缩成摘要。换了模型按实际窗口改 |
| `model.embedding_name` | 不配 | 配了才开向量检索；Kimi 没有嵌入接口 |

并发上限经共用的 PG 排队，所以几台加起来也不会超：每个在途请求占一把 PG 会话级 advisory lock，独占一条专用连接到响应读完；
进程挂了连接断开，锁自动释放。名额都占着时，新请求每 0.2 秒再试一次。

账号并发是 3【占位：按开放平台控制台显示的额度核对 `model.max_concurrency`；改了 `conf/` 要每台重跑安装脚本】。同时在跑的运行多时，
它们在模型这一层排队，排了多久记在运行时间线 `model_call` 的 `queued_ms` 里；调大 `worker.max_concurrent_runs` 不会更快。
任务的 `timeout_s` 把排队时间也算在内（种子的 agent 任务是 600–900 秒）。撞了 429 由 SDK 按 `model.max_retries` 退避重试，
报错原文会写明撞的是哪一项（如 `max organization concurrency`）。

其他常调的键：

| 键 | 默认 | 说明 |
|---|---|---|
| `worker.max_concurrent_runs` | 4 | 一台主机同时执行几个运行；满了就不再认领，排队的按创建时间先到先得 |
| `kernel.idle_minutes` | 30 | 项目内核空闲多久回收 |
| `kernel.max_kernels` | 3 | 一台主机同时最多几个项目内核（每个 会话×服务×环境 一个），超了先回收最久没用的；都在执行代码时新会话的 `py` 最多等 120 秒空位，还没有才报「项目内核已满」。和线上服务同机，宁少勿多 |
| `limits.enabled` | false（prod.yaml 里是 true） | 项目内核与 bash 各套一个 systemd 用户 scope，只限内存，CPU 不设上限（§5） |
| `limits.slice` | `agent.slice` | scope 放在哪个 slice 下 |
| `limits.kernel_memory` | `32G` | 每个项目内核的内存上限（不换 swap）。生产机和测试机内存一样，所有主机用同一个值 |
| `limits.bash_memory` | `8G` | 每条 bash 命令的内存上限，同上 |
| `limits.tasks` | 4096 | 每个 scope 的进程 + 线程数上限（numpy 这类库按核数开线程，核多的机器别设小） |
| `require_sandbox` | true | 没有 bwrap 时拒绝执行模型写的代码。只有开发机可以关（`dev.yaml`） |
| `home_allow` | `[]` | 沙箱里 home 是空的；项目运行要用到 home 下别的目录（只读挂回）时写这里，如 `[~/.local/lib]`。写 `~` 本身或它的上级会被丢掉 |
| `hidden_paths` | `[/var/run/docker.sock, /run/docker.sock]` | 沙箱里额外遮蔽的 home 以外的路径（存在的才遮）。写了就整体替换默认值，docker 的两个 socket 要一起写上。服务声明的 `configs`、`hidden` 按环境遮蔽（§5.2），不用写；`agent-conf/`、`~/.config/agent-platform`、`~/.ssh` 不管这里写什么都遮 |
| `retention.run_events_days` | 90 | 已结束运行的过程事件保留几天；被 👎 过的运行不清（回归重放要用） |
| `retention.checkpoints_days` | 30 | 会话 checkpoint：最后一轮结束这么久后清掉，之后该会话不能续跑，新一轮从头开始 |
| `retention.recall_hits_days` | 90 | 召回埋点 |
| `retention.scratch_days` | 7 | 本机工作目录里多久没动过的文件清掉（`work/<会话>/`、`queries/<run_id>/` 按目录算） |

数据保留由维护循环每 6 小时清一次；运行台账本身（输入、输出、配方）一直保留。

链路追踪（可选）：`otel` 打开后经 OTLP/HTTP 导出到任意兼容后端，需要装 `[obs]`（§3.3）。页面不依赖它，运行详情的时间线
（含每次模型调用的耗时、token 与思考）来自平台自己的过程事件。

```yaml
otel:
  enabled: true
  endpoint: http://otel-collector.internal:4318/v1/traces   # 默认 http://127.0.0.1:4318/v1/traces
  headers: {Authorization: "Bearer ${OTEL_TOKEN}"}           # 口令写 secrets.env
```

`serve` 同进程跑接口和 worker（执行队列、定时、维护循环），没有单独的 worker 进程。

服务、角色、任务，以及平台配置（环境、通知、记忆、提示词）**都不在这里**。
它们存在库里，在控制台编辑。`conf/seeds/` 只在库里还没有对应对象时播种一次，之后改种子文件不会覆盖库里的内容。
种子与库里的定义不一致时，启动日志会提示。

### 3.3 安装（每台主机）

把平台仓库放到这台主机上（`git clone` 或从别处 rsync 过来，位置随意，比如 `~/src/agent-platform`【占位】），
然后**经 ssh 以部署用户登录**（`sudo -u`、`su` 拿不到该用户的 systemd 会话），在仓库根目录执行：

```bash
ssh vision-service@172.24.16.100
cd ~/src/agent-platform && bash deploy/install-user.sh
```

脚本依次完成以下动作：

1. 找 ≥ 3.11 的 Python（§3.0）；
2. 删掉 `~/agent-platform` 下旧的 `src`、`conf`、`mcp_servers`、`build`，再从仓库拷 `src`、`conf`、`mcp_servers`、`pyproject.toml`
   （仓库里删掉的模块不会留下；仓库里没有构建好的控制台时，保留上一次装好的）；
   建数据目录 `scratch`、`assets`、`agent-conf`（700）和 `~/.config/agent-platform`（700）、`~/.local/bin`；
3. 装了 Node（npm）就按当前代码构建控制台。构建产物不进仓库，`git pull` 之后要重新构建；没有 Node 时用已有的，一份都没有就提示；
4. 建 venv 并安装 `agent-platform[mcp,dagster-mcp]`：`db_query` 的驱动（pymysql、clickhouse-connect、pymongo）是核心依赖，
   服务 MCP 和仓库自带的 dagster MCP（`mcp_servers/dagster_mcp.py`）要的两组可选依赖也一起装上；
5. 前置检查，只提示不中断：bwrap 在不在、用平台实际的参数能不能起；git；memory 控制器有没有委派给用户（没有就警告），
   cpu 有没有委派（只提示：只影响 `CPUWeight`）；`systemd-run --user --scope` 实际能不能起；linger（没开就自己试着开）；
   `secrets.env` 在不在；`local.yaml` 里有没有 `env:`；该用户能不能用 docker；
6. 安装用户单元 `agent-platform.service` 和 `agent.slice`，`daemon-reload`、enable 并（重新）启动；起不来不中断脚本，打印状态和看日志的命令。

第一次执行时 secrets.env 还没放（或 `local.yaml` 还没写 `env`），服务起不来，**这是预期的**；下一步放好后重启即可。

内网不通外网时，执行安装脚本前设置 `PIP_INDEX_URL`（pip 镜像）。

开链路追踪（§3.2 的 `otel`）另装 `obs`：`~/agent-platform/venv/bin/pip install "$HOME/agent-platform[mcp,dagster-mcp,obs]"`。
重跑安装脚本不会卸掉已装的可选依赖。

### 3.4 放置密钥并重启

```bash
install -m 600 /dev/null ~/.config/agent-platform/secrets.env
cat > ~/.config/agent-platform/secrets.env <<'EOF'
# 注释只能单独成行：systemd 的 EnvironmentFile 不认行尾注释，会把它当成值的一部分
# 引导密钥：首次登录、创建 API 密钥；不可吊销，务必够长。各台用同一个（控制台的登录 cookie 用它签名）
AGENT_ROOT_TOKEN=...
# 共用的 PG（§3.1）：地址和口令
AGENT_DB_HOST=...
AGENT_DB_PASSWORD=...
# Kimi 开放平台的 API key（prod.yaml 的 model.tokens 引用它）
MODEL_TOKEN_A=sk-...
# 种子通知渠道 default 用（设置 → 通知 里也能改）；通知由执行运行的那台发，每台都要

# 种子里只读库 ck（ClickHouse）的只读账户：服务定义里写 ${VAR}，连库时才取值

CK_PROD_RO_PASSWORD=...
CK_TEST_RO_PASSWORD=...

```

- 服务定义、通知渠道、MCP 连接里引用的每个 `${VAR}` 都要在这里有值。环境变量只在平台启动时读：以后新登记的库、渠道用到新的 `${VAR}`，

- 各台的文件内容基本相同。测试机可以不放生产库的口令（`CK_PROD_RO_PASSWORD`）：测试机是 `env: test`，不执行生产的运行，

- secrets.env 里的变量不会下发给 bash 和项目内核（§5）。

### 3.7 服务定义与给 agent 的配置

**服务定义**在控制台 服务 → 定义 里改（字段说明见接口文档 §5.1）。种子 `conf/seeds/services/*.yaml` 里的路径**全是【占位】**，
上线前在对应主机上逐项核对：

| 字段 | 写什么 | 怎么核对 |
|---|---|---|
| `root`（`envs.<环境>.root` 可覆盖） | 线上的代码目录 | 在那台主机上 `ls`；`git -C <root> log -1` 能看到当前部署的提交 |
| `python`（`envs.<环境>.python` 可覆盖） | 线上用的解释器 | `<python> -c 'import sys; print(sys.prefix)'` |
| `configs` | 项目读配置的路径（可写 `{env}`、`~`） | 线上真实文件就在这些路径上 |
| `hidden` | 代码目录里其他含口令的文件或目录：生产只遮蔽、不替换；测试不遮 | |
| `logs` | `{名字: 文件路径 \| docker:<容器名> \| journal:<systemd 单元>}`；文件路径可带 `*` `?` `[` 通配，读匹配到的最新那个（按日期滚动的写成 `~/deploy/x/logs/app-*.log`） | `tail -n1 <文件>`、`docker logs --tail 1 <容器>`、`journalctl -n1 -u <单元>`（或加 `--user`）能读（§3.8） |
| `databases`、`urls`、`mcp` | 只读库、地址、服务 MCP | §3.10、§3.11 |

服务定义里 `~` 开头的路径展开成部署用户的 home（平台和项目是同一个用户）。旧写法 `configs: [{canonical, template}]` 仍然能读，取 `canonical`。
服务定义里不写部署在哪台主机，由各台 `local.yaml` 的 `env`、`services` 决定（§2.1）。

**给 agent 用的配置**按环境分，由 设置 → 环境 的「受保护」决定（种子：prod 受保护，test 不受保护）：

- **受保护（生产）**：真实配置 agent 看不到。每个服务、每个 `configs` 路径，由运维在控制台填一份**只读账号**的版本（「只读版配置」），
  项目内核启动时盖在项目读配置的那个路径上。步骤见下。
- **不受保护（测试）**：不用填。agent 直接用项目的真实配置，bash、`py` 都能读本环境的配置和 `hidden` 文件；文件照样只读，
  库只读靠提示词约束（真实配置里的账号可能有写权限，这是接受的风险）。控制台的 服务 → 配置文件 在测试环境只显示说明，
  接口读写返回 `409 config_not_used`。

生产的步骤：

1. 在生产机上看线上那份（部署用户本来就能读），复制一份，把库、接口的账号口令换成只读的，去掉内核不该连的东西；写账号不要贴进来。
2. 控制台 服务 → 配置文件，选环境 prod、选路径，粘贴保存。每次保存是一个新版本（谁、何时），可回看历史；不做并发编辑检查
   （组里分工明确，不会有两个人同时改同一份）。存在 PG 的 `service_configs` 表里，控制台由哪台主机回答都一样。
3. 执行运行的那台主机在起项目内核前，把当前版本写到本机 `~/.local/share/agent-platform/agent-conf/<服务>/<环境>/`（目录 700、文件 600），
   再只读 bind 到项目读的路径上。线上那份文件不动。改了配置不用重启：下一次 `py` 调用发现版本变了，内核自动重启。

### 3.8 日志与主机权限

`logs` 工具只读服务定义里声明过的日志，由平台进程在沙箱外执行，命令写死，模型只能选看哪个、看多少行、怎么过滤：

- 文件：从末尾往前读最后 N 行（`lines` 最多 2000）；路径带通配时读匹配到的最新那个文件；
- `docker:<容器>`：`docker logs --tail N --timestamps [--since …]`；
- `journal:<单元>`：`journalctl -u <单元>`，先查系统日志（平台用户要在 `systemd-journal` 组里，见下），没有条目再查本用户的（`--user`）；
- `since`（如 `30m`、`2h`、`2026-10-21 08:00:00`）对 docker、journal 有效，文件日志忽略；
- `grep` 是正则，不分大小写：文件在整个文件里流式搜（超过 512MB 只搜末尾 512MB），docker、journal 在最后 5 万行里搜；
  返回最后 N 条匹配和匹配总数。输出最多 12000 字。

读不了时工具如实返回 `[没有权限]`、`[不存在]` 或 `[读取失败]`。

**应用日志**在部署用户的目录里，本来就能读。

**nginx 日志**一般归 root，部署用户读不了。先看权限：`ls -ld /var/log/nginx; ls -l /var/log/nginx/`。请管理员用 ACL 给部署用户只读权限：

```bash
# 【占位：按实际的目录权限和用户名改；logrotate 新建的文件靠第三行的默认 ACL 继承】
setfacl -m u:vision-service:rx /var/log/nginx
setfacl -m u:vision-service:r /var/log/nginx/*.log
setfacl -d -m u:vision-service:r /var/log/nginx
```

以部署用户验证：`tail -n1 /var/log/nginx/error.log`。测试机 172.21.0.45 上换成那台的部署用户。

**docker**：读容器日志要该用户能执行 `docker ps`（一般在 docker 组里；生产机上 vision-service 本来就用 docker 部署【占位：确认】）。
沙箱里 docker 的 socket 是遮蔽的，模型写的代码用不了 docker；只有 `logs`（`docker logs`）和 `host_status`（`docker ps -a`、`docker stats --no-stream`）这几个写死的命令用它。

**systemd 单元的日志**（`journal:`）：系统单元的日志要平台用户在 `systemd-journal` 组里，请管理员 `usermod -aG systemd-journal <部署用户>`
（重新登录、重启平台后生效）；不在组里时只能读到本用户 systemd --user 单元的日志。验证：`journalctl -n1 -u <单元>`。

**host_status** 返回：负载与核数、内存与 swap、`/` 和代码目录所在磁盘的用量、占内存最多的 10 个进程（`ps -eo pid,user,rss,pcpu,etime,args`，
命令行截到 160 字）；本服务的进程（命令行里带服务代码目录的）、监听端口（`ss -ltnp`）、本用户的 crontab（去掉注释行）、
本服务容器（服务 `logs` 里 `docker:` 的那些）的 CPU / 内存（`docker stats --no-stream`）；`docker ps -a`（名字、状态、镜像）、
`systemctl is-active nginx`（没在跑也显示 inactive / failed）。拿不到的项跳过，不需要额外权限。

### 3.9 接外部事件

| 来源 | 配法 |
|---|---|
| Dagster | `run_failure_sensor` 里 `POST {public_url}/v1/events/dagster`，请求头 `Authorization: Bearer <dagster-sensor 的密钥>`，请求体 `{run_id, asset_key, error, env}` |
| GitLab | 项目 → Webhooks，地址 `{public_url}/v1/events/gitlab`，Secret token 填 gitlab 那把密钥，勾选 Deployment events |
| 其他系统 | `POST /v1/events/webhook`，事件名放请求头 `X-Event` |

- 回调都打到控制台主机（`public_url`）：线上 Dagster 所在的网络要能访问它。运行再由负责该环境（和服务）的那台认领执行；
  那台没在跑时运行排着，起来后接着执行。
- 哪个事件触发哪个任务，在任务的「触发」里声明。种子任务 `frontend-smoke`（Board 冒烟测试）声明了 GitLab 部署事件，
  只认 `filter.project: ^vision-board$`（回调里的项目名），GitLab 项目名不同的话改它。
- GitLab 部署的 `environment` 要和平台的环境名一致（`prod` / `test`）。部署事件只用来触发检查，代码由项目自己的部署流程更新，
  agent 读到的就是部署之后的代码。

### 3.10 MCP（可选）

MCP 工具分两种，要的 Python 依赖安装脚本都装好了（§3.3）：

| | 平台 MCP | 服务 MCP |
|---|---|---|
| 放什么 | 通用能力，比如浏览器 | 某个服务特有的能力，比如 vision-dagster 的运行记录与重跑 |
| 写在哪 | 部署配置 `mcp_servers`（`conf/`），改了要在各台重跑安装脚本 | 服务定义的 `mcp`（控制台），写库即生效，下次运行自动重连 |
| 怎么用上 | 角色的 `tools` 里写 `"mcp:<名字>"`、工具名或 `"*"` | 运行在该服务上自动出现 |

**平台 MCP** 以浏览器为例（种子角色 `qa_engineer` 用 `"mcp:browser"`），写进 `conf/env/prod.yaml`：

```yaml
mcp_servers:
  browser:
    transport: stdio
    command: npx
    args: ["-y", "@playwright/mcp@0.0.83", "--headless", "--isolated", "--output-dir", "/home/<用户>/.local/share/agent-platform/scratch"]
```

- 需要 Node.js。平台 MCP 在每台启动时加载，配了就每台都要能跑 `npx`；内网不通外网时先把 `@playwright/mcp` 和浏览器装好，或配 npm 镜像。
- MCP 会话按 会话 × 连接 常驻：同一个会话里先 navigate 再 snapshot 落在同一个浏览器进程上。空闲 30 分钟回收，
  所有 MCP 连接合计同时最多 16 条（超了回收最久没用的）。
- 页面地址来自服务定义的 `urls`（如 vision-board 的 `site`），agent 在运行环境提示里看得到。
- 没配 `browser` 时，角色里的 `"mcp:browser"` 被忽略，只记一条 warning。

**服务 MCP** 以种子 vision-dagster 为例：`mcp.dagster` 用平台解释器跑仓库自带的 `mcp_servers/dagster_mcp.py`，按运行的环境连该环境线上部署的
Dagster（`DAGSTER_URL` 取 `urls.deployed`：prod `https://vision-dagster-prod.ipa.zs:9902`、test `https://vision-dagster-test.ipa.zs:9901`）。

工具共 8 个：查询类 `get_run`、`get_run_logs`、`get_asset_materializations`、`recent_runs`、`asset_info`、`list_jobs`；
重跑类 `launch_job(job_name, partition, run_config)`（`run_config` 是 JSON 文本）和 `reexecute_run(run_id, from_failure=True)`。
重跑是在线上那套部署里、用线上的真实配置跑，有三道约束：

- `DAGSTER_LAUNCH_JOBS`：允许重跑的作业名正则（整名匹配）；**不设就不允许重跑**，只能查。种子写的是 `".*"`：已确认线上作业重复运行没有副作用
  （覆盖写同一分区）。要收窄就改成作业名正则，如 `"^(daily_.*|ods_.*)$"`；
- 同一作业（带分区时看 `dagster/partition` 标签）已经有 QUEUED / NOT_STARTED / STARTING / STARTED 的运行时拒绝，不和定时、传感器撞车；
- `launch_job` 起的运行打标签 `agent/launched_by=agent-platform`，在 Dagster 页面里能筛出来；`reexecute_run` 沿用原运行的标签。
  两种在 agent 的运行时间线里都有这次工具调用和返回的 run_id。

要求：执行 vision-dagster 运行的主机（生产机、测试机 172.24.24.136）能访问对应环境的 Dagster 地址。
内网证书校验不过时，在服务定义 `mcp.dagster.env` 里加 `DAGSTER_VERIFY`：CA 文件路径（如 `/etc/ipa/ca.crt`），实在不行写 `false`。
连接配置里的口令写 `${VAR}`，放 secrets.env，连接时才取值。

验证：`GET /v1/services/vision-dagster/tools?reload=true`，`tools` 里应有 8 个工具，`failed` 为空。这个接口由回答请求的那台（控制台主机）
现连两个环境，所以控制台主机也要能访问两个 Dagster 地址；连不上的会列在 `failed`（形如 `vision-dagster.dagster@test`），不影响执行运行的主机上的运行。

### 3.11 只读库（db_query）

服务定义的 `databases` 登记 agent 能查的库：`{库名: 连接串}`，scheme 决定类型（PostgreSQL / MySQL / MariaDB / Doris /
ClickHouse / MongoDB，见设计文档 §2.3），`envs[env].databases` 按库名覆盖。种子里 vision-dagster、vision-board 登记了 `ck`：

| 环境 | ClickHouse | 连接串 |
|---|---|---|
| prod | 国内生产 172.168.0.125 | `clickhouse://${CK_RO_USER}:${CK_PROD_RO_PASSWORD}@172.168.0.125:8123/default` |
| test | 国内测试 172.24.17.66 | `clickhouse://${CK_RO_USER}:${CK_TEST_RO_PASSWORD}@172.24.17.66:8123/default` |

- 账户必须是只读的。`db_query` 自己的检查（单条语句、关键字白名单、只读事务 / `readonly=2`、30 秒超时）只是第一道。
  ClickHouse 账户是 `readonly=1` 时不能带任何设置：报「Cannot modify … readonly」时平台去掉超时和行数上限的设置重试，按账户自己的限制执行；
  查询里自己写了 `SETTINGS` 的不重试。
- **库这一侧也要限时、限内存**：`py` 里的项目代码用配置里的账号自己发查询（生产是只读版里的只读账号，测试是真实配置里的账号），
  不经过 `db_query` 的 30 秒超时。请 DBA 给只读账号挂上限制，
  ClickHouse 例如：

  ```sql
  -- 【占位：数值按库的规模定；账号用 users.xml 管理的，写进它的 profiles 段】
  CREATE SETTINGS PROFILE IF NOT EXISTS agent_ro SETTINGS readonly = 1, max_execution_time = 60, max_memory_usage = 4000000000;
  ```

- 口令写 `${VAR}`，放 secrets.env（§3.4），重启后生效。取不到时工具返回 `[未配置]`，不会把占位原样拿去连库。
- vision-web 还没登记库：按它 settings 里实际连的库加，例如 `main: "mysql://${VISION_WEB_RO_USER}:${VISION_WEB_RO_PASSWORD}@<地址>:3306/<库>"`；

- 超过 20 行的结果整份写进执行运行的那台主机上本会话的工作目录 `scratch/work/<会话键>/queries/<run_id>/`（CSV / JSONL），最多 10 万行、50MB。

## 4. 对外访问

只有控制台主机对外，其他主机保持默认，只听 `127.0.0.1:8100`（本机检查用）。对外有两种方式，二选一。

**平台直接对外（不需要 root）**：在控制台主机的 `local.yaml` 打开 `listen`，平台自己做 HTTPS：

```yaml
listen:
  host: 0.0.0.0
  port: 8100                                         # 普通用户只能绑 ≥ 1024 的端口
  tls_cert: ~/.config/agent-platform/tls/cert.pem    # PEM，证书在前、中间证书接在后面
  tls_key: ~/.config/agent-platform/tls/key.pem      # 600；这个目录在沙箱里看不到
```

- `public_url` 写成 `https://<主机名>:8100`，主机名用 `hostname -f` 的结果（内网 DNS 里通常已经有），不用另申请域名【占位：确认控制台放哪台和主机名】；
- 证书请内部 CA（FreeIPA）的管理员按这个主机名签一张。自签也能用，只是浏览器会提示不受信任；
- 防火墙放行这个端口（§3.0，要管理员）；
- 开了 TLS 之后，本机检查用 `curl -sk https://127.0.0.1:8100/healthz`；
- 不填 `tls_cert` / `tls_key` 就是明文 http，内网也能跑，但 API 密钥和登录 cookie 明文传输，不建议。

改了 `local.yaml` 只需 `systemctl --user restart agent-platform`；改了仓库里的 `conf/` 要在每台重跑 `bash deploy/install-user.sh`（会拷过去并重启）。

**经 nginx 反代**：要走 443 或已有统一网关时用。装 nginx、绑 443、改 nginx 配置要 root；`listen` 保持默认。
生产机上的 nginx 是 vision-board 在用的线上 nginx，在它上面加反代就是改线上配置，要和 vision-board 的配置分开一个 `server` 块，由管理员做。

```nginx
server {
    listen 443 ssl;
    server_name agent.internal;              # 与 public_url 一致【占位】
    location / {
        proxy_pass http://127.0.0.1:8100;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 3600s;            # SSE：对话与运行推流
        proxy_buffering off;                 # SSE 需要实时冲刷
    }
}
```

- `public_url` 必须与最终访问地址一致：通知里的跳转链接用它拼；它是 https 时，登录 cookie 带 Secure 标记。
- SSE 端点（`/v1/chat`、`/v1/runs/{id}/stream`）要求反代关闭缓冲、拉长超时。
- Rocky 开着 SELinux 时，nginx 要连本机端口还得 `setsebool -P httpd_can_network_connect 1`。

## 5. 沙箱与资源上限

平台和线上项目是同一个用户。这个用户能读到的东西很多：线上的真实配置、`~/.ssh`、docker（能 `docker exec` 进生产容器）、
systemd 用户总线（能 `systemctl --user` 停服务）、同用户其他进程的 `/proc/<pid>/environ`。所以只把文件系统设成只读不够：
只读也能把真实口令读走。沙箱按「能看到什么」做白名单。

### 5.1 哪些代码在沙箱里跑

模型自己写的代码只从两个工具进来，都跑在 bubblewrap 里：

- `bash`：每次调用一条命令；
- `py`：项目内核，每个 会话×服务×环境 一个常驻 Python 进程。

`grep` 工具也在 bash 的沙箱里跑（命令由平台拼，参数转义过），所以遮蔽的配置搜不到。`read` 在平台进程里读文件，
但先按 bash 沙箱的同一套规则判断路径看不看得到（home 白名单、遮蔽的配置、`/proc` 等），看不到的直接拒绝。

其余工具（`db_query`、`logs`、`host_status`、`service_info`、`todo`、MCP 工具…）在平台进程里执行，逻辑写死，模型只给参数，拼不了命令。

### 5.2 沙箱里能看到什么

| | `bash` | `py`（项目内核） |
|---|---|---|
| 文件系统 | 全盘只读 | 全盘只读 |
| home | 换成空的 tmpfs，只挂回（只读）：本机负责的各服务的代码目录、各服务解释器所在的 conda / venv 环境、方法目录、`home_allow` | 换成空的 tmpfs，只挂回（只读）：本服务本环境的代码目录、解释器所在的环境（写的路径和解析软链接后的都挂；conda 环境再加有 `conda-meta/` 的 conda 根目录）、方法目录、`home_allow` |
| 可写 | 整个 scratch；独立的 `/tmp`。当前目录和 `$SCRATCH` 是本会话的工作目录 `scratch/work/<会话键>`（同会话的 bash 和 py 共用，和同机别的运行隔开） | 同左；另外服务声明的日志文件换成可写的 `/dev/null`（见下） |
| 配置文件 | 生产的运行：所有服务所有环境声明的 `configs` 和 `hidden` 都遮蔽（文件换成 /dev/null，目录换成空目录）。测试的运行：只遮受保护环境（生产）的，本环境的照常可读；没写 `{env}` 的路径在测试机上就是测试那份，不遮 | 生产：本环境的 `configs` 路径上是给 agent 的只读版（§3.7），其余照样遮蔽。测试：项目的真实配置，遮蔽同左 |
| `/run/user/<uid>` | 换成空目录：碰不到 systemd 用户总线 | 同左 |
| docker socket、`agent-conf/`、`~/.config/agent-platform`、`~/.ssh` | 都遮蔽（docker socket 在 `hidden_paths` 里；其余三个总是遮，不看 `hidden_paths`） | 同左 |
| 进程 | 独立 pid、ipc 命名空间：看不到同用户的其他进程，读不到它们的 `/proc/<pid>/environ`、`/proc/<pid>/root`，也碰不到它们的共享内存 | 同左 |
| 网络 | 不限（§5.7） | 同左 |
| 输出 | stdout 和 stderr 按先后合在一起，给模型的最多 12000 字（开头 + 结尾），全文写进工作目录的 `outputs/`（最多 200MB；平台内存里只留首尾各 64KB）；超时返回退出码 124 和已有的输出；运行被取消时立即杀掉 | 超过 20000 字同样给预览、全文进 `outputs/`；运行被取消时杀掉内核 |
| 环境变量 | 只有 PATH、HOME、LANG、LC_ALL、TZ、USER、SHELL、`SCRATCH`，加服务的 `env_vars`；PATH 最前面是本服务项目解释器所在目录（python / pip / pytest 用项目的环境）；secrets.env 的变量不下发 | 白名单同左，加服务的 `env_vars` 与 `SVC_ENV`、`SVC_NAME`、`SCRATCH` |
| 生命期 | 命令是命名空间的 pid 1：调用结束（含超时、worker 崩溃）整个命名空间被杀，`&` / nohup 起的后台进程不留；每次调用是新的 shell，`cd`、`export` 不带到下一次 | 常驻；空闲 30 分钟回收；平台进程退出时一起退出 |

home 以外的路径照常可读（只读）：`/etc`、部署用户有权限的 `/var/log/...`、`/data/...`。项目的口令放在 home 以外时，
写进服务的 `hidden` 或部署配置 `hidden_paths`。home 本身或它的上级不会被挂回（`home_allow` 里写了、从解释器路径推出来的都丢掉）。

**项目自己的日志文件**：`py` 内核里，服务定义 `logs` 声明的文件（不含 `docker:`）换成可写的 `/dev/null`。项目 import 时就打开自己的日志文件
（比如 Django `LOGGING` 的 `FileHandler`）不会报 `Read-only file system`；写进去的丢掉，内核里读这些文件是空的，看日志用 `logs` 工具。
bash 里不换。项目 import 时还写别的路径的照样报只读：把那个文件也写进 `logs`，或者（生产）在给 agent 的只读版配置里改成写 `/tmp`。

### 5.3 配置：生产给只读版，测试用真实的

两个环境的尺度不同（组长定的，见需求背景 §4.3），由 设置 → 环境 的「受保护」决定：

- **生产（受保护）**：bash 里所有服务所有环境的配置文件都被遮蔽；`service_info(what=config)` 读的是给 agent 的只读版（密钥打码后）。
  项目内核里，平台把给 agent 的只读版 bind 在项目读配置的那个路径上（比如 `vision_board/settings-prod.py`）。项目代码照常 import settings、
  照常连库，连上去的是只读账号。
- 为什么生产不靠规则禁止 `import settings`：项目自己的函数内部就会 import 它，规则拦不住；能做到的是让沙箱里唯一拿得到的口令是只读的。
  这也是 §3.7 要求把被引用的配置文件一起处理的原因。
- **测试（不受保护）**：只要求文件只读，库只读靠提示词。agent 直接用项目的真实配置：不 bind、不用填、没有 `config_missing`，
  bash、`py` 都能读本环境的配置和 `hidden` 文件，`service_info(what=config)` 读本机上的真实文件（打码）。真实配置里的账号可能能写，
  平台提示词和 `[运行环境]` 要求只查不改、不调会写库的项目函数；这是接受的风险。
- 两个环境都一样：生产的配置在测试的运行里也遮蔽；home 是空的 tmpfs，平台自己的密钥看不到；docker socket、`agent-conf/`、
  `~/.config/agent-platform`、`~/.ssh` 遮蔽；`db_query` 用服务定义里登记的只读账号。
- 在 设置 → 环境 里改了某个环境的「受保护」，那个环境的项目内核下一次调用时自动重启（§5.6）。

### 5.4 没有沙箱就不跑

`require_sandbox: true`（默认）：没有 bwrap 时 bash 返回「没有 bwrap（bubblewrap），按部署配置 require_sandbox 拒绝执行」，
`py` 不起内核。只有开发机的 `dev.yaml` 把它关掉。

### 5.5 资源上限

资源上限只管线上主机的内存安全：只限内存，CPU 不设上限。`limits.enabled: true`（prod.yaml）时，每个项目内核、每条 bash 命令
各跑在一个 systemd 用户 scope 里：

```
systemd-run --user --scope --quiet --collect --slice=agent.slice -p MemoryMax=<kernel_memory|bash_memory> -p MemorySwapMax=0 \
  -p TasksMax=<tasks> -- bwrap …
```

- 每个内核 `32G`、每条 bash `8G`，进程 + 线程 4096。生产机和测试机内存一样，所有主机用同一组固定值【占位：确认各台主机的物理内存放得下这几个值】。
  上限放得宽，只防一个内核或一条命令把主机内存吃光；
- 超了内存只在这个 scope 里 OOM，杀掉的是这个内核或这条命令，不波及线上服务，也不波及平台进程；
- 全部 scope 都在 `agent.slice` 下，slice 再设内存总上限（`MemoryMax=64G`，§2.2）。slice 里只有模型写的代码：平台进程不在里面、不设上限，
  slice 到了 64G 也不会杀到它；
- CPU：`agent.slice` 的 `CPUWeight=20` 低于默认的 100，只在线上服务也要 CPU 时让着它们，CPU 空闲时照常用满；
- 要求 memory、pids 控制器委派给了用户（§3.0），否则上限不生效（安装脚本会提示）；cpu 没委派只是 `CPUWeight` 不生效；
- 没有 `systemd-run` 时只能在 `local.yaml` 里设 `limits.enabled: false`，这时**没有任何资源上限**，不建议在线上主机这样跑。

要改上限：单个内核、单条 bash 改 `conf/base/common.yaml` 的 `limits`，总上限改 `deploy/user/agent.slice`，改完在每台重跑安装脚本。

### 5.6 内核自动重启

内核的规格有一个摘要：解释器、环境是否受保护、各配置的版本（只有生产有）、环境变量、代码目录、遮蔽与挂回的路径、日志文件。任何一项变了（比如有人在控制台改了
给 agent 的配置，或在 设置 → 环境 改了「受保护」，不管控制台由哪台回答），下一次 `py` 调用前内核自动重启，结果开头注明「内核已重启…之前的变量已清空」。

### 5.7 其他要知道的边界

- **库这一侧也要限**：`py` 里的代码能用配置里的账号自己发查询（生产是只读账号），给只读账号配上执行时间、内存上限（§3.11）。`db_query` 自己有 30 秒超时，
  大结果写文件。
- **网络有意不限**：组里定的，只保证数据库和内存安全（需求背景 §4.3）。`py` 和 bash 都能访问内网和本机端口，没有鉴权的内网接口
  （比如线上 Dagster 的 GraphQL）也能直接调，`DAGSTER_LAUNCH_JOBS` 只约束 MCP 工具。这个风险是接受的。
- **发给模型的数据**：工具返回的内容（代码、日志、查询结果、打码后的配置、`host_status` 里的进程命令行与 crontab）会进模型上下文，发给 Kimi 开放平台
  （公网 `api.moonshot.cn`），也记进运行台账。
- **同用户的代价**：沙箱防的是模型写的代码。线上项目自己的进程和平台是同一个用户，能读到平台的 secrets.env 和 `agent-conf/`，
  平台的密钥和线上服务的密钥处在同一个信任域。

## 6. 升级与回滚

每台主机：

```bash
cd ~/src/agent-platform && git pull     # 【占位：仓库位置】
bash deploy/install-user.sh             # 幂等：整份替换代码、重新构建控制台（要 Node）、重装依赖、重启
```

- 控制台的构建产物不在 git 里：`git pull` 之后要重新构建。主机上没有 Node 时，先在别处构建好 `src/agent_platform/webui/dist` 拷进仓库再跑安装脚本，
  否则用的还是上一次装好的旧版。

- 表结构在启动时幂等创建（`store/db.py`），不需要迁移脚本。表结构有改动的版本，各台一起升级，不要长时间混跑新旧版本。
- 重启一台只要几秒：期间提交照常受理，这台负责的运行排队等它起来。
- 定义和平台配置在库里不在包里，升级不会动它们；改了种子文件也不会覆盖库里的内容。数据层面的「回滚」走控制台：
  - 定义、平台配置：版本恢复；
  - 记忆：内容历史恢复；
  - 给 agent 的配置：配置文件的版本历史里取旧版本，再保存一次。
- 代码回滚：仓库切回旧提交，在每台重跑安装脚本。
- 去掉了 `host_metrics` 工具、部署配置的 `grafana` 节和服务定义的 `hosts`（顶层和 `envs.<环境>.hosts`）：库里旧定义带着 `hosts` 照常能读（忽略），
  配置里留着 `grafana` 也不生效，角色里还写着 `host_metrics` 的只记一条 warning，可以在控制台顺手删掉。

**从旧版（独立 agent 机器、按环境另放代码副本）迁过来**：建议用新库，按 §3 从头部署。沿用旧库时，种子不会覆盖库里已有的对象，要在控制台手工改：

1. 设置 → 环境：删掉 `dev`，只留 `prod`、`test`；确认 `prod` 受保护、`test` 不受保护（受保护决定配置怎么给，§3.7）；
2. 设置 → 通知：规则里的旧事件 `process_stopped`、`config_outdated` 读取时自动去掉，只剩这两个事件的规则不会再触发，删掉即可；规则的触发里去掉 `watch`；
3. 任务：删掉内建任务 `code-sync`；`memory-gardener` 按新种子 `conf/seeds/tasks.yaml` 改成 `service: "*"`、每个服务一条夜间定时（见设计文档 §2.4）；
4. 角色：工具里的 `service_ctl` 换成 `logs`、`host_status`（不认识的工具名只是被忽略）；
5. 服务：按新种子改 `root`、`python`、`configs`、`hidden`、`logs`；旧的仓库、分支、同步步骤、进程定义这些字段保存时自动丢掉；
6. 每台主机的 `local.yaml` 写 `env`，测试机再写 `services`（§2.1、§3.2）；
7. 生产的每个服务填给 agent 的配置（§3.7）；测试不用填，库里以前存的测试环境只读版不再使用。

旧机器上的代码副本目录、配置备份、业务进程单元，确认不用后自己删。

## 7. 备份与恢复

| 数据 | 位置 | 方式 |
|---|---|---|
| PG 全库：台账与执行队列、定义与档案、平台配置、密钥摘要、记忆、方法元数据、回归重放、**给 agent 的配置及其全部版本**（`service_configs`） | 共用的 `agent_platform` 库 | 定期 `pg_dump -Fc agent_platform`。dump 里有只读账号的口令，按密钥文件对待 |
| 方法的文件本体 | 每台主机的数据目录 `assets/` | 每台各自做文件级备份。服务×环境换了主机时，把对应目录拷到新主机 |
| 本机的部署配置与密钥 | `~/.config/agent-platform/`（`local.yaml`、`secrets.env`、`tls/`） | 文件级备份，按密钥文件对待 |

不需要备份的：

- `scratch/`：临时工作区（含 `db_query` 的结果文件），按 `retention.scratch_days` 自动清。
- `agent-conf/`：下次起内核时从库里重写。
- 业务项目的代码目录和 conda 环境：项目自己的部署流程负责。

恢复步骤：装 PG → 恢复 dump → 每台跑安装脚本 → 放回 `local.yaml`、`secrets.env`（和证书）→ 恢复各台的 `assets/` → 启动 → 按 §3.5 验证。

## 8. 日常运维

```bash
journalctl --user -u agent-platform -f                        # 本机的平台日志
curl -s 127.0.0.1:8100/healthz
systemctl --user status agent.slice --no-pager                # 项目内核、bash 合计用了多少内存、多少任务（不含平台进程）
systemctl --user restart agent-platform                       # 只有改了 local.yaml、secrets.env 才需要
```

- **各台在认领什么**：启动日志里的「执行队列已启动（…，环境 …，服务 …）」。运行列表里长时间 `queued` 的，就是负责它的那台没在跑（§9）。
- **定义和平台配置**在控制台改，写库即生效，不用重启。
- **部署配置**和 secrets.env 只在启动时读：改了仓库里的 `conf/` 要在每台重跑安装脚本；`local.yaml`、`secrets.env` 改了重启本机。
- **代码**平台不管，跟着项目原来的部署流程走；agent 读到的就是当前部署的那份，`service_info` 显示当前提交。
- **给 agent 的配置**：生产的线上配置改了口令、加了键，运维跟着改一下给 agent 的只读版（服务 → 配置文件）。平台不跟踪线上配置的变化。
  保存后下一次 `py` 调用时内核自动换上新版本。测试用的就是真实配置，不用跟。
- **换主机**：在旧主机上 `systemctl --user disable --now agent-platform`；在新主机上安装，`local.yaml` 写同样的 `env`（和 `services`），
  `assets/` 拷过去（§7）。服务定义不用改。
- **重启平台**时本机执行中的运行记为 `interrupted`，可以在运行详情续跑。
- **密钥轮换**：
  - API 密钥：控制台新建一把 → 调用方换上 → 吊销旧的；
  - root_token、Kimi key、只读库口令、PG 口令：改每台的 secrets.env 后重启；只读库口令同时改生产给 agent 的配置。

## 9. 故障排查

| 现象 | 排查 |
|---|---|
| 启动即退出 | `journalctl --user -u agent-platform -n 200`：多半是 secrets.env 缺变量（`${VAR}` 插值报错）、PG 连不上（`AGENT_DB_HOST`、pg_hba、防火墙），或 `local.yaml` 没写 `env`（报「部署配置没有写 env…」：写 `env: prod` 或 `env: test`，测试机再写 `services`，§3.2）。`agent-platform check` 能单独验证配置与数据库，并打印这台负责的环境和服务 |
| 运行一直 queued | 负责这个环境（和服务）的那台没有 worker 在认领。看运行的 `env`、`service`，到对应主机上看 `systemctl --user status agent-platform`、日志里有没有「执行队列已启动（…，环境 <env>，服务 …）」，确认 linger 开着、能连上 PG；`local.yaml` 的 `env` / `services` 写错（比如服务名拼错）时，那个服务的运行没有哪台认领。也可能并发满了（`worker.max_concurrent_runs`），看那台有没有长时间 running 的运行 |
| `py` 返回「这台主机上的 agent 服务负责 …，不执行 … 的运行」（`wrong_env`） | 运行要在不负责它的主机上起内核。认领时已经按 `env` / `services` 过滤，一般不会出现；出现时核对那台 `local.yaml` 的 `env`、`services`，然后重跑 |
| `py` 返回「还没有填给 agent 用的配置 …」（`config_missing`） | 只在受保护的环境（生产）出现：控制台 服务 → 配置文件，给这个环境的这个路径填只读版（§3.7） |
| `py` 返回「配置文件 … 在本机不存在」（`config_missing`） | 只在生产出现：服务定义 `configs` 的路径写错了，或项目还没部署在这台主机上。在执行运行的那台上 `ls` 那个路径 |
| 测试的运行里 bash 能读到测试环境的配置文件 | 有意如此：测试直接用项目的真实配置，只遮生产的（§5.3）。要遮就在 设置 → 环境 把它标成受保护，再给它填只读版 |
| 控制台或接口读写测试环境的配置返回 `config_not_used` | 测试不受保护，agent 直接用项目的真实配置，不用填只读版（§3.7） |
| `py` 里 import 项目时报 `Read-only file system` | 项目 import 时要写某个文件。是项目自己的日志文件就写进服务定义的 `logs`（内核里换成可写的 `/dev/null`）；别的路径在生产的只读版配置里改成写 `/tmp`（§5.2） |
| `py` 报找不到解释器 / 代码目录在本机不存在 | 服务定义的 `python`、`root` 和执行运行的那台主机上的实际位置对不上；vision-dagster 要在宿主上另建环境（§3.7） |
| `py`、`bash` 返回「没有 bwrap … 拒绝执行」 | 安装 bubblewrap（§3.0）；自己取的 bwrap 要在 `~/.local/bin` |
| bwrap 报 `setting up uid map: Permission denied`、`No space left on device`（创建命名空间）一类错误 | 普通用户建不了命名空间：RHEL / Rocky 看 `/proc/sys/user/max_user_namespaces` 是不是 0；Ubuntu 24.04+ 是 AppArmor 的限制。都要管理员改一次，见 §3.0 |
| 安装脚本提示「没有把 memory 控制器委派给用户」 | 内核与 bash 的内存上限不生效。管理员加 `delegate.conf`（§3.0），之后重跑安装脚本确认提示消失 |
| `py`、`bash` 报 `systemd-run` 的错 | 经 ssh 登录该用户试 `systemd-run --user --scope -p MemoryMax=100M true`。没有 `systemd-run` 时只能在 `local.yaml` 设 `limits.enabled: false`（没有资源上限，§5.5） |
| `py` 返回「内核已退出」、退出码是 -9 / 137 | 多半撞了 `limits.kernel_memory` 被 OOM 杀掉（`journalctl --user --since -10min \| grep -iE 'oom\|memory'`）。分批处理数据，或调大 `conf/base/common.yaml` 的 `limits.kernel_memory`（所有主机同一个值，不超过 agent.slice 的 64G，改完各台重跑安装脚本） |
| `logs` 返回 `[没有权限]` | 部署用户读不了那个文件，多半是 nginx 日志：按 §3.8 加 ACL |
| `logs` 返回 `[读取失败] … docker` | 该用户用不了 docker（`docker ps` 试一下），或容器名不对（`docker ps -a` 对照服务定义的 `docker:<容器>`）；本机没有 docker 命令时报「本机没有 docker 命令」 |
| `logs` 返回 `[不存在]` | 服务定义 `logs` 里的路径和实际不符；带通配的路径一个文件都没匹配到 |
| `logs` 读 `journal:<单元>` 没有内容或报权限 | 系统单元的日志要平台用户在 `systemd-journal` 组里（§3.8）；单元名用 `systemctl list-units` 对照 |
| `py` 返回「项目内核已满…」 | 这台的 `kernel.max_kernels`（默认 3）个内核都在执行代码，等了 120 秒还没有空位：稍后再试，或错开同时跑的运行 |
| 日志告警 vector 扩展 | 没装 pgvector：只是不能做向量检索。Kimi 没有嵌入接口，默认本来就不用，可以忽略 |
| 运行很慢 | 看时间线上 `model_call` 的 `queued_ms`：有，就是账号的 3 个并发名额占满了（prod、test 所有运行和辅助调用共用），同时跑的运行越多排得越久，见 §3.2；没有，就是模型本身慢（耗时在 `ms` 里） |
| 运行失败，报 `timeout` | 排队也算在 `timeout_s` 里：同时运行多时调大任务的 `timeout_s`，或错开定时 |
| 模型调用报 404 / model not found | `model.name` 这把 key 用不了：`curl -H "Authorization: Bearer $MODEL_TOKEN_A" https://api.moonshot.cn/v1/models` 看可用的，改 `conf/` 后各台重跑安装脚本 |
| 模型调用一直 429 | 看报错原文撞的是哪一项。并发名额已经经库在各台之间共用，多半是别的程序也在用这个账号，或各台连的不是同一个库。撞的是并发就把 `model.max_concurrency` 调小（改 `conf/` 后各台重跑安装脚本） |
| 运行失败，`error_code` 是 `orphaned` / `interrupted` | 执行它的进程崩溃或重启了，运行详情里续跑 |
| 定时没触发 | 控制台 → 任务 → 概览，看「下次定时」；任务或触发器是否停用；服务在该环境是否启用；同一触发器上一次还没跑完会跳过；停机期间错过的不补（所有主机都停着时才会错过）。负责的那台没在跑时定时照样建运行、排着等它；它起来之前，之后的触发因为上一次还在排队会跳过 |
| 调用返回 `service_env_disabled` 等 | 原因码与解法见接口文档 §1.4 |
| `db_query` 返回 `[未配置]` | 服务在该环境没登记库，或 `${VAR}` 在执行运行的那台的 secrets.env 里没有（加上后重启平台） |
| `db_query` 返回 `[拒绝]` | 只能执行一条查询类语句；MongoDB 要写成 JSON（工具说明里有写法），聚合不能有 `$out` / `$merge` |
| `db_query` 返回 `[查询出错]` | 库侧的原文：连不上就查执行运行的那台到库的网络（种子 CK 是 8123 端口）和账户口令；超时就加条件或先在库里聚合 |
| `db_query` 返回 `[不可用] 平台没装 … 的驱动` | 平台 venv 少了核心依赖：重跑安装脚本 |
| 安装脚本报找不到 Python ≥ 3.11 | 系统自带的太旧（Rocky 9 是 3.9）：见 §3.0，或 `PYTHON=/path/to/python3 bash deploy/install-user.sh` |
| 日志说找不到 bwrap / git，命令行里明明有 | 用户单元的 PATH 是 `~/.local/bin` 加系统目录，不读 `.bashrc`：把自己装的 bwrap、git 链接进 `~/.local/bin` |
| 登录后又跳回登录页 | cookie 被拦：`public_url` 是 https 时必须用 https 访问；经反代时反代不能改写 Set-Cookie |
| 收不到钉钉 | 设置 → 通知 → 渠道「发送测试」；再看通知规则是否覆盖该事件；执行运行的那台的 secrets.env 里有没有 `DINGTALK_ACCESS_TOKEN`、能不能连钉钉中继 |
| SSE 首字节慢或断开 | 反代缓冲或超时：`proxy_buffering off`，并拉长 `proxy_read_timeout` |
| 服务的 MCP 工具没出现 | `GET /v1/services/<服务>/tools?reload=true` 看 `failed`；执行运行的那台用新版安装脚本装过（会装 `[mcp,dagster-mcp]`）；`mcp.envs` 里列了该环境、服务在该环境启用；`${VAR}` 在 secrets.env 里有值；日志搜「MCP 连接」 |
| dagster 的 MCP 工具报证书错误 | 线上 Dagster 是内网 HTTPS：在 `mcp.dagster.env` 里加 `DAGSTER_VERIFY`（CA 文件路径，或 `false`，§3.10） |
| `launch_job` / `reexecute_run` 返回「不在允许重跑的清单里」 | 服务定义 `mcp.dagster.env.DAGSTER_LAUNCH_JOBS` 没设或不匹配（整名匹配的正则） |
| `launch_job` / `reexecute_run` 返回「已经有运行在进行」 | 同一作业同一分区正在排队或运行，这是有意拦的：等它结束再重跑 |
| 平台 MCP（浏览器）没出现 | 改了 `mcp_servers` 要在各台重跑安装脚本；`npx` 能拉到包；角色写了 `"mcp:browser"`。启动日志有「平台 MCP 加载 N 个工具」 |
| MCP 工具报 `[调用失败]`、连接相关 | 适配器版本要是 0.3.x（`~/agent-platform/venv/bin/pip show langchain-mcp-adapters`），不对就重跑安装脚本（§3.3）；日志搜「MCP 常驻会话」看连接建没建起来 |
| 运行失败，`error_code` 是 `invalid_output` | 任务声明了 `output_schema`，agent 没交回合规的结构化结果：看时间线里 `submit_result` 的校验报错，放宽 schema 或在任务 / 角色提示词里写清字段 |
| 结论上方提示「模型调用次数到了上限」 | 主 agent 用满了 80 次模型调用（子代理 40 次），工具被停用、让它收尾：看时间线最后几步在做什么（有没有原地打转），改提示词或把问题拆小；要接着查就在同一会话里追问 |
| 运行失败，`error_code` 是 `step_limit` | 很少见：LangGraph 的步数兜底（主 280 步）先于调用次数上限用完。看时间线最后几步；可以续跑 |
| 时间线里出现「[重复调用] … 不再执行」 | agent 连续 5 次用同样的参数调同一个工具、结果都一样，被拦下了（第 3 次已提醒过）：多半是提示词让它在等一个不会变的状态，或者工具一直报同样的错 |
| 跑得久的 bash / py 在页面上看不到进度 | 进度写在 `runs.progress`，每 3 秒、输出有变化才写；表是平台启动时自动加列的（`ALTER TABLE … ADD COLUMN IF NOT EXISTS progress`），看平台日志里建表有没有报错 |
| 老会话续问时 agent 不记得前文 | 会话的 checkpoint 超过 `retention.checkpoints_days` 被清了，新一轮从头开始；交接摘要和记忆还在 |
