# 需求背景

本文说明这套 agent 平台要解决什么问题、面对的是什么现场、有哪些约束。怎么实现见[设计文档](设计文档.md)，怎么装见[部署指南](部署指南.md)。

本分支（`transition`）从 `colocated`（**同机部署**：agent 服务装在业务项目实际部署的主机上，直接面对线上现场）拉出来，
是**过渡期**的部署：先只在测试机上部署，生产的运行由测试机代管（见 4.2）。确认没有安全问题之后再切到生产机部署，回到同机部署。
master 上是更早的方案（独立机器 + 本机代码副本），差别和改的原因见第 6 节。

## 1. 要解决的问题

组里几个人维护 Vision 的几套业务服务。有几类工作要同时看代码、配置、库和线上现场才能做，又经常重复：

- 回答数据口径问题：报表上的某个数来自哪几张表、怎么算的；
- Dagster 资产物化失败时查根因：是上游延迟级联、数据问题还是代码问题；
- 部署之后检查报表页面和接口是否正常；
- 每天巡检报表数据的新鲜度和线上页面；
- 出了问题翻线上日志，看主机和 nginx 的状况。

希望由一套 agent 服务来做这些事：业务项目和组里的人随时能问；固定的检查按时自己跑，结论直接推到钉钉群。

## 3. 怎么用

1. **项目调 agent**：业务项目通过 HTTP API 或 Python SDK 请 agent 做事，例如问口径、分析一次报错、跑一次检查。
2. **任务自己跑**：定时（每天巡检 prod 和 test）、事件（Dagster 运行失败、GitLab 部署完成）或在控制台点一下触发，
   无人值守跑完，结果投递到钉钉或回调地址。
3. **在控制台对话**：组里的人直接提问，过程（模型调用、工具调用）实时可见，会话能接着问。

## 4. 需求

### 4.1 agent 要面对线上现场

- 读线上正在跑的代码；
- 看线上日志（应用、nginx、docker 容器、systemd 单元）和主机状况（负载、内存、磁盘、进程、监听端口、crontab、容器、nginx）；
- 查只读库（目前是 ClickHouse，以后可能有 MySQL、Doris、MongoDB）；
- 用项目线上用的解释器跑项目代码：import 项目模块，调项目自己的口径函数、ORM、Dagster 资产，口径和线上一致；
- 查线上 Dagster 的运行记录，必要时重跑作业。生产 Dagster 的作业重复运行没有影响，所以允许 agent 重跑。

另放一份代码副本做不到这些：副本和线上总有差别；配置全换成只读账号后，副本里很多地方跑不起来；
也看不到线上的日志、主机和 nginx。

### 4.2 部署

- 生产、测试各有自己的 agent 服务，共用一套控制台和一个 PostgreSQL。
- 哪个环境的任务就由哪个环境的 agent 服务执行。测试环境的 dagster 和 board 在两台机器上，测试环境就装两个，各管本机上的项目。
- **过渡期**：先只在两台测试机上部署，生产的运行也由它们执行（各管本机上的那几个项目）。生产也要能调用；因为不在生产机上，
  生产的日志、主机状况这些看不到，可以接受。生产库经控制台填的只读版配置（只读账号）照样能查；代码参考测试机上那份；
  生产的页面（Dagster、Board）用浏览器看。确认没有安全问题后再切到生产机部署。
- 和项目用同一个用户部署：不另起机器，不新建用户，基本不用 root。
- 平台不改线上：不拉代码、不装依赖、不启停业务进程。

### 4.3 安全：只保证数据库和内存

**数据库安全**，生产和测试的尺度不同（和组长确认过）：

| | 生产 | 测试 |
|---|---|---|
| 项目的配置文件 | 遮蔽：agent 看不到真实配置。每个服务的每个配置文件由人在控制台填一份只读账号的版本，运行时盖在项目读配置的路径上 | 不遮蔽：agent 直接用项目的真实配置 |
| 数据库只读靠什么 | 只读账号（项目代码会自己 import 配置、连库，靠规则拦不住，所以只给只读账号） | 提示词要求只读：只查不改，不执行写操作，不调会写库的项目函数 |
| 文件 | 项目文件只读，只有工作目录和 `/tmp` 可写 | 同左 |

两个环境都一样的：

- 生产环境的配置在测试的运行里也看不到；
- 平台自己的密钥（模型 key、平台库口令、引导密钥）在部署用户的 home 下，agent 都看不到；
- `db_query` 用的是服务定义里登记的只读账号。

**线上机器的内存安全**：模型写的代码（`py`、`bash`）限内存，超了只杀它自己，不影响同机的线上服务。
生产机和测试机内存一样，所有主机用同一组固定值：每个项目内核 32G、每条 bash 命令 8G，模型写的代码（所有内核和 bash）合计 64G；
平台进程不算在内，也不会因为这 64G 被杀。CPU 不限。

除此之外不做额外的管控：

- 不分权限，不做审批。用户是组里几个人，分工明确，都在内网；谁做了什么按 API 密钥名记在运行台账里。
- 给 agent 的配置不做并发编辑检查，不会有两个人同时改同一份。
- 会改动线上的只有 Dagster 重跑：可重跑的作业用正则限定，同一作业同一分区正在跑时拒绝。

已知并接受的风险：

- 测试环境的库账号可能有写权限，只读靠提示词约束；
- 网络不限（组里定的：只保证数据库和内存安全）：agent 跑的代码（`py`、`bash`）能访问内网里不需要认证的接口（比如 Dagster GraphQL）；
- 平台和项目是同一个用户，这个用户下的业务进程能读到平台的密钥文件。

### 4.4 模型

- Kimi（月之暗面开放平台，OpenAI 兼容），模型 `kimi-k2.7-code`，可以多把 key 轮换。
- 第二套模型配置当备用：平时只用第一套；第一套重试几次还超时 / 报错，自动切到第二套把任务接着做完，第一套好了再切回来。
  第二套可以是同一个账号的另一个模型，也可以是另一个账号或另一家 OpenAI 兼容的服务。
- 账号并发 3，prod、test 两边合计。不按分钟限速：一次响应回来，下一步立刻发请求。

### 4.5 其他约束

- 必需的外部依赖只有 PostgreSQL；不用容器，跑在部署用户的 systemd --user 里。
- 没有用户体系，身份就是 API 密钥。
- 钉钉只发不收。
- 服务、角色、任务的定义在控制台改，存库、带版本，改完就生效。
- 项目还在定架构阶段，没有发过正式版。

## 5. 不做什么

- 不做部署：代码发布、依赖安装、配置变更、业务进程启停照旧走项目自己的流程。
- 不做用户、权限和审批。
- 不做网络隔离。

## 6. 和 master 方案的区别

master 上的方案：平台装在一台机器上，新建一个独立用户；为每个服务、每个环境（prod / test / dev）拉一份代码，
跟踪 master，由平台自动同步、装依赖；每个环境一份配置文件；需要时由平台按环境起业务进程。

改成同机部署的原因：

- 本机副本和线上总有差别，排查线上问题时看的不是线上那份；
- 配置换成只读账号之后，副本里的 Dagster 很多地方跑不起来；
- 看不到线上的日志、主机状况和 nginx；
- 要单独建用户、配权限，还要维护代码同步和进程启停。

同机部署之后，平台不再管代码和进程，只需要保证数据库和线上机器的内存安全（4.3）；只读配置也只在生产用，
测试直接用真实配置。
