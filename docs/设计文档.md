# agent-platform v9 设计文档

读者：协作开发者。看完本文应能回答三件事：

1. 平台里有哪些对象。
2. 这些对象怎么连起来。
3. 某个功能的代码在哪。

版本号唯一出处是 `src/agent_platform/__init__.py`。接口的逐字段契约见 `docs/外部接口文档.md`，部署步骤见 `docs/部署指南.md`。

## 1. 平台是干什么的

平台是一套 agent 服务，装在业务项目（vision-dagster、vision-board、vision-web）实际部署的主机上，和项目用同一个 Linux 用户运行。
它有两类用法，所有设计都从这两类用法出发：

1. **项目调 agent**：业务项目通过 HTTP API 或 SDK 请 agent 做事，例如问数据口径、分析一次报错、
   跑一次检查。调用方是项目自己。
2. **任务自己跑**：由定时（每天巡检 prod 和 test）、事件（Dagster 失败、GitLab 部署完成）或人在网页上点一下触发。
   触发后无人值守跑完，结果投递到钉钉或回调地址。

同机部署是为了让 agent 直接面对线上现场。agent 可以：

- 读线上正在跑的代码目录；
- 读项目的配置：生产是给 agent 用的只读版（真实配置看不到），测试是项目的真实配置；
- 查只读库（`db_query`）；
- 看线上日志（应用、nginx、docker 容器、systemd 单元）和主机状况（`logs`、`host_status`）；
- 在线上用的解释器里跑项目代码（项目内核），生产的配置换成只读版；
- 用服务自己的 MCP 工具查线上 Dagster，在允许的范围内重跑作业。

### 1.1 项目背景与部署场景

项目还在定架构阶段，还没有发过正式版。目标部署场景是：

- 已有几套业务服务：vision-dagster（数据编排，docker 部署）、vision-board（报表展示，Django，nginx + 源码）、vision-web（配置管理，Django）。
  线上有国内生产（prod）、国内测试（test）两套部署，分在三台主机上：生产 172.24.16.100（`nmg-saturn-home1`）；
  测试 172.24.24.136（vision-dagster）、172.21.0.45（vision-board）；vision-web 的位置【占位】。
- 部署**一套统一的 agent 服务**，供这些服务共同使用。
- 平台装在这些主机上，每台一个 agent 服务，用部署项目的那个用户（生产机是 `vision-service`），跑在它的 systemd --user 里
  （`deploy/install-user.sh`）。生产机上的执行 prod 的运行；测试环境的项目分在两台上，各装一个，各管本机的项目。
  各台共用一个 PostgreSQL 和一套控制台。
- 代码、依赖、业务进程、线上配置照旧由项目原来的部署流程维护；平台只读，不改它们。

由此得出几条贯穿全文的设计决定：

| 决定 | 原因 | 落在哪 |
|---|---|---|
| **同机部署**：平台装在项目的部署主机上，用部署项目的同一个用户 | agent 要看的是线上现场：正在跑的代码、线上的解释器、真实的日志、主机与 nginx 状态。另放一份代码副本就得自己同步代码、装依赖、维护配置，和线上总有差别 | 全文 |
| **按环境分主机**：每台主机的 agent 服务在本机 `local.yaml` 写它负责的业务环境（`env`），同一环境的项目分在几台上时再写本机部署了哪些服务（`services`）；worker 只认领这些运行；各台共用一个库 | 一个服务×环境的现场只在一台主机上；台账、定义、配置、控制台仍然只有一套。服务定义里不用写部署在哪台，也不用判断哪台在线：那台没在跑时运行就排着，起来后接着执行 | §3 |
| **平台不改线上**：不拉代码、不装依赖、不启停业务进程 | 线上由项目自己的部署流程负责；平台只读，线上出了变化不会是平台改的 | §2.3 |
| **配置按环境给**（平台配置 `envs` 的 `protected`）：受保护的环境（生产）真实配置不给 agent，每个服务×环境×配置路径在控制台填一份只读账号的版本（存库、带版本），项目内核里盖在项目读配置的路径上；不受保护的环境（测试）直接用项目的真实配置 | 组长定的尺度：生产用只读配置遮蔽，项目代码会自己 import 配置，靠规则禁止拦不住，能做到的是 agent 拿得到的唯一口令是只读的；测试只要文件只读，加上提示词要求库只读（测试库账号可能能写，接受这个风险） | §2.3、§4 |
| **模型写的代码按白名单隔离**：bwrap 里文件只读，home 是空的，只挂回需要的目录；配置文件按环境遮蔽（§2.3），docker socket、systemd 用户总线遮蔽；独立 pid、ipc 命名空间；网络不限；每个内核、每条 bash 命令各一个 systemd 用户 scope 限内存（CPU 不限）；没有 bwrap 就拒绝执行 | 平台和线上项目是同一个用户，只把文件系统设成只读不够：只读也能读走口令、进生产容器、停服务、读别的进程的环境变量。内存超了只杀那一个 scope，不波及线上服务 | §4 |
| **跑项目代码用项目内核**（`py`） | 复现和取数多半只要调项目自己的函数（口径函数、ORM、资产），口径与线上一致 | §2.3、§4 |
| **看现场用写死的工具**：`logs` 只读服务声明过的日志，`host_status` 只看本机状况，命令由平台在沙箱外执行 | 模型只能选看哪个、看多少、怎么过滤，拼不了命令；日志和 docker 的读权限不用放进沙箱 | §4 |
| bash 沙箱里**按环境遮蔽配置文件**：生产的运行里遮蔽所有服务所有环境的配置文件，配置内容只能经 `service_info` 读给 agent 的只读版（打码）；测试的运行里只遮生产的，本环境的真实配置 bash、`py` 都能读 | 生产：工具输出会进模型上下文和运行台账，跨服务也遮，vision-board 的运行里读不到 vision-dagster 的配置。测试：组长定的尺度是文件只读即可，但生产的配置在测试的运行里照样看不到 | §4 |
| **模型账号的并发上限经库在各台之间共用** | 一个账号、几台主机：各台各算各的就会撞 429 | §4 |
| agent 只用 langchain `create_agent` + 三个自选中间件；**工具收敛**：读代码用 read / grep（按 bash 沙箱的规则），写文件、跑命令用 bash，批量 / 循环调工具在 `py` 里写 | 框架自带的英文提示词、文件工具、待办清单和平台约定重复或冲突；工具少、职责不重叠，模型不用在几种等价做法之间选 | §4 |
| 每次运行记**配方**（各定义与平台提示词的版本）；平台提示词存库、带版本 | 效果变了能对上是哪一版改的；回归重放两边对照、按版本统计都看它 | §3 |
| 定义里的口令写 `${VAR}`，用到时才取值 | 口令只放 secrets.env，不进库、不进接口、不进版本历史 | §2.3 |
| 工具（含 MCP）一律绑定本次运行的服务×环境；会话 thread 也按 服务×环境 分开 | 一套 agent 同时服务多套环境，不能查到别的环境，也不能把 prod 的对话上下文带进 test | §4 |
| **服务特有的能力挂在服务上**：服务定义的 `urls`（有名字的地址）、`logs`、`mcp`（服务自己的 MCP 工具），运行在哪个服务上就带哪个服务的；角色只管通用能力 | vision-dagster 的运行记录、vision-board 的页面地址只对一个服务有意义，写进角色就得每个服务复制一份角色；角色保持与服务无关 | §2.3、§4 |
| **只读库一个工具**：服务登记 `databases`（库名 → 连接串，scheme 决定类型），`db_query` 按类型选驱动和只读手段；超过 20 行的结果写进文件，agent 按需用 bash / py 读 | 各项目用的库不一样（种子里是 ClickHouse，也会有 MySQL、Doris、MongoDB）；整份结果进模型上下文既贵又容易截断 | §2.3、§4 |
| **记忆三分**：档案（人写）/ 记忆（agent 记下）/ 方法（可执行）；记忆权重**只罚不奖** | 三者来源、可信度、生命周期不同：档案逐字置顶不过期，记忆靠检索、会过时，方法要能直接跑。没人点 👍，正分没有信号，只有 👎 可用 | §5 |
| **runs 表就是执行队列**，不用外部编排服务 | 台账本来就是事实源，队列和台账合一；各台从同一张表认领自己负责的环境（和服务）的运行；少一个要装、要备份的服务 | §3 |
| **没有审批，也不分权限**：API 密钥只标识是谁，有效密钥都能做全部操作；受保护环境不拦操作，只决定配置怎么给 | 生产里 agent 拿得到的口令都是只读的，测试的库只读靠提示词；文件系统只读；会改动线上的出口只有 dagster 的重跑，有作业白名单和防撞车；调用方都在内网，谁做了什么按密钥名记在台账和版本历史里 | §2.6、§2.7 |
| 回归评测**默认用 👎**，也能拿最近的运行查退步 | 没人会去点 👍；👎 自带「错在哪」，正好当判卷标准，不用另外维护评测集；没被 👎 的运行把原答案当参照，看改动有没有带来退步 | §5.1 |

硬约束：

- 单部署：一套平台（各台主机上的 agent 服务、一个库、一套控制台）操作所有项目的所有环境。
- 主机 + systemd --user，不用容器，基本不要 root（少数一次性的系统设置见部署指南 §3.0）；必需的外部依赖只有 PostgreSQL。
- 单一模型 API：Kimi（月之暗面开放平台，OpenAI 兼容），可多 token 轮换；账号同时在途的请求最多 3 个，prod、test 合计，经库排队，不按分钟限速（§4）。
- 没有用户体系：身份就是 API 密钥，不分权限。
- 钉钉单向只发。
- 定义写库即生效。

### 1.2 和上一版相比删掉的

上一版平台装在一台独立机器上，为每个服务、每个环境另放一份代码副本。改成同机部署后删掉了：

- 自动拉代码、装依赖：内建任务 `code-sync`、代码跟踪（触发类型 `watch`）、同步步骤、部署配置 `code_sync`、表 `code_sync_state`；
- 业务进程的启停：服务定义里的进程定义、工具 `service_ctl`、systemd 模板单元、部署配置 `process_control`、表 `service_instances`、
  平台配置的「进程」一节、通知事件 `process_stopped`；
- 配置文件的「固定路径 + 代码目录外的真实文件 + 仓库里的上游模板」三件套，和模板变化的提醒（通知事件 `config_outdated`）、
  数据目录里的配置备份与同步补丁；
- 业务环境 `dev`；服务定义的 `repo`、`ref`、`sync`；`urls` 里的 `{port:进程名}`。

对应删掉的接口列在接口文档 §6。

## 2. 对象模型

```
平台配置          环境列表 / 通知 / 记忆 / 平台提示词：对所有人生效，带版本
服务 Service      一个业务项目：线上代码目录、解释器、配置路径、日志、只读库、地址、服务 MCP、档案、按环境启用
  服务×环境       agent 实际操作的单位，比如"vision-board 的 test"：目录/解释器/配置/日志/库/项目内核/服务 MCP 连接都按它解析
  给 agent 的配置  受保护的环境（生产）里服务×环境×配置路径一份只读版，带版本；项目内核里盖在项目读配置的路径上
角色 Role         可复用的能力：系统提示 + 工具 + 可委派的子代理。与服务无关
任务 Task         要做的事：目标 + 形态（agent / builtin）+ 输入 + 触发 + 投递 + 记忆开关 + 档案
  子任务          任务:对象名，同一件事针对某个具体对象（一张表/一条链路），只存差异
  触发 Trigger    任务上声明：api / chat / schedule（cron × 环境）/ event（来源 × 事件）
API 密钥          调用方身份：名字 = 发起方；只标识是谁，不分权限
运行 Run          一次执行：配方（各定义版本）+ (服务, 环境, 触发, 发起方) 的快照 + 全过程事件；runs 表兼执行队列
会话 Session      对话连续性：多次运行串成一段上下文；LangGraph thread 按 服务×环境 分开
档案/记忆/方法    档案：人写的，在服务 / 任务定义里；记忆：agent 记下的事实 / 教训 / 交接摘要，按服务分区；方法：可执行的做法与脚本
回归重放 Replay   改了定义或记忆之后，拿过去的运行（默认被 👎 的）用现在的定义和记忆重跑并判定
```

### 2.1 每个对象回答一个问题

| 对象 | 回答 | 存储 |
|---|---|---|
| 平台配置 | 平台默认怎么办 | `definitions(kind=config, name=节名)` |
| Service | 对哪个项目、在哪些环境可用、用哪个解释器 | `definitions(kind=service)` |
| 给 agent 的配置 | 受保护的环境里，某服务的某个配置路径 agent 用的只读版是什么 | `service_configs`（服务 × 环境 × 路径 × 版本） |
| Role | 谁来做（能力边界、能委派给谁） | `definitions(kind=role)` |
| Task | 做什么、何时做、结果给谁 | `definitions(kind=task)` |
| 档案 | 人确认过的口径、禁区、坑 | 服务 / 任务定义的 `profile` |
| 记忆 | agent 过去记下了什么 | `knowledge`（`kind` = fact / lesson / handoff）+ `knowledge_history` + `recall_hits` |
| 方法 | 以前是怎么做的、能直接跑的脚本 | `assets` + `asset_history`，文件本体在执行运行的那台主机的数据目录 |
| API 密钥 | 谁在调 | `api_keys`（只存 sha256 摘要） |
| Run | 这一次发生了什么 | `runs` + `run_events`（事实表，`runs.recipe` 记配方；`runs` 同时是执行队列） |
| Session | 哪些运行是同一段对话 | 运行的聚合键 |
| Replay | 改了定义之后，被 👎 的问题好了没有、别的有没有退步 | `replays` + `replay_items` |

粒度的尺子不变：一样东西同时具备独立生命周期、独立归属和独立审计需求，才值得做成独立对象；
否则做成字段或过滤器。所以「环境」不是独立对象：环境列表是平台配置里的一节，
「某服务在某环境是否启用」是服务自己的字段。

### 2.2 关系规则（写死）

1. **一次运行永远只有一个服务、一个环境**（平台任务除外，服务为空）。
   工具作用域和记忆的适用范围（按服务分区，`env` 为空即各环境通用）都挂在这两个维度上。跨服务的事，用会话串起多个运行来表达。
   运行由负责这个环境（和服务）的那台主机执行（§3）。
2. **任务归属**三选一：
   - `service: "vision-board"`：专属任务，只在 vision-board 上跑；
   - `service: "*"`：通用任务（如 data-qa、memory-gardener），调用时指定服务；
   - 不填：平台任务，不涉及业务服务，负责该环境的哪台都能执行。
3. **角色不知道服务**。角色是能力，任务是目标；同一个 `ops_analyst` 可以给任何服务干活。
   工具在运行时绑定到这次运行的「服务 × 环境」，模型无法跨服务调用。服务特有的工具挂在服务上（§2.3），运行在哪个服务就带哪个服务的。
4. **角色真正生效**：一次运行由任务指定的主角色执行，系统提示是这个角色的，工具是这个角色的（加上所在服务的 MCP 工具）。
   主角色可以在运行中把子问题委派给它声明的子代理，仍在同一次运行、同一个服务×环境里（§2.8）。
5. **环境是请求维度**：每个运行请求带 env，缺省为平台默认环境。业务环境只有 `prod`（国内生产，受保护）和 `test`（国内测试，默认）。
   - 服务的 `envs[env].enabled` 决定这个服务在哪些环境可用；
   - 任务的 `envs` 再限定任务能跑在哪些环境；
   - 受保护决定配置怎么给：受保护的环境（prod）agent 用控制台填的只读版，真实配置看不到；不受保护的（test）直接用项目的真实配置（§2.3）。
     受保护的环境在控制台上醒目显示，不拦任何操作。
6. **定义只有一套**：单部署就只有一套定义，各台读同一个库。`AGENT_ENV` 只决定读哪份部署配置（开发机还是生产 / 测试主机），
   与业务环境无关；这台负责哪个业务环境写在本机 `local.yaml` 的 `env` 里。
7. **配置分三层**，各管各的：

   | 层 | 存在哪 | 内容 |
   |---|---|---|
   | 部署参数 | `conf/` 文件 + 本机的 `~/.config/agent-platform/local.yaml` | 数据库、本机负责的环境与服务（`env`、`services`）、监听（`listen`）、模型（含上下文长度、并发）、执行并发（`worker`）、项目内核（`kernel`）、资源上限（`limits`）、沙箱（`require_sandbox`、`home_allow`、`hidden_paths`）、平台 MCP（`mcp_servers`）、链路追踪（`otel`）、数据保留（`retention`）、引导密钥 |
   | 平台配置 | 库 | 环境、通知、记忆、平台提示词 |
   | 界面状态 | 浏览器 | 主题、环境视角、对话页上次用的服务 / 环境 / 任务 / 记忆开关 |

### 2.3 服务（Service）

种子 `conf/seeds/services/vision-dagster.yaml`（略有删减；路径都是【占位】，部署时按实际改）：

```yaml
name: vision-dagster
title: Vision Dagster
root: ~/deploy/vision-dagster          # 线上的代码目录（agent 只读）；可写 {env}；~ = 部署用户的 home（平台和项目是同一个用户）
code_paths: []                         # 读代码 / 核对记忆新鲜度的目录；缺省 = [root]
python: ~/miniconda3/envs/vision-dagster/bin/python   # 项目解释器；线上跑在 docker 里时，要在宿主上另建一个装了项目依赖的环境
databases:                             # 只读库：{库名: 连接串}，scheme 决定类型；口令写 ${VAR}；envs[env].databases 按库名覆盖
  ck: "clickhouse://${CK_RO_USER}:${CK_TEST_RO_PASSWORD}@172.24.17.66:8123/default"
configs:                               # 项目读的配置路径（可写 {env}、~）。生产：真实内容 agent 看不到，内核里盖上给 agent 的只读版；测试：用真实的
  - ~/deploy/vision-dagster/.env
  - ~/deploy/vision-dagster/dagster.yaml
hidden:                                # 其他含口令的文件或目录：生产只遮蔽、不替换；测试不遮
  - ~/deploy/vision-dagster/docker-compose.yaml
logs:                                  # {名字: 文件路径（可带通配）| docker:<容器名> | journal:<systemd 单元>}，logs 工具读
  webserver: "docker:vision-dagster-webserver"
  daemon: "docker:vision-dagster-daemon"
  code: "docker:vision-dagster-code"
mcp:                                   # 服务自己的 MCP server：运行在本服务上时工具自动出现
  dagster:
    transport: stdio
    command: "{platform_python}"
    args: ["{platform}/mcp_servers/dagster_mcp.py"]
    env: {DAGSTER_URL: "{url:deployed}", DAGSTER_LAUNCH_JOBS: ".*"}   # 允许重跑的作业名正则；不设 = 只能查
    envs: {prod: {}, test: {}}         # 写了 envs 就只在列出的环境可用
envs:                                  # 按环境覆盖：只写差异
  prod:
    urls: {deployed: "https://vision-dagster-prod.ipa.zs:9902"}
    databases: {ck: "clickhouse://${CK_RO_USER}:${CK_PROD_RO_PASSWORD}@172.168.0.125:8123/default"}
  test:
    urls: {deployed: "https://vision-dagster-test.ipa.zs:9901"}
profile:                               # 服务档案：自由键，逐字注入该服务所有运行
  no_go: 不在宿主上起 dagster-daemon / webserver；要在线上重跑作业用 dagster 的 MCP 工具，不要在 py 里 materialize 去写库

```

| 字段 | 按环境覆盖 | 说明 |
|---|---|---|
| `root` | `envs.<环境>.root` | 线上的代码目录 |
| `code_paths` | `envs.<环境>.code_paths` | 读代码、核对记忆新鲜度的目录；缺省 `[root]` |
| `python` | `envs.<环境>.python` | 项目解释器；空 = `python3` |
| `env_vars` | — | 项目内核带上的环境变量，可写 `{env}`、`{python}`；不允许 `${VAR}`（会出现在内核进程的环境里，口令写进给 agent 的配置） |
| `urls` | `envs.<环境>.urls` 按键 | 有名字的地址，可写 `{env}` |
| `databases` | `envs.<环境>.databases` 按库名 | 只读库；值写空串 = 本环境没有这个库 |
| `configs` | — | 项目读的配置路径列表（受保护的环境里盖上只读版）；旧写法 `[{canonical, template}]` 仍能读，取 `canonical` |
| `hidden` | — | 含口令的其他路径：受保护的环境只遮蔽、不替换，不受保护的不遮 |
| `logs` | `envs.<环境>.logs` 按名字 | 值写空串 = 本环境没有这个日志 |
| `mcp` | `mcp.<名字>.envs` 深合并 | 服务自己的 MCP server |
| `profile` | `envs.<环境>.profile` 按键 | 服务档案 |
| `enabled` | `envs.<环境>.enabled` | 服务整体 / 在某环境是否接收运行 |

所有路径都要写绝对路径（可以 `~` 开头），`~` 展开成部署用户的 home。
服务定义里不写部署在哪台主机：哪台执行由各台 `local.yaml` 的 `env`、`services` 决定（§3）。旧定义里的 `node` 字段读取时忽略。

另两个种子：vision-board（Django，nginx + 源码；`configs` 是 `vision_board/settings-{env}.py`，`DJANGO_SETTINGS_MODULE=vision_board.settings-{env}`；
日志有应用的 `app` / `access` / `crontab` 和 nginx 的 `nginx_access` / `nginx_error`；prod 在生产机、test 在测试机 172.21.0.45；同样登记 `ck` 库）、
vision-web（Django 配置管理系统，结构同 vision-board，全部【占位】，还没登记只读库）。

agent 读到的「服务 × 环境视图」（`ServiceView`）由三部分组成：基座定义、该环境的覆盖、
渲染后的值（`root`、`code_paths`、`configs`、`logs`、`python`、`env_vars`、`urls` 里的 `{env}` 换成该环境，`~` 展开）。
提示词、工具和页面用的都是这一份；提示词（`[运行环境]`，`ServiceView.prompt_block`）里会写明「你就在这个环境部署它的那台主机上」，
以及配置怎么读：生产是给 agent 的只读版；测试是项目的真实配置，另加一行「数据库只读」（不执行 INSERT / UPDATE / DELETE / DDL，不调会写库的项目函数）。
`Registry.service_view(服务, 环境)` 是取视图的唯一入口，环境不存在时报 `unknown_env`。

**只读库**（`databases`）：`{库名: 连接串}`，库名小写字母开头。连接串的 scheme 决定类型：

| scheme | 类型 | 驱动 |
|---|---|---|
| `postgresql://` `postgres://` | PostgreSQL | psycopg |
| `mysql://` `mariadb://` | MySQL / MariaDB | pymysql |
| `doris://` | Apache Doris（MySQL 协议，默认端口 9030） | pymysql |
| `clickhouse://` `clickhouses://` | ClickHouse（HTTP 接口，默认 8123；`clickhouses` 是 HTTPS，默认 8443） | clickhouse-connect |
| `mongodb://` `mongodb+srv://` | MongoDB | pymongo |

`envs[env].databases` 按库名覆盖基座，值写空串表示这个环境没有该库。不认识的 scheme 保存时就拒绝。
三个驱动是平台的核心依赖。视图里的库名、类型、主机进 agent 的 `[运行环境]` 提示，查询走 `db_query`（§4）。

**地址**（`urls`）：有名字的地址，比如线上部署的页面或 API（`deployed`、`site`）。可写 `{env}`，`envs[env].urls` 按键覆盖。
渲染后出现在 agent 的 `[运行环境]` 提示里，浏览器之类的工具按它打开页面；`mcp` 配置里用 `{url:名字}` 引用。

**日志**（`logs`）：`{名字: 文件路径 | docker:<容器名> | journal:<systemd 单元>}`，名字小写字母开头。文件路径可带 `*` `?` `[` 通配，
读匹配到的最新那个文件（按日期滚动的日志写成 `~/deploy/x/logs/app-*.log`）。`logs` 工具只能读这里声明过的（§4）。

**服务 MCP**（`mcp`）：`{名字: langchain-mcp-adapters 连接配置}`，放这个服务特有的能力。规则：

- `envs: {环境: 覆盖}` 深合并到基础配置上；**写了 `envs` 就只在列出的环境可用**，没配的环境不会悄悄连到别处。只在服务启用的环境建连接。
- 字符串里的占位：`{env}`、`{url:名字}`（该环境的地址）、`${VAR}`（连接时才取值，口令只在 secrets.env）、
  `{platform}`（平台安装目录，仓库自带的 `mcp_servers/` 在它下面）、`{platform_python}`（平台解释器）。
- 运行在这个服务上时工具自动出现（角色 `service_tools: false` 时不带，§2.8），调用按运行的环境路由。连接由执行运行的那台主机建。
- 懒加载：第一次有运行用到（或调 `GET /v1/services/{s}/tools`）才连；按定义内容缓存，改了定义下次自动重连；
  有连接失败时 5 分钟后重试；一个连接失败不影响别的，只是少几个工具。
- 种子 vision-dagster 的 `mcp` 用仓库自带的 `mcp_servers/dagster_mcp.py`，经 GraphQL 连各环境线上部署的 Dagster
  （`urls.deployed`：prod `https://vision-dagster-prod.ipa.zs:9902`、test `https://vision-dagster-test.ipa.zs:9901`）。
  8 个工具：6 个查询（运行、运行日志、物化记录、最近运行、资产定义、作业列表）和 2 个重跑（`launch_job`、`reexecute_run`）。
  重跑用线上的真实配置在线上跑，约束三道：`DAGSTER_LAUNCH_JOBS` 作业名白名单（正则整名匹配，不设就不能重跑；种子是 `".*"`，
  已确认线上作业重复运行没有副作用）；同一作业同一分区（`dagster/partition` 标签）已有排队 / 运行中的就拒绝；
  `launch_job` 起的运行打标签 `agent/launched_by=agent-platform`（`reexecute_run` 沿用原运行的标签）。HTTPS 证书校验按 `DAGSTER_VERIFY`（默认系统信任，
  可写 CA 文件路径或 `false`）。安装脚本会装上 `agent-platform[mcp,dagster-mcp]`。

分工：高频、固定的操作做成 MCP（类型化的工具，agent 不用猜接口）；临时、不常用的，直接在 `py` 里用项目自带的客户端调。
代码在 `domain/services.py`（`urls_for`、`mcp_connections`）、`agent/tools/mcp_bridge.py`（`ServiceMcp`）、
`orchestration/pipeline.py`（`service_mcp_tools`）。

**按环境的开关只有一个**：`envs[env].enabled`。关掉意味着这个服务在该环境不接收运行（闸门第 2 环），
不起项目内核。

**配置按环境给**（`services/envspec.py`、`services/inspect.py`），由平台配置 `envs` 的 `protected` 决定（种子：prod 受保护，test 不受保护）：

| | 受保护（prod） | 不受保护（test） |
|---|---|---|
| 项目内核里 | 控制台填的只读版 bind 在项目读配置的路径上 | 项目的真实配置，不 bind |
| bash 里遮蔽 | 所有服务所有环境的 `configs`、`hidden` | 只遮受保护环境的；和本环境同一个路径的不遮（没写 `{env}` 的路径，比如 `~/deploy/vision-dagster/.env`，在测试机上就是测试那份） |
| `service_info(what=config)` | 读库里的只读版（打码） | 读本机上的真实文件（打码） |
| 没填只读版 | `py` 返回 `config_missing` | 不用填，没有 `config_missing` |
| 库只读靠什么 | 只读账号 | 提示词（真实配置里的账号可能能写，这是接受的风险） |

两种都一样：文件系统只读，只有工作目录和 `/tmp` 可写；home 是空的 tmpfs，平台自己的密钥看不到；docker socket、`agent-conf/`、
`~/.config/agent-platform`、`~/.ssh` 遮蔽；`db_query` 用服务定义里登记的只读账号。遮蔽哪些在 `envspec.masked_configs`，bind 哪些在 `envspec.runtime_spec`。

**给 agent 的只读版**（`store/service_configs.py`，只在受保护的环境）：生产的真实配置 agent 看不到，看到的是运维在控制台填的只读版。

- 存库：`service_configs` 表，按 服务 × 环境 × 路径（定义里 `configs` 的写法）存，每次保存一个新版本，记谁、何时；内容没变不加版本，
  超过 1MB 拒绝。保存直接存成新版本，不做并发编辑检查：组里几个人分工明确，不会有两个人同时改同一份。
  存库而不存文件：控制台的接口由哪台主机回答都能读写，只有执行运行的那台才需要文件。
- 落地：起项目内核前（`envspec.runtime_spec`），执行运行的那台主机把当前版本写到数据目录 `agent-conf/<服务>/<环境>/`（目录 700、文件 600；
  内容没变不重写，变了写临时文件再换名，正在跑的内核读的还是旧文件），再只读 bind 到项目读配置的路径上。
- 缺了就拒：某个路径还没有版本，或这个路径在本机不存在（bwrap 只能往已存在的路径上 bind），`py` 返回 `config_missing` 的说明。
- 读：`service_info(what=config)` 和控制台默认读的都是这份，按键名打码（键名像 password、secret、token… 的行，值换成 `***`），
  连接串里的口令也打码（`scheme://user:***@host`）；线上真实文件平台不读、不显示。
- 不受保护的环境不用填：控制台和接口读、存只读版都返回 `409 config_not_used`（`api/routes/services.py` 的 `_protected`）。
- 换版本：内核规格的摘要里有各配置的版本，下一次 `py` 前发现变了就重启内核（见下）。控制台由哪台主机回答，改出来的都一样。

**项目内核**（`services/kernel.py`，工具 `py`）：每个 会话×服务×环境 一个常驻 Python 进程，键和会话 thread 一样是
`<session_id>@<服务>:<环境>`。规格来自 `services/envspec.py`（`runtime_spec`）：

- 解释器是服务的 `python`（线上这个环境用的那个；可写 `{env}`，可在 `envs[env].python` 覆盖；空 = `python3`），工作目录是线上的代码目录，
  import 到的就是线上那份代码。
- 受保护的环境：本环境给 agent 的只读版 bind 在项目读配置的路径上，别的环境、别的服务声明的 `configs` 与 `hidden` 遮蔽。
  不受保护的环境：项目照常读本环境的真实配置，只遮受保护环境的（见上表）。
- 这台主机不负责这个服务×环境（`local.yaml` 的 `env`、`services`，`envspec.check_serves`）时拒绝（`wrong_env`），
  防止在别的主机上拿错代码。认领时已经按环境过滤过，这里是兜底。
- 沙箱（bwrap）：全盘只读；home 换成空目录，只挂回本服务本环境的代码目录、解释器所在的环境（写的路径和解析软链接后的都挂；
  conda 环境再加有 `conda-meta/` 的 conda 根目录）、方法目录、`home_allow`；scratch 整个可写，`$SCRATCH` 是本会话的工作目录
  `<scratch>/work/<会话键>`（和同会话的 bash 共用，和同机别的运行隔开），`/tmp` 独立；
  `/run/user/<uid>` 是空的；docker socket 遮蔽；独立 pid、ipc 命名空间；网络不限。
- 服务声明的日志文件（`logs` 里的文件，不含 `docker:`、`journal:`；带通配的取当前最新那个）在内核里换成可写的 `/dev/null`：项目 import 时就打开自己的日志文件
  （比如 Django `LOGGING` 的 `FileHandler`）不会报 Read-only file system。写进去的丢掉，内核里读这些文件是空的，看日志用 `logs`。
  bash 里不换。项目 import 时还写别的路径的照样报只读：写进 `logs`，或者（生产）在只读版配置里改成写 `/tmp`。
- 资源：每个内核一个 systemd 用户 scope（部署配置 `limits.kernel_memory`，32G；`tasks`；在 `agent.slice` 下），内存超了只杀这个内核；CPU 不设上限。
- 环境变量只带白名单（PATH、HOME、LANG…）、服务的 `env_vars` 与 `SVC_ENV`、`SVC_NAME`、`SCRATCH`；secrets.env 的变量不带。
- 可以直接 import 项目模块、调项目自己的口径函数 / ORM / dagster 资产，用项目的方式连库（生产连的是只读账号）。
  变量在会话内保留，最后一个表达式的值会显示，`restart=true` 清空。文件类方法的目录在 `sys.path` 上（§5）。
- 角色的其他工具（和服务 MCP 工具）在内核里是同名函数，经 RPC 回到平台执行（§4）。
- 驱动只用标准库，业务的 conda 环境里不用额外装东西。
- 空闲 30 分钟回收，每台主机同时最多 3 个，超了先回收最久没用的；都在执行代码时不打断，新会话的 `py` 在锁外最多等 120 秒空位
  （别的会话的调用照常进出），还没有才报「项目内核已满」（部署配置 `kernel.idle_minutes` / `kernel.max_kernels`）。
- 规格摘要（解释器、环境是否受保护、各配置的版本、环境变量、代码目录、遮蔽与挂回的路径、日志文件）变了，下一次调用前自动重启，结果开头注明之前的变量已清空；
  正在执行的不打断。设置里改了某个环境的受保护，那个环境的内核也因此重启。
- 服务在该环境停用、这台不负责这个服务×环境、给 agent 的配置缺失（只在受保护的环境）、代码目录不存在、找不到解释器时，`py` 直接报错。
- 没有 bwrap 时按 `require_sandbox`（默认 true）拒绝起内核；只有开发机关掉它，退化成直接在宿主上跑，只读版配置不会就位。

**口令**：只读库连接串（`databases` 的每一项，含各环境覆盖）、通知渠道的 url / token、MCP 连接配置里写 `${VAR}`，真实值放 secrets.env，
用到的那一刻才取（`credentials.expand`）。种子原样入库，播种时不展开。直接写了明文的，
接口回显时按库逐项打成 `***`，原样传回表示不改。服务的 `env_vars` 不允许 `${VAR}`。

**代码状态**：平台不改代码目录。代码目录在不在、`git log -1`（提交、标题、时间）、有没有未提交的改动
（`services/inspect.py` 的 `git_state`）只在部署主机上看得到，agent 运行时用 `service_info` 看。控制台的接口可能由另一台主机回答，
服务页不显示这些。

### 2.4 任务（Task）

```yaml
name: failure-analysis
service: vision-dagster
title: Dagster 失败分析
role: ops_analyst
form: agent                       # agent | builtin
input:
  run_id: {type: str, required: true}
  asset_key: {type: str, required: true, description: 失败的资产}
  error: {type: text, required: true}
envs: [prod, test]                # 能跑的环境；空 = 全部
triggers:
  - {id: on-failure, type: event, source: dagster, event: run_failure,
     rules: [{pattern: "connection.*(refused|timeout|reset)", category: infra, conclusion: 数据库/服务连接失败，检查目标服务存活与网络}],
     session: "dagster:{asset_key}:{error_class}:{date}"}
  - {id: api, type: api}
deliver: {channel: default}       # 或 {url: …}；不写 = 调用方自取
dedup: {key: run_id, window_s: 600}
memory: {recall: null, save: null}  # null = 跟随平台默认
timeout_s: 900
output_schema: null               # 可选：结构化输出的 JSON Schema（见下）
profile:                          # 任务档案（子任务只写差异）
  pitfalls: 资产失败先看上游资产是否完成，多数失败是上游延迟级联
```

**触发**全部声明在任务上，平台不写死「某个 webhook 跑某个任务」：

| type | 含义 | 关键字段 |
|---|---|---|
| `api` | 允许 `/v1/runs` 和 SDK 调用 | — |
| `chat` | 出现在对话页，可以多轮 | — |
| `schedule` | 定时，**每个环境各跑一份** | `cron`、`envs`、`input`、`timezone`；通用任务另需 `service` |
| `event` | 外部事件 | `source`、`event`、`filter`、`map`、`rules`、`session`、`service` |

事件走统一入口 `POST /v1/events/{source}`。来源适配器在 `triggers/sources.py`，把各家回调翻译成
「事件名 + 扁平字段」：Dagster 翻成 `run_failure`，GitLab 翻成 `deployment`，通用 webhook 直接透传。
新接一个事件源，就在这个文件里加一个函数，或者直接用通用 webhook。

`rules` 是规则先行：报错命中规则时**也建一条运行**（`resolution=rule`），直接成功、照常投递，
这样审计记录不留空洞。

**子任务**名形如 `failure-analysis:<资产>`，只嵌套一层，定义里只存差异：
档案按键合并，其他字段子任务写了就用自己的，没写就跟随父任务。

- 调用方显式带 `subtask` 来选用；平台不从输入里猜。
- 点名的子任务不存在时，按父任务继承建出来，闸门受理后才落库。
- 控制台在父任务的「子任务」标签里一行输入对象名就能新建，建完直接跳到它的档案。

**形态**：

| form | 含义 |
|---|---|
| `agent` | 一个主角色执行，需要时委派子代理（§2.8） |
| `builtin` | 内建处理器，不过模型。现在只有 `memory-gardener` |

API、对话、定时、事件四种入口对两种形态一视同仁。

**记忆园丁**（`memory-gardener`）是通用任务（`service: "*"`），种子里每个服务一条夜间定时（vision-dagster 03:00、vision-board 03:10、
vision-web 03:20，各跑 prod、test）。这样每次运行都由部署了该服务×环境的那台主机执行，拿记忆里的 `code_ref` 对照那台主机上线上的代码目录（§5）。

**通用入口 `ask`**（种子任务）：`service: "*"`、角色 `generalist`、声明 `chat` 与 `api` 触发、输入只有 `question`。
任何服务任何环境直接提问或交代一件事，不用先建任务；要定时、事件、投递、去重时再建正式任务。
`POST /v1/runs` 不写 `task` 就是 `ask`；对话没指定任务时，服务专属的对话任务优先，没有就用 `ask`。

**投递**（`deliver`）：结果总在运行台账里，调用方随时能取。`deliver` 只声明「另外推到哪」，
可以是设置 → 通知里的某个渠道，也可以是 HTTP 回调地址。投递失败重试 3 次，仍失败只记一条事件，不改运行状态。

**结构化输出**（`output_schema`）：给服务 / 自动化调用方用的、字段固定的结果。值是 JSON Schema，顶层须是 object，
保存时校验。声明了就给 agent 多一个 `submit_result` 工具，参数就是这个 schema：调用时当场校验，不合格把错误还给模型改；
最后一次通过校验的提交放进 `output.data`（`output.answer` 照旧是文字结论），运行详情和 HTTP 回调投递里都有。
运行结束还没交就提醒一次，仍没有则运行失败，`error_code` 为 `invalid_output`。代码在 `agent/factory.py`（`_submit_tool`、`invoke`）。

### 2.5 档案

档案有两层，都存在定义库里，逐字置顶注入，不走召回：

| 层 | 字段 | 作用范围 | 合并方式 |
|---|---|---|---|
| 服务档案 | `service.profile` | 该服务所有运行 | 可按环境覆盖 |
| 任务档案 | `task.profile` | 该任务 | 沿子任务按键合并 |

档案只记代码和配置里读不出来的东西：口径与术语、禁区、环境差异、踩过的坑。记忆里被反复用到、确认无误的事实可以升格进档案（§5）。
prepare 阶段统一拼装，原文落一条 `stage=profile` 事件。控制台的任务「档案」标签可以就地编辑；
子任务那一页会区分「继承的键」和「自己写的键」。

### 2.6 平台配置（设置）

| 节 | 管什么 |
|---|---|
| `envs` | 有哪些业务环境、默认哪个、哪些受保护（受保护：agent 用控制台填的只读版配置，真实配置遮蔽；不受保护：直接用真实配置，§2.3）；种子是 prod 国内生产（受保护）、test 国内测试（默认） |
| `notifications` | 渠道（钉钉 / webhook）+ 规则（事件 × 服务 / 环境 / 任务 / 触发 → 渠道） |
| `memory` | 召回、沉淀、交接摘要的默认开关与条数 |
| `prompts` | 平台提示词（见下） |

每节是 `definitions` 表里 `kind=config` 的一行，和其他定义一样有版本历史、可以恢复。
`conf/seeds/settings.yaml` 只在库里还没有这一节时播种一次。

**平台提示词**（`prompts`，`domain/prompts.py`）：所有角色共用的几段，以及平台自己发起的辅助模型调用。

| 键 | 用途 | 占位 |
|---|---|---|
| `base` | 每个主 agent 的系统提示开头（平台约定，其中写明不论哪个环境数据库都只读、生产格外谨慎，配置怎么读见 `[运行环境]`），后接角色提示词 | — |
| `subagent` | 每个子代理的系统提示开头，后接子代理角色的提示词 | — |
| `compaction` | 上下文压缩（§4） | `{messages}` |
| `distill` | 记忆沉淀（§5） | `{service}` `{env}` `{task}` `{input}` `{output}` |
| `handoff_summary` | 会话交接摘要（§5） | `{task}` `{input}` `{output}` |
| `replay_judge` | 回归判定（§5.1） | `{task}` `{where}` `{input}` `{old}` `{issues}` `{new}` |

带占位的是 `str.format` 模板，字面花括号写成 `{{ }}`，保存时校验（占位填不上、`compaction` 缺 `{messages}` 都拒绝）。
默认文本在 `domain/prompts.py`，种子 `prompts: {}` 把它写成第一版。改了下一次运行就用新的（agent 缓存的版本键含提示词版本），
每次运行的配方记着用的是第几版（§3）。平台升级改了默认文本时，库里存的某一节如果一字不差还是旧版默认（`BASE_V1` 等），
读出来就换成新的默认（`PromptsConfig._upgrade`），不另起版本；改过的保持原样，要用新写法就对照 `domain/prompts.py` 在设置页自己改。

记忆开关的优先级是：请求 > 任务 > 平台默认。通知不是写死在代码里的：「运行失败」（`run_failed`）、「运行成功」（`run_succeeded`）、
「负反馈」（`feedback_negative`）这些事件按规则发到渠道，任务投递也是选一个渠道。通知由执行运行的那台主机发。

### 2.7 身份

- 每个调用方一把 API 密钥（`api_keys` 表只存摘要），密钥名就是运行里的 `caller`。密钥只有名字、备注、过期时间，可吊销。
- 密钥只标识身份，不分权限：有效密钥和控制台登录都能做全部操作（发起运行、改定义与设置、管密钥、改记忆、改给 agent 的配置），没有 403。
- 控制台用密钥登录，换一个签名 cookie。登录时可以写操作人姓名，它会进版本台账和运行的发起方。
- 部署配置里的 `root_token` 是引导密钥：不可吊销，用于首次登录和建第一批密钥。

### 2.8 角色（Role）

```yaml
name: qa_engineer
title: 冒烟测试
description: 部署后按沉淀的方法跑冒烟脚本和页面检查   # 也是委派时给主角色看的「擅长什么」
prompt: …
tools: [py, bash, service_info, logs, host_status, save_asset, "mcp:browser"]
subagents: [ops_analyst]          # 运行中可委派的角色；null = 跟随父角色，[] = 明确不要
service_tools: true               # 自动带上运行所在服务的 MCP 工具；null = 跟随父角色（没有父角色就是 true）
extends: null                     # 继承父角色
prompt_append: ""                 # 有 extends 时追加在父角色提示词之后
```

| 字段 | 规则 |
|---|---|
| `tools` | 内置工具名或平台 MCP 工具名；`"*"` = 全部内置工具 + 全部平台 MCP 工具；`"mcp:<server>"` = 某个平台 MCP server 的全部工具，不用一个个列。写成 `sql_query` 的按 `db_query` 处理；没登记的名字忽略并记 warning |
| `subagents` | 主角色运行中按需把子问题委派给这些角色（平台的 `task` 工具，§4）：子代理用自己的提示词和工具、独立上下文，最后一条回复交回主角色。只委派一层，子代理自己的 `subagents` 不生效 |
| `service_tools` | 默认 `true`：运行所在服务声明的 MCP 工具（§2.3）自动带上；和 `tools` 里的工具重名时以 `tools` 为准。子代理按它自己的设置 |
| `extends` | 子角色写了 `tools`（非空）/ `subagents`（非 `null`）/ `service_tools`（非 `null`）就**整体替换**父角色的，没写就跟随；提示词在父角色之后追加 `prompt_append` |

**一个任务一个主角色**。需要多种能力时，给主角色挂子代理，由它在运行中按需委派（动态委派），
而不是把几个角色排成静态流水线（任务图仍然不要）。委派发生在同一次运行里，同一个服务×环境，工具同样绑定 RunScope。

种子角色：

| 角色 | 工具 | 子代理 |
|---|---|---|
| `generalist` | `["*"]`（通用入口 `ask` 用它） | `ops_analyst`、`data_searcher` |
| `ops_analyst` | py、bash、service_info、logs、host_status、db_query、save_asset、notify | `data_searcher` |
| `data_searcher` | py、bash、db_query、service_info | — |
| `qa_engineer` | py、bash、service_info、logs、host_status、save_asset、`"mcp:browser"` | `ops_analyst` |
| `inspector` | `extends: ops_analyst`，工具同 ops_analyst，提示词追加巡检要求 | `[]`（显式不委派） |

`ops_analyst` 的做法：先看档案、教训与交接摘要排除已知原因；再看线上现场（`logs`、`host_status`，服务有自己的工具时先用它）；
读代码和本环境的配置定位，用 `py` 只复现读的部分（生产的库是只读账号，写库的步骤会失败，这是预期的；测试用的是真实配置、账号能写，
写库的步骤一律跳过不调）；档案或任务说明允许时，用服务的 MCP 工具
在线上安全重跑（如 dagster 的 `reexecute_run`）并跟踪结果。

校验：子代理角色必须存在、不能列自己（`invalid_definition`）；被任务使用、被别的角色继承或列为子代理时不能删（`in_use`）。
`GET /v1/roles/{name}/resolved` 返回合并后的提示词、工具、子代理与继承链。
代码在 `domain/roles.py`（`resolve_role`）、`registry.agent_roles`、`agent/factory.py`、`agent/tools/catalog.py`（`Toolbox.expand`）。

## 3. 一次运行的生命周期

```
入口（API / 对话 / 定时 / 事件 / 网页 / 重跑 / 续跑 / 纠正 / 回归重放）
  → Submitter.submit(RunRequest)
      幂等键 → 解析任务 → 解析服务 → 解析环境 → 校验输入 → 闸门链 → 任务去重
      →（点名的子任务不存在就建）→ 建台账行 status=queued，pg_notify('runs_queued')
  → Executor（负责该环境的那台主机上的 worker）：认领 queued 行，改成 running
  → Pipeline.execute
      build_spec  台账行 → RunSpec
      prepare     重过开关（1–4）、记配方、拼档案、召回记忆、注入方法
      execute     agent：按角色装配执行 / builtin：处理器 / rule：直接给结论
      finalize    落 success、沉淀记忆
      deliver     投递结果
      任一步失败 → fail（落 failed）→ deliver
```

建行之后的一切都从台账行出发（`build_spec`）：新提交、续跑、重跑、纠正、回归重放走的是同一段代码。

**配方**（`runs.recipe`，prepare 时写，`Pipeline._record_recipe`）：这次运行用到的每样定义各是第几版。

```json
{"task": {"name": "failure-analysis:<资产>", "version": 3, "parent": {"name": "failure-analysis", "version": 7}},
 "role": {"name": "ops_analyst", "lineage": [{"name": "ops_analyst", "version": 5}]},
 "subagents": [{"name": "data_searcher", "lineage": [{"name": "data_searcher", "version": 4}]}],
 "service": {"name": "vision-dagster", "version": 12}, "prompts": 2, "model": "kimi-k2.7-code", "platform": "9.0.0"}
```

`lineage` 是继承链（根 → 自己）每一层的版本；`parent` 只有子任务有；`subagents` 只有 agent 形态且角色有子代理时有；`service` 平台任务没有；`prompts` 是平台提示词的版本，
只有 agent 形态有。`task_version` / `role_version` 两列另外单独写（`role_version` = 主角色继承链最末一层的版本），按版本统计用它们聚合。
运行详情和回归重放的两边都带配方。

**按版本统计**：`GET /v1/{tasks,roles}/{name}/version-stats`、`GET /v1/settings/prompts/version-stats`，每个版本的运行数、
成功 / 失败、被 👎 的运行数、平均 token 与耗时、首末次时间，新版本在前；回归重放的运行不算，角色按任务主角色的版本算
（`store/runs.py` 的 `version_stats`）。

**执行队列**：runs 表就是队列，不依赖外部编排服务（`orchestration/executor.py`）。

- 唤醒：进入 queued 时 `pg_notify('runs_queued')`，worker LISTEN 毫秒级唤醒，5 秒轮询兜底。
- 认领：按创建时间先到先得，`FOR UPDATE SKIP LOCKED`，多个 worker 并发也不会重复认领。部署配置写了 `env` 的 worker
  只认领 `env` 相同的行，再写了 `services` 的只认领这几个服务的行（平台任务没有服务，该环境哪台都能认领）；
  没写 `env`（开发机）的什么都认领（`store/runs.py` 的 `claim_next`，索引 `idx_runs_queue_env`）。
- 限并发：每个 worker 同时最多执行 `worker.max_concurrent_runs` 个（部署配置，默认 4），满了就不再认领。
- 心跳：执行中每 20 秒刷新 `heartbeat_at`，台账记下认领它的 `worker`（主机:pid）。只刷还归这个 worker、还在 running 的；
  发现运行已被取消或已判成孤儿（取消通知漏了也一样），就停下它。
- 取消：提交端先把台账标成 cancelled（事实源），再 `pg_notify('run_cancel')`，持有它的 worker 取消执行。
- 中断：worker 退出时，执行中的运行记为 failed / `interrupted`；worker 崩溃或被杀时心跳停了，
  维护循环把超过 120 秒没心跳的标为 failed / `orphaned`（一条 UPDATE，几台同时跑也只标一次）。两种都可以续跑。
- 落终态：只改还在 queued / running 的运行。已取消、已判成孤儿的，执行端迟到的成功 / 失败不覆盖它，也不沉淀记忆、不发通知。
  落终态时 `pg_notify('run_events')`，推流（运行详情、对话）马上收尾。
- 取消：执行端的 asyncio 任务被取消，正在跑的 bash 命令立刻被杀（不跑到自己的超时）；正在执行的 py 连内核一起杀掉
  （内核里那段代码停不下来，留着会让下一次调用读到它迟到的结果），会话的下一次 py 重起内核。
- 续跑：同一个 run_id 放回队列（`resume=true`），清掉上一次的 `error_code`、`finished_at`、`duration_ms`，
  从会话 thread 的 checkpoint 接着走，不重新拼提示。只有 agent 任务能续跑。

`agent-platform serve` 同进程跑接口和 worker（没有单独的 worker 进程）。不是开发机（`AGENT_ENV` ≠ dev）而部署配置没写 `env` 时，
拒绝启动 worker：不写就会认领所有环境的运行。

**按环境分主机**（同机部署，`config.Settings.serves`、`store/runs.py` 的 `claim_next`、`services/envspec.py` 的 `check_serves`）：
每台部署主机一个 agent 服务，所有主机共用一个库。

- 负责什么：本机 `local.yaml` 的 `env` 是这台负责的业务环境（`prod` / `test`，和 `AGENT_ENV` 无关）；同一环境的项目分在几台上时，
  再写 `services`（本机部署了哪些服务）。现在是：生产机 `env: prod`；测试机 172.24.24.136 `env: test`、`services: [vision-dagster]`；
  测试机 172.21.0.45 `env: test`、`services: [vision-board, vision-web]`（vision-web 测试在哪台【占位】）。
- 提交不看主机：台账行只记服务和环境。负责它的那台没在跑时，提交照常受理，运行停在 queued，那台起来后接着执行。
- 执行时再核对：项目内核起之前核对这台负责不负责这个服务×环境，不负责就 `wrong_env`（运行时的失败，不是接口错误码）。
- 定时在每台都跑，幂等键 `schedule:<任务>:<触发器>:<环境>:<计划时间>` 保证每次只建一条；维护循环也在每台都跑，都是幂等的。
- 开发机（不写 `env`）：认领一切。

**执行步骤**在 `orchestration/pipeline.py`。agent / 内建步骤限时 = 任务的 `timeout_s`（上限 7200 秒）；
模型排队（§4）的时间也算在里面。finalize 先落 success，之后的纠正取代、沉淀、
通知都是旁路，失败只留日志，不翻案运行结果。投递失败重试 3 次，仍失败只留一条事件。

**定时**（`orchestration/scheduler.py`）：进程内每 20 秒按 cron 检查一次，把上次检查以来该触发的各提交一次，每个环境各一份。

- 不重复：幂等键 `schedule:<任务>:<触发器>:<环境>:<计划时间>`，worker 重启或多个 worker 同时在跑都只建一条；
  运行失败也不释放这个键，否则别的主机会把同一时刻再触发一遍；
- 不重叠：同一触发器在同一环境上一次定时触发的运行还没跑完（排队 / 运行中），这次跳过；
- 不补：停机期间错过的不补，启动时只回看 90 秒；
- 不用同步：每轮读最新定义（定义缓存最多 5 秒），改了定时、停了任务，下一轮就生效。

子任务只有自己声明了 `triggers` 才有自己的定时，否则每个子任务都会继承父任务的定时、重复触发。

**维护循环**（`orchestration/maintenance.py`）随 worker 每分钟一轮，每台各跑一份：
心跳超时的运行（不论在哪台主机）标 failed / `orphaned`；每 6 小时按部署配置 `retention` 清一次数据（`store/retention.py`）：

| 数据 | 默认 | 规则 |
|---|---|---|
| 过程事件 `run_events` | 90 天 | 已结束的运行；被 👎 过的运行不清（回归重放要看） |
| 会话 checkpoint | 30 天 | thread 的最后一轮结束超过保留期就整串删掉，之后这个会话不能再续跑，新一轮从头开始 |
| 召回埋点 `recall_hits` | 90 天 | 按记录时间 |
| 工作目录 scratch | 7 天 | 本机的；超过保留期没动过的文件删掉，`work/<会话>/`、`queries/<run_id>/` 按目录算 |

runs 行本身（输入、输出、配方、状态）一直保留。

**去重**：调用方的幂等键（请求头 `Idempotency-Key`，最长 200 字符）不限时间窗，失败的运行会释放这个键（定时触发的除外，见上）；
任务声明的去重（`dedup`）看时间窗内同键的运行，排队、运行中、成功的都算，
所以重复回调不会在前一次还没跑完时再起一份。

**闸门链**在 `orchestration/gates.py`，是唯一的判断点，拒绝时带稳定的原因码：

1. `service_disabled`：服务停用
2. `service_env_disabled`：服务在这个环境停用
3. `task_disabled`：任务停用，或子任务的父任务停用
4. `env_not_allowed`：任务的 `envs` 不含该环境
5. `trigger_not_allowed`：任务没声明这种触发

续跑、重跑、纠正、回归重放只过 1–4；新提交（含定时、事件）过 1–5，控制台手动运行不受第 5 环约束，因为那是人点的。
worker 认领后 prepare 再过一遍 1–4：排队期间开关可能变了，没过就落 failed，`error_code` 是对应的原因码。

**状态机**：`queued → running → success | failed | cancelled`。
`resolution` 记录运行是怎么结束的：`agent` / `builtin` / `rule`。

## 4. agent 执行

- **按角色装配**（`agent/factory.py`）：一个角色 = 一个 langchain `create_agent`。`AgentFactory` 按（角色, 服务, 服务 MCP 的版本,
  输出 schema）缓存编译好的 agent，版本键是角色与子代理继承链各层的版本 + 平台提示词的版本，一改就变，下一次运行自然用新的。
  一个 agent 由这几部分组成：
  - 系统提示 = `prompts.base` + 角色提示词，有子代理时附子代理清单，声明了 `output_schema` 时附交回说明；
    每次运行（续跑除外）原文落一条 `stage=system` 事件；
  - 工具：角色的工具（展开 `"*"` 与 `"mcp:<server>"`）、所在服务的 MCP 工具（`service_tools`），
    加上平台按需添的 `task`（有子代理时）和 `submit_result`（有 `output_schema` 时，§2.4）；
  - 三个中间件：补齐悬空的工具调用（中断 / 续跑后历史里有没回复的 tool_call，模型 API 会拒收，补一条「未执行」的回复）；
    上下文压缩（`SummarizationMiddleware`：历史到部署配置 `model.context_tokens`（默认 400000）的 75% 时，把早期消息压成摘要，
    保留最近 20 条，提示词是 `prompts.compaction`）；执行守卫（`ExecutionGuard`，见下）。

  没有框架自带的英文提示词、文件工具、待办清单，也没有自动的通用子代理（read / grep / todo 是平台自己的，见工具目录）。
  用户消息开头是 `[时间]`（本机时区的当前时间和星期，模型不知道今天几号），然后是档案、服务 × 环境视图、召回块与方法。
- **执行守卫**（`ExecutionGuard`，`agent/factory.py`；参照 Kilo Code 的 max-steps、doom loop、prune）：
  - 模型调用次数：主 agent 80 次、每次子代理调用 40 次（一次「想 → 调工具」算一次）。到了不报错：最后一次调用前追加一条
    「步数用完」的提示、停用工具（`tool_choice="none"`；要交结构化结果的只留 `submit_result`，提示改成先交结果再简述），
    让 agent 交代查明了什么、结论、还剩什么；
    记一条 `stage=step_limit` 事件，运行照常成功，`output.step_limit = true`，页面在答案上方提示可能没查完、要接着查就在同一会话里追问或纠正
    （同一会话的下一轮带着这次的上下文，再给 80 次）。
    LangGraph 的步数上限（主 280、子 150）只剩兜底，撞上才以 `step_limit` 失败。
  - 重复调用：同一工具、同样参数、结果也一样，连续第 3 次时在结果后面提醒换个查法，第 5 次起不再执行、直接回一条错误
    （时间线上照样记一对 tool_call / tool_result）。`todo` 不算；轮询（同样的命令、结果在变）不提醒也不拦；
    同一条消息里并发的同样调用、同会话上一轮的调用不连着算。
  - 修剪旧工具输出：发给模型前，最近 6 条工具结果和从后往前累计 6 万字以内的原样保留，更早的换成一行说明（工具名、原长度，
    落过盘的保留文件路径）。新的可修剪的攒够 2 万字才成批修剪一次，两批之间发给模型的前缀不变（模型那边的前缀缓存才用得上）。
    `todo`、`task`（子代理的结论）、`submit_result` 不修剪。只改发给模型的，checkpoint 里的历史不变。
- **模型**（`model/chat.py`、`model/pool.py`）：Kimi 开放平台（OpenAI 兼容，部署配置 `model`，默认 `kimi-k2.7-code`）。
  - `ChatModel` 继承 langchain 的 `ChatOpenAI`，把 Kimi 响应里的 `reasoning_content`（流式按块拼接）留在消息上，
    时间线的 `model_call` 里显示为思考；发回给模型时不带。
  - `RotatingTokenAuth` 逐请求轮换 token。账号的并发上限装在 httpx 客户端的 `send` 上（`QuotaClient`），agent 的模型调用、平台的辅助调用、
    SDK 的每次重试都过它，有空位就发；撞了 429 或网关错误由 SDK 按 `model.max_retries` 退避重试。
  - 并发上限 `model.max_concurrency`（默认 3）是**整个账号**的，prod、test 各台共用，经共用的库排队（`SharedQuota`，
    装配时 `share_quota_via_db()` 打开）：每个名额一把 PG 会话级 advisory lock，抢到的请求独占一条专用连接，到响应体读完（流式读完）
    才断开、归还名额；进程挂了连接断开，锁自动释放，不会卡死名额。名额都占着时每 0.2 秒再试。
    每台主机先过一道同样大小的本地信号量，所以一台主机为模型名额最多占 3 条 PG 连接。
    不按分钟限速：一次响应回来，下一步有空位就立刻发。进程内版本 `Quota` 只在没连库时（测试）用。
  - `ModelPool` 跑平台的辅助调用（记忆沉淀、交接摘要、回归判定）。
  - 没有嵌入接口：不配 `model.embedding_name`，召回只用 pg_trgm（§5）。
  - 同时在途的模型请求超过 3 个时，多出来的在模型这一层排队，排队时间记在 `model_call` 的 `queued_ms` 里；
    调大 worker 的并发（`worker.max_concurrent_runs`）不会让它变快。
- **子代理**：角色声明的每个子代理各编译成一个 agent（系统提示 = `prompts.subagent` + 子代理角色的提示词，自己的工具和中间件）。
  主 agent 的 `task` 工具（参数 `subagent`、`description`）把子问题交给它，子代理在独立上下文里跑完，最后一条回复作为工具结果交回。
  只一层；子代理里发生的模型调用、工具调用在时间线上带 `agent` 字段。
- **工具绑定运行**：每次运行生成一个 `RunScope`（run_id、会话、服务视图、环境、是否受保护、通知渠道、沙箱的遮蔽路径与 home 白名单）。
  工具从 scope 里取服务和环境，签名里没有 `service`/`env` 参数，模型想跨服务也做不到。
- **工具目录**（`agent/tools/catalog.py`）：

  | 工具 | 作用 |
  |---|---|
  | `py` | 项目内核（§2.3）：在线上的代码目录和解释器里执行代码，配置在生产是给 agent 的只读版、在测试是项目的真实配置；import 项目模块、调项目函数、直接调角色的其他工具（见下）；变量会话内保留，`restart=true` 清空。输出超过 20000 字时全文写进 `$SCRATCH/outputs/py-*.txt`，返回预览 + 路径；跑得久时每 3 秒报一次输出尾部；运行被取消时杀掉内核（变量清空，下次调用重起）。标为危险工具 |
  | `bash` | bwrap 沙箱（见下）：全盘只读、home 只露代码目录和解释器环境、scratch 和 `/tmp` 可写、网络不限，调用结束进程全灭。每次调用是新的 shell（`cd`、`export` 不带到下一次），当前目录是本会话的工作目录（`$SCRATCH`，和 py 共用）；PATH 最前面是本服务项目解释器所在目录（python / pip / pytest 用项目的环境），带上服务的 `env_vars`。stdout 和 stderr 按先后合在一起；给模型的最多 12000 字（开头 1/3 + 结尾 2/3），超了全文写进工作目录的 `outputs/bash-<时间>-<随机>.txt`（最多 200MB）、返回里带路径，内存里只留开头和结尾各 64KB。超时返回退出码 124；运行被取消（或超时）时立即杀掉命令（沙箱命名空间随之全灭），不会在后台跑到自己的超时。跑得久时每 3 秒把输出尾部写进 `runs.progress`（见下）。标为危险工具 |
  | `read` | `read(path, offset=1, limit=2000)`：带行号读文件，一次最多 2000 行、50KB，单行超过 2000 字截断，末尾提示怎么用 `offset` 接着读；二进制文件拒读；路径是目录时列出内容。相对路径相对本服务本环境的代码目录。在平台进程里读，能读什么按 bash 沙箱的规则判断（home 白名单、遮蔽的配置、`/proc` 等看不到；路径和白名单 / 遮蔽项都按解析软链接前后两种比），和 bash 里一致：先打开文件，再按打开的那个文件的真实路径（`/proc/self/fd`）查一次，查和读之间换软链接也读不到别处；FIFO、设备不读；单行再长也不会整行读进内存。角色有 `bash` 就自动带上 |
  | `grep` | `grep(pattern, path="", glob="", ignore_case=false)`：在代码里按正则搜，返回 `文件:行号:内容`，最多 300 条、每个文件 50 条、每行 400 字；`path` 不填搜本服务代码目录。在 bash 的沙箱里跑（遮蔽的配置搜不到）：沙箱里看得到 `rg` 就用 ripgrep（跳过 .gitignore 里的和二进制文件），否则 `grep -rnIE`。角色有 `bash` 就自动带上 |
  | `todo` | `todo(items)`：整份替换这次运行的待办清单（`content` + `status`：pending / in_progress / completed / cancelled）。运行详情的侧栏显示主 agent 最后一次的清单。所有角色都有，不用写 |
  | `service_info` | `overview`：服务 × 环境视图，加代码目录当前的 git 提交、每个配置的状态（生产：给 agent 的只读版填没填、第几版；测试：真实配置在本机在不在）；`config`：读本环境的一份配置（打码；生产读库里的只读版，测试读本机上的真实文件）；`git`：代码目录最近 10 次提交 |
  | `logs` | `logs(name, lines=200, grep="", since="")`：读本服务本环境声明过的日志（`hostlocal.read_log`）。文件（带通配的读最新那个）取最后 N 行；`docker:<容器>` 用 `docker logs --tail N --timestamps [--since]`；`journal:<单元>` 用 journalctl，先查系统日志（平台用户要在 systemd-journal 组里）、没有再查用户日志。`lines` 最多 2000，给模型的最多 12000 字，超了全文写进 `outputs/logs-*.txt`。`grep` 是不分大小写的正则：文件在整个文件里流式搜（超过 512MB 只搜末尾 512MB），docker / journal 在最后 5 万行里搜，返回最后 `lines` 条匹配和匹配总数。`since`（如 `30m`、`2h`、`"2026-10-21 08:00:00"`）对 docker、journal 有效，文件忽略。`name` 不填列出有哪些 |
  | `host_status` | 本机现状（`hostlocal.host_status`）：负载、内存与 swap、`/` 和代码目录所在磁盘、占内存最多的 10 个进程；本服务的进程（命令行里带代码目录的）、监听端口（`ss -ltnp`）、本用户的 crontab（去掉注释行）、本服务容器（服务 `logs` 里 `docker:` 的）的 CPU / 内存（`docker stats --no-stream`）；`docker ps -a`、`systemctl is-active nginx`（没在跑也显示状态） |
  | `db_query` | `db_query(query, db="")`：查该服务该环境登记的只读库（见下） |
  | `save_asset` | 沉淀方法；`files` 是相对本会话工作目录的路径 |
  | `notify` | 发到通知渠道 |
  | MCP 工具 | 平台 MCP 与服务 MCP 两种，同样绑定服务×环境（见下） |
  | `task` | 角色声明了 `subagents` 时出现：把子问题委派给子代理（见上） |
  | `submit_result` | 任务声明了 `output_schema` 时出现：交回结构化结果，当场校验（§2.4） |

  工具集刻意收敛：文件工具只有只读的 read / grep（写文件用 bash，工作目录可写、服务代码只读），没有单独的代码编排工具。
  `read`、`grep` 跟着 `bash`、`todo` 所有角色都有，由 `Toolbox.expand` 在运行时加上，角色定义里不用写（库里已有的角色不用迁移）。
  工具输出超过各自的上限时，全文落在工作目录的 `outputs/` 下（`agent/tools/outputs.py`，bash / py / logs 都是），
  模型拿到开头 + 结尾的预览和路径，再用 `read`（offset）或 `grep` 看需要的部分；和 `queries/` 一样按工作目录的保留期（默认 7 天，§3）清理。
  agent 取数靠 `db_query`、`py`（用项目自己的数据访问层）和 bash。
- **db_query**（`agent/tools/db.py`）：`db` 填库名，只登记了一个库时可省略。`query` 是一条 SQL（用该库自己的方言），
  MongoDB 写 JSON：

  | 写法 | 做什么 |
  |---|---|
  | `{"collection", "filter", "projection", "sort", "limit", "skip"}` | 查文档 |
  | `{"collection", "pipeline"}` | 聚合；不能有 `$out` / `$merge` |
  | `{"collection", "count"}` | 计数，`count` 是过滤条件 |
  | `{"collection", "distinct", "filter"}` | 去重取值 |
  | `{"collections": true}` | 列出集合 |

  都可以另带 `"database"`，不带就用连接串里的库。只读按库的类型做：

  | 类型 | 平台这一侧的手段 |
  |---|---|
  | 所有 SQL 库 | 单条语句；开头关键字白名单（`SELECT` / `WITH` / `EXPLAIN` / `SHOW` 等，各库略有不同） |
  | PostgreSQL | 只读事务 + `statement_timeout` |
  | MySQL / MariaDB | 去掉字符串和注释后再查一遍写操作关键字（`INSERT`、`UPDATE`、`INTO OUTFILE`…）；只读事务会话 + `max_execution_time` / `max_statement_time` |
  | Doris | 写操作关键字检查；`query_timeout` |
  | ClickHouse | 写操作关键字检查；`readonly=2` + `max_execution_time` + `max_result_rows`（超了截断）；账号本身是 `readonly=1`（不许带任何设置）、报「Cannot modify … readonly」时去掉设置重试，查询里自己写了 `SETTINGS` 的不重试 |
  | MongoDB | 只允许上表几种读法；`maxTimeMS` |

  这些只是第一道，真正兜底的是服务定义里配的只读账号。每条限时 30 秒。结果 20 行以内直接返回表格；更多时整份结果边取边写进
  本会话工作目录下 `queries/<run_id>/` 的文件（SQL 库是带表头的 CSV，MongoDB 是 JSONL；bash / py 里按相对路径就能读，save_asset 也能收编），工具只返回行数、列数、前 20 行和文件路径，
  agent 再按需用 read / grep、bash（`awk`）或 py（pandas）读。最多取 10 万行、50MB，到上限就截断并注明。
  口令在连库那一刻才从 `${VAR}` 展开，取不到时返回 `[未配置]`。
- **py 里调工具**：角色白名单里的其他工具（`py` 自己除外）和运行所在服务的 MCP 工具，在项目内核里是同名函数
  （`db_query("select …")`、`service_info(what="config")`，返回文本）。调用时内核写一行 `{"rpc", "call", "args", "kwargs"}`，
  宿主在本次运行的上下文（RunScope）里执行该工具，回一行 `{"rpc", "result" | "error"}`（`services/kernel.py`）。
  要批量、循环地调工具时写一段 py，中间结果不进模型上下文；用户代码里有同名变量时不覆盖。
- **沙箱按白名单做**（`agent/tools/sandbox.py`、`services/envspec.py`）：平台和线上项目是同一个用户，「全盘只读」还远不等于安全：
  只读也能读走真实配置里的口令、用 docker socket 进生产容器、经 systemd 用户总线停服务、读同用户进程的 `/proc/<pid>/environ`。
  所以 bash 和项目内核都这样起：
  - `--ro-bind / /`，全盘只读；
  - home 换成空的 tmpfs，只挂回（只读）需要的目录。bash：这台主机负责的各服务的代码目录（跨服务排查要能读别的服务的代码）、
    各服务解释器所在的 conda / venv 环境（bash 里的 python、pytest 用项目的）、方法目录、`home_allow`（`envspec.sandbox_paths`）。项目内核：本服务本环境的代码目录、解释器所在的环境（写的路径和解析软链接后的；
    conda 环境再加有 `conda-meta/` 的 conda 根目录）、方法目录、`home_allow`（`envspec.runtime_spec`）。
    home 本身或它的上级不挂回（`home_allow` 里写了、从解释器路径推出来的都丢掉），否则平台密钥、`~/.ssh` 都会露出来；
  - scratch 整个可写，当前目录和 `$SCRATCH` 是本会话的工作目录 `work/<会话键>`（`db_query` 的结果文件在它下面的 `queries/<run_id>/`）；`/tmp` 是独立的 tmpfs；
  - `/run/user/<uid>` 换成空目录，碰不到 systemd 用户总线；
  - 遮蔽（文件换成 /dev/null，目录换成空目录）：服务声明的 `configs` 与 `hidden` 按环境遮（§2.3 的表，`envspec.masked_configs`）：
    生产的运行里所有服务所有环境的都遮，跨服务也遮，vision-board 的运行里同样读不到 vision-dagster 的配置；测试的运行里只遮受保护环境的，
    本环境的真实配置照常可读。两种环境都总是遮 `agent-conf/`、`~/.config/agent-platform`（平台密钥）、`~/.ssh`，不管 `hidden_paths` 写了什么
    （`config.Settings.always_hidden`），再加部署配置 `hidden_paths`（默认 docker 的两个 socket）；
  - `--unshare-pid`、`--unshare-ipc`：看不到同用户的其他进程，也碰不到它们的共享内存等 IPC；`--die-with-parent`；环境变量只有白名单，secrets.env 的变量不下发；
  - bash 另加 `--as-pid-1`（命令是命名空间的 init，调用结束整个命名空间被杀，后台进程不留）；
  - 网络不限（见下）；项目内核另把服务声明的日志文件换成可写的 `/dev/null`（§2.3），受保护的环境再把本环境给 agent 的只读版配置
    `--ro-bind` 到项目读的路径。

  生产的配置内容只能经 `service_info(what=config)` 读本服务本环境给 agent 的只读版（打码）；测试的真实配置 bash、`py` 都能直接读。
  没有 bwrap 时，`require_sandbox: true`（默认）直接拒绝执行；只有开发机关掉它，退化成直接在宿主上执行。
- **资源上限**（部署配置 `limits`）：只为线上主机的内存安全，只限内存，上限放得宽。每个项目内核、每条 bash 命令外面套一个
  `systemd-run --user --scope --quiet --collect --slice=agent.slice`，带 `MemoryMax`、`MemorySwapMax=0`、`TasksMax`
  （内核 `32G`、bash `8G`；进程 + 线程数 4096，numpy 这类库按核数开线程）。生产机和测试机内存一样，所有主机用同一组固定值。
  超了只在这个 scope 里 OOM，不波及线上服务和平台进程。`agent.slice` 里只有模型写的代码（所有内核和 bash），再设内存总上限
  （`deploy/user/agent.slice`，`MemoryMax=64G`）；平台进程不在 slice 里、不设上限，slice 到了 64G 也不会杀到它。
  CPU 不设上限：slice 的 `CPUWeight=20`，只在线上服务也要 CPU 时让着它们。
  systemd-run 要用 `XDG_RUNTIME_DIR` 找用户总线，进 bwrap 时再 `--unsetenv` 掉（`sandbox.scope_env`）。
- **agent 改不了线上**：bash 和 `py` 都是全盘只读（scratch 除外），装不了依赖、改不了代码和配置。生产的 `py` 连库用的是只读账号；
  测试的真实配置里账号可能能写，库只读靠平台提示词和 `[运行环境]` 的要求（只查不改，不调会写库的项目函数）。
  会改动线上的出口只有服务 MCP 里明确开放的操作（vision-dagster 的 `launch_job` / `reexecute_run`，有作业白名单和防撞车，§2.3）。
  网络有意不限（组里定的：只保证数据库和内存安全，需求背景 §4.3）：`py`、bash 都能访问内网接口，没有鉴权的（比如 Dagster 的 GraphQL）
  也能直接调，作业白名单只约束 MCP 工具。这个风险是接受的。
- **MCP 工具分两种**（`agent/tools/mcp_bridge.py`）：

  | | 平台 MCP | 服务 MCP |
  |---|---|---|
  | 写在哪 | 部署配置 `mcp_servers` | 服务定义的 `mcp`（§2.3） |
  | 放什么 | 通用能力，比如浏览器 | 某个服务特有的能力，比如 vision-dagster 的运行记录 |
  | 怎么用上 | 角色里写工具名、`"mcp:<server>"` 或 `"*"` | 运行在这个服务上自动出现（角色 `service_tools: false` 时不带） |
  | 何时连接 | 平台启动时，改了要重启 | 第一次用到时（懒加载、按定义内容缓存、失败 5 分钟后重试） |

  两种都绑定服务×环境：每个环境一份连接，同名工具的各环境版本合成一个工具，调用时按 RunScope 路由到本次运行的环境；
  没配该环境的连接就如实返回「不可用」，不会退回到别的环境。MCP 工具调用出错（连不上、服务端报错）也如实返回给模型，不炸运行。
  平台 MCP 也能写 `service`（只在该服务的运行里可用）和 `envs`，但服务特有的能力推荐写进服务定义。
- **MCP 会话常驻**（`McpSessions`）：适配器默认每次工具调用新开一条连接（stdio 就是每次新起一个进程），有状态的 server
  （浏览器：先 navigate 再 snapshot）状态会全丢。平台按 会话 × 连接 保持一条常驻 MCP 会话，同一个会话里的调用落在同一条连接上；
  空闲 30 分钟回收，同时最多 16 条（超了回收最久没用的），连接断了或连接配置变了（服务定义改了）下次调用自动重连，平台关闭时全部关掉。
  取工具清单仍是一次性连接。
- **会话 thread 按 服务×环境 分开**：`thread_id = <session_id>@<服务>:<环境>`（`RunSpec.thread_id`），
  同一个会话键（比如事件模板 `dagster:{asset_key}:…`）在 prod 和 test 不共用上下文；项目内核也用这个键。
  thread 存在 PG checkpointer 里，崩溃后可以断点续跑；最后一轮结束超过 `retention.checkpoints_days` 后被清掉（§3）。
  thread 只装本段对话，太长时由压缩中间件收成摘要，长期连续性由记忆层承载。
- **过程事件**（`run_events`，运行详情的时间线）：

  | kind | 内容 |
  |---|---|
  | `stage` | 阶段：profile / recall / assets / system（系统提示原文）/ output（提醒交回结构化结果）/ step_limit（模型调用到上限、停用工具收尾）/ resume / deliver 等 |
  | `model_call` | 每次模型调用一条：哪个 agent（子代理才带 `agent`）、模型、耗时（其中排队等账号并发名额的部分单记 `queued_ms`）、输入 / 输出 / 总 token、调了哪些工具，以及思考（Kimi 的 `reasoning_content`；没有时是调工具前说的话）。平台的辅助调用（记忆沉淀、交接摘要、回归判定）也记一条，带 `purpose` |
  | `tool_call` / `tool_result` | 工具调用与返回，子代理里的带 `agent` |
  | `final` / `error` | 结论（有结构化结果时带 `data`）、出错 |

  辅助调用的 token 计入运行的 `tokens`。
- **执行中的进度**（`runs.progress`，`agent/tools/progress.py`）：工具调用要到结束才有 `tool_result`，跑几分钟的 pytest、pandas
  汇总在时间线上看不出动静。bash 和 py 跑得久时每 3 秒（输出有变化才写）把输出尾部（最多 2000 字）写进 `runs.progress`，
  一次调用一个键 `{tool, title, output, ms, at}`，工具结束删键，运行结束（`set_status`、孤儿清理、续跑入队）整列清空。
  只写这一列、不写事件，不会让 `run_events` 膨胀；运行详情接口返回它，页面在「执行中」下面显示。
  py 的进度由内核驱动里的线程每 3 秒发一行 `{"progress", "out", "ms"}`，和工具调用的 rpc 共用一把写锁。
- **链路追踪**（可选，`observability.py`）：部署配置 `otel` 打开后，经 OTLP/HTTP 导出到任意兼容后端（Jaeger、Tempo、各家 APM）。
  LangChain 探针把模型调用、工具调用做成 span，每次运行一个根 span（挂 run_id / 任务 / 服务 / 环境），辅助模型调用各一个 span。
  页面不依赖它，时间线来自 `run_events`。

### 4.1 agent 能力与性能边界

数值写在代码里（`agent/tools/`、`services/hostlocal.py`、`services/kernel.py`、`agent/factory.py`）或部署配置里（`worker`、`kernel`、`limits`、`model`）。

| 项 | 边界 |
|---|---|
| 模型看到的输出 | bash 12000 字、py 20000 字、logs 12000 字（文件按正则搜最多扫 20 秒），超了给开头 + 结尾的预览，全文在工作目录 `outputs/`（bash 全文最多 200MB，平台内存里只留首尾各 64KB）；read 一次 2000 行 / 50KB；grep 300 条；db_query 预览 20 行，整份写进 `queries/<run_id>/` 的 CSV / JSONL |
| 旧的工具输出 | 最近 6 条、或从后往前 6 万字以内的原样发给模型，更早的换成一行说明（落过盘的留路径）；省不到 2 万字不动 |
| 时间线里的工具结果 | `run_events` 每条截到 4000 字，只给页面看；模型拿到的按各工具自己的上限 |
| 超时 | bash 默认 60 秒、最多 600；py 默认 120 秒、最多 1800；db_query 每条 30 秒；任务 `timeout_s` 最多 7200 秒（含模型排队） |
| 每次调用的开销 | bash 每次都起 `systemd-run --user --scope` + bwrap（几十到约 150 毫秒），而且是新的 shell；py 跑在 会话×服务×环境 的常驻内核里，第一次付项目 import 的代价，之后很快，空闲 30 分钟回收 |
| 每台主机的并发 | `worker.max_concurrent_runs` 4 个运行；`kernel.max_kernels` 3 个内核，第 4 个并发会话的 py 最多等 120 秒；模型并发 3，所有主机经库共用，排队时间记在 `model_call` 的 `queued_ms` |
| 内存 | 每个内核 32G、每条 bash 8G（各一个 scope），`agent.slice` 合计 64G |
| 步数 | 主 agent 每次执行 80 次模型调用、子代理每次调用 40 次；到了停用工具、让 agent 交代查明的和没做完的，运行照常成功（`output.step_limit`），要接着查就在同一会话里追问（下一轮再给 80 次）。LangGraph 步数上限（主 280、子 150）只是兜底，撞上才以 `step_limit` 失败，可续跑 |
| 重复调用 | 同样的参数、同样的结果连续第 3 次提醒，第 5 次不执行；结果在变的轮询不管 |
| 进度 | bash / py 跑得久时每 3 秒一条输出尾部（`runs.progress`），页面「执行中」下面显示 |
| 上下文 | 到 `model.context_tokens` 的 75% 时把早期消息压成摘要 |

要留意的代价与风险：

- 长运行每一步都写 LangGraph checkpoint，行数随步数涨；最后一轮结束 `retention.checkpoints_days`（30 天）后才清。
- bash 没有常驻的 shell 状态，要连着做的写进同一条命令；要跨调用留变量用 py。
- 回归重放不拦服务 MCP 里有副作用的工具（如 dagster 的 `launch_job` / `reexecute_run`，§5.1）。

## 5. 记忆

记忆层分三样，来源、可信度和生命周期都不同：

| | 是什么 | 谁写 | 怎么进提示词 | 存在哪 |
|---|---|---|---|---|
| 档案 | 口径、禁区、环境差异、踩过的坑（§2.5） | 人 | 逐字置顶注入，不检索、不过期 | 服务 / 任务定义的 `profile` |
| 记忆 | agent 记下的事：`fact` 事实（口径、表与字段、拓扑）/ `lesson` 报错教训（带报错指纹与类别）/ `handoff` 会话交接摘要 | agent 沉淀；人可录入、改正 | 召回（见下） | `knowledge` 一张表 |
| 方法 | 可执行的做法与脚本：`procedure` / `script` / `query` / `baseline` | agent 用 `save_asset`；人可登记 | 该任务的优先、其次服务通用的，整段注入 | `assets` + 数据目录里的文件 |

教训的 key 是 `lesson:<指纹>`：同一服务同一指纹只有一条，新结论覆盖旧的，旧内容进历史。
报错指纹（`store/knowledge/lessons.py`）取报错末两行，抹掉易变部分（`file:line`、Python traceback 的 `File "…", line N`、
十六进制地址、uuid、数字、引号里的字面量）后哈希；`file:line` 规则排在纯数字之前，否则行号先被抹掉、规则失效。

**分区**：记忆按服务分区，`env=''` 表示对该服务所有环境成立。沉淀时默认记成通用的；模型判断「只在本环境成立」
（`env_specific: true`，比如这个环境特有的配置、数据量、主机）的才记在本环境下。召回 = 本环境的 + 通用的；
交接摘要按 服务 + 环境 取，prod 的对话结论不会带进 test。方法按 服务 × 环境 分区。

**召回**（`memory/recall.py`）在 prepare 阶段，档案另起一块（§2.5），之后按顺序拼：

1. 前序交接摘要：同一类事件的上一个会话的结论（会话键去掉最后一段就是「同一类」，如 `dagster:<资产>:<错误类>`）；
2. 同类报错的教训：有报错输入时按指纹精确命中，本环境的优先，其次通用的；
3. 记忆混合检索：事实与教训一起，pg_trgm + pgvector，RRF 融合，再按权重调整（见下），条数是 设置 → 记忆 的 `knowledge_limit`。
   没配嵌入模型（Kimi 没有嵌入接口）时只用 pg_trgm。
   `code_ref` 引用的文件自记录的提交以来改过即过期（看的是 `git diff 记录提交 HEAD -- 文件`，不是仓库 HEAD 变没变：
   线上每次部署都会换提交，别的文件的提交不让它过期；记录的提交已不在仓库里时按过期处理）。代码目录是部署主机上线上的那份，
   所以核对在部署主机上做（记忆园丁按服务×环境由部署它的那台执行，§2.4）。
   本任务谱系（自己 → 父任务）沉淀的排前面，兄弟子任务的排后并标来源。

方法单独一块。文件类方法（沉淀的脚本）的目录在项目内核启动时加到 `sys.path`（环境变量 `AGENT_METHOD_PATHS`），
`py` 里可以直接 import，不用复制一遍。

命中写 `recall_hits`：「30 天命中」、可升格都从它算，运行被 👎 时也据此找到它召回过的条目。回归重放的运行不写；
旧版本留下的 `source=playground` 行统计不算。

**沉淀**（`memory/distill.py`）在 finalize 阶段：一次轻量模型调用，提炼出事实（带 `code_ref`：文件路径 + 当前提交）
和教训（有报错输入时，按报错算指纹）。有会话时，再写一份四节交接摘要：结论、被否方案、当前约束、未决问题。
两段提示词是平台配置 `prompts.distill` / `prompts.handoff_summary`（§2.6）；这两次调用作为 `model_call` 记进该运行的时间线，token 计入运行。
纠正（§3）成功后，取代本会话上一轮沉淀的记忆。

**权重只罚不奖**（`store/knowledge/retrieval.py`、`store/feedback.py` 的 `shift_memory_weight`）：

- 没人会去点 👍，正分没有信号，所以 👍 只留档、不改权重；
- 整次运行被 👎 时，它沉淀的记忆和它召回的记忆各扣 1 分（排序时最多算到 -5）；改主意、撤回按差值回补；
- 人工录入的条目（没有来源运行）加 3 分（`MANUAL_BONUS_POINTS`）；
- 方法仍按来源运行扣分；
- 终排 = RRF 名次分 + 分数 × 系数，在截断前加权：人写的后排条目能挤进前几名，反复惹麻烦的会沉下去。

**升格**：被反复用到、确认无误的事实，值得从记忆升格成档案（逐字置顶、不过期）。

- `GET /v1/knowledge/promotable` 列出候选：近 30 天被 ≥ 5 次运行召回、没挨过 👎 的事实。
- `POST /v1/knowledge/{id}/promote {target: service | task, key, task?, content?}` 写进服务档案（条目只在某环境成立时写进
  `envs[env].profile`）或任务档案；同一个键已有内容就接在后面。原条目标为被取代
  （`superseded_by = profile:<目标>:<键>`），召回不再重复注入。

**反馈**是人对一次运行（或其中一步）的评价，由三部分组成：分数、问题类型（结论不对、口径不对、取数有误、
没答全、工具用错等）和文字说明。规则如下：

- 一个人对同一步只有一条反馈，改主意就是覆盖，所以重复点 👎 不会把分扣两次。
- 整次运行的 👎 按变化量调整权重（见上）；单步评价只留档。
- 新的 👎 按通知规则（`feedback_negative`）推给负责人，运行页的「反馈」标签是收件箱。
- 想让 agent 按意见重答，走「纠正」：同会话开新一轮，成功后取代上一轮沉淀的记忆。👎 面板里可以一并勾选。

代码在 `domain/feedback.py`、`store/feedback.py`、`api/routes/feedback.py`。

人可以在三处直接维护记忆：记忆页、任务详情的「记忆」标签、服务详情的「记忆」标签。
接口见 `docs/外部接口文档.md` §7：新建事实或教训（教训要给报错原文，按它算指纹）、登记方法、改正内容、让条目过期、升格。

### 5.1 回归重放

改完角色提示词、任务定义、档案、平台提示词或记忆（包括 👎 带来的扣分）后，拿过去的 agent 运行用现在的一切重跑，
看人指出的问题改好没有、别的有没有退步。代码在 `orchestration/replay.py`、`store/replays.py`、`api/routes/replays.py`。

默认用 👎：没人会去点 👍，而 👎 自带「错在哪」（问题类型、说明、被点的那一步），正好当判卷标准，不用另外维护评测集。
没被 👎 的运行（选最近的运行，或点名任意一条）把原答案当参照，看有没有退步。

一次重放是一批：

1. **选样**：默认取被 👎（整次或某一步）的 agent 运行，最近被评的在前；`negative_only=false` 取最近结束（成功 / 失败）的 agent 运行，
   新的在前。都可按任务（含子任务）、服务、环境、最近几小时（👎 按评价时间，其余按运行创建时间）筛，默认 20 条；
   也可以直接点名任意结束了的 agent 运行。重放出来的运行、还在跑的、规则命中的、内建任务的不进样本，点名了也逐条拒（`error`，带原因）。
2. **重跑**：每条原运行用同样的输入开一个重放运行，触发类型 `replay`（运行详情的 `replay_of` 指向原运行）：
   新会话、不投递，只过闸门 1–4。记忆隔离（按 `RunSpec.replay_of`）：
   - 召回用**现在**的记忆（之后的修正和 👎 扣分都算），但去掉原运行自己沉淀的：事实、教训、方法（`source_run` = 原运行），
     以及原会话自己的交接摘要；前序交接摘要按原运行的会话找，和原运行当时看到的一致；
   - 只读：不沉淀、不记 `recall_hits`、不加方法的使用次数、不标过期；`save_asset`、`notify` 返回「[回归重放] …」，什么也不做；
   - 服务 MCP 的工具**不拦**：dagster 的 `launch_job` / `reexecute_run` 在重放里照样会在线上执行。
3. **判定**：重放运行结束后，一次模型调用（提示词 `prompts.replay_judge`，记在重放运行的时间线上）对照
   「原答案 + 人指出的问题（问题类型、说明、被点的那一步；没被 👎 的写「无」）+ 新答案」判定：

   | 判定 | 原运行被 👎 | 原运行没被 👎（原答案当参照） |
   |---|---|---|
   | `fixed` | 已改好：被指出的问题解决了，且没引入明显的新错 | 更好：明显更准确、更完整、依据更充分 |
   | `same` | 没改好：问题还在 | 持平：结论一致、质量相当 |
   | `worse` | 更差：更糟，或引入了明显的新错 | 退步：和原答案矛盾又拿不出更充分的依据，或丢了关键内容 |
   | `unclear` | 判断不了（要看实际数据才能确认，或判定调用失败） | 同左 |
   | `error` | 重放运行没建成（被闸门拒，或不能重放） | 同左 |

   默认的 `replay_judge` 按这两种读法写（占位不变）；库里存的还是旧版默认原文的，读出来时换成新的（§2.6），改过的仍是自己的写法。

   重放运行没有成功结束时不调模型：原运行是成功的记 `worse`，否则记 `same`。
4. **对照**：详情里逐条给出原答案、新答案、两边的配方（§3）、判定与理由；每条标出原运行有没有被 👎，判定按对应的读法显示。
   还没判或 `unclear` 的可以重判。

## 6. 接口（/v1）

接口按资源组织，过滤参数平铺，错误体统一为 `{"error": {"code", "message", "detail"}}`。
完整契约见 `docs/外部接口文档.md`。

| 资源 | 端点 |
|---|---|
| 定义 | `/v1/{services,roles,tasks}`：列表、新建、单个、`PATCH`、删除、版本、恢复；角色与任务另有 `version-stats` |
| 子任务 / 定时 | `/v1/tasks/{t}/subtasks`、`/v1/tasks/{t}/schedule` |
| 服务 × 环境 | `/v1/services/{s}/envs/{env}`、`…/config?path=&raw=`（`PUT` 保存、`/history`、`/history/{version}`）、`/v1/services/{s}/tools?reload=` |
| 运行 | `POST /v1/runs`、`GET /v1/runs`、`/{id}`、`/{id}/events`、`/{id}/stream`、`/{id}/cancel\|rerun\|resume\|correct\|feedback` |
| 回归重放 | `/v1/replays`、`/{id}`、`/{id}/judge` |
| 对话 | `POST /v1/chat`（SSE）、`/v1/sessions` |
| 事件 | `POST /v1/events/{source}` |
| 记忆 | `/v1/knowledge`（含 `/promotable`、`/{id}/promote`）、`/v1/assets` |
| 设置 | `/v1/settings/{section}`、`/v1/settings/prompts/version-stats`、`/v1/api-keys` |
| 其他 | `/v1/meta`、`/v1/stats`、`/v1/search`、`/auth/session`、`/healthz` |

接口设计的几条原则：

- **定义的读写只有一套**：三种定义同一组端点；修改一律是 `PATCH`，请求里出现的顶层字段整体替换，合并在库里的最新版本上
  （新建、修改都不看各进程的定义缓存）。
- **动词端点只用于状态迁移**：cancel / rerun / resume / correct / judge / promote。
  其余操作都是资源的增删改查。
- **提交回执说清楚发生了什么**：是否命中去重、是否顺带建了子任务，调用方不必再查一次就能知道。
- **拒绝原因可编程**：`code` 稳定，`message` 给人看。

## 7. 网页（控制台）

控制台是 React + TypeScript 单页应用，用 esbuild 构建，Tailwind v4 编译 CSS，交互组件用 Headless UI。
路由和查询缓存是自写的小模块，没有引入重型框架。构建产物 `webui/dist` 不进仓库：安装脚本在装了 Node 的主机上按当前代码构建，
没有 Node 时先把别处构建好的 dist 拷进仓库再装；由 FastAPI 同进程托管。

`node scripts/build.mjs preview` 会产出一个带 mock 数据的单文件预览，不连后端也能看全部页面。

- **顶栏**：全局环境切换（全部 / prod / test）、⌘K 全局搜索与命令。
- **侧栏**：概览、服务、任务、运行、对话、记忆；底部是「设置」和用户菜单（主题、退出）。
- **列表页**（运行、对话、记忆）：顶部都有快捷筛选，包括服务、环境、任务、触发、发起方等。
  筛选状态全部放在 URL 里，可以分享、可以回退。列表总是定时刷新（页面可见时）；运行列表每页 50 条；
  时间一律显示相对时间，超过 7 天显示 `MM-DD HH:mm`。
- **服务页**：
  - 「环境」标签：按环境开关服务、查看覆盖项；代码目录在不在、git 提交只有部署主机上看得到，页面不显示（agent 用 `service_info` 看）；
  - 配置文件：受保护的环境按路径编辑给 agent 的只读版，看版本历史（谁、何时），没填的标出来；不受保护的环境不显示编辑器，
    只说明 agent 直接用项目的真实配置；
  - 任务、近期运行、记忆、版本。
- **任务列表**：按服务分组。有子任务的父任务可以展开，子任务缩进列在下面，并标出档案待补、可以直接运行。
  搜索同时匹配对象名，命中时父任务自动展开；也可以一键展开全部子任务。
- **运行页**：「运行」「反馈」「回归重放」三个标签。「反馈」默认只看 👎，可以按服务、环境、任务、问题类型筛选；
  「重放」按当前筛选发起回归重放，对话框里选样本（被 👎 的 / 最近的运行）。
- **记忆页**：「记忆」「方法」「可升格」三个标签；记忆的状态筛选默认生效中，第一个选项「挨过 👎」是生效中、`feedback_score < 0` 的条目。
- **任务页**：
  - 概览；
  - 档案（就地编辑）；
  - 子任务（一行新建）；
  - 记忆（这个任务名下的记忆与方法）；
  - 定义（分节表单：基本 / 输入 / 触发 / 结果与去重 / 记忆 / 环境 / 高级），子任务这一页是「覆盖」；
  - 运行、版本。
- **运行对话框**：表单按输入定义生成；对象（子任务）用可新建的下拉选择；记忆开关可以按次覆盖。
- **运行详情**：
  - 步骤时间线：系统提示、模型调用（耗时、token、思考）、工具调用，每一步可以 👍👎；执行中时末尾显示正在跑的 bash / py 的输出尾部；
    调用次数到上限收尾的结论上方有提示；
  - 上下文面板：待办（agent 的 todo 清单）、输入、配方、档案、召回、沉淀、同会话运行、谱系；
  - 操作：续跑、重跑、纠正、取消；结束了的 agent 运行（规则命中、内建、本身就是重放出来的除外）可以单独重放。
- **对话**：
  - 维度条：服务、环境、任务、对象、额外输入、记忆开关；
  - 新对话自动沿用上次的服务、环境、任务和记忆开关（存在浏览器里）；
  - 侧栏的会话列表可以按服务、环境、任务筛选。
- **设置**：环境（`/settings` 直接打开它）、通知、记忆、提示词、API 密钥、角色。主题在侧栏底部的用户菜单里切，环境视角在顶栏。

  config.py          部署配置（conf/base + conf/env/{AGENT_ENV}（可 extends）+ 本机 local.yaml，${VAR} 插值）；

  runtime.py         装配：store / registry / 通知 / 项目内核 / 工具 / 提交端 / 定时 / 回归重放；模型并发上限改走库（share_quota_via_db）；

依赖单向向下：

- `domain` 不依赖任何人；

- `api` 在最上面。
