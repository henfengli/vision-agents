# agent-platform v6 设计文档

读者：协作开发者。看完本文应能回答三件事：平台里有哪些对象、它们怎么连起来、
某个功能的代码在哪。版本号唯一出处是 `src/agent_platform/__init__.py`。

## 1. 平台是干什么的

一套 agent 服务，和若干业务项目（Dagster、board、配置中心…）部署在同一台机器上。
它有两类用法，所有设计都从这两类用法出发：

1. **项目调 agent**：业务项目通过 HTTP API / SDK 请 agent 做事——问数据口径、
   分析一次报错、跑一次检查。调用方是项目自己。
2. **任务自己跑**：定时（每天巡检 prod 和 test）、事件（Dagster 失败、GitLab
   部署完成）、人在网页上点一下。触发后无人值守跑完，结果投递到钉钉/回调。

项目和 agent 同机部署，主要是给 agent 当参考和调试对象：agent 能读项目的部署目录
和代码、读对应环境的配置文件、查只读库、按需启停某个环境的进程来复现问题。

硬约束：单部署（一套 agent 服务操作所有项目的所有环境）、主机 + systemd（无容器）、
单一内部模型 API（OpenAI 兼容，多 token 轮询）、无用户体系（服务间固定 bearer，
网页 cookie 登录）、钉钉单向只发、定义写库即生效。

## 2. 对象模型

```
环境 Env          prod / test / dev ……  平台级列表；可停用、可标"受保护"
服务 Service      一个业务项目：部署目录、代码、进程、各环境配置文件、只读库、档案
  服务×环境       agent 实际操作的单位——"board 的 test"：目录/配置/库/进程都按它解析
角色 Role         可复用的能力：系统提示 + 工具白名单。与服务无关
任务 Task         要做的事：目标 + 形态 + 输入 + 触发 + 输出。归属一个服务（或通用/平台级）
  子任务          任务:对象名——同一件事针对某个具体对象（一张表/一条链路），只存差异
  触发 Trigger    任务上声明：api / chat / schedule（cron × 环境）/ event（来源 × 事件）
策略 Policy       提交前的输入闸门：命中正则 → 拒绝 / 需审批
运行 Run          一次执行：(任务版本, 角色版本, 服务, 环境, 触发) 的快照 + 全过程事件
会话 Session      对话连续性：多次 run 串成一段上下文
记忆              知识（事实）/ 案例（教训）/ 方法（可复用的做法与脚本），按 服务×环境 分区
审批 Approval     人工门：提交审批 / 危险命令 / 产物门禁 / 受保护环境的进程启停
```

### 2.1 每个对象回答一个问题

| 对象 | 回答 | 存储 |
|---|---|---|
| Env | 操作哪套业务环境 | `definitions(kind=env)` |
| Service | 对哪个项目 | `definitions(kind=service)` |
| Role | 谁来做（能力边界） | `definitions(kind=role)` |
| Task | 做什么、何时做、结果给谁 | `definitions(kind=task)` |
| Policy | 能不能发起 | `definitions(kind=policy)` |
| Run | 这一次发生了什么 | `runs` + `run_events`（事实表，钉死定义版本） |
| Session | 哪些 run 是同一段对话 | run 的聚合键 |
| Instance | 某服务×环境的进程现在什么状态 | `service_instances` |

粒度尺子不变：值得成为独立对象，当且仅当同时有独立生命周期、独立归属、
独立审计需求；否则做成字段或过滤器。

### 2.2 关系规则（写死）

1. **run 永远只有一个服务、一个环境**（平台维护任务除外，服务为空）。记忆分区、
   工具作用域、权限边界都挂在这两个维度上。跨服务的事用会话串起多个 run 表达。
2. **任务归属**三选一：
   - `service: "board"`——专属任务，只在 board 上跑；
   - `service: "*"`——通用任务（如 data-qa），调用时指定服务；
   - 不填——平台任务（如 memory-gardener），不涉及业务服务。
3. **角色不知道服务**。角色是能力，任务是目标；同一个 `ops_analyst` 可以给任何
   服务干活。工具在 run 时绑定到该 run 的服务×环境，模型无法跨服务调用。
4. **角色真正生效**：一次 run 由任务指定的角色执行——系统提示是这个角色的，
   工具只有这个角色白名单里的。（v5 是一个主控 agent 带全部角色当子代理，
   主控自己握着 bash，角色白名单形同虚设。）
5. **环境是请求维度**：每个 run 请求带 env（缺省 = 平台默认环境）。任务的
   `envs` 限定它能跑在哪些环境；受保护环境（prod）上的写操作默认走审批。
6. **定义只有一套**：单部署就只有一套定义，`definitions` 不再带"实例环境"列
   （v5 的 instance env 维度去掉）。`AGENT_ENV` 只决定读哪份平台配置文件。

### 2.3 服务（Service）

服务定义把 v5 里分散在两处的信息合成一份（v5：`conf/services.yaml` 给 svcrun
起进程，`definitions(kind=domain)` 给 agent 看代码——描述的是同一个项目）：

```yaml
name: dagster
title: Dagster 数据编排
description: 数仓 ETL 编排，资产按天物化
root: /srv/dagster                # 部署目录（agent 只读访问）
code_paths: [/srv/dagster]        # 读代码/校验记忆新鲜度的目录；缺省 = [root]
configs:                          # 各环境配置文件：{env} 占位
  - canonical: /srv/dagster/dagster.yaml
    template: /srv/dagster/conf/dagster.{env}.yaml
processes:                        # 可启停的进程（可多个）
  webserver:
    cmd: [/srv/dagster/venv/bin/dagster-webserver, -w, workspace.yaml, -p, "{port}"]
    ports: {prod: 3000, test: 3001, dev: 3002}
  daemon:
    cmd: [/srv/dagster/venv/bin/dagster-daemon, run, -w, workspace.yaml]
envs:                             # 按环境覆盖（深合并）：只写差异
  prod: {hosts: [10.0.0.11], readonly_dsn: "postgresql://ro@prod-db/dagster"}
  test: {hosts: [10.0.1.11], readonly_dsn: "postgresql://ro@test-db/dagster"}
profile:                          # 服务档案：自由键，逐字注入该服务所有 run
  conventions: 资产按 dt 分区，T+1 物化
  no_go: prod 不手工触发 backfill
enabled: true
```

agent 读到的"服务×环境视图"（`ServiceView`）= 基座 + 该环境覆盖 + 该环境的配置
文件路径（`template` 渲染后）——提示词、工具、页面用的都是这一份。

**进程启停**：`processes` 由 `ProcessController` 管。生产走 systemd 模板单元
`agent-svc@<服务>.<进程>.<环境>.service`（ExecStart 是 `svcrun`，bwrap 把选中环境
的配置 bind 到 canonical、其他环境同名文件遮蔽）；开发机走本地子进程。每次启动
带租约（默认 2 小时，可续期），到期自动停——"按需启动，用完即停"。
受保护环境的启停需要审批。状态落 `service_instances`，页面和 API 同源。

### 2.4 任务（Task）

```yaml
name: failure-analysis
service: dagster
title: Dagster 失败分析
role: ops_analyst
form: agent                       # agent | graph | builtin
input:                            # 输入字段：类型 / 必填 / 说明（页面据此生成表单）
  run_id: {type: str, required: true}
  asset_key: {type: str, required: true, description: 失败的资产}
  error: {type: text, required: true}
envs: [prod, test]                # 能跑的环境；空 = 全部
triggers:
  - {id: t1, type: event, source: dagster, event: run_failure,
     rules: [{pattern: "connection.*refused", category: infra,
              conclusion: 连接失败，检查目标服务存活}],
     session: "dagster:{asset_key}:{error_class}:{date}"}
  - {id: t2, type: api}
output: {channel: dingtalk}       # caller | dingtalk | http(callback)
dedup: {key: run_id, window_s: 600}
timeout_s: 300
context:                          # 任务档案（子任务只写差异）
  pitfalls: 上游 ods 延迟会级联失败
```

**触发**全部声明在任务上，平台不再写死"某个 webhook 跑某个任务"：

| type | 含义 | 关键字段 |
|---|---|---|
| `api` | 允许 `/v1/runs` 和 SDK 调用 | — |
| `chat` | 出现在对话页，可多轮 | — |
| `schedule` | 定时，**每个环境各跑一份** | `cron`、`envs`、`input`、`timezone` |
| `event` | 外部事件 | `source`、`event`、`filter`、`rules`、`session` |

事件走统一入口 `POST /v1/events/{source}`。来源适配器（`triggers/sources/`）把各家
payload 归一成 `{event, env, service?, data}`：Dagster → `run_failure`，GitLab →
`deployment`，通用 webhook 直接透传。平台按 `source + event` 找声明了它的任务，
`filter` 过滤、`rules` 先行分类：规则命中也**建一条 run**（`resolution=rule`，
直接成功、照常投递），审计不再有空洞。新接一个事件源 = 写一个几十行的适配器，
或者直接用通用 webhook。

**子任务**：`failure-analysis:dwd_trade_order`，只嵌套一层；调用方显式带
`subtask`（或提交完整名）选用；点名不存在时继承父任务建桩，闸门受理后才落库。

**形态**：`agent`（单角色执行）/ `graph`（资产化任务图：节点是产物、边是依赖，
`route`/`map` 两个动态出口，输入指纹未变即复用）/ `builtin`（内建处理器，不过模型）。
调度、API、事件三种入口对三种形态一视同仁（v5 的调度一律起单 agent workflow，
图任务和内建任务定时跑都是错的）。

### 2.5 档案

两层，都在定义库里、逐字置顶注入、不走召回：服务档案（`service.profile`，
可按环境覆盖）对该服务所有 run；任务档案（`task.context`，沿子任务继承合并）
对该任务。只记代码和配置里读不出来的东西：口径与术语、禁区、环境差异、踩过的坑。
prepare 阶段统一拼装，原文落 `stage=profile` 事件。

## 3. 一次 run 的生命周期

```
入口（API / chat / schedule / event / 网页 / 重跑）
  → Submitter.submit(RunRequest)
      解析任务（子任务桩）→ 解析服务×环境 → 闸门链 → 去重/幂等 → 建行 → 启动 workflow
  → Workflow（Temporal）
      prepare   定版本、拼档案、召回记忆、注入方法
      execute   agent：按角色装配执行 / graph：解释任务图 / builtin：处理器
      finalize  落终态、沉淀记忆
      deliver   投递结果（失败只留事件，不翻案 run 状态）
```

**闸门链**（`orchestration/gates.py`，唯一判断点，拒绝带原因码）：

1. `env_disabled` 目标环境停用
2. `service_disabled` 服务停用
3. `task_disabled` 任务停用
4. `env_not_allowed` 任务的 `envs` 不含该环境
5. `trigger_not_allowed` 任务没声明这种触发（比如没有 api 触发却被 API 调用）
6. `policy` 输入策略 deny / require_approval

续跑、重跑、审批放行、调度只过 1–4；新提交过全部。

**状态机**：`queued → (awaiting_approval →) running → success | failed | cancelled`。
`resolution` 记怎么结束的：`agent` / `graph` / `builtin` / `rule`。

## 4. agent 执行

- **按角色装配**：`AgentFactory` 按（角色名, 角色版本）缓存编译好的 agent；角色的
  系统提示 + 工具白名单 + 平台基础提示（服务×环境视图、档案、召回块）。
- **工具绑定 run**：每个 run 生成 `RunScope`（run_id、服务视图、环境、审批钩子），
  工具从它取服务和环境，签名里没有 `domain`/`env` 参数——模型想跨服务也做不到。
- 工具清单：`bash`（bwrap：全盘只读、scratch 可写、默认断网、调用结束进程全灭）、
  `run_code`（CodeAct，桩函数回调白名单工具）、`read_file`/`write_file`/`edit_file`/
  `ls`/`grep`（scratch 内真实磁盘）、`service_info`（服务×环境视图、配置文件内容）、
  `service_ctl`（进程 status/start/stop/logs，受保护环境走审批）、`sql_query`（该服务
  该环境的只读库）、`host_metrics`（Grafana）、`save_asset`、`notify`（钉钉）、
  `read_artifact`（图任务产物）、MCP 工具。
- **危险命令审批**：bash/run_code/service_ctl 命中危险模式或作用于受保护环境，
  挂起等审批（DB 行是事实源，LISTEN/NOTIFY 毫秒唤醒，超时视同拒绝）。
- 会话即 LangGraph thread（PG checkpointer），崩溃可断点续跑；thread 只装本段对话，
  长期连续性由记忆层承载。

## 5. 记忆

召回（prepare）自上而下：档案 → 前序交接摘要 → 历史知识（pg_trgm + pgvector，
RRF 融合，反馈加权，code_ref 漂移即过期）→ 同类案例（报错指纹）→ 方法（该任务的
优先，其次服务通用）。沉淀（finalize）：一次轻量模型调用提炼知识与案例；有会话
时写四节交接摘要（结论 / 被否方案 / 当前约束 / 未决问题）。

全部按 **服务×环境** 分区：prod 沉淀的口径不污染 test。知识带来源任务，召回时
同谱系（自己→父任务）优先。纠正式反馈只取代最近一次 run 的沉淀。

## 6. 接口（/v1）

资源化、平面过滤、统一错误体 `{"error": {"code", "message"}}`。完整契约见
`docs/外部接口文档.md`，前端类型定义 `web/src/api/types.ts` 与后端
`api/schemas.py` 一一对应。

| 资源 | 端点 |
|---|---|
| 元信息 | `GET /v1/meta`（版本、环境、工具目录、事件源） |
| 环境 | `GET /v1/envs`、`PUT /v1/envs/{env}` |
| 服务 | `GET/POST /v1/services`、`GET/PUT /v1/services/{s}`、`GET /v1/services/{s}/view?env=` |
| 进程 | `GET /v1/services/{s}/instances`、`POST .../instances/{env}/{proc}/start|stop|renew`、`GET .../logs` |
| 任务 | `GET/POST /v1/tasks`、`GET/PUT /v1/tasks/{t}`、`GET /v1/tasks/{t}/schedule`（下次触发） |
| 角色 / 策略 | `GET/POST /v1/roles`、`/v1/policies`，同上 |
| 版本 | `GET /v1/{kind}/{name}/versions`、`GET .../versions/{v}`、`POST .../versions/{v}/restore` |
| 运行 | `POST /v1/runs`、`GET /v1/runs`、`GET /v1/runs/{id}`、`GET /v1/runs/{id}/events`（`?stream=1` 走 SSE）、`POST .../cancel|rerun|feedback`、`POST .../steps/{seq}/feedback` |
| 对话 | `POST /v1/chat`（SSE）、`GET /v1/sessions`、`GET /v1/sessions/{id}`、`POST /v1/sessions/{id}/correct` |
| 事件 | `POST /v1/events/{source}` |
| 审批 | `GET /v1/approvals`、`POST /v1/approvals/{id}/decision` |
| 记忆 | `/v1/knowledge`、`/v1/cases`、`/v1/assets`（按 `service`、`env` 过滤） |
| 统计 / 搜索 | `GET /v1/stats`、`GET /v1/search?q=` |

`POST /v1/runs` 的请求体就是 `RunRequest`：`{task, service?, env?, subtask?, input,
session_id?, caller?}`；角色由任务决定，调用方不传。SDK：

```python
agent = AgentClient(service="board", env="test")
agent.ask("3 月以来 total_fee 是多少")          # 对话（服务的默认 chat 任务）
agent.run("frontend-smoke", {"version": "1.2"}) # 任务，等结果
```

## 7. 网页

React + TypeScript + Vite 单页应用，构建产物随 Python 包发布（`webui/dist`），由
FastAPI 同进程托管，部署不需要 Node。信息架构以服务为中心：

- **顶栏**：全局环境切换（全部 / prod / test / dev）、⌘K 全局搜索与命令、审批角标、主题。
- **侧栏**：概览、服务、任务、运行、对话、审批、记忆、设置（角色 / 策略 / 环境）。
- **服务页**：环境 tab → 进程（启停、租约、日志）、配置文件、任务与下次触发、近期运行、
  记忆；配置用结构化表单编辑，版本时间线带 diff。
- **任务页**：运行对话框（按输入 schema 生成表单）、触发器编辑（cron 显示接下来几次时间）、
  分节定义表单、子任务、版本。
- **运行详情**：步骤时间线（工具调用 / 思考 / 审批，逐步 👍👎）+ 上下文面板（输入、
  输出、注入的档案、召回的知识与方法、本次沉淀、同会话 run）；图任务带 DAG 视图。

## 8. 代码地图

```
src/agent_platform/
  config.py          平台配置（AGENT_ENV → conf/env/*.yaml）
  domain/            对象模型：env / service / role / task / policy / run（纯 pydantic + 纯函数）
  store/             PG：db（唯一建表点）/ definitions / runs / instances / approvals /
                     knowledge / cases / assets / feedback / artifacts
  registry.py        定义读取面：带缓存的 Envs / Services / Roles / Tasks / Policies
  orchestration/     submitter / gates / workflows / activities / artgraph / scheduler / worker
  agent/             factory（按角色装配）/ scope（RunScope）/ approvals / tools/
  services/          ProcessController（systemd / local）+ svcrun（bwrap 配置隔离）
  memory/            recall / distill / gardener
  triggers/          events（统一入口）/ sources/（dagster、gitlab、webhook）
  api/               FastAPI 路由（按资源分文件）+ schemas + 错误
  webui/             SPA 托管（dist 静态资源 + history fallback + 登录）
  model/ notify/ langfuse.py
web/                 前端源码（React + Vite）
sdk/agent_client/    Python SDK + CLI
```

依赖单向向下：`domain` 不依赖任何人；`store` 只依赖 `domain`；`orchestration`、
`agent` 依赖 `registry` 与 `store`；`api` 在最上面。

## 9. 从 v5 迁移

`scripts/migrate_v5.py`：definitions 去掉 env 列（取部署实例那一套），`domain` →
`service`（合并 `conf/services.yaml` 的进程与配置文件）、任务的 `schedule` /
`schedule_input` / `triggers` / `env_gate` → 新的 `triggers` / `envs`，`rules` 定义
并入对应事件触发；runs 的 `domain`/`target_env` 列改名 `service`/`env`。迁移幂等、
先备份再执行。
