# agent-platform v8 设计文档

读者：协作开发者。看完本文应能回答三件事：

1. 平台里有哪些对象。
2. 这些对象怎么连起来。
3. 某个功能的代码在哪。

版本号唯一出处是 `src/agent_platform/__init__.py`。接口的逐字段契约见 `docs/外部接口文档.md`。

## 1. 平台是干什么的

平台是一套 agent 服务，和若干业务项目（Dagster、board、配置中心等）部署在同一台机器上。
它有两类用法，所有设计都从这两类用法出发：

1. **项目调 agent**：业务项目通过 HTTP API 或 SDK 请 agent 做事，例如问数据口径、分析一次报错、
   跑一次检查。调用方是项目自己。
2. **任务自己跑**：由定时（每天巡检 prod 和 test）、事件（Dagster 失败、GitLab 部署完成）或人在网页上点一下触发。
   触发后无人值守跑完，结果投递到钉钉或回调地址。

项目和 agent 同机部署，主要是为了让项目给 agent 当参考和调试对象。agent 可以：

- 读项目的部署目录和代码；
- 读对应环境的配置文件；
- 查只读库；
- 在该环境的项目 Python 里直接跑项目代码（项目内核）；需要长驻时按需启停该环境的进程。

### 1.1 项目背景与部署场景

项目还在定架构阶段。目标部署场景是：

- 已有几套业务服务（Dagster、board、统一配置中心等），各自分 prod / test / dev 三个环境，线上实例跑在各自的机器上。
- 部署**一套统一的 agent 服务**，供这些服务共同使用。
- agent 服务部署在一台机器的**一个新的独立用户环境**里。这个用户不一定有长期 root，所以除了系统级安装（`install.sh`），
  还有用户级安装（`install-user.sh`，systemd --user）。
- 在同一环境里**拉取各服务的代码**、按环境建 venv，并放好每个服务 prod / test / dev 各自的**配置文件**，供 agent 按需查看、按需运行。

由此得出几条贯穿全文的设计决定：

| 决定 | 原因 | 落在哪 |
|---|---|---|
| 项目在平台机器上是**本机副本**，不是线上实例 | 线上服务跑在别处，平台只拿代码与配置给 agent 参考、调试 | 全文 |
| **每个服务、每个环境一份代码**（`/srv/svc/<服务>/code/<环境>`），由内建任务 `code-sync` 切到该环境部署的版本；**每个环境一个 venv**（`/srv/svc/<服务>/venv/<环境>`） | 三个环境往往跑在不同的提交上，依赖也可能不同，复现生产问题要读、要跑生产那份代码；GitLab 部署事件触发自动同步 | §2.3 |
| 配置文件放在代码目录外（`/srv/svc/<服务>/conf/<环境>`），起进程和项目内核时只读 bind 到固定路径 | 配置不进仓库、重新 clone 不丢；业务代码零改动就能按环境跑 | §2.3 |
| **跑项目代码用项目内核**（`py`），只有需要长驻才起进程 | 复现和取数多半只要调项目自己的函数（口径函数、ORM、资产），口径与线上一致；起进程会按该环境的配置真的跑起服务（比如 dagster 的 daemon 会跑调度） | §2.3、§4 |
| bash / run_code 沙箱里**遮蔽所有配置文件与密钥**，配置原文只能经 `service_info` 读本环境打码后的版本；项目内核只放开本服务本环境的配置 | 配置里有各环境的口令，工具输出会进模型上下文和运行台账；项目代码要按原样读配置才能连库 | §4 |
| 定义里的口令写 `${VAR}`，用到时才取值 | 口令只放 secrets.env，不进库、不进接口、不进版本历史 | §2.3 |
| 工具（含 MCP）一律绑定本次运行的服务×环境；会话 thread 也按 服务×环境 分开 | 一套 agent 同时服务多套环境，不能查到别的环境，也不能把 prod 的对话上下文带进 test | §4 |
| **服务特有的能力挂在服务上**：服务定义的 `urls`（有名字的地址）和 `mcp`（服务自己的 MCP 工具），运行在哪个服务上就带哪个服务的；角色只管通用能力 | dagster 的运行记录、board 的页面地址只对一个服务有意义，写进角色就得每个服务复制一份角色；角色保持与服务无关 | §2.3、§4 |
| **记忆三分**：档案（人写）/ 记忆（agent 记下）/ 方法（可执行）；记忆权重**只罚不奖** | 三者来源、可信度、生命周期不同：档案逐字置顶不过期，记忆靠检索、会过时，方法要能直接跑。没人点 👍，正分没有信号，只有 👎 可用 | §5 |
| **runs 表就是执行队列**，不用外部编排服务 | 单部署单机，台账本来就是事实源，队列和台账合一；少一个要装、要备份的服务 | §3 |
| **审批默认关闭** | 各环境配置里都是只读账户、文件系统只读，agent 做不了真正危险的事；以后让它执行变更类任务时再打开 | §2.6 |
| 回归评测**只用 👎** | 没人会去点 👍；👎 自带「错在哪」，正好当判卷标准，不用另外维护评测集 | §5.1 |

硬约束：

- 单部署：一套 agent 服务操作所有项目的所有环境。
- 主机 + systemd，不用容器；必需的外部依赖只有 PostgreSQL。
- 单一内部模型 API（OpenAI 兼容，多 token 轮询）。
- 没有用户体系：身份就是 API 密钥。
- 钉钉单向只发。
- 定义写库即生效。

## 2. 对象模型

```
平台配置          环境列表 / 审批 / 通知 / 记忆 / 进程默认值——对所有人生效，带版本
服务 Service      一个业务项目：部署目录、代码、解释器、进程、各环境配置文件、只读库、地址、服务 MCP、档案、按环境启用
  服务×环境       agent 实际操作的单位——"board 的 test"：目录/解释器/配置/库/进程/项目内核/服务 MCP 连接都按它解析
角色 Role         可复用的能力：系统提示 + 工具 + 可委派的子代理。与服务无关
任务 Task         要做的事：目标 + 形态（agent / builtin）+ 输入 + 触发 + 投递 + 记忆开关 + 档案
  子任务          任务:对象名——同一件事针对某个具体对象（一张表/一条链路），只存差异
  触发 Trigger    任务上声明：api / chat / schedule（cron × 环境）/ event（来源 × 事件）
API 密钥          调用方身份：名字 = 发起方；范围 run / admin；可限定服务与环境
运行 Run          一次执行：(任务版本, 角色版本, 服务, 环境, 触发, 发起方) 的快照 + 全过程事件；runs 表兼执行队列
会话 Session      对话连续性：多次运行串成一段上下文；LangGraph thread 按 服务×环境 分开
档案/记忆/方法    档案：人写的，在服务 / 任务定义里；记忆：agent 记下的事实 / 教训 / 交接摘要，按服务分区；方法：可执行的做法与脚本
审批 Approval     人工门（默认关闭）：危险命令 / 进程启停
回归重放 Replay   改了定义之后，拿被 👎 的运行用当前定义重跑并判定
```

### 2.1 每个对象回答一个问题

| 对象 | 回答 | 存储 |
|---|---|---|
| 平台配置 | 平台默认怎么办 | `definitions(kind=config, name=节名)` |
| Service | 对哪个项目、在哪些环境可用、用哪个解释器 | `definitions(kind=service)` |
| Role | 谁来做（能力边界、能委派给谁） | `definitions(kind=role)` |
| Task | 做什么、何时做、结果给谁 | `definitions(kind=task)` |
| 档案 | 人确认过的口径、禁区、坑 | 服务 / 任务定义的 `profile` |
| 记忆 | agent 过去记下了什么 | `knowledge`（`kind` = fact / lesson / handoff）+ `knowledge_history` + `recall_hits` |
| 方法 | 以前是怎么做的、能直接跑的脚本 | `assets` + `asset_history`，文件本体在数据目录 |
| API 密钥 | 谁在调 | `api_keys`（只存 sha256 摘要） |
| Run | 这一次发生了什么 | `runs` + `run_events`（事实表，钉死定义版本；`runs` 同时是执行队列） |
| Session | 哪些运行是同一段对话 | 运行的聚合键 |
| Instance | 某个「服务 × 环境」的进程现在什么状态 | `service_instances` |
| Replay | 改了定义之后，被 👎 的问题好了没有 | `replays` + `replay_items` |

粒度的尺子不变：一样东西同时具备独立生命周期、独立归属和独立审计需求，才值得做成独立对象；
否则做成字段或过滤器。所以「环境」不是独立对象：环境列表是平台配置里的一节，
「某服务在某环境是否启用」是服务自己的字段。

### 2.2 关系规则（写死）

1. **一次运行永远只有一个服务、一个环境**（平台任务除外，服务为空）。
   工具作用域、权限边界和记忆的适用范围（按服务分区，`env` 为空即各环境通用）都挂在这两个维度上。跨服务的事，用会话串起多个运行来表达。
2. **任务归属**三选一：
   - `service: "board"`：专属任务，只在 board 上跑；
   - `service: "*"`：通用任务（如 data-qa），调用时指定服务；
   - 不填：平台任务（如 memory-gardener），不涉及业务服务。
3. **角色不知道服务**。角色是能力，任务是目标；同一个 `ops_analyst` 可以给任何服务干活。
   工具在运行时绑定到这次运行的「服务 × 环境」，模型无法跨服务调用。服务特有的工具挂在服务上（§2.3），运行在哪个服务就带哪个服务的。
4. **角色真正生效**：一次运行由任务指定的主角色执行，系统提示是这个角色的，工具是这个角色的（加上所在服务的 MCP 工具）。
   主角色可以在运行中把子问题委派给它声明的子代理，仍在同一次运行、同一个服务×环境里（§2.8）。
5. **环境是请求维度**：每个运行请求带 env，缺省为平台默认环境。
   - 服务的 `envs[env].enabled` 决定这个服务在哪些环境可用；
   - 任务的 `envs` 再限定任务能跑在哪些环境；
   - 设置里打开审批时，受保护环境（prod）上的危险操作走审批（默认关闭，§2.6）。
6. **定义只有一套**：单部署就只有一套定义。`AGENT_ENV` 只决定读哪份部署配置（开发机还是生产机），
   与业务环境无关。
7. **配置分三层**，各管各的：

   | 层 | 存在哪 | 内容 |
   |---|---|---|
   | 部署参数 | `conf/` 文件 | 数据库、模型、执行并发（`worker`）、项目内核（`kernel`）、平台 MCP（`mcp_servers`）、引导密钥 |
   | 平台配置 | 库 | 环境、审批、通知、记忆、进程 |
   | 个人偏好 | 浏览器 | 主题、密度、默认视角 |

### 2.3 服务（Service）

```yaml
name: dagster
title: Dagster 数据编排
root: /srv/svc/dagster/code/{env} # 部署目录（agent 只读访问）；{env} = 每个环境一份代码
code_paths: []                    # 读代码/校验记忆新鲜度的目录；缺省 = [root]
repo: git@gitlab.internal:data/dagster.git   # 代码同步从这里拉
ref: main                         # 默认跟踪的分支
python: /srv/svc/dagster/venv/{env}/bin/python   # 项目解释器：每个环境一个 venv；envs[env].python 可覆盖；空 = python3
env_vars: {DAGSTER_HOME: "/srv/svc/dagster/code/{env}"}   # 服务级环境变量（可写 {env}）：项目内核与进程都带上
urls:                             # 有名字的地址：可写 {env}、{port:进程名}；envs[env].urls 按键覆盖
  local: "http://127.0.0.1:{port:webserver}"
configs:                          # 各环境配置文件：两端都可以写 {env}
  - canonical: /srv/svc/dagster/code/{env}/dagster.yaml
    template: /srv/svc/dagster/conf/{env}/dagster.yaml
processes:                        # 需要长驻时才起的进程（可多个）；cmd 里可写 {env} {port} {python}
  webserver:
    cmd: ["/srv/svc/dagster/venv/{env}/bin/dagster-webserver", -w, workspace.yaml, -p, "{port}"]
    ports: {prod: 3000, test: 3001, dev: 3002}
mcp:                              # 服务自己的 MCP server：运行在本服务上时工具自动出现
  dagster:
    transport: stdio
    command: "{platform_python}"
    args: ["{platform}/mcp_servers/dagster_mcp.py"]
    env: {DAGSTER_URL: "{url:deployed}"}
    envs: {prod: {}, test: {}}    # 写了 envs 就只在列出的环境可用
envs:                             # 按环境覆盖：只写差异
  prod: {ref: release, readonly_dsn: "postgresql://ro:${DAGSTER_RO_PASSWORD}@prod-db/dagster",
         urls: {deployed: "http://10.0.0.11:3000"}}
  test: {ref: test, urls: {deployed: "http://10.0.1.11:3001"}}
  dev:  {enabled: false}          # 这个服务在 dev 不接收运行、不起进程和内核
profile:                          # 服务档案：自由键，逐字注入该服务所有运行
  conventions: 资产按 dt 分区，T+1 物化
  no_go: prod 不手工触发 backfill
enabled: true
```

agent 读到的「服务 × 环境视图」（`ServiceView`）由三部分组成：基座定义、该环境的覆盖、
渲染后的路径（`root`、`code_paths`、配置文件两端、`python`、`env_vars`、`urls` 里的 `{env}` 换成该环境）。
提示词、工具和页面用的都是这一份。`Registry.service_view(服务, 环境)` 是取视图的唯一入口，环境不存在时报 `unknown_env`。

**地址**（`urls`）：有名字的地址，比如本机副本的端口（`local`）、线上部署的页面或 API（`deployed`、`site`）。
可写 `{env}` 和 `{port:进程名}`（该进程在这个环境的端口），`envs[env].urls` 按键覆盖。渲染后出现在 agent 的
`[运行环境]` 提示里，浏览器之类的工具按它打开页面；`mcp` 配置里用 `{url:名字}` 引用。

**服务 MCP**（`mcp`）：`{名字: langchain-mcp-adapters 连接配置}`，放这个服务特有的能力。规则：

- `envs: {环境: 覆盖}` 深合并到基础配置上；**写了 `envs` 就只在列出的环境可用**，没配的环境不会悄悄连到别处。只在服务启用的环境建连接。
- 字符串里的占位：`{env}`、`{url:名字}`（该环境的地址）、`${VAR}`（连接时才取值，口令只在 secrets.env）、
  `{platform}`（平台安装目录，仓库自带的 `mcp_servers/` 在它下面）、`{platform_python}`（平台解释器）。
- 运行在这个服务上时工具自动出现（角色 `service_tools: false` 时不带，§2.8），调用按运行的环境路由。
- 懒加载：第一次有运行用到（或调 `GET /v1/services/{s}/tools`）才连；按定义内容缓存，改了定义下次自动重连；
  有连接失败时 5 分钟后重试；一个连接失败不影响别的，只是少几个工具。
- 种子里 dagster 的 `mcp` 用仓库自带的 `mcp_servers/dagster_mcp.py`，连各环境线上部署的 Dagster（`urls.deployed`，prod / test），
  5 个只读查询工具（运行、运行日志、物化记录、最近运行、资产定义）；平台要装 `agent-platform[mcp,dagster-mcp]`。

分工：高频、固定的操作做成 MCP（类型化的工具，agent 不用猜接口）；临时、不常用的，直接在 `py` 里用项目自带的客户端调。
代码在 `domain/services.py`（`urls_for`、`mcp_connections`）、`agent/tools/mcp_bridge.py`（`ServiceMcp`）、
`orchestration/pipeline.py`（`service_mcp_tools`）。

**按环境的开关只有一个**：`envs[env].enabled`。关掉意味着这个服务在该环境不接收运行（闸门第 2 环），
也不起进程和项目内核。启用就能按需起进程（带租约，用完停）；平台起的是本机副本，各环境配置里都是只读账户。

**项目内核**（`services/kernel.py`，工具 `py`）：每个 会话×服务×环境 一个常驻 Python 进程，键和会话 thread 一样是
`<session_id>@<服务>:<环境>`。

- 解释器是该环境的（`python`，可写 `{env}`，可在 `envs[env].python` 覆盖；空 = `python3`），工作目录是该环境的部署目录。
- 该环境的配置文件按和起进程同一份规格（`ProcessController.env_spec` / `runtime_spec`）只读 bind 到项目读的固定路径，
  其他环境和别的服务的配置、平台密钥遮蔽。
- 可以直接 import 项目模块、调项目自己的口径函数 / ORM / dagster 资产，用项目的方式连只读库。
  变量在会话内保留，最后一个表达式的值会显示，`restart=true` 清空。文件类方法的目录在 `sys.path` 上（§5）。
- 文件系统只读，`$SCRATCH`（和 bash 共用的工作区）可写，`/tmp` 独立；网络照常。
- 驱动只用标准库，业务 venv 里不用额外装东西。
- 空闲 30 分钟回收，同时最多 8 个，超了先回收最久没用的（部署配置 `kernel.idle_minutes` / `kernel.max_kernels`）。
- 服务在该环境停用、配置文件缺失、部署目录不存在、找不到解释器时，`py` 直接报错。不依赖进程控制后端（`backend: off` 也能用）。
- 没有 bwrap 时直接在宿主上跑（开发机），配置文件不会按环境就位。

**代码同步**是内建任务 `code-sync`（`services/codesync.py`）：把某个服务×环境的代码目录切到指定版本。
目标版本按「请求的 `ref` > `envs[env].ref` > `ref` > 远端默认分支」取；目录不存在就 clone，
有未提交改动就拒绝（不替人丢改动），最后 `checkout --detach` 到目标提交。
种子里给每个服务声明了 GitLab 部署事件的触发，部署成功后把对应环境切到刚部署的提交，
这样复现生产问题时读到的就是生产在跑的那份代码。venv 不由平台维护，依赖变了要运维按环境重装。

**口令**：只读库连接串、通知渠道的 url / token 里写 `${VAR}`，真实值放 secrets.env，
用到的那一刻才取（`credentials.expand`）。种子原样入库，不再在播种时展开。直接写了明文的，
接口回显时打成 `***`，原样传回表示不改。服务和进程的 `env_vars` 都不允许 `${VAR}`：启动规格是落盘的明文 JSON，
口令应放进该环境的配置文件。

**进程启停**由 `ProcessController` 管：

- 生产走 systemd 模板单元 `agent-svc@<服务:环境:进程>.service`（系统级用 polkit 授权；用户级部署用
  `systemctl --user`，见 `process_control.scope`）。
  ExecStart 是 `svcrun`：用 bwrap 把选中环境的配置文件只读 bind 到 canonical 路径，遮蔽其他环境的配置文件
  与平台密钥（`hidden_paths`），并给业务进程独立的 pid 命名空间——用户级部署时平台和业务进程是同一个用户，
  这样业务进程也读不到平台进程的环境变量。
- `env_spec()` 是「按环境把配置文件就位」的唯一出处，进程启动规格和项目内核共用。
- 固定路径（canonical）不存在时，平台先建一个空文件占位（bwrap 只能往已存在的路径上 bind）。
- 进程的环境变量 = 服务级 `env_vars` 叠加进程自己的 `env_vars`。
- 开发机走本地子进程。
- 每次启动带租约（平台默认值在 设置 → 进程），可以续期，到期自动停，即「按需启动，用完即停」。
- 设置里打开审批后，受保护环境（`protected`）或所有环境（`all`）的启停要先审批。
- 状态落 `service_instances`，页面和 API 读的是同一份。

### 2.4 任务（Task）

```yaml
name: failure-analysis
service: dagster
title: Dagster 失败分析
role: ops_analyst
form: agent                       # agent | builtin
input:
  run_id: {type: str, required: true}
  asset_key: {type: str, required: true, description: 失败的资产}
  error: {type: text, required: true}
envs: [prod, test]                # 能跑的环境；空 = 全部
triggers:
  - {id: on-failure, type: event, source: dagster, event: run_failure,
     rules: [{pattern: "connection.*refused", category: infra, conclusion: 连接失败，检查目标服务存活}],
     session: "dagster:{asset_key}:{error_class}:{date}"}
  - {id: api, type: api}
deliver: {channel: default}       # 或 {url: …}；不写 = 调用方自取
dedup: {key: run_id, window_s: 600}
memory: {recall: null, save: null}  # null = 跟随平台默认
timeout_s: 300
profile:                          # 任务档案（子任务只写差异）
  pitfalls: 上游 ods 延迟会级联失败
```

**触发**全部声明在任务上，平台不写死「某个 webhook 跑某个任务」：

| type | 含义 | 关键字段 |
|---|---|---|
| `api` | 允许 `/v1/runs` 和 SDK 调用 | — |
| `chat` | 出现在对话页，可以多轮 | — |
| `schedule` | 定时，**每个环境各跑一份** | `cron`、`envs`、`input`、`timezone`；通用任务另需 `service` |
| `event` | 外部事件 | `source`、`event`、`filter`、`map`、`rules`、`session`、`service` |

事件走统一入口 `POST /v1/events/{source}`。来源适配器在 `triggers/sources.py`，把各家回调翻译成
「事件名 + 扁平字段」：Dagster 翻成 `run_failure`，GitLab 翻成 `deployment`，通用 webhook 直接透传。
新接一个事件源，就在这个文件里加一个函数，或者直接用通用 webhook。

`rules` 是规则先行：报错命中规则时**也建一条运行**（`resolution=rule`），直接成功、照常投递，
这样审计记录不留空洞。

**子任务**名为 `failure-analysis:dwd_trade_order`，只嵌套一层，定义里只存差异：
档案按键合并，其他字段子任务写了就用自己的，没写就跟随父任务。

- 调用方显式带 `subtask` 来选用；平台不从输入里猜。
- 点名的子任务不存在时，按父任务继承建出来，闸门受理后才落库。
- 控制台在父任务的「子任务」标签里一行输入对象名就能新建，建完直接跳到它的档案。

**形态**：

| form | 含义 |
|---|---|
| `agent` | 一个主角色执行，需要时委派子代理（§2.8） |
| `builtin` | 内建处理器（`memory-gardener`、`code-sync`），不过模型 |

API、对话、定时、事件四种入口对两种形态一视同仁。

**通用入口 `ask`**（种子任务）：`service: "*"`、角色 `generalist`、声明 `chat` 与 `api` 触发、输入只有 `question`。
任何服务任何环境直接提问或交代一件事，不用先建任务；要定时、事件、投递、去重时再建正式任务。
`POST /v1/runs` 不写 `task` 就是 `ask`；对话没指定任务时，服务专属的对话任务优先，没有就用 `ask`。

**投递**（`deliver`）：结果总在运行台账里，调用方随时能取。`deliver` 只声明「另外推到哪」，
可以是设置 → 通知里的某个渠道，也可以是 HTTP 回调地址。投递失败重试 3 次，仍失败只记一条事件，不改运行状态。

### 2.5 档案

档案有两层，都存在定义库里，逐字置顶注入，不走召回：

| 层 | 字段 | 作用范围 | 合并方式 |
|---|---|---|---|
| 服务档案 | `service.profile` | 该服务所有运行 | 可按环境覆盖 |
| 任务档案 | `task.profile` | 该任务 | 沿子任务按键合并 |

档案只记代码和配置里读不出来的东西：口径与术语、禁区、环境差异、踩过的坑。记忆里被反复用到、确认无误的事实可以升格进档案（§5）。
prepare 阶段统一拼装，原文落一条 `stage=profile` 事件。控制台的任务「档案」标签可以就地编辑；
子任务那一页会区分「继承的键」和「自己写的键」。

### 2.6 平台配置（设置）

| 节 | 管什么 |
|---|---|
| `envs` | 有哪些业务环境、默认哪个、哪些受保护 |
| `approvals` | 审批开关 `required_in`：`off`（默认）/ `protected`（只在受保护环境）/ `all`；哪些命令算危险（正则）；超时 |
| `notifications` | 渠道（钉钉 / webhook）+ 规则（事件 × 服务 / 环境 / 任务 / 触发 → 渠道） |
| `memory` | 召回、沉淀、交接摘要的默认开关与条数 |
| `processes` | 默认租约与租约上限 |

每节是 `definitions` 表里 `kind=config` 的一行，和其他定义一样有版本历史、可以恢复。
`conf/seeds/settings.yaml` 只在库里还没有这一节时播种一次。

审批默认关闭，种子也是 `off`：各环境配置里都是只读账户、文件系统只读，agent 做不了真正危险的事。
打开后只有两类审批单：`command`（危险命令）和 `process`（进程启停）。

记忆开关的优先级是：请求 > 任务 > 平台默认。通知不是写死在代码里的：「运行失败」「有审批」
「进程停止」这些事件按规则发到渠道，任务投递也是选一个渠道。

### 2.7 身份

- 每个调用方一把 API 密钥（`api_keys` 表只存摘要），密钥名就是运行里的 `caller`。
- 范围有两种：`run` 只能发起和查询；`admin` 还能改定义、改设置、审批、改记忆、启停进程。
- 密钥可以限定服务和环境，越界返回 `403 forbidden`。
- 控制台用密钥登录，换一个签名 cookie。登录时可以写操作人姓名，它会进版本台账和审批记录。
- 部署配置里的 `root_token` 是引导密钥。

### 2.8 角色（Role）

```yaml
name: qa_engineer
title: 冒烟测试
description: 部署后按沉淀的方法跑冒烟脚本和页面检查   # 也是委派时给主角色看的「擅长什么」
prompt: …
tools: [py, bash, service_info, service_ctl, save_asset, "mcp:browser"]
subagents: [ops_analyst]          # 运行中可委派的角色；null = 跟随父角色，[] = 明确不要
service_tools: true               # 自动带上运行所在服务的 MCP 工具；null = 跟随父角色（没有父角色就是 true）
extends: null                     # 继承父角色
prompt_append: ""                 # 有 extends 时追加在父角色提示词之后
```

| 字段 | 规则 |
|---|---|
| `tools` | 内置工具名或平台 MCP 工具名；`"*"` = 全部内置工具 + 全部平台 MCP 工具；`"mcp:<server>"` = 某个平台 MCP server 的全部工具，不用一个个列。文件工具总是可用，不用写 |
| `subagents` | 主角色运行中按需把子问题委派给这些角色（DeepAgents 的 `task` 工具）：子代理用自己的提示词和工具、独立上下文，结论交回主角色。只委派一层，子代理自己的 `subagents` 不生效 |
| `service_tools` | 默认 `true`：运行所在服务声明的 MCP 工具（§2.3）自动带上；和 `tools` 里的工具重名时以 `tools` 为准。子代理按它自己的设置 |
| `extends` | 子角色写了 `tools`（非空）/ `subagents`（非 `null`）/ `service_tools`（非 `null`）就**整体替换**父角色的，没写就跟随；提示词在父角色之后追加 `prompt_append` |

**一个任务一个主角色**。需要多种能力时，给主角色挂子代理，由它在运行中按需委派（动态委派），
而不是把几个角色排成静态流水线（任务图仍然不要）。委派发生在同一次运行里，同一个服务×环境，工具同样绑定 RunScope。

种子角色：

| 角色 | 工具 | 子代理 |
|---|---|---|
| `generalist` | `["*"]`（通用入口 `ask` 用它） | `ops_analyst`、`data_searcher` |
| `ops_analyst` | py、bash、run_code、service_info、service_ctl、sql_query、host_metrics、save_asset、notify | `data_searcher` |
| `data_searcher` | py、sql_query、service_info、run_code | — |
| `qa_engineer` | py、bash、service_info、service_ctl、save_asset、`"mcp:browser"` | `ops_analyst` |
| `inspector` | `extends: ops_analyst`，换了一组工具 | `[]`（显式不委派） |

校验：子代理角色必须存在、不能列自己（`invalid_definition`）；被任务使用、被别的角色继承或列为子代理时不能删（`in_use`）。
`GET /v1/roles/{name}/resolved` 返回合并后的提示词、工具、子代理与继承链。
代码在 `domain/roles.py`（`resolve_role`）、`registry.agent_roles`、`agent/factory.py`、`agent/tools/catalog.py`（`Toolbox.expand`）。

## 3. 一次运行的生命周期

```
入口（API / 对话 / 定时 / 事件 / 网页 / 重跑 / 续跑 / 纠正 / 回归重放）
  → Submitter.submit(RunRequest)
      幂等键 → 解析任务 → 解析服务 → 解析环境 → 调用方权限 → 校验输入 → 闸门链 → 任务去重
      →（点名的子任务不存在就建）→ 建台账行 status=queued，pg_notify('runs_queued')
  → Executor（worker）：认领 queued 行，改成 running
  → Pipeline.execute
      build_spec  台账行 → RunSpec
      prepare     定版本、重过开关（1–4）、拼档案、召回记忆、注入方法
      execute     agent：按角色装配执行 / builtin：处理器 / rule：直接给结论
      finalize    落 success、沉淀记忆
      deliver     投递结果
      任一步失败 → fail（落 failed）→ deliver
```

建行之后的一切都从台账行出发（`build_spec`）：新提交、续跑、重跑、纠正、回归重放走的是同一段代码。

**执行队列**：runs 表就是队列，不依赖外部编排服务（`orchestration/executor.py`）。

- 唤醒：进入 queued 时 `pg_notify('runs_queued')`，worker LISTEN 毫秒级唤醒，5 秒轮询兜底。
- 认领：按创建时间先到先得，`FOR UPDATE SKIP LOCKED`，多个 worker 并发也不会重复认领。
- 限并发：每个 worker 同时最多执行 `worker.max_concurrent_runs` 个（部署配置，默认 10），满了就不再认领。
- 心跳：执行中每 20 秒刷新 `heartbeat_at`，台账记下认领它的 `worker`（主机:pid）。
- 取消：提交端先把台账标成 cancelled（事实源）、拒掉挂起的审批，再 `pg_notify('run_cancel')`，持有它的 worker 取消执行。
- 中断：worker 退出时，执行中的运行记为 failed / `interrupted`；worker 崩溃或被杀时心跳停了，
  维护循环把超过 120 秒没心跳的标为 failed / `orphaned`。两种都可以续跑。
- 续跑：同一个 run_id 放回队列（`resume=true`），从会话 thread 的 checkpoint 接着走，不重新拼提示。只有 agent 任务能续跑。

`agent-platform serve` 默认同进程跑 worker；`agent-platform worker` 只跑执行队列、定时和维护循环，配合 `serve --no-worker` 分开部署。

**执行步骤**在 `orchestration/pipeline.py`。agent / 内建步骤限时 = 任务的 `timeout_s` + 一次审批的等待预留
（只在打开了审批时，按审批超时预留），等人放行不会把运行等成超时。finalize 先落 success，之后的纠正取代、沉淀、
通知都是旁路，失败只留日志，不翻案运行结果。投递失败重试 3 次，仍失败只留一条事件。

**定时**（`orchestration/scheduler.py`）：进程内每 20 秒按 cron 检查一次，把上次检查以来该触发的各提交一次，每个环境各一份。

- 不重复：幂等键 `schedule:<任务>:<触发器>:<环境>:<计划时间>`，worker 重启或多个 worker 同时在跑都只建一条；
- 不重叠：同一触发器在同一环境上一次还没跑完（排队 / 等审批 / 运行中），这次跳过；
- 不补：停机期间错过的不补，启动时只回看 90 秒；
- 不用同步：每轮读最新定义（定义缓存最多 5 秒），改了定时、停了任务，下一轮就生效。

子任务只有自己声明了 `triggers` 才有自己的定时，否则每个子任务都会继承父任务的定时、重复触发。

**维护循环**（`orchestration/maintenance.py`）随 worker 每分钟一轮：心跳超时的运行标 failed / `orphaned`、
到期的审批单标 expired、租约到期的进程停掉并通知。

**去重**：调用方的幂等键（请求头 `Idempotency-Key`）不限时间窗，失败的运行会释放这个键；
任务声明的去重（`dedup`）看时间窗内同键的运行，排队、等审批、运行中、成功的都算，
所以重复回调不会在前一次还没跑完时再起一份。

**闸门链**在 `orchestration/gates.py`，是唯一的判断点，拒绝时带稳定的原因码：

1. `service_disabled`：服务停用
2. `service_env_disabled`：服务在这个环境停用
3. `task_disabled`：任务停用，或子任务的父任务停用
4. `env_not_allowed`：任务的 `envs` 不含该环境
5. `trigger_not_allowed`：任务没声明这种触发

续跑、重跑、纠正、回归重放只过 1–4；新提交（含定时、事件）过 1–5，控制台手动运行不受第 5 环约束，因为那是人点的。
worker 认领后 prepare 再过一遍 1–4：排队期间开关可能变了，没过就落 failed，`error_code` 是对应的原因码。

**状态机**：`queued → running →（awaiting_approval ⇄ running）→ success | failed | cancelled`。
`awaiting_approval` 只出现在运行中途的审批（设置里打开了审批才有）。
`resolution` 记录运行是怎么结束的：`agent` / `builtin` / `rule`。

## 4. agent 执行

- **按角色装配**：`AgentFactory` 按（角色, 服务, 角色与子代理的版本, 服务 MCP 的版本）缓存编译好的 agent，
  定义一改版本就变，下一次运行自然用新定义。一个 agent 由这几部分组成：平台基础提示 + 角色的系统提示、
  角色的工具（展开 `"*"` 与 `"mcp:<server>"`）、所在服务的 MCP 工具（`service_tools`）、子代理（§2.8），
  以及 DeepAgents 文件工具；用户消息里是档案、服务 × 环境视图、召回块与方法。
- **工具绑定运行**：每次运行生成一个 `RunScope`（run_id、会话、服务视图、环境、是否受保护、通知渠道、遮蔽路径）。
  工具从 scope 里取服务和环境，签名里没有 `service`/`env` 参数，模型想跨服务也做不到。
- **工具目录**（`agent/tools/catalog.py`）：

  | 工具 | 作用 |
  |---|---|
  | `py` | 项目内核（§2.3）：在本服务本环境的项目 Python 里执行代码，import 项目模块、调项目函数；变量会话内保留，`restart=true` 清空 |
  | `bash` | bwrap 沙箱：全盘只读、scratch 可写、默认断网，调用结束进程全灭；配置文件与密钥被遮蔽 |
  | `run_code` | CodeAct，代码里用桩函数回调白名单工具 |
  | `service_info` | 服务 × 环境视图、配置文件内容 |
  | `service_ctl` | 进程 status / start / stop / restart / logs；只是跑一段项目代码用 `py`，需要长驻才起进程 |
  | `sql_query` | 该服务该环境的只读库 |
  | `host_metrics` | Grafana |
  | `save_asset` | 沉淀方法 |
  | `notify` | 发到通知渠道 |
  | MCP 工具 | 平台 MCP 与服务 MCP 两种，同样绑定服务×环境（见下） |
  | `task` | 角色声明了 `subagents` 时出现：把子问题委派给子代理（DeepAgents 提供） |
  | 文件工具 | `read_file` / `write_file` / `edit_file` / `ls` / `grep`，只在 scratch 内 |

- **「全盘只读」不等于「全盘可读」**：bash 与 run_code 的沙箱里，所有服务所有环境声明过的配置文件（两端）、
  平台密钥目录、运行用户的凭据（`~/.ssh` 等，部署配置 `hidden_paths`）、进程启动规格目录都被遮蔽
  （文件换成 /dev/null，目录换成空目录）。跨服务也遮：board 的运行里同样读不到 dagster 的生产配置。
  配置内容只能经 `service_info(what=config)` 读本服务本环境的、密钥打码后的版本。
  项目内核是唯一的例外：本服务本环境的配置文件 bind 在项目读的固定路径上（项目代码要按原样读它连库），
  其他环境、别的服务的配置与平台密钥照样遮蔽。
- **MCP 工具分两种**（`agent/tools/mcp_bridge.py`）：

  | | 平台 MCP | 服务 MCP |
  |---|---|---|
  | 写在哪 | 部署配置 `mcp_servers` | 服务定义的 `mcp`（§2.3） |
  | 放什么 | 通用能力，比如浏览器 | 某个服务特有的能力，比如 dagster 的运行记录 |
  | 怎么用上 | 角色里写工具名、`"mcp:<server>"` 或 `"*"` | 运行在这个服务上自动出现（角色 `service_tools: false` 时不带） |
  | 何时连接 | 平台启动时，改了要重启 | 第一次用到时（懒加载、按定义内容缓存、失败 5 分钟后重试） |

  两种都绑定服务×环境：每个环境一份连接，同名工具的各环境版本合成一个工具，调用时按 RunScope 路由到本次运行的环境；
  没配该环境的连接就如实返回「不可用」，不会退回到别的环境。MCP 工具调用出错（连不上、服务端报错）也如实返回给模型，不炸运行。
  平台 MCP 也能写 `service`（只在该服务的运行里可用）和 `envs`，但服务特有的能力推荐写进服务定义。
- **危险操作审批**：设置 → 审批 打开后（默认关闭），`py`、`bash`、`run_code` 的代码命中危险模式，或 `service_ctl`
  启停进程，且所在环境需要审批时，挂起等审批，运行状态变为 `awaiting_approval`。DB 行是事实源，
  LISTEN/NOTIFY 毫秒级唤醒，超时视同拒绝；被拒时工具拿到「未执行」，agent 自己决定怎么继续。
- **会话 thread 按 服务×环境 分开**：`thread_id = <session_id>@<服务>:<环境>`（`RunSpec.thread_id`），
  同一个会话键（比如事件模板 `dagster:{asset_key}:…`）在 prod 和 test 不共用上下文；项目内核也用这个键。
  thread 存在 PG checkpointer 里，崩溃后可以断点续跑。thread 只装本段对话，长期连续性由记忆层承载。

## 5. 记忆

记忆层分三样，来源、可信度和生命周期都不同：

| | 是什么 | 谁写 | 怎么进提示词 | 存在哪 |
|---|---|---|---|---|
| 档案 | 口径、禁区、环境差异、踩过的坑（§2.5） | 人 | 逐字置顶注入，不检索、不过期 | 服务 / 任务定义的 `profile` |
| 记忆 | agent 记下的事：`fact` 事实（口径、表与字段、拓扑）/ `lesson` 报错教训（带报错指纹与类别）/ `handoff` 会话交接摘要 | agent 沉淀；人可录入、改正 | 召回（见下） | `knowledge` 一张表 |
| 方法 | 可执行的做法与脚本：`procedure` / `script` / `query` / `baseline` | agent 用 `save_asset`；人可登记 | 该任务的优先、其次服务通用的，整段注入 | `assets` + 数据目录里的文件 |

教训的 key 是 `lesson:<指纹>`：同一服务同一指纹只有一条，新结论覆盖旧的，旧内容进历史。
报错指纹（`store/knowledge/lessons.py`）取报错末两行，抹掉易变部分（`file:line`、Python traceback 的 `File "…", line N`、
十六进制地址、uuid、数字、引号里的字面量）后哈希；`file:line` 规则排在纯数字之前，否则行号先被抹掉、规则失效。

**分区**：记忆按服务分区，`env=''` 表示对该服务所有环境成立。沉淀时默认记成通用的；模型判断「只在本环境成立」
（`env_specific: true`，比如这个环境特有的配置、数据量、主机）的才记在本环境下。召回 = 本环境的 + 通用的；
交接摘要按 服务 + 环境 取，prod 的对话结论不会带进 test。方法按 服务 × 环境 分区。

**召回**（`memory/recall.py`）在 prepare 阶段，档案另起一块（§2.5），之后按顺序拼：

1. 前序交接摘要：同一类事件的上一个会话的结论（会话键去掉最后一段就是「同一类」，如 `dagster:<资产>:<错误类>`）；
2. 同类报错的教训：有报错输入时按指纹精确命中，本环境的优先，其次通用的；
3. 记忆混合检索：事实与教训一起，pg_trgm + pgvector，RRF 融合，再按权重调整（见下），条数是 设置 → 记忆 的 `knowledge_limit`。
   `code_ref` 引用的文件自记录的提交以来改过即过期（看的是 `git diff 记录提交 HEAD -- 文件`，不是仓库 HEAD 变没变——
   代码目录定期同步时，别的文件的提交不让它过期；记录的提交已不在仓库里时按过期处理）。
   本任务谱系（自己 → 父任务）沉淀的排前面，兄弟子任务的排后并标来源。

方法单独一块。文件类方法（沉淀的脚本）的目录在项目内核启动时加到 `sys.path`（环境变量 `AGENT_METHOD_PATHS`），
`py` 里可以直接 import，不用复制一遍。

命中写 `recall_hits`：「30 天命中」、零召回、可升格都从它算，运行被 👎 时也据此找到它召回过的条目。

**沉淀**（`memory/distill.py`）在 finalize 阶段：一次轻量模型调用，提炼出事实（带 `code_ref`：文件路径 + 当前提交）
和教训（有报错输入时，按报错算指纹）。有会话时，再写一份四节交接摘要：结论、被否方案、当前约束、未决问题。
纠正（§3）成功后，取代本会话上一轮沉淀的记忆。

**权重只罚不奖**（`store/knowledge/retrieval.py`、`store/feedback.py` 的 `shift_memory_weight`）：

- 没人会去点 👍，正分没有信号，所以 👍 只留档、不改权重；
- 整次运行被 👎 时，它沉淀的记忆和它召回的记忆各扣 1 分（排序时最多算到 -5）；改主意、撤回按差值回补；
- 人工录入的条目（没有来源运行）加 3 分（`MANUAL_BONUS_POINTS`）；
- 方法仍按来源运行扣分；
- 终排 = RRF 名次分 + 分数 × 系数，在截断前加权：人写的后排条目能挤进前几名，反复惹麻烦的会沉下去。

**升格**：被反复用到、确认无误的事实，值得从记忆升格成档案（逐字置顶、不过期）。

- `GET /v1/knowledge/promotable` 列出候选：近 30 天被 ≥ 5 次运行召回、没挨过 👎 的事实。
- `POST /v1/knowledge/{id}/promote {target: service | task, key, task?, content?}` 写进服务档案（条目只在某环境成立时写进
  `envs[env].profile`）或任务档案；同一个键已有内容就接在后面。原条目标为被取代
  （`superseded_by = profile:<目标>:<键>`），召回不再重复注入。

**反馈**是人对一次运行（或其中一步）的评价，由三部分组成：分数、问题类型（结论不对、口径不对、取数有误、
没答全、工具用错等）和文字说明。规则如下：

- 一个人对同一步只有一条反馈，改主意就是覆盖，所以重复点 👎 不会把分扣两次。
- 整次运行的 👎 按变化量调整权重（见上）；单步评价只留档。
- 新的 👎 按通知规则（`feedback_negative`）推给负责人，运行页的「反馈」标签是收件箱。
- 想让 agent 按意见重答，走「纠正」：同会话开新一轮，成功后取代上一轮沉淀的记忆。👎 面板里可以一并勾选。

代码在 `domain/feedback.py`、`store/feedback.py`、`api/routes/feedback.py`。

人可以在三处直接维护记忆：记忆页、任务详情的「记忆」标签、服务详情的「记忆」标签。
接口见 `docs/外部接口文档.md` §8：新建事实或教训（教训要给报错原文，按它算指纹）、登记方法、改正内容、让条目过期、升格。

### 5.1 回归重放

改完角色提示词、任务定义或档案后，拿被 👎 过的 agent 运行用当前定义重跑，看人指出的问题改好没有。
代码在 `orchestration/replay.py`、`store/replays.py`、`api/routes/replays.py`。

只看 👎：没人会去点 👍，而 👎 自带「错在哪」（问题类型、说明、被点的那一步），正好当判卷标准，不用另外维护评测集。

一次重放是一批：

1. **选样**：默认取被 👎（整次或某一步）的 agent 运行，可按任务（含子任务）、服务、环境、最近几小时筛，
   最近被评的在前，默认 20 条；也可以直接点名运行。重放出来的运行不进样本。
2. **重跑**：每条原运行用同样的输入开一个重放运行，触发类型 `replay`（运行详情的 `replay_of` 指向原运行）：
   新会话、不沉淀记忆、不投递，只过闸门 1–4。
3. **判定**：重放运行结束后，一次模型调用对照「原答案 + 人指出的问题（问题类型、说明、被点的那一步）+ 新答案」判定：

   | 判定 | 含义 |
   |---|---|
   | `fixed` | 被指出的问题解决了，且没引入明显的新错 |
   | `same` | 问题还在 |
   | `worse` | 更糟，或引入了明显的新错 |
   | `unclear` | 判断不了（要看实际数据才能确认，或判定调用失败） |
   | `error` | 重放运行没建成（被闸门拒、没权限） |

   重放运行没有成功结束时不调模型：原运行是成功的记 `worse`，否则记 `same`。
4. **对照**：详情里逐条给出原答案、新答案、两边的任务 / 角色版本、判定与理由。还没判或 `unclear` 的可以重判。

## 6. 接口（/v1）

接口按资源组织，过滤参数平铺，错误体统一为 `{"error": {"code", "message", "detail"}}`。
完整契约见 `docs/外部接口文档.md`。

| 资源 | 端点 |
|---|---|
| 定义 | `/v1/{services,roles,tasks}`：列表、新建、单个、`PATCH`、删除、版本、恢复 |
| 子任务 / 定时 | `/v1/tasks/{t}/subtasks`、`/v1/tasks/{t}/schedule` |
| 服务 × 环境 | `/v1/services/{s}/envs/{env}`、`…/config?path=`、`/v1/services/{s}/tools?reload=`、`/v1/services/{s}/processes`、`…/processes/{p}/start\|stop\|renew\|logs` |
| 运行 | `POST /v1/runs`、`GET /v1/runs`、`/{id}`、`/{id}/events`、`/{id}/stream`、`/{id}/cancel\|rerun\|resume\|correct\|feedback` |
| 回归重放 | `/v1/replays`、`/{id}`、`/{id}/judge` |
| 对话 | `POST /v1/chat`（SSE）、`/v1/sessions` |
| 事件 | `POST /v1/events/{source}` |
| 审批 | `/v1/approvals`、`/{id}/approve`、`/{id}/reject` |
| 记忆 | `/v1/knowledge`（含 `/promotable`、`/{id}/promote`）、`/v1/assets` |
| 设置 | `/v1/settings/{section}`、`/v1/api-keys` |
| 其他 | `/v1/meta`、`/v1/stats`、`/v1/search`、`/auth/session`、`/healthz` |

接口设计的几条原则：

- **定义的读写只有一套**：三种定义同一组端点；修改一律是 `PATCH`，请求里出现的顶层字段整体替换。
- **动词端点只用于状态迁移**：cancel / rerun / resume / correct / approve / reject / start / stop / renew / judge / promote。
  其余操作都是资源的增删改查。
- **提交回执说清楚发生了什么**：是否命中去重、是否顺带建了子任务，调用方不必再查一次就能知道。
- **拒绝原因可编程**：`code` 稳定，`message` 给人看。

## 7. 网页（控制台）

控制台是 React + TypeScript 单页应用，用 esbuild 构建，Tailwind v4 编译 CSS，交互组件用 Headless UI。
路由和查询缓存是自写的小模块，没有引入重型框架。构建产物 `webui/dist` 随 Python 包发布，
由 FastAPI 同进程托管，部署不需要 Node。

`node scripts/build.mjs preview` 会产出一个带 mock 数据的单文件预览，不连后端也能看全部页面。

- **顶栏**：全局环境切换（全部 / prod / test / dev）、⌘K 全局搜索与命令、审批角标。
- **侧栏**：概览、服务、任务、运行、对话、审批、记忆；底部是「设置」和用户菜单（个人偏好、退出）。
- **列表页**（运行、审批、对话、记忆）：顶部都有快捷筛选，包括服务、环境、任务、触发、发起方等。
  筛选状态全部放在 URL 里，可以分享、可以回退。
- **服务页**：
  - 「环境」标签：按环境开关服务、查看覆盖项；
  - 进程：启停、租约、日志；
  - 配置文件、任务、近期运行、记忆、版本。
- **任务列表**：按服务分组。有子任务的父任务可以展开，子任务缩进列在下面，并标出档案待补、可以直接运行。
  搜索同时匹配对象名，命中时父任务自动展开；也可以一键展开全部子任务。
- **运行页**：「运行」与「反馈」两个标签。「反馈」默认只看 👎，可以按服务、环境、任务、问题类型筛选。
- **任务页**：
  - 概览；
  - 档案（就地编辑）；
  - 子任务（一行新建）；
  - 记忆（这个任务名下的记忆与方法）；
  - 定义（分节表单：基本 / 输入 / 触发 / 结果与去重 / 记忆 / 环境 / 高级），子任务这一页是「覆盖」；
  - 运行、版本。
- **运行对话框**：表单按输入定义生成；对象（子任务）用可新建的下拉选择；记忆开关可以按次覆盖。
- **运行详情**：
  - 步骤时间线：工具调用、思考、审批，每一步可以 👍👎；
  - 上下文面板：输入、档案、召回、沉淀、同会话运行、谱系；
  - 操作：续跑、重跑、纠正、取消。
- **对话**：
  - 维度条：服务、环境、任务、对象、额外输入、记忆开关；
  - 侧栏的会话列表可以按服务、环境、任务筛选。
- **设置**：个人偏好（只存在浏览器）、环境、审批、通知、记忆、进程、API 密钥、角色。

## 9. 从 v5 迁移

`scripts/migrate_v5.py` 做以下几件事：

- definitions 去掉 env 列，取部署实例那一套定义；
- `domain` 改为 `service`，并合并 `conf/services.yaml` 里的进程与配置文件；
- 任务的 `schedule` / `schedule_input` / `triggers` / `env_gate` 转成新的 `triggers` / `envs`，
  `rules` 定义并入对应的事件触发；
- runs 的 `domain` / `target_env` 列改名为 `service` / `env`；
- 记忆表按显式列出的表名逐张迁移；案例（cases）直接迁成 `kind=lesson` 的记忆；
- 任务图任务和产物不迁移（任务图已去掉），留在备份里。

迁移是幂等的。执行前先备份。
